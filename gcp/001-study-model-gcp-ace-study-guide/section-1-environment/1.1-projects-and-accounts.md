# 1.1 — Setting up cloud projects and accounts

> **Exam guide reference:** Section 1.1. Sub-topics: resource hierarchy, organizational policies, IAM roles in a project, Cloud Identity users/groups (manual + automated), enabling APIs, Cloud Observability provisioning, quotas, standalone organizations, cloud networking, geographical availability of products, Cloud Asset Inventory, Gemini Cloud Assist.

---

## 1. Why this matters for the exam

Almost every other topic in the exam **assumes** you understand the resource hierarchy and how policies flow through it. If you cannot answer "where does this IAM binding live and what does it inherit?" you will get a lot of scenario questions wrong, even ones that look like they're about Compute or BigQuery.

Expect questions that:

- Show you a hierarchy and ask **where to apply** a policy (org / folder / project) for the right blast radius.
- Describe a multi-team setup and ask which **Cloud Identity** structure (groups vs. users) makes the policy maintainable.
- Ask why an API call fails — usually because the **API isn't enabled** in the project, or a **quota** is exhausted, or an **org policy** denies the action.

## 2. Core concepts

### 2.1 The resource hierarchy

Google Cloud organizes everything in a strict tree:

```
Organization
  └── Folder(s)        (optional, can be nested up to 10 levels)
       └── Project(s)
            └── Resources  (VMs, buckets, datasets, …)
```

- **Organization node** — the root. Tied 1:1 with a Cloud Identity or Google Workspace domain. Created automatically when the domain signs up. It is the *only* node where you can manage org-wide policies and the only place "Organization Admin" makes sense.
- **Folders** — optional grouping. Typically used to model **departments**, **environments** (prod / staging / dev), or **business units**. Folders can contain folders.
- **Projects** — the unit that *owns* resources. Every resource lives in exactly one project. Projects are the boundary for billing, API enablement, quotas, and most permissions.
- **Resources** — VMs, buckets, datasets, etc. They inherit from their project upward.

Three project identifiers — know all three:

| Identifier | Mutable? | Unique? | Example |
|---|---|---|---|
| Project name | yes | no | `My Web App` |
| Project ID | **no** (immutable) | globally unique | `my-web-app-12345` |
| Project number | no (auto-assigned) | globally unique | `123456789012` |

Project lifecycle:
- States: `ACTIVE` → `DELETE_REQUESTED` → `DELETE_IN_PROGRESS`.
- After deletion, the project sits in `DELETE_REQUESTED` for **~30 days** during which it can be **restored**. After that, the project ID is released and resources are gone permanently.

### 2.2 How inheritance works

Two policy types flow down the hierarchy, but with **opposite logic**:

| Policy type | Direction | Combination rule |
|---|---|---|
| **IAM policy** (who can do what) | Inherits downward | **Union** — the most permissive wins. A grant at the org node applies to every project below it. |
| **Organization policy** (constraints) | Inherits downward | **Intersection** — the most restrictive wins. A child folder cannot loosen a constraint set above it (unless the constraint allows overrides). |

This is the single most important rule to internalize. "If I add Editor at the folder, can the project remove it?" → No, IAM is additive. "If the org disables external IPs, can a project re-enable them?" → No, org policy is restrictive.

### 2.3 Organization policies

- Defined as **constraints** (e.g. `compute.vmExternalIpAccess`, `iam.disableServiceAccountKeyCreation`).
- Two flavours: **list constraints** (allow/deny lists of values) and **boolean constraints** (on/off).
- Set at any node; lower nodes inherit. Lower nodes can either **inherit**, **override** (if the constraint permits), or **merge** with parent values.
- Used for guardrails: *"no public buckets anywhere in the company"*, *"only EU regions allowed in this folder"*, *"no service-account key creation"*.

### 2.4 Cloud Identity

This is the **identity provider** for Google Cloud. It manages who *can be granted* permissions; IAM is what they're granted.

- **Cloud Identity Free** vs. **Premium** — premium adds enterprise SSO, mobile device management, advanced security.
- Stores **users** and **groups**. Always prefer granting roles to **groups**, never to individual users — when someone joins/leaves a team you change one membership instead of dozens of bindings.
- **Automated user lifecycle** typically uses **Google Cloud Directory Sync (GCDS)** to sync from on-prem LDAP / Active Directory, or SCIM provisioning from an external IdP (Okta, Azure AD, etc.).
- **Standalone organizations** — when a company doesn't use Workspace, they can sign up for Cloud Identity Free to get an organization node. This is the "set up a standalone organization" bullet on the exam guide.

### 2.5 Enabling APIs

Every Google Cloud service has at least one API, and **APIs are enabled per-project**. A common failure mode the exam will test: a script fails with `SERVICE_DISABLED` — the answer is to enable that API in the project.

- A project starts with a default set enabled.
- Enabling an API may also create a default service account or grant default service-agent roles.
- Some APIs require **billing to be enabled** on the project before they will turn on.

### 2.6 Cloud Observability provisioning

**Cloud Observability** = Cloud Monitoring + Cloud Logging + Cloud Trace + Cloud Profiler + Error Reporting.

- Each project gets **logs and metrics by default** for most services.
- For monitoring, projects send metrics to a **Metrics Scope**. A scope can read metrics from multiple projects, which is how you build a single dashboard across an org.
- The scoping project (the one that hosts the scope) is the one you log into to see all the others.

### 2.7 Quotas

Quotas are **per-project, per-region** ceilings on how much of a resource you can use. Two flavours:

- **Rate quotas** — requests per minute (e.g. API calls).
- **Allocation quotas** — total amount of a resource (e.g. CPUs in `us-central1`).

If you hit a quota you must **request an increase** through the console or via support. The request goes to Google; it is not instantaneous.

### 2.8 Geographic availability

- **Global** services exist outside any region (e.g. IAM, Cloud DNS, global load balancers).
- **Regional** services live in one region but are replicated across multiple zones (e.g. regional Persistent Disks, regional Cloud Storage).
- **Zonal** services live in a single zone (e.g. a default Compute Engine VM, a zonal Persistent Disk).

The exam will ask you to **confirm a product is available** in a region before designing for it — the source of truth is the official **Cloud locations** page.

### 2.8.1 GCP global infrastructure (regions, zones, edge locations)

The geographic-availability rules above only make sense once you have a mental picture of the physical infrastructure they map to. Google Cloud runs on a private, fibre-connected global network with three distinct layers:

#### Regions
- A **region** is a specific geographic area (e.g. `europe-west3` = Frankfurt, `us-central1` = Iowa, `asia-southeast1` = Singapore). 40+ regions exist worldwide, with new ones added regularly.
- Each region is **isolated** from the others for fault containment — a region-wide outage does not propagate.
- Pick a region for: **proximity to users** (latency), **data-residency compliance** (GDPR, regional sovereignty), **service availability** (not every product is in every region), and **price** (regions vary by ~10–30%).
- Most resources are **regional** (Cloud SQL HA pair, regional Persistent Disk, regional MIG, regional GKE control plane).

#### Zones
- A **zone** is an **independent failure domain** inside a region — its own power, cooling, and networking. Most regions have **3 zones** (a few have 4); zones are named like `europe-west3-a`, `-b`, `-c`.
- A zone is roughly *one or more data-centre rooms*. Two zones in the same region are typically **<1 ms RTT** apart, low enough for synchronous replication.
- Zonal resources (a default GCE VM, a zonal Persistent Disk, a zonal GKE cluster) **die with their zone**. Regional resources spread across zones to survive a zone failure.

The single most important deployment rule: **at least 2 zones for HA inside a region; at least 2 regions for DR across regions.**

#### Multi-region locations
A handful of services support a **multi-region** location — a logical group of regions on a continent (`us`, `eu`, `asia`). Cloud Storage multi-region buckets, BigQuery multi-region datasets, and Spanner multi-region configs replicate across the constituent regions automatically. Use them when you want continent-wide availability without managing replication yourself.

#### Edge locations (PoPs) and the global network
Beyond regions and zones there are **180+ network edge locations** (Points of Presence) where Google peers with ISPs around the world. These are **not** places where you deploy resources directly — they're entry/exit points for traffic and are used by:

- **Cloud CDN** — caches content close to users at the edge.
- **Global external Application Load Balancer** — accepts user requests at the nearest PoP, then carries them over Google's private backbone to the backend region. This is what **Premium tier** buys you.
- **Cloud Armor** — DDoS / WAF inspection at the edge.
- **Google's private backbone** itself — links every region and PoP via dedicated fibre and submarine cables, so cross-region traffic doesn't traverse the public internet.

For the exam, recognise that **regions are for placing resources, zones are for HA inside a region, edge locations are for serving users from close to them**. When a question stresses *global users* + *low latency* + *DDoS resistance*, the architecture is global LB on Premium tier with backends in one or more regions, Cloud CDN at the edge.

#### Quick mental map

```
Continent (multi-region: us / eu / asia)
   └── Region (europe-west3 — Frankfurt)
        └── Zone (europe-west3-a, -b, -c)            ← place VMs / zonal disks here
             └── Resources (VMs, PDs, GKE nodes)
   ─── connected by ───
Google's private global backbone
   ─── reaches users via ───
Edge PoPs (180+) ← Cloud CDN, global LB frontends, Cloud Armor
```

### 2.9 Cloud Asset Inventory

A read-only inventory of every resource and IAM policy in your org/folder/project, with a **5-week history**. Use it for:

- Searching ("find every public bucket in the org").
- Exporting a snapshot to BigQuery or Cloud Storage for audit.
- Watching for changes via Pub/Sub feeds.

### 2.10 Gemini Cloud Assist

A built-in AI assistant that can analyse resources, explain configurations, and recommend changes. For the exam know that it exists, that it can answer natural-language questions about your environment, and that it leverages Cloud Asset Inventory plus other signals to do so.

## 3. Decision criteria

| Question | Rule of thumb |
|---|---|
| Where should I apply this policy? | Apply at the **highest node** where the policy should universally be true. Apply at the lowest node when only one team needs it. |
| Should I grant this role to a user or a group? | **Always a group**, except for emergency break-glass identities. |
| Folder hierarchy: by environment or by team? | Most orgs use **team / business-unit at the top**, then **environment underneath** (so prod/dev policies are uniform per team). Either is acceptable; just be consistent. |
| Do I need an organization node? | Yes for any non-trivial setup — it is required for org policies, central IAM, and folders. Standalone Cloud Identity gets you one without Workspace. |
| Quota request or design change? | If you only occasionally hit it, request an increase. If you hit it constantly, the architecture is wrong (split projects, switch regions, redesign). |

## 4. Console walkthrough

Knowing where things live in the console saves time on hands-on questions.

- **Resource hierarchy & projects** — *Navigation menu → IAM & Admin → Manage resources*. From here you create folders, move projects, and set IAM at any node.
- **Organization policies** — *IAM & Admin → Organization policies*. You filter by constraint name, see effective values, and set inheritance/override.
- **Cloud Identity users & groups** — *admin.google.com* (the Admin Console, not the GCP console). This is a different UI and a frequent source of confusion.
- **Enabling APIs** — *APIs & Services → Library*. Search the API, click Enable. Or *APIs & Services → Enabled APIs* to see what is already on.
- **Quotas** — *IAM & Admin → Quotas*. Filter by service and region; the "Edit quotas" button starts an increase request.
- **Cloud Observability** — *Monitoring* (left nav) for dashboards, alerting, scopes; *Logging* for log explorer.
- **Cloud Asset Inventory** — *IAM & Admin → Asset Inventory*. Tabs for Resources, IAM policies, Org policies, with a search box.
- **Gemini Cloud Assist** — the spark icon in the top bar of the console; opens a chat panel scoped to the current page.

## 5. gcloud reference

Only the commands you really need. The pattern is `gcloud <service> <verb>`.

```bash
# Hierarchy
gcloud organizations list
gcloud resource-manager folders list --organization=ORG_ID
gcloud resource-manager folders create --display-name="prod" --organization=ORG_ID

gcloud projects list
gcloud projects create my-project-id --name="My Project" --folder=FOLDER_ID
gcloud projects describe PROJECT_ID
gcloud projects delete PROJECT_ID
gcloud projects undelete PROJECT_ID            # within the 30-day window

# Active context
gcloud config set project PROJECT_ID
gcloud config list

# IAM at any level (same verb pattern, different parent flag)
gcloud projects       add-iam-policy-binding PROJECT_ID \
    --member=user:alice@example.com --role=roles/viewer
gcloud resource-manager folders add-iam-policy-binding FOLDER_ID \
    --member=group:devs@example.com --role=roles/editor
gcloud organizations  add-iam-policy-binding ORG_ID \
    --member=user:cto@example.com --role=roles/resourcemanager.organizationAdmin

# Organization policies
gcloud resource-manager org-policies list --project=PROJECT_ID
gcloud resource-manager org-policies set-policy POLICY.yaml --project=PROJECT_ID

# APIs
gcloud services list --available
gcloud services list --enabled
gcloud services enable compute.googleapis.com
gcloud services disable compute.googleapis.com

# Quotas (read-only via CLI; increases are requested in the console)
gcloud compute regions describe us-central1   # shows quotas + usage

# Asset Inventory
gcloud asset search-all-resources --scope=organizations/ORG_ID --query="state:ACTIVE"
gcloud asset search-all-iam-policies --scope=projects/PROJECT_ID --query="policy:roles/owner"
```

The CLI mirrors the console: every console screen has a `gcloud` equivalent, and once you recognize the pattern (`gcloud <thing> list / describe / create / delete`) you can guess most commands.

## 6. Exam gotchas

- **Project ID is forever.** Once chosen it cannot be renamed, and it stays reserved for ~30 days after deletion before it can be reused (and even then, not always).
- **IAM = union, org policy = intersection.** This trips people up constantly. A child cannot remove a parent's IAM grant; a child cannot loosen a parent's org-policy constraint.
- **Cloud Identity ≠ IAM.** Cloud Identity is the user directory (admin.google.com). IAM is what those users *can do* in GCP. Many exam scenarios deliberately conflate them.
- **APIs are per-project, not per-organization.** Enabling an API at the org node is not a thing. Each project must have it enabled.
- **Quota increases are not instantaneous.** They go through Google support. If a question says "we need more capacity by tomorrow's launch", the answer probably involves *requesting* the increase now, not "just enable it".
- **Standalone organization** is exam vocabulary for a Cloud Identity Free tenant used purely to get an organization node, without paying for Workspace.
- **Folders are optional, projects are mandatory.** A common distractor on hierarchy questions.
- **Editing a Cloud Identity group does not require IAM.** It is done in the Admin Console — but the group can then be referenced as `group:` in any IAM binding.
- **Asset Inventory keeps 35 days of history.** If a question asks "audit what changed last quarter", the answer is *export to BigQuery*, not "look in Asset Inventory directly".

## 6.5 Named scenarios

These are deeper, narrative walk-throughs of the kind of design questions the exam asks — distinct from the multiple-choice quiz below.

### Scenario A — Designing for compliance and availability
**Context.** A European fintech is moving its first workload to GCP. Three constraints:
1. All customer data must remain inside the EU (GDPR Article 44 transfer rules).
2. The service must survive a single data-centre fire with ≤1 minute downtime.
3. A single Frankfurt region is acceptable initially, but the company plans an EU-wide product within 12 months.

**Recommended design.**
- **Region:** start in `europe-west3` (Frankfurt). Confirm the chosen services (Cloud SQL, Cloud Run, Cloud Storage) are listed for that region on `cloud.google.com/about/locations`.
- **Zonal redundancy:** every stateful service gets multi-zone replication inside the region — Cloud SQL `--availability-type=REGIONAL` (synchronous standby in another zone), regional MIG spread across `-a`, `-b`, `-c`, regional Persistent Disks for self-managed databases.
- **Storage bucket:** dual-region `eu-west3 + eu-west4` for the document store — keeps data inside the EU while surviving a region-level outage.
- **Org-policy guardrail:** at the org node, set `gcp.resourceLocations` to `in:eu-locations` so no engineer can accidentally provision in `us-*` or `asia-*`. This is enforced *above* IAM — even Owners cannot bypass it.
- **Future-proofing:** the move to EU-wide later means migrating to a multi-region Cloud Storage `EU` location, a Spanner EU multi-region instance for the relational tier, and a global external Application Load Balancer (Premium tier) fronting backends in two EU regions.

**Why this works.** The hierarchy of *zones for HA, regions for DR, multi-region for global availability* maps directly to the three constraints. The org-policy lock is the single durable artefact that prevents a one-line gcloud mistake from breaking compliance.

### Scenario B — Hierarchy & guardrails
**Context.** A 200-person engineering org has 12 product teams, each with three environments (dev / staging / prod). New teams are added quarterly. Security wants:
1. The same set of org policies applied to every prod project automatically.
2. The data-platform team to have read-only visibility everywhere; each product team should only have access to their own projects.
3. No one outside SecOps should be able to create new billing accounts.

**Recommended design.**
- **Folder layout:**
  ```
  Organization
    ├── prod/
    │     ├── team-checkout/
    │     ├── team-search/        (≈12 product folders)
    │     └── …
    ├── nonprod/
    │     └── (same shape)
    └── shared/
          └── security/, networking/, billing-ops/
  ```
  Two top-level folders (`prod` / `nonprod`) make it trivial to apply prod-only org policies (deny external IPs, lock CMEK, require VPC-SC, etc.) — every project beneath inherits them automatically. New teams = new folders, never new policies.
- **IAM grants:**
  - `data-platform@` group → `roles/viewer` at the **org** node — universal read.
  - `team-checkout@` group → predefined per-service roles (`roles/run.admin`, `roles/cloudsql.editor`, …) at the `team-checkout` folder — covers all three of their envs.
  - SecOps → `roles/billing.creator` at the org; everyone else: nothing on billing.
- **Quota & API guardrails:** enable required APIs once at project-template time (a Terraform module under `prod/team-*`); each team can request additional APIs via PR.

**Why this works.** Two principles do most of the work: **apply IAM at the highest node where the rule is universally true**, and **let the folder structure mirror the policy structure**. Adding the 13th team is a single folder + a single IAM binding — no per-project copy-paste.

## 7. Practice scenarios

### Q1 — Hierarchy and inheritance
Your company has the resource hierarchy: Organization → "Engineering" folder → 5 production projects. The security team must have *Viewer* across every Engineering project, with the minimum number of bindings. Where do you grant the role?

A. Grant `roles/viewer` to the security group on every project individually.
B. Grant `roles/viewer` to the security group on the Engineering folder.
C. Grant `roles/viewer` to the security group on the organization.
D. Add each security team member individually to each project as Viewer.

**Answer: B.** A folder-level binding is inherited by every child project — one binding covers all five. Granting at the org node (C) over-scopes (covers folders the team shouldn't see). A and D are correct in effect but violate "minimum number of bindings" and "groups over users".

### Q2 — Project ID
You created project `proj-prod-2024` and accidentally typed it instead of `proj-prod-app`. You want to rename the Project ID. What's the correct action?

A. Use `gcloud projects update --new-id=proj-prod-app`.
B. Edit the project in the console under *Project Settings*.
C. Create a new project with the desired ID; migrate resources; delete the old one.
D. Rename the Project Name; the Project ID will follow.

**Answer: C.** Project IDs are **immutable**. There is no rename. Project Name (D) is mutable but unrelated to the ID. A and B don't exist as features.

### Q3 — IAM vs. org policy
A user with `roles/owner` on a project complains they cannot create a VM with an external IP. Which is the most likely cause?

A. The Compute Engine API is disabled.
B. An organization policy `compute.vmExternalIpAccess` is restricting external IPs.
C. The user is missing `roles/compute.networkAdmin`.
D. Quota for external IPs is exhausted.

**Answer: B.** Owner cannot bypass an org policy. IAM (C) is moot since Owner already has all permissions. A would block any VM creation, not just external IP. D would fail for everyone, not specifically external IP scenarios — and Google would surface a quota error.

### Q4 — Cloud Identity and groups
A new engineering group of 12 people needs *Editor* on a development project. What is the recommended approach?

A. Add each user as Editor on the project.
B. Create a Google Group, add users to it, and bind the group to `roles/editor` on the project.
C. Use the default service account to act on their behalf.
D. Add `allAuthenticatedUsers` as Editor.

**Answer: B.** Always grant roles to groups, never individuals. D (allAuthenticatedUsers) makes the project accessible to *every* Google account on the internet — disastrous.

### Q5 — Asset Inventory
Compliance asks you to produce a list of every Cloud Storage bucket in the entire organization that is publicly accessible. The fastest single action is:

A. Run `gcloud storage buckets list` in every project.
B. Use Cloud Asset Inventory to search all IAM policies in the org for bindings of `allUsers` on storage resources.
C. Enable Data Access audit logs for Cloud Storage and review them.
D. Open each project's Cloud Storage page in the console and inspect bucket permissions.

**Answer: B.** Asset Inventory's `search-all-iam-policies` answers exactly this kind of org-wide question in one call. C is for *who accessed what*, not *what is exposed*. A and D are unscalable.

## 8. Hands-on labs

These are the practical walk-throughs you need to be comfortable with before the exam. Console steps first, gcloud equivalents at the end of each lab.

### Lab 1 — Console tour: orient yourself
**Goal:** Recognize every place referenced in the rest of the guide.

1. Sign in at `console.cloud.google.com`.
2. **Top bar (left):** the **Project picker** — click it to switch project / org / folder context. Pin frequently-used projects with the star icon.
3. **Top bar (right):** the **Cloud Shell** icon (`>_`) opens a free Linux shell with `gcloud`, `kubectl`, `terraform` pre-installed. The **Notifications**, **Help**, and **Avatar** icons are next to it.
4. **Hamburger menu (☰)** at top-left: the navigation menu. Pin your top services by hovering and clicking the pin.
5. The **search bar** in the top center is the fastest way to jump to any service or resource — type "VM instances" or a project ID.
6. Settings live under the **avatar** in the top-right (preferences, language, theme).

### Lab 2 — Check service availability by region
**Goal:** Confirm a product is offered in a chosen region before designing for it.

1. Open `cloud.google.com/about/locations` (the Cloud locations page) — this is the source of truth.
2. Find the region you intend to use (e.g. `europe-west3 — Frankfurt`).
3. Cross-reference the service: search the page for "BigQuery", "Spanner", "Cloud Run", etc.
4. In the console: when creating any resource (e.g. *Compute Engine → Create instance*), the region/zone dropdowns only show valid options for that service — a quick consistency check.

### Lab 3 — Three ways to interact with GCP
**Goal:** Use console, Cloud Shell, and the local gcloud SDK interchangeably.

**Console:** the GUI at `console.cloud.google.com` — already covered.

**Cloud Shell** (no install required):
1. Click the `>_` icon in the top bar of the console.
2. A terminal opens at the bottom with you already authenticated. The first launch provisions a 5 GB persistent home directory.
3. Try `gcloud projects list`, `gcloud auth list`, `gcloud config list`.
4. Cloud Shell **Editor** opens a VS Code-like editor in the same panel — useful for editing Terraform/scripts without leaving the browser.

**Local gcloud SDK:**
1. Install: `brew install --cask google-cloud-sdk` on macOS, or download the installer from `cloud.google.com/sdk/docs/install`.
2. Authenticate: `gcloud auth login` (opens a browser).
3. Set defaults: `gcloud config set project PROJECT_ID`, `gcloud config set compute/region europe-west3`.
4. Sanity check: `gcloud projects list`.

### Lab 4 — Create and manage projects
**Goal:** Create a project under a folder, switch context, delete and undelete.

**Console:**
1. *Navigation menu → IAM & Admin → Manage resources*.
2. Click **Create project**.
3. Enter Project Name; the Project ID is auto-suggested — accept or override (remember: immutable).
4. Pick the parent organization or folder.
5. Click **Create**.
6. Use the project picker (top bar) to switch into the new project.
7. To delete: same page → tick the project → **Delete**. Type the project ID to confirm.
8. To restore within 30 days: *Manage resources* → top filter → **Pending deletion** → tick → **Restore**.

**gcloud:**
```bash
gcloud projects create my-app-2024 --name="My App" --folder=FOLDER_ID
gcloud config set project my-app-2024
gcloud projects describe my-app-2024
gcloud projects delete my-app-2024
gcloud projects undelete my-app-2024
```

### Lab 5 — Apply an organization policy
**Goal:** Restrict external IPs at the organization level.

**Console:**
1. Switch the project picker to the **organization** scope.
2. *Navigation menu → IAM & Admin → Organization policies*.
3. In the search box, type `compute.vmExternalIpAccess`.
4. Click the policy → **Manage policy**.
5. Set **Policy enforcement** to *Replace*.
6. Choose **Deny all** (or define an allow list of specific VM URIs that may have external IPs).
7. Click **Save**. Inheritance now blocks external-IP VM creation in every project under the org unless overridden at a folder/project (and the constraint allows overrides).

**gcloud:**
```bash
gcloud resource-manager org-policies set-policy policy.yaml --organization=ORG_ID
# policy.yaml example:
# constraint: constraints/compute.vmExternalIpAccess
# listPolicy:
#   allValues: DENY
```

### Lab 6 — Enable APIs in a project
**Goal:** Turn on the APIs your workloads need.

**Console:**
1. Confirm you are in the right project (top bar).
2. *Navigation menu → APIs & Services → Library*.
3. Search for the API by name (e.g. "Compute Engine API", "Pub/Sub API").
4. Click the result → **Enable**. Wait a few seconds.
5. To audit currently-enabled APIs: *APIs & Services → Enabled APIs & services*.
6. To disable: same screen → click the API → **Disable API** (be careful — disables in-use APIs break running workloads).

**gcloud:**
```bash
gcloud services list --available | grep -i compute
gcloud services enable compute.googleapis.com pubsub.googleapis.com
gcloud services list --enabled
gcloud services disable compute.googleapis.com
```

### Lab 7 — Create a user and a group in Cloud Identity
**Goal:** Manage humans in `admin.google.com`, then reference the group from IAM.

**Admin Console (admin.google.com):**
1. Sign in to `admin.google.com` with a Cloud Identity admin account.
2. *Directory → Users → Add new user*. Fill name, primary email (under your domain), set a temporary password. Click **Add new user**.
3. *Directory → Groups → Create group*. Enter group name (e.g. `devs`), email (`devs@example.com`), description. Save.
4. Open the group → **Members → Add members** → add the user you just created.

**Then in GCP:**
1. *IAM & Admin → IAM → Grant access*.
2. **New principals:** `devs@example.com`. **Role:** `roles/viewer` (or whatever you intend).
3. **Save**. The user inherits the role through group membership.

**gcloud / gcloud-cli (Cloud Identity uses `gcloud identity` and the Admin SDK; most flows are console-driven):**
```bash
# Reference a group in any IAM binding:
gcloud projects add-iam-policy-binding PROJECT_ID \
    --member=group:devs@example.com --role=roles/viewer
```

### Lab 8 — Day-to-day Cloud Identity management
**Goal:** Add/remove members from groups, suspend a user, reset a password.

In `admin.google.com`:
- **Add a user to a group:** *Groups → (group) → Members → Add members*.
- **Remove a user:** same page → tick member → **Remove members**.
- **Suspend a user:** *Users → (user) → More options → Suspend user*. Suspended users keep their data but cannot sign in. Reverse with **Reactivate**.
- **Reset password:** *Users → (user) → Reset password*. Generate or set; force a change at next sign-in.
- **Bulk operations:** *Users → Bulk update users* (CSV upload).

For **scaled** automation, sync from external IdPs:
- **Google Cloud Directory Sync (GCDS)** for on-prem LDAP / Active Directory.
- **SCIM provisioning** from Okta / Azure AD.
