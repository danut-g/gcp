# 2.1 — Planning and implementing compute resources

> **Exam guide reference:** Section 2.1. Sub-topics: choosing the right compute service (Compute Engine, GKE, Cloud Run, Cloud Run functions, Knative serving), launching VMs, choosing storage for VMs (Persistent Disk, Hyperdisk), managed instance groups + autoscaling, OS Login, VM Manager, Spot VMs, custom machine types, kubectl install/config, GKE cluster types (Autopilot, regional, private), deploying containerized apps to GKE, deploying to serverless (Cloud Run, Cloud Run functions, Eventarc).

---

## 1. Why this matters for the exam

Section 2 is the largest weight on the exam (~30%) and **compute is the heart of it**. The single most common question pattern is "given this workload, which compute service?" If you can confidently pick between Compute Engine, GKE, and Cloud Run for a described workload, you will get a lot of points easily.

Beyond the choice itself, the exam tests whether you understand the **operational model** of each — who patches the OS, who scales the nodes, what triggers an autoscale, what happens when an instance dies.

## 2. Core concepts

### 2.1 The four compute options

| Service | Abstraction | You manage | Google manages | Sweet spot |
|---|---|---|---|---|
| **Compute Engine** | Virtual machine | OS, runtime, app, scaling logic | Hypervisor, hardware | Lift-and-shift, custom OS, GPU/TPU workloads, anything that won't fit a container |
| **GKE Standard** | Kubernetes cluster | Cluster config, node pools, workloads | Control plane (master) | Microservices at scale, complex orchestration, when you want Kubernetes APIs |
| **GKE Autopilot** | Kubernetes workloads | Workloads only | Everything below the workload, including nodes | Kubernetes without operating nodes; pay per pod |
| **Cloud Run** | Container as a service | The container image | Everything else, including scale-to-zero | Stateless web apps and APIs, event-driven services |
| **Cloud Run functions** (formerly Cloud Functions) | A single function | Source code | Build, deploy, runtime, scaling | Glue code, single-purpose handlers, light event processing |

A useful **continuum**: more control / more ops on the left, less control / less ops on the right.

```
Compute Engine  →  GKE Standard  →  GKE Autopilot  →  Cloud Run  →  Cloud Run functions
```

**Knative serving** is the open-source spec that Cloud Run implements; you'll occasionally see it in the exam guide as a reminder that Cloud Run runs Knative-compatible containers.

### 2.2 Compute Engine — VM fundamentals

A VM is defined by:

- **Machine type** — predefined families: `e2` (cost-optimised), `n2`/`n2d` (general purpose), `c2`/`c3` (compute-optimised), `m2`/`m3` (memory-optimised), `a2`/`a3` (GPU/AI). Or **custom** — pick exact vCPU and memory amounts within family limits.
- **Image** — the boot disk template (public OS image, or a custom one you've built).
- **Boot disk** — by default a Persistent Disk; can be a Local SSD for ephemeral workloads.
- **Network** — VPC + subnet + zone; optional external IP.
- **Service account** — the identity the VM uses to call other GCP APIs.

#### Availability policy
- **On host maintenance** — `MIGRATE` (live migrate to another host, default) or `TERMINATE` (stop the VM during maintenance, required for some configs like sole-tenant or some GPU types).
- **Automatic restart** — restart the VM if it crashes (default on).

#### SSH access
- **OS Login** (recommended) — SSH access controlled by IAM. The VM looks up your IAM identity instead of metadata SSH keys. Two relevant roles: `roles/compute.osLogin` (login) and `roles/compute.osAdminLogin` (sudo).
- **Metadata SSH keys** — old method, keys stored in project or instance metadata. Still works but managed in two places.

OS Login is preferred for the exam: centralised IAM, audit-logged, supports 2FA.

#### Spot VMs and custom machine types
- **Spot VMs** — heavily discounted (up to 91%), but Google can preempt them at any time with a 30-second shutdown signal. Use for fault-tolerant batch work, CI runners, render farms.
- **Preemptible VMs** — the older version of Spot, capped at 24-hour lifetime. Both names appear in older docs; treat them as roughly equivalent for the exam.
- **Custom machine types** — you specify vCPU + memory exactly (within ratios). Useful when off-the-shelf shapes are wasteful.
- **Sole-tenant nodes** — your VMs run on hardware that hosts no one else's workloads. Usually a licensing or compliance requirement.

#### Storage for VMs

| Option | Performance | Persistence | Notes |
|---|---|---|---|
| **Zonal Persistent Disk** | Standard, balanced, SSD, extreme | Survives VM deletion | The default; lives in one zone |
| **Regional Persistent Disk** | Same tiers | Synchronously replicated to a 2nd zone | For HA: failover with no data loss |
| **Local SSD** | Highest IOPS / lowest latency | **Ephemeral** — lost when VM stops | Caches, temp scratch space |
| **Hyperdisk** | Newer, tunable IOPS + throughput separately from size | Persistent | The modern option for high-performance workloads; available on newer machine families |
| **Cloud Storage FUSE / NetApp / Filestore** | File-level access | External | Used as a network file system, not a VM boot disk |

Persistent Disks can be **resized while attached** (you cannot shrink), and **snapshots** are incremental and stored as Cloud Storage objects.

#### VM Manager

A suite that automates **fleet-level OS operations** on Compute Engine VMs (and on-prem with Anthos):

- **OS Inventory Management** — collects installed packages, kernel version, OS metadata for every VM.
- **OS Patch Management** — schedules and runs patch jobs across thousands of VMs (Linux + Windows). Can target by zone/label and roll out in batches.
- **OS Configuration Management** — declarative desired state for packages, files, services (think "small Ansible inside Google Cloud").

Enable VM Manager on the project; the **OS Config agent** must be running on each VM (it ships with most public images and with the Ops Agent installer). Exam-relevant phrasing: "we need to know what's installed on every VM" → OS Inventory; "we need to apply security patches in waves" → OS Patch.

### 2.3 Managed instance groups (MIGs)

A MIG is a fleet of identical VMs created from an **instance template**. Critical exam concept.

- **Instance template** — immutable spec (machine type, image, network, startup script, service account, …). To change anything you create a new template and roll it out.
- **Zonal MIG** — VMs in a single zone.
- **Regional MIG** — VMs spread across multiple zones in a region (better availability; you don't choose which zone, the MIG balances).
- **Autoscaling** — scales the MIG based on:
  - CPU utilization
  - HTTP load-balancer serving capacity (requests per second, or backend utilization)
  - Cloud Monitoring metric (any metric)
  - Pub/Sub queue depth (via metric)
  - Schedule
- **Auto-healing** — replaces VMs that fail a *health check*. Important: this is a separate concept from load-balancer health checks (though they often share configuration).
- **Updates** — rolling updates with configurable surge / max unavailable / canary distribution.

Autoscaling **adds and removes** VMs. Vertical scaling (changing machine size) requires recreating instances.

#### Containers vs. VMs (the analogy)

A VM virtualises **hardware** — every VM ships with its own OS kernel, takes minutes to boot, and weighs gigabytes. A container virtualises the **process tree** — many containers share one host kernel, start in seconds, and weigh megabytes.

Concrete differences the exam probes:
- **Boot time** — minutes (VM) vs. seconds (container).
- **Density** — dozens of VMs per host vs. hundreds of containers.
- **Isolation** — VM has hardware-level isolation; container has kernel-level (namespaces, cgroups).
- **Image format** — disk image (GB) vs. layered OCI image (MB), built once with a Dockerfile and pushed to a registry.

#### Containerizing an application with Docker

The standard packaging step before GKE / Cloud Run:

1. Write a **Dockerfile** — `FROM`, `COPY`, `RUN`, `CMD` instructions describing how to build the image.
2. `docker build -t IMAGE:TAG .` — produces a local image.
3. `docker run IMAGE:TAG` — verify it works locally.
4. Tag and push to a registry: `docker push REGION-docker.pkg.dev/PROJECT/REPO/IMAGE:TAG` (Artifact Registry).
5. Deploy that image to GKE / Cloud Run / Cloud Run functions.

For multi-language stacks, **Cloud Buildpacks** (`pack` CLI) can produce an image without a Dockerfile by detecting the language and applying Google-maintained build steps.

### 2.4 GKE essentials

Kubernetes on Google Cloud comes in two flavours:

| Mode | You pay for | You configure |
|---|---|---|
| **GKE Standard** | Nodes (VMs in your project) + control plane fee per cluster | Node pools, networking, autoscaling, node OS |
| **GKE Autopilot** | Pods (CPU/memory requested) | Workloads only — no nodes to see |

Cluster topologies:

- **Zonal** — control plane in one zone, default node pool in one zone. Simple, cheap, weakest availability.
- **Regional** — control plane replicated across 3 zones, nodes spread across zones. Recommended for production.
- **Private cluster** — nodes have only internal IPs; the control plane has a private endpoint. The classic way to keep clusters off the public internet.

Node pools:
- A cluster has one or more **node pools**, each with its own machine type, autoscaling config, and labels/taints.
- You scale node pools, not the cluster as a whole. Different workloads can target different pools (e.g. a GPU pool for ML, a small pool for batch).
- **Cluster autoscaler** adds/removes nodes; **Horizontal Pod Autoscaler (HPA)** scales pods inside a deployment; **Vertical Pod Autoscaler (VPA)** adjusts pod resource requests.

`kubectl` is the CLI for Kubernetes. To configure it for a GKE cluster, the standard pattern is:

1. Install the `gke-gcloud-auth-plugin` (required for kubectl to authenticate via gcloud).
2. `gcloud container clusters get-credentials NAME --region=REGION` — writes a kubeconfig entry.
3. `kubectl get nodes` to confirm.

### 2.5 Serverless: Cloud Run and Cloud Run functions

**Cloud Run** runs **stateless containers**. You give it an image, a port, and a region. Google handles the rest.

- **Concurrency** — multiple requests can hit the same container instance (configurable, default 80).
- **CPU allocation** — `default` (CPU only during requests) or `always` (background work allowed).
- **Scale** — to zero by default; can set min instances to keep N warm.
- **Two execution environments**:
  - **Cloud Run service** — long-running web service, handles HTTP requests.
  - **Cloud Run job** — runs to completion, like a batch job. Can be triggered manually, scheduled, or invoked.
- **Traffic splitting** — deployments are versioned as **revisions**; you can route 50/50 between revisions for canaries or rollbacks.

**Cloud Run functions** = the next generation of Cloud Functions, now built on Cloud Run. You upload **source code**, Google builds the container, and the rest works like Cloud Run. There are still two generations in the docs; always pick "Cloud Run functions" / 2nd gen on the exam unless told otherwise.

### 2.6 Eventing — Pub/Sub, Cloud Storage triggers, Eventarc

Serverless workloads are usually triggered by events:

- **HTTP trigger** — direct HTTP request.
- **Pub/Sub trigger** — invoked when a message arrives on a topic.
- **Cloud Storage object change trigger** — invoked when an object is created/deleted/updated in a bucket.
- **Eventarc** — the unified event router. It standardises events from many sources (Audit Logs, Pub/Sub, Cloud Storage, third-party SaaS) into the **CloudEvents** format and delivers them to Cloud Run, Cloud Run functions, GKE, or Workflows. The exam wants you to know Eventarc as the **modern pattern** for event-driven architecture.

## 3. Decision criteria

The "which compute?" question shows up many times. A simple decision flow:

1. **Do you need a specific OS, kernel, GPU/TPU, or licensed software?** → Compute Engine.
2. **Are you running an existing Kubernetes cluster or do you need full Kubernetes APIs?** → GKE (Autopilot for hands-off, Standard for full control).
3. **Is the workload a stateless container or function?** → Cloud Run (a service or a job) or Cloud Run functions.
4. **Is it a single-purpose handler responding to an event?** → Cloud Run functions.

Side-by-side details:

| Concern | Pick |
|---|---|
| Long-running stateful service | Compute Engine, or GKE with StatefulSet |
| Spiky traffic, scale-to-zero acceptable | Cloud Run |
| Predictable traffic, want a fleet of identical VMs | Compute Engine + MIG |
| Event-driven glue (object lands → process) | Cloud Run functions |
| Heterogeneous microservices in containers | GKE |
| 30-second handlers, no infrastructure to manage | Cloud Run functions |
| Need root / kernel modules | Compute Engine |
| Batch job that must run to completion | Cloud Run job, or a Compute Engine MIG with custom logic |

## 4. Console walkthrough

- **Create a VM** — *Compute Engine → VM instances → Create instance*. The form covers machine type, boot disk image, networking, security (service account, OS Login), and "advanced options" for sole-tenant, host maintenance, etc.
- **Instance templates & MIGs** — *Compute Engine → Instance templates* to define a template. Then *Instance groups → Create instance group*, choose "Managed", pick the template, set autoscaling and health checks.
- **Snapshots & images** — *Compute Engine → Snapshots* and *Images*. Snapshot schedules are configured under *Compute Engine → Snapshots → Snapshot schedules*.
- **GKE clusters** — *Kubernetes Engine → Clusters → Create*. Choose Autopilot or Standard, region/zone, network, then for Standard you configure node pools.
- **Cloud Run** — *Cloud Run → Services* (long-running) or *Jobs*. "Deploy container" walks through image, region, scaling, networking.
- **Cloud Run functions** — *Cloud Run functions → Create function*. Pick trigger (HTTP, Pub/Sub, Cloud Storage, Eventarc), runtime, source.
- **Eventarc** — *Eventarc → Triggers → Create trigger*.

## 6. Exam gotchas

- **GKE Autopilot pricing is per-pod**, not per-node. If a question complains about "paying for unused node capacity", the answer is Autopilot or Cloud Run, not "fix the autoscaler".
- **Spot VMs can be preempted at any time.** The 24-hour cap was for the *old* preemptible model. Don't conflate.
- **Regional Persistent Disks** synchronously replicate across two zones. Snapshots replicate across regions, but they are *backups*, not real-time replicas.
- **Local SSD is ephemeral.** A VM stop/restart loses the data. The exam loves this.
- **Custom machine types** still have ratio constraints (memory per vCPU), don't promise "any combination".
- **OS Login** doesn't work if metadata SSH keys are in use on the project — they coexist awkwardly. Best practice is to enable OS Login project-wide and remove metadata keys.
- **Instance templates are immutable.** "Update the MIG to use a new image" → create a new template and roll it out.
- **Cloud Run scales to zero by default**, which means cold starts. If a scenario complains about latency on first request, the answer is **min instances**.
- **Cloud Run requires a stateless container**. Persistent state belongs in Cloud SQL, Cloud Storage, etc.
- **Eventarc vs. direct triggers** — the exam may give you both as options. Eventarc is the unified, future-proof choice. Direct Pub/Sub triggers still exist for simple cases.
- **GKE private cluster** still needs egress to pull container images; that's where Cloud NAT or VPC peering with Artifact Registry comes in.
- **kubectl needs the auth plugin.** Recent gcloud versions require `gke-gcloud-auth-plugin`; if the question says "kubectl returns auth errors after `get-credentials`", that's the cause.

## 6.5 Named scenarios

These are deeper, narrative walk-throughs of the kind of design questions the exam asks — distinct from the multiple-choice quiz below.

### Scenario A — Cost optimisation & workload types
**Context.** A startup is over-spending on compute. Three workloads dominate the bill:
1. A Python web API serving variable traffic (peaks at lunch, near-zero overnight).
2. A nightly ML training batch that takes 6 hours on 32 vCPUs and tolerates restarts.
3. A long-running self-managed PostgreSQL on a single n2-standard-8 VM running 24/7 because they need a Postgres extension Cloud SQL doesn't support.

**Recommended design.**
| Workload | Right answer | Why it saves money |
|---|---|---|
| Python web API | **Cloud Run** with `min-instances=0`, concurrency 80 | Scale-to-zero overnight = $0; pay only for request seconds. Cold-start penalty acceptable for the API's SLO. |
| ML batch | **Spot VMs** in a regional MIG, instance template with the training image, `--instance-termination-action=STOP` | Up to **91% discount**. Restartable code makes preemption a non-event. |
| Self-managed Postgres | Keep on Compute Engine but right-size: switch to **custom machine type** (e.g. 4 vCPU / 32 GB if memory-bound), enable **committed-use discount** for 1 year | Custom shape removes wasted vCPU; CUD trims another 25–37% on the steady-state base. |

**Why this works.** Each workload picks the *cheapest service that fits its tolerance for disruption*. Stateless + bursty → Cloud Run. Stateful + restartable → Spot. Long-running + cannot move to managed → CUD + right-sizing on GCE. Lifting all three to "always-on n2 VMs" was the original mistake.

### Scenario B — Building a scalable web application (use case)
**Context.** End-to-end design for a public web app that should survive a zone failure, scale automatically, and serve users worldwide. This is the canonical *Practical Use Case* the Udemy course walks through.

**Architecture.**
```
Users  →  Cloud DNS  →  Global external Application LB (Premium tier)
                              │  + Cloud Armor (WAF/DDoS) + Cloud CDN
                              ▼
                       Regional MIG (web tier, e2-medium)
                          • Instance template w/ startup script
                          • Auto-healing on HTTP /health
                          • Autoscaling on backend utilization 60%
                          • Spread across europe-west3-a/b/c
                              │
                              ▼
                       Cloud SQL Postgres (Regional HA) + Read Replica
                              │
                              ▼
                       Cloud Storage (eu multi-region) for user uploads
```

**Build order.**
1. Custom-mode VPC with one subnet in `europe-west3` (`/20`); enable Private Google Access.
2. Instance template `web-tmpl-v1` (e2-medium, Debian, startup script installing the app, attached to a least-privileged service account).
3. Health check `web-hc` → `/health` on port 80.
4. **Regional MIG** `web-mig` (3 zones, autoscaling 2–10, auto-healing with the health check, initial delay 60 s).
5. Reserve a global static external IPv4 → create global external Application LB with a Google-managed cert and the MIG as backend; enable Cloud CDN on the backend service.
6. Add `roles/storage.objectAdmin` on the uploads bucket to the MIG's SA so app code can write directly via the metadata server (no keys).
7. (Optional) Cloud Armor security policy attached to the LB backend service for IP allowlists / rate limiting / OWASP rules.

**Why this works.** Every layer covers one concern: LB = global entry + TLS, MIG = horizontal scale + auto-heal, regional Cloud SQL = stateful HA, multi-region bucket = continent-wide static-asset durability. Adding a second region later means cloning the MIG into another region and adding it as a second backend on the same LB — no app rewrite.

### Scenario C — Infrastructure as a Service (when to pick GCE)
**Context.** A team is debating whether to lift-and-shift a Windows + .NET Framework 4.7 application that depends on a custom kernel-level USB driver and a per-CPU licensed library.

**Recommended pick: Compute Engine (IaaS).** Three constraints rule out the alternatives:
- **Custom kernel driver** → containers and serverless can't load arbitrary kernel modules. GKE / Cloud Run are out.
- **Licensed library priced per CPU** → you need a **predictable CPU shape**. Cloud Run / Autopilot autoscale CPU allocation, breaking the license model. A fixed-shape `n2` or `c3` VM is the right answer.
- **Windows + .NET Framework 4.7** → Windows containers on GKE are technically possible but unusual; the simplest path is a Windows Server VM with the binary installed.

**Operational pattern.** Build a **golden image** (custom image baked from a configured VM), put it behind an instance template + small MIG (size 2 for HA across zones), front with an internal/external LB. Use **Sole-tenant nodes** if the license requires "no shared hardware". Schedule daily disk snapshots via a resource policy. This is *exactly* the IaaS sweet spot — the VM lives a long time, runs a custom binary, and benefits from Compute Engine's HA primitives without asking you to refactor the app.

### Scenario D — Security & private clusters
**Context.** A regulated SaaS company runs their workloads on GKE. Audit findings require:
1. The control plane must not be reachable from the public internet.
2. Worker nodes must have no external IPs.
3. The cluster must still pull container images from Artifact Registry and call Google APIs (BigQuery, Pub/Sub).
4. Operators on corporate laptops must still administer the cluster via `kubectl`.

**Recommended design.**
- **Regional Standard cluster** (control-plane HA across 3 zones) with **Private nodes: Enabled** and **Private endpoint** for the control plane. The public endpoint is **disabled**; the control-plane CIDR block is `172.16.0.0/28`.
- **Master authorized networks**: add the corporate egress CIDR (or, better, only the IAP TCP forwarding range `35.235.240.0/20`) so operators reach the private endpoint via IAP.
- **Egress for image pulls and APIs**: enable **Private Google Access** on the node subnet. Artifact Registry, `*.googleapis.com`, and `gcr.io` resolve to private VIPs that don't traverse the internet. No Cloud NAT needed unless workloads also call third-party HTTPS endpoints.
- **Workload Identity** enabled cluster-wide. Each workload runs as its own Kubernetes SA bound to a Google SA with only the IAM roles that workload needs.
- **kubectl access**: operators use `gcloud container clusters get-credentials … --internal-ip` and connect through an **IAP TCP tunnel** to a small bastion VM in the same VPC, or use Cloud Shell (which is whitelisted via an authorized network).

**Why this works.** Private nodes + private endpoint solve constraints 1 and 2. Private Google Access satisfies 3 without re-exposing the cluster to the public internet. IAP + master authorized networks satisfy 4 with identity-aware, audit-logged access.

### Scenario E — GKE: pods & nodes
**Context.** A workload owner says: "My pods are stuck in `Pending` and the cluster autoscaler isn't adding nodes. Some pods OOM-kill mid-day. We pay too much for nodes overnight."

**Diagnosis & fix, in order.**
1. **Pending pods** — `kubectl describe pod <p>` shows `0/3 nodes are available: insufficient memory`. The pods request 8 Gi each but the existing pool is `e2-standard-4` (16 Gi total per node, only ~12 Gi usable for pods after system reserves). Two fixes: shrink the request if real usage is smaller, or add a node pool with a larger machine type.
2. **Cluster autoscaler not scaling** — check the pool's max-nodes setting. If max is already reached, the autoscaler can do nothing. Either raise the cap or move workload to a pool that can grow.
3. **OOM at midday** — set a sensible **memory limit** AND raise the **request**. Use **VPA in `recommend` mode** (don't combine with HPA on memory) to get Google-recommended values; bake them into the deployment YAML.
4. **Overnight overpay** — the default node pool has `min-nodes=1`. For a non-prod cluster, set min-nodes=0 on a separate "burst" pool with a taint, and put workloads there with a matching toleration. Cluster autoscaler will scale that pool to 0 overnight when pods drain.
5. **Steady-state efficiency** — switch the burst pool to **Spot VMs** if the workload is restart-tolerant, then add a **PodDisruptionBudget** to keep at least one replica during preemptions.

**Why this works.** Each symptom maps to the *correct autoscaler*: HPA scales pods, VPA tunes requests, cluster autoscaler scales nodes — all three are needed for an efficient cluster. Adding nodes blindly would have masked the request misconfiguration.

### Scenario F — Serverless computing with Cloud Run
**Context.** A team has a small Node.js HTTP API. Latency requirement: p99 < 400 ms warm, < 2 s cold. Traffic: 0–500 RPS, very spiky. They want to deploy in `europe-west3` and bill back per request.

**Recommended design.**
- **Cloud Run service** with a container built via Cloud Buildpacks (no Dockerfile needed for a vanilla Node app).
- **Concurrency 50** — Node is single-threaded; tune below the default 80 to avoid event-loop saturation under load.
- **Min instances = 1** — keeps one warm to absorb the first request after idle without a cold start. (Cost: one always-on instance ≈ $5–10/month — much cheaper than losing customers to a 2 s cold start.)
- **Max instances = 50** — caps blast radius if a runaway client floods the service.
- **CPU allocation = "CPU only during requests"** — the API has no background work. Combined with **Startup CPU boost** to shrink the warm-up window for any cold instance that does spawn during a spike.
- **Autoscaling signal** is implicit (concurrent requests / instance), not configurable; Cloud Run hits the target on its own.
- **Deploy with `--no-traffic`**, then `update-traffic --to-revisions=<new>=10` for a 10% canary, watch the SLO dashboards in Cloud Monitoring, then ramp to 100%. Roll back instantly with another `update-traffic` if the canary regresses.
- **Per-team chargeback**: tag the service with `--labels=team=growth,env=prod`. Labels propagate to the billing export, so finance can split the line item by team.

**Why this works.** The default Cloud Run knobs are tuned for stateless web traffic; the only intentional changes (min instances, concurrency, CPU boost) directly address the latency SLO and the runtime model. Revisions + traffic splits give zero-downtime rollouts and rollbacks without needing a separate deployer.

## 7. Practice scenarios

### Q1 — Picking the right compute service
A team is migrating a stateless Python web API. Traffic is highly variable: bursts during work hours, near-zero overnight. They want minimum operations and the lowest cost during idle periods. Which service?

A. Compute Engine with a managed instance group.
B. GKE Standard with HPA.
C. **Cloud Run.**
D. App Engine standard.

**Answer: C.** Stateless + scale-to-zero + minimum ops = Cloud Run. A and B don't scale to zero (you keep paying nodes). D is acceptable but Cloud Run is the modern recommended answer for new containerised workloads.

### Q2 — VM availability policy
You're running a CPU-intensive batch job that tolerates restarts but you want it cheaper. Which configuration?

A. n2-standard-4 with `--maintenance-policy=MIGRATE`.
B. n2-standard-4 Spot VM with `--maintenance-policy=TERMINATE`.
C. e2-medium with `--maintenance-policy=MIGRATE`.
D. n2-standard-4 with sole-tenant.

**Answer: B.** Spot VMs are deeply discounted (up to 91%) and require `TERMINATE` (they're preemptible). Sole-tenant (D) is *more* expensive. A is fine but full price. C downgrades CPU/memory but pays full price.

### Q3 — MIG vs. instance template
You want to update the boot image on every VM in a regional MIG. What's the correct workflow?

A. SSH each VM and update the OS in place.
B. Modify the existing instance template's image.
C. Create a new instance template referencing the new image; configure a rolling update on the MIG to use it.
D. Delete the MIG and recreate with the new image.

**Answer: C.** Instance templates are **immutable** — you cannot modify (B). A is unscalable and breaks the MIG model. D causes downtime. The correct pattern is "new template + rolling update".

### Q4 — Persistent Disk choice for an HA database
A self-managed PostgreSQL VM must survive a zone failure with no data loss. What disk type?

A. Local SSD.
B. Zonal Persistent Disk standard.
C. **Regional Persistent Disk SSD.**
D. Zonal Persistent Disk SSD with daily snapshot schedule.

**Answer: C.** Regional PD synchronously replicates across two zones in the same region — the requirement is "no data loss across zone failure". A loses data on stop. B and D are zonal (lose access on zone failure; snapshots provide point-in-time recovery, not zero-data-loss failover).

### Q5 — GKE cluster type for a regulated workload
A GKE cluster must be unreachable from the public internet (control plane and nodes). The team also wants the highest control-plane availability. Which configuration?

A. Zonal cluster with private nodes.
B. Regional cluster with private nodes and private endpoint for the control plane.
C. Autopilot cluster with public endpoint disabled.
D. Regional Standard cluster with public endpoint and authorized networks.

**Answer: B.** Regional gives multi-zone control-plane HA; private nodes have no external IPs; private endpoint blocks public access to the control plane. A is single-zone (less HA). C also works but the question implies needing the standard cluster's control. D leaves a public endpoint, just IP-restricted — not "unreachable".
