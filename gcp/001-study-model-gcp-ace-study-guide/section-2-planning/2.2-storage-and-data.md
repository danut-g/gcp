# 2.2 — Planning and implementing storage and data solutions

> **Exam guide reference:** Section 2.2. Sub-topics: choosing data products (Cloud SQL, BigQuery, Firestore, Spanner, Bigtable, AlloyDB, Dataflow, Pub/Sub, Managed Service for Apache Kafka, Memorystore), choosing storage products (Cloud Storage, Filestore, NetApp Volumes), Cloud Storage classes (Standard / Nearline / Coldline / Archive), loading data (CLI, Cloud Storage, Storage Transfer Service), maintaining multi-region redundancy.

---

## 1. Why this matters for the exam

Storage and data is a *huge* surface area on Google Cloud, and almost every exam scenario will say something like "we need to store / query / move data of this shape" — your job is to pick the right product. The exam doesn't really test how to write SQL or design a schema; it tests whether you know **which product fits which workload**.

The two skills you need:
1. **Pattern-match** the workload (relational? OLAP? key-value? document? streaming? files? blobs?) to the product.
2. Understand **redundancy and locality** options — regional vs. multi-regional, replication, backup.

---

## 2. Core concepts

### 2.1 The data product map

Group products by what they actually are:

#### Object storage — Cloud Storage
Buckets of arbitrary blobs. Anything binary: images, videos, backups, ML training data, static website assets.

#### File storage — Filestore, Google Cloud NetApp Volumes
NFS-style network file systems. Use when an application **must** see a POSIX filesystem (legacy apps, lift-and-shift, shared scratch space across VMs).

- **Filestore** — Google's managed NFS (NFSv3). Picked by **service tier**:

  | Tier | Performance | Availability | Use case |
  |---|---|---|---|
  | **Basic HDD** | Low IOPS, cheap | Zonal | Cold home directories, archive shares |
  | **Basic SSD** | Higher IOPS | Zonal | General-purpose POSIX share |
  | **Zonal** (formerly High Scale) | Up to 920k IOPS | Zonal | High-throughput analytics, render farms |
  | **Regional** | Same as Zonal but replicated | Regional (synchronous) | Production workloads needing zone-failure resilience |
  | **Enterprise** | High IOPS, low latency | Regional | SAP, EDA, mission-critical apps |

  Filestore instances expose an internal IP; clients mount with `mount -t nfs IP:/SHARE /mnt/...`. They live inside a VPC; cross-VPC access uses peering or a private service connection.

- **NetApp Volumes** (Google Cloud NetApp Volumes) — Google-managed ONTAP. Supports **NFS (v3, v4.1)**, **SMB (v2/v3)**, and dual-protocol. Picked when:
  - You already run NetApp on-prem and want SnapMirror replication into Google Cloud.
  - You need SMB shares (which Filestore doesn't offer).
  - You need ONTAP features (snapshots, FlexClone, dedup).

#### Relational databases — Cloud SQL, AlloyDB, Spanner
- **Cloud SQL** — managed MySQL / PostgreSQL / SQL Server. Single region, can have read replicas and HA failover. The default "I need a relational DB" answer.

  **High availability (HA)** — set `--availability-type=REGIONAL` at create time. Cloud SQL provisions a **synchronous standby in another zone in the same region**. If the primary fails, Cloud SQL fails over to the standby automatically with the same connection name (no DNS change). RTO is typically a minute or two; RPO is zero (synchronous).

  **Read replicas** are different from HA standbys:
  - They are **asynchronous** read-only copies; clients must explicitly connect to them.
  - Used to **offload read traffic** from the primary, or to keep a copy in another region for **DR**.
  - In a regional HA pair, the standby is **not** queryable; only the primary serves traffic. Need read scale-out → add explicit read replicas.
  - Cross-region read replicas exist; promotion to a standalone primary is **manual** and is the DR pattern for a regional outage.
- **AlloyDB** — PostgreSQL-compatible, but architected differently for performance and analytics. Use when you want PostgreSQL but Cloud SQL won't scale enough.
- **Spanner** — globally distributed, strongly consistent, horizontally scalable relational database. Built for huge transactional systems that need cross-region consistency. Expensive; only the right answer when geo-distribution + ACID is genuinely required.

#### NoSQL — Firestore, Bigtable
- **Firestore** — document database, low-latency, simple queries, mobile/web SDKs. Default for app data, user profiles, shopping carts.
- **Bigtable** — wide-column, petabyte-scale, single-digit-millisecond latency. Time-series, IoT telemetry, ad tech, financial ticks. **Not** for a typical app DB.

#### Analytical — BigQuery
Serverless data warehouse, columnar storage, runs SQL over petabytes. Used for analytics, dashboards, BI, large-scale reporting.

- Two pricing models: **on-demand** (per TB scanned) and **capacity** (slot-based reservations).
- Storage and compute are separated; you pay storage even when not querying.

#### Caching — Memorystore
Managed Redis or Memcached. In-memory cache for sub-millisecond reads. Sessions, leaderboards, rate-limiting counters.

#### Messaging & streaming — Pub/Sub, Managed Service for Apache Kafka
- **Pub/Sub** — Google-native publish/subscribe, fully managed, global. Standard for event-driven architectures.
- **Pub/Sub Lite** — cheaper, zonal, lower-throughput variant. Newer exams may not feature it heavily.
- **Managed Service for Apache Kafka** — when you specifically need Kafka APIs (existing Kafka clients, ecosystem). Otherwise prefer Pub/Sub.

#### Stream and batch processing — Dataflow
Managed Apache Beam. Runs ETL pipelines for both **streaming** and **batch**. Often pairs with Pub/Sub on the input side and BigQuery / Cloud Storage on the output.

### 2.2 Cloud Storage in detail

A **bucket** holds **objects**. Names are globally unique.

**Location types**:

| Type | Replicated where | Use case |
|---|---|---|
| **Region** | One region (multiple zones) | Most workloads — low latency near compute |
| **Dual-region** | Two specific regions, synchronously replicated | HA across regions you choose |
| **Multi-region** | Multiple regions in a continent (e.g. `eu`, `us`, `asia`) | Globally served content, max availability |

**Storage classes** — chosen per object (or as bucket default):

| Class | Min storage duration | Retrieval cost | Access pattern |
|---|---|---|---|
| **Standard** | none | none | Hot data, frequent access |
| **Nearline** | 30 days | per-GB retrieval fee | Once a month |
| **Coldline** | 90 days | higher retrieval fee | A few times a year |
| **Archive** | 365 days | highest retrieval fee | Compliance archives, "almost never" |

The **min storage duration** matters — deleting a Coldline object after 10 days still incurs the 90-day charge.

You can switch classes per object, manually or via **Object Lifecycle Management** (rules like "after 30 days, transition to Nearline; after 365, delete"). Lifecycle policies are evaluated daily.

**Versioning** — enable at the bucket level; each overwrite or delete keeps the prior copy. Combined with lifecycle rules (e.g. "delete non-current versions older than 30 days"), this gives you a soft-delete system.

**Object holds and retention policies** — for compliance:
- **Retention policy** on the bucket — objects cannot be deleted before N seconds since creation.
- **Object holds** (event-based / temporary) — pin an individual object against deletion.
- **Object versioning** — soft delete via version history.

**Encryption** — Google encrypts at rest by default. Options:
- **Google-managed keys (GMEK)** — default.
- **Customer-managed keys (CMEK)** — you create a key in Cloud KMS and the service uses it.
- **Customer-supplied keys (CSEK)** — you supply the key on every request; Google never stores it.

### 2.3 Loading data

Multiple options; pick by size and cadence.

| Tool | Use for |
|---|---|
| `gcloud storage cp` (or older `gsutil cp`) | One-off uploads / downloads, scripts |
| **Cloud Storage console upload** | Small ad-hoc files |
| **Storage Transfer Service** | Scheduled transfers from S3, Azure Blob, on-prem (via agent), or Cloud Storage to Cloud Storage |
| **Transfer Appliance** | Petabyte-scale offline transfer — Google ships a physical box you fill and return |
| **BigQuery Data Transfer Service** | Scheduled imports into BigQuery from SaaS sources (YouTube, Google Ads, S3, etc.) |
| **Database Migration Service** | Online migration of MySQL / PostgreSQL / SQL Server / Oracle into Cloud SQL or AlloyDB |
| **bq load** | Load files from Cloud Storage into BigQuery |

#### Storage Transfer Service in detail

Three source families:

| Source family | Auth pattern |
|---|---|
| **Cloud-to-cloud** | AWS S3 (access key or AWS WIF), Azure Blob (SAS token), other GCS buckets |
| **From a public URL list** | TSV file with HTTPS URLs and MD5/sizes |
| **On-premises (or any POSIX filesystem)** | Install **Transfer Service for on-prem agents** as a Docker container; agents stream over TLS |

Job options:
- **Schedule** — one-shot, daily, hourly.
- **Filters** — include/exclude prefixes, modified-since timestamps.
- **Overwrite policy** — when destination has the file, overwrite vs. skip.
- **Bandwidth limit** — cap MB/s to avoid saturating the link.
- **Notifications** — Pub/Sub topic on completion.

For >50 TB on a slow link, **Transfer Appliance** is the answer instead — Google ships a 7 TB / 40 TB / 300 TB device, you load it, ship it back, they upload to your bucket.

For Cloud Storage → BigQuery, the standard pattern is **load** (batch) or **streaming inserts** / **Storage Write API** (continuous).

### 2.4 Multi-region redundancy

Each data product has its own redundancy story:

- **Cloud Storage** — pick a multi-region or dual-region bucket; replication is automatic and transparent.
- **Cloud SQL** — enable HA (regional, synchronous standby in another zone) + read replicas. **Cross-region** replicas exist for DR but failover is manual.
- **Spanner** — choose a multi-region instance configuration; replication is built in.
- **Firestore** — pick a multi-region location at database creation; it's permanent.
- **BigQuery** — choose dataset location (region or multi-region) at creation. You can copy datasets across regions, but you cannot move them.
- **Bigtable** — set up **replication** with one or more cluster copies in additional regions.
- **Pub/Sub** — already global; messages are stored in the closest region by default.

**Backups vs. replication** — replication is for availability, backups are for "oops, I deleted the table". Make sure your scenario has both.

## 3. Decision criteria

The most important table on the whole exam:

| Workload description | Pick |
|---|---|
| Petabytes of analytical SQL queries | **BigQuery** |
| Online transaction processing (OLTP), regional | **Cloud SQL** |
| OLTP that must scale globally with strong consistency | **Spanner** |
| PostgreSQL workload too big/slow for Cloud SQL | **AlloyDB** |
| Mobile / web app data, simple queries | **Firestore** |
| Time-series, IoT, ad-tech, very high throughput | **Bigtable** |
| Cache | **Memorystore** |
| Pub/sub / event bus | **Pub/Sub** (or Managed Kafka if Kafka APIs required) |
| ETL streaming pipeline | **Dataflow** |
| Static web content, backups, ML data | **Cloud Storage** |
| App needs an NFS share | **Filestore** |
| Enterprise wants ONTAP / SMB | **NetApp Volumes** |
| Frequent reads, daily access | Cloud Storage **Standard** |
| Once a month | **Nearline** |
| A few times a year | **Coldline** |
| Compliance archive | **Archive** |
| Move 100 TB from on-prem | **Storage Transfer Service** (or Transfer Appliance if no bandwidth) |
| Move a MySQL DB into Cloud SQL with minimal downtime | **Database Migration Service** |

A useful rule of thumb: **Cloud SQL until it stops working**, then think about Spanner or AlloyDB. Don't reach for Spanner unless the scenario explicitly demands global ACID.

## 4. Console walkthrough

- **Cloud Storage** — *Cloud Storage → Buckets → Create*. Pick name, location type (region / dual / multi), default storage class, access control (uniform vs. fine-grained), protection (versioning, retention, holds).
- **Object Lifecycle** — bucket page → *Lifecycle* tab → *Add rule*. Rules consist of conditions (age, class, version) + action (set storage class / delete).
- **Cloud SQL** — *SQL → Create instance*. Choose engine, region, machine type, HA (regional), backups, networking.
- **BigQuery** — *BigQuery → Create dataset* → choose location. Datasets contain tables and views. The Studio is where you write SQL; Saved queries, Scheduled queries, and Data Transfer Service are linked from the left rail.
- **Firestore** — *Firestore → Create database*. Pick **Native** or **Datastore** mode (Native is the modern one; Datastore mode is for legacy GAE apps). Pick location.
- **Spanner** — *Spanner → Create instance*. Multi-region requires picking from the predefined configurations.
- **Bigtable** — *Bigtable → Create instance*. Production vs. development; instance type determines replication options.
- **Memorystore** — *Memorystore → Redis* or *Memcached* → *Create instance*.
- **Pub/Sub** — *Pub/Sub → Topics → Create topic*. Subscriptions are managed under the topic.
- **Storage Transfer Service** — *Storage Transfer → Transfer jobs → Create*. Pick source (S3, Azure, GCS, on-prem) and destination GCS bucket, schedule.
- **Dataflow** — *Dataflow → Jobs → Create job from template*. Templates cover common pipelines (Pub/Sub → BigQuery, GCS → BigQuery, etc.).

## 6. Exam gotchas

- **Bucket names are globally unique.** Choose names accordingly; once taken, gone.
- **Storage class minimum-duration charges** are per-object. Switching to Coldline and deleting next day still costs you 90 days of storage.
- **Object Lifecycle is async** — rules run roughly daily, not immediately. Don't expect millisecond enforcement.
- **Versioning + lifecycle is the recommended "soft delete"** pattern, but it costs storage. The exam tests this combination.
- **Retention policy locks you in.** Once locked, you cannot reduce or remove the policy until the period passes — Google specifically built this for compliance.
- **Cloud Storage default access** is **Uniform Bucket-Level Access** in new projects. Don't reach for ACLs on the exam unless the question explicitly involves them.
- **Cloud SQL HA ≠ read replicas.** HA is automatic synchronous failover within a region. Read replicas are read-only copies that you fail over manually.
- **Spanner is expensive** — only the right answer when the scenario insists on global strong consistency. "Big PostgreSQL workload" alone is not enough; that's AlloyDB territory.
- **Firestore Native vs. Datastore mode** is a permanent choice at database creation. Native is the modern one.
- **Bigtable does not have a free tier** and doesn't fit "small app DB". The right scenarios are at-scale.
- **BigQuery dataset location is permanent** — to "move" a dataset you copy it.
- **Pub/Sub is global, but messages have a regional storage policy** if you need data residency.
- **Storage Transfer Service ≠ Transfer Appliance.** Transfer Service is online; Appliance is a literal box for huge offline migrations.
- **Database Migration Service** is the right answer for online MySQL/Postgres/Oracle migrations into Google's managed databases — not "use mysqldump and copy".
- **Memorystore is regional, single-zone in Basic tier**; for HA you need Standard tier.

## 6.5 Named scenarios

These narrative walk-throughs cover the kind of design questions the exam asks — distinct from the multiple-choice quiz below.

### Scenario A — The "Waterfall" lifecycle strategy
**Context.** A media company keeps user-uploaded video. Access pattern is well-known:
- Day 0–30: heavy access (just uploaded, hot in feeds).
- Day 31–90: occasional access (some users come back to share).
- Day 91–365: rare access (≈ once or twice a year, usually a dispute or compliance pull).
- After 1 year: legal hold for 7 years, almost never read, but **must be retrievable** within 12 hours.
- Versions kept on overwrite for 30 days, then deleted.

**Recommended design — a "waterfall" of lifecycle rules on a single bucket:**

```yaml
lifecycle:
  rule:
    - action:    {type: SetStorageClass, storageClass: NEARLINE}
      condition: {age: 30,  matchesStorageClass: [STANDARD]}
    - action:    {type: SetStorageClass, storageClass: COLDLINE}
      condition: {age: 90,  matchesStorageClass: [NEARLINE]}
    - action:    {type: SetStorageClass, storageClass: ARCHIVE}
      condition: {age: 365, matchesStorageClass: [COLDLINE]}
    - action:    {type: Delete}
      condition: {age: 30,  isLive: false}          # non-current versions
```

Plus: enable **versioning** (so the non-current rule has something to delete), and lock a **bucket retention policy** of 7 years (`220752000s`) — the lock is irrevocable and exactly satisfies the legal hold.

**Why this works.** Each rule fires when the *previous* tier is no longer cost-justified by access frequency. The min-storage-duration penalties (30/90/365) align naturally with the transition ages — you never delete a Coldline object before its 90 days are up. Lifecycle is async (~daily) so don't expect millisecond enforcement, but the math works out to roughly 1/10th the cost of leaving everything in Standard for the full 7 years.

### Scenario B — Global scale & consistency
**Context.** A global ride-hailing app needs a single source of truth for trips. Requirements:
- Drivers and riders in 30+ countries; users may move between regions mid-trip.
- Reads must reflect writes immediately, everywhere (driver reassignments must be globally consistent).
- 50,000 writes/sec at peak; horizontal scale is a hard requirement.
- SQL workload — joins across `trips`, `drivers`, `riders`, `payments`.

**Right answer: Spanner**, in a multi-region instance configuration (e.g. `nam3` for North America or `eur6` for Europe + secondary).

**Why not the alternatives?**
- **Cloud SQL with cross-region read replicas** — replicas are *async read-only*; promotion to primary is manual. You don't get global writes, and reads can be stale.
- **AlloyDB** — scales reads beautifully, but the primary is in a single region. Writes don't scale globally and a regional outage means manual failover.
- **Bigtable** — wide-column, no SQL joins; great latency but the wrong query model for trip ledger work.
- **Firestore (multi-region)** — strongly consistent, but document-oriented and not ideal for the SQL/relational queries the app already runs.

**Trade-offs.** Spanner is **expensive** — minimum 1 PU (processing unit) per region in a multi-region config; budget hundreds of $/month at the smallest size. Pick it only when *both* global distribution and ACID transactions are non-negotiable. The exam loves to lay out scenarios that *seem* to need Spanner but actually fit AlloyDB; read carefully for "globally consistent" or "strongly consistent across regions" before reaching for it.

### Scenario C — The processing engine choice
**Context.** A retail company has three distinct data jobs:
1. **Streaming clickstream → real-time dashboard** — every click in a mobile app is published to Pub/Sub; a near-real-time dashboard shows current funnel conversion.
2. **Nightly batch ETL** — yesterday's transactions land in Cloud Storage as JSON; need to clean/aggregate and load into BigQuery for analyst queries.
3. **Scheduled SQL transforms** — once daily, recompute a "customer lifetime value" table from existing BigQuery tables.

**Right pick per job:**

| Job | Service | Why |
|---|---|---|
| Streaming clickstream | **Dataflow (streaming)** with a Pub/Sub → BigQuery pipeline (or the Google-provided template) | Apache Beam handles windowing, watermarks, and exactly-once semantics into BigQuery. Auto-scaling workers absorb spikes. |
| Nightly batch ETL | **Dataflow (batch)**, or **bq load** if no transformation is needed | Dataflow if you need transforms; plain `bq load` for trivial schemas-already-match cases. |
| In-warehouse SQL transform | **BigQuery scheduled queries** (or **Dataform** for a managed dbt-style workflow) | The data is already in BigQuery; spinning up Dataflow for a SQL aggregation is overkill. |

**Why this works.** Each engine has a sweet spot: **Dataflow** for stream + complex transforms, **BigQuery scheduled queries / Dataform** for in-warehouse SQL, **Pub/Sub** as the streaming bus, **bq load** for trivial ingest. Don't reach for Managed Service for Apache Kafka unless you specifically need Kafka APIs (existing Kafka clients, ecosystem) — Pub/Sub is simpler and cheaper for greenfield.

### Scenario D — The Windows migration challenge
**Context.** A company is migrating an on-prem Windows-based application that:
- Uses **SMB shares** for shared file storage between multiple Windows VMs.
- Runs SQL Server (already migrated to Cloud SQL for SQL Server).
- Has a single .NET app server group that needs the SMB share for user-uploaded documents and report templates.

**The trap.** Filestore is the obvious "managed file storage" answer — but **Filestore is NFS-only (NFSv3 / v4.1)**. Windows can technically mount NFS, but it's awkward, undertested, and not how Windows admins expect to operate.

**Right answer: Google Cloud NetApp Volumes.** It's the only Google-managed file service that supports **SMB (v2/v3)** natively, and it also speaks NFS for the same volume (dual-protocol) if you ever need Linux access too.

**Architecture.**
- **NetApp Volumes capacity pool** in `europe-west3` with the *Premium* service level (or *Extreme* for higher IOPS) inside the same VPC as the Windows VMs.
- Create an **SMB volume** with Active Directory integration (NetApp Volumes can join your AD domain so file-level ACLs work like on-prem).
- Windows VMs `net use Z: \\<volume-host>\share` — looks identical to the on-prem fileserver.
- Snapshots and SnapMirror replication come built-in for backup/DR.

**Why not Filestore?** SMB is unsupported. Forcing Windows to use Filestore via NFS would require client tweaks, lose proper ACL semantics, and surprise the Windows ops team — exactly the things a lift-and-shift is supposed to avoid. The exam frames this as "the Windows migration challenge" and the answer is always NetApp Volumes.

## 7. Practice scenarios

### Q1 — Picking the right database
An application needs to store millions of small JSON documents (user profiles), with low-latency reads from web/mobile SDKs and minimal operations overhead. Which database?

A. Cloud SQL for MySQL.
B. BigQuery.
C. **Firestore (Native mode).**
D. Bigtable.

**Answer: C.** Firestore Native is the document DB designed for app data with mobile/web SDKs and simple queries. A would work but requires schema and is less mobile-SDK friendly. B is analytical, not OLTP. D is for huge wide-column workloads (IoT/ad-tech), not user profiles.

### Q2 — Storage class for archival
A team has 50 TB of compliance archives that must be retained for 7 years and accessed *less than once a year*. Cost is the priority. What's the right storage class?

A. Standard.
B. Nearline.
C. Coldline.
D. **Archive.**

**Answer: D.** Archive is designed for compliance data accessed almost never; minimum 365-day storage. C (Coldline) targets a few times a year. B (Nearline) is roughly monthly access. A is hot data.

### Q3 — Loading data
An on-prem team has 200 TB of historical logs to move into Cloud Storage. Bandwidth is limited (50 Mbps WAN) and they need it in 1 week. Which approach?

A. Scripted `gcloud storage cp` with parallelism.
B. Storage Transfer Service with on-prem agents.
C. **Transfer Appliance.**
D. Database Migration Service.

**Answer: C.** 200 TB at 50 Mbps takes ~370 days — hopeless over the wire. Transfer Appliance is the physical-shipping solution for petabyte-scale offline transfer. B is the *online* equivalent and would still saturate the link. D is a database migration tool, not for object storage.

### Q4 — BigQuery cost
A team's monthly BigQuery on-demand bill is dominated by repeated queries scanning the same large tables. They want predictable cost. The recommended action is:

A. Switch to **BigQuery capacity (slot-based) reservations**.
B. Move data to Cloud Storage and query it as external tables.
C. Increase the dataset's time-travel window.
D. Switch tables to long-term storage.

**Answer: A.** Capacity pricing (slot reservations) is the predictable, flat-rate alternative to on-demand per-TB-scanned pricing. B usually performs worse and still scans bytes. C is unrelated to query cost. D affects *storage* cost, not query cost.

### Q5 — Multi-region resilience for a relational DB
A globally distributed e-commerce platform requires single SQL queries to be strongly consistent across regions, with horizontal scale to thousands of writes per second. Which database?

A. Cloud SQL with cross-region read replicas.
B. **Spanner.**
C. AlloyDB.
D. Bigtable.

**Answer: B.** Spanner is the only managed database that combines global distribution with strong consistency and horizontal write scale. A's cross-region replicas are read-only. C scales reads beautifully but is regional. D scales but is non-relational and not strongly consistent across regions in the same way.

### Lab 5 — Manage objects with the `gcloud storage` CLI
**Goal:** practice the day-to-day object operations from the terminal — copy, move, set storage class, set metadata, parallel upload of a folder.

**Cloud Shell:**
```bash
BUCKET=$DEVSHELL_PROJECT_ID-demo-bucket

# Listing (long, recursive, with sizes)
gcloud storage ls -l gs://$BUCKET/
gcloud storage ls -lr gs://$BUCKET/**

# Copy local → bucket (parallel, recursive)
mkdir -p site && for i in 1 2 3; do echo "page $i" > site/page$i.html; done
gcloud storage cp -r site/ gs://$BUCKET/site/

# Copy bucket → bucket (server-side, no local hop)
gcloud storage cp gs://$BUCKET/site/page1.html gs://$BUCKET/archive/

# Move (rename) — server-side
gcloud storage mv gs://$BUCKET/archive/page1.html gs://$BUCKET/archive/page1-renamed.html

# Change storage class on a single object
gcloud storage objects update gs://$BUCKET/archive/page1-renamed.html --storage-class=COLDLINE

# Set custom metadata
gcloud storage objects update gs://$BUCKET/site/page1.html \
    --custom-metadata=owner=alice,env=dev

# Inspect
gcloud storage objects describe gs://$BUCKET/site/page1.html

# Delete
gcloud storage rm gs://$BUCKET/archive/page1-renamed.html
gcloud storage rm -r gs://$BUCKET/site/

# Note: `gsutil` is the older CLI; same verbs but different flags. Migrate to `gcloud storage`.
gsutil ls gs://$BUCKET/   # still works
```

**Console verification:** *Cloud Storage → Buckets → ${BUCKET}* — refresh and watch the file tree change as you run commands.

### Lab 6 — Create a Filestore instance and mount it on a VM
**Goal:** stand up a Filestore Basic SSD share, mount it from a Linux VM, write a file, then delete the (billable) instance.

**Console (create):**
1. *Navigation menu → Filestore → Instances → Create instance*. **Enable** the API if prompted.
2. **Instance ID:** `fs-1`. **Instance type:** *Basic*. **Storage type:** *SSD*. **Region:** `europe-west3`. **Zone:** `europe-west3-a`.
3. **Capacity:** 1 TiB (the minimum for Basic SSD).
4. **VPC network:** `default` (or your custom VPC).
5. **File share name:** `share1`. *Create*. Wait ~5–10 min until **Ready**.
6. Copy the instance's **IP address** (e.g. `10.150.0.2`) and share name from the row.

**SSH on a VM in the same VPC:**
```bash
sudo apt-get update && sudo apt-get install -y nfs-common
sudo mkdir -p /mnt/fs
sudo mount 10.150.0.2:/share1 /mnt/fs
df -h /mnt/fs
sudo bash -c 'echo "hello from $(hostname)" > /mnt/fs/note.txt'
ls -l /mnt/fs/
```

**[ALERT] Delete the Filestore instance** (1 TiB Basic SSD = ~$300/month — delete promptly):

**Console:**
7. *Filestore → Instances → fs-1 → Delete*. Type the name to confirm.

**gcloud:**
```bash
gcloud filestore instances create fs-1 \
    --zone=europe-west3-a --tier=BASIC_SSD \
    --file-share=name=share1,capacity=1TiB \
    --network=name=default

gcloud filestore instances describe fs-1 --zone=europe-west3-a
gcloud filestore instances delete fs-1 --zone=europe-west3-a --quiet
```
