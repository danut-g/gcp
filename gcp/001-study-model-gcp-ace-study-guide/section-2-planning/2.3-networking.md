# 2.3 — Planning and implementing networking resources

> **Exam guide reference:** Section 2.3. Sub-topics: VPC with subnets (custom mode, Shared VPC), Cloud Next Generation Firewall (Cloud NGFW) ingress/egress policies and attributes, Tags (secure Tags) and service accounts in firewall rules, network connectivity (Cloud VPN, VPC Network Peering, Cloud Interconnect), choosing/deploying load balancers, Network Service Tiers.

---

## 1. Why this matters for the exam

Networking is one of the most distinctive parts of Google Cloud — VPCs are **global**, subnets are **regional**, and routing/firewalls work differently than in AWS or on-prem. Many exam questions test whether you grasp these defaults, plus the choice between connectivity options (peering / VPN / Interconnect) and load balancers.

Common scenario types:
- A team can't reach a resource → diagnose firewall, route, or service IP issue.
- A company needs hybrid connectivity → pick VPN vs. Interconnect based on bandwidth and SLA.
- An app needs a load balancer → match traffic type and scope to the right LB product.

---

## 2. Core concepts

### 2.1 VPC fundamentals

A **VPC (Virtual Private Cloud)** is a global network. Inside it:

- **Subnets are regional.** A single VPC spans every region; you put a subnet in each region you want to operate in. This is unlike AWS, where VPCs are regional.
- **Internal IPs route freely** between subnets in the same VPC, across regions, with no extra config.
- **Routes are part of the VPC**, not the subnet. Default routes go to the internet gateway, the default gateway, etc. Custom routes are added at the VPC level.
- **Firewall rules are at the VPC level** but can target subnets, tags, or service accounts.

#### VPC modes

| Mode | Behaviour |
|---|---|
| **Auto** | Subnet automatically created in every region with a Google-chosen CIDR. Convenient for demos, **not recommended** for production. |
| **Custom** | You create subnets explicitly with the CIDRs you want. The exam expects custom mode for any real workload. |

#### Default VPC
Each new project gets a `default` VPC in auto mode with permissive firewall rules (allow internal, allow ICMP, allow SSH/RDP from any source). For production you delete it and build a custom VPC.

### 2.2 Shared VPC

A pattern for **organization-level network centralization**:

- A **host project** owns the VPC and its subnets.
- One or more **service projects** are attached to the host project; their resources (VMs, GKE nodes, etc.) live in the host's network.
- Network admins manage the network in one place; application teams operate in their own projects but share the network.

Shared VPC is the answer for "central security/network team owns the network, multiple application teams build on it". It requires the **Compute Shared VPC Admin** role at the org level.

### 2.3 VPC Peering

Connects two VPCs (in the same or different orgs) so their internal IPs reach each other directly.

- **Non-transitive** — A peered with B and B peered with C does not let A reach C.
- **No overlapping CIDRs allowed.**
- **Cheaper than VPN** since traffic stays on Google's network and isn't encrypted by you.
- Perfect for "two GCP projects, internal traffic only".

### 2.4 Hybrid connectivity — VPN and Interconnect

Two main ways to connect on-prem (or another cloud) to a VPC:

| Product | Bandwidth | SLA | Use when |
|---|---|---|---|
| **Cloud VPN** (Classic / HA) | Up to ~3 Gbps per tunnel | 99.9% (Classic) / 99.99% (HA) | Quick to provision, traffic over the public internet, encrypted with IPsec |
| **Dedicated Interconnect** | 10 / 100 Gbps per circuit | 99.9% / 99.99% with redundancy | High bandwidth, private physical fiber to a Google PoP, requires colocation |
| **Partner Interconnect** | 50 Mbps – 50 Gbps | 99.9% / 99.99% with redundancy | Connection through a service provider, no colocation required |
| **Cross-Cloud Interconnect** | 10 / 100 Gbps | 99.9% / 99.99% | Direct private link to AWS / Azure / Oracle Cloud / Alibaba |

**HA VPN** is the modern variant — two tunnels for active/active redundancy and the higher SLA. Go with HA VPN unless told otherwise.

For routing across these links you typically use **Cloud Router** with BGP, which dynamically learns and announces routes.

### 2.5 Firewall — Cloud NGFW

Google's firewall product was renamed to **Cloud Next Generation Firewall (Cloud NGFW)**. The exam guide lists it explicitly. Two layers:

- **VPC firewall rules** (the classic) — ingress/egress at the VPC level, attached to a single VPC.
- **Firewall policies** — hierarchical: at the **organization**, **folder**, or **regional** level. They enforce rules above the VPC, in priority order, before VPC rules apply.

A rule has:

- **Direction** — `INGRESS` or `EGRESS`. Default policy: deny ingress from anywhere, allow egress to anywhere.
- **Action** — `ALLOW`, `DENY`, or (NGFW) `GOTO_NEXT` to chain policies.
- **Source / destination** — CIDRs, secure tags, service accounts.
- **Targets** — which instances the rule applies to; usually by tag or service account.
- **Protocol & ports** — `tcp:80,443`, `udp:53`, `icmp`, `all`, etc.
- **Priority** — lower number = higher priority. Range 0–65535. Two implicit rules (allow egress, deny ingress) sit at priority 65535.

#### Tags vs. secure tags vs. service accounts

Three ways to identify "which VMs this rule applies to":

| Identifier | Scope | Notes |
|---|---|---|
| **Network tags** (legacy) | Per-VM, free-form strings | Simple but not access-controlled — anyone with edit on the VM can self-assign |
| **Secure tags** (Resource Manager tags) | Org/folder/project/resource scoped, IAM-controlled | The modern choice; you can audit and restrict who applies them |
| **Service accounts** | Identity attached to the VM | Often the cleanest target — you tie firewall rules to identity rather than a string |

The exam guide specifically calls out **secure Tags and service accounts** in firewall rules — Google is steering you away from network tags.

### 2.6 Load balancers

Google's load balancers are a family of products. The exam tests **which one to pick** for a given scenario.

Two big axes:

1. **Where is the LB?** Global vs. regional.
2. **What traffic?** HTTP(S) / TCP / UDP / SSL passthrough / proxy.
3. **External (internet-facing)** or **internal (within VPC)**.

Names you'll see in current docs:

| LB | Layer | Scope | Traffic | Use case |
|---|---|---|---|---|
| **Global external Application Load Balancer** | L7 (HTTP/S) | Global, anycast | HTTPS | Public websites and APIs, multi-region apps |
| **Regional external Application Load Balancer** | L7 | Regional | HTTPS | App in a single region, public-facing |
| **Internal Application Load Balancer** | L7 | Regional | HTTPS | Microservices inside a VPC |
| **Cross-region internal Application Load Balancer** | L7 | Multi-region | HTTPS | Internal services across regions |
| **Global external Proxy Network Load Balancer** | L4 (TCP/SSL proxy) | Global | TCP / SSL | Non-HTTP TCP traffic to a global frontend |
| **External passthrough Network Load Balancer** | L4 | Regional | TCP / UDP | Preserves client IP, raw L4, e.g. game servers, custom protocols |
| **Internal passthrough Network Load Balancer** | L4 | Regional | TCP / UDP | Internal L4 LB; preserves client IP within the VPC |

A simple decision flow:
- **HTTP/S?** → Application Load Balancer.
- **TCP/UDP and need to preserve client IP?** → Passthrough Network Load Balancer.
- **TCP/SSL but want global anycast and proxy termination?** → Proxy Network Load Balancer.
- **Public or private?** → external vs. internal flavour.
- **Single region or multi-region?** → regional vs. global.

### 2.7 Network Service Tiers

How traffic exits Google's network:

| Tier | Path | Cost | When |
|---|---|---|---|
| **Premium** (default) | Through Google's global private backbone end-to-end, exits as close to the user as possible | Higher | Production user-facing traffic; needed for global LBs |
| **Standard** | Exits Google near the source region and traverses the public internet | Lower | Cost-sensitive, regional workloads, dev/test |

**Premium tier** is required for global external Application Load Balancers and Cloud CDN; **Standard tier** locks you to regional LBs only.

### 2.8 Cloud DNS, Cloud NAT (briefly)

These also live in section 2.3 territory but are covered in more depth in 3.3:

- **Cloud DNS** — managed authoritative DNS, public or private zones.
- **Cloud NAT** — outbound-only NAT for VMs without external IPs (most private subnets).

## 3. Decision criteria

| Question | Answer |
|---|---|
| Two GCP projects need internal connectivity | **VPC Peering**, or Shared VPC if they're under the same org |
| 10+ teams, central network control | **Shared VPC** |
| On-prem to GCP, fast to set up, < 3 Gbps | **HA VPN** |
| On-prem to GCP, need 10 Gbps+ and physical isolation | **Dedicated Interconnect** |
| On-prem to GCP through an existing telco | **Partner Interconnect** |
| Public website with global users | **Global external Application Load Balancer** + Premium tier |
| TCP gaming traffic preserving client IP | **External passthrough Network LB** |
| Internal microservice fronting | **Internal Application LB** |
| Cost > performance, single region | **Standard tier** |
| Replace network tags with something controllable | **Secure tags** (or service accounts as targets) |

## 4. Console walkthrough

- **VPCs** — *VPC network → VPC networks*. Create a custom-mode VPC, then add subnets per region.
- **Shared VPC** — *VPC network → Shared VPC*. Set up the host project (org-level role required), then attach service projects.
- **VPC Peering** — *VPC network → VPC network peering → Create peering connection*. Both sides must create matching peerings.
- **Firewall rules** — *VPC network → Firewall*. Filter by direction; create with priority, target tags / service accounts / secure tags.
- **Firewall policies** — *VPC network → Firewall policies*. Choose hierarchical (org/folder) or regional.
- **Cloud VPN** — *Hybrid connectivity → VPN → Create VPN connection*. Choose Classic or HA, attach to a Cloud Router.
- **Cloud Interconnect** — *Hybrid connectivity → Interconnect*. Order a connection (Dedicated) or attach to a partner (Partner).
- **Load balancers** — *Network services → Load balancing → Create load balancer*. The wizard asks layer (HTTP/TCP/UDP), facing (internet/internal), region/global.
- **Network Service Tiers** — set per-resource (per-VM IP, per-LB) or as a project default under *Network services → Network Tiers*.

## 5. gcloud reference

```bash
# ── VPC & subnets ──
gcloud compute networks create prod-vpc --subnet-mode=custom
gcloud compute networks subnets create prod-eu \
    --network=prod-vpc --region=europe-west3 --range=10.10.0.0/20
gcloud compute networks subnets expand-ip-range prod-eu --region=europe-west3 --prefix-length=18

# ── Shared VPC ──
gcloud compute shared-vpc enable HOST_PROJECT_ID
gcloud compute shared-vpc associated-projects add SERVICE_PROJECT_ID --host-project=HOST_PROJECT_ID

# ── VPC Peering ──
gcloud compute networks peerings create prod-to-data \
    --network=prod-vpc --peer-network=data-vpc --peer-project=other-project

# ── Firewall rules ──
gcloud compute firewall-rules create allow-http \
    --network=prod-vpc --direction=INGRESS --action=ALLOW \
    --rules=tcp:80,tcp:443 --source-ranges=0.0.0.0/0 --target-tags=http-server

gcloud compute firewall-rules create allow-internal \
    --network=prod-vpc --direction=INGRESS --action=ALLOW \
    --rules=all --source-ranges=10.10.0.0/16

# Service-account-targeted rule (no tags)
gcloud compute firewall-rules create allow-from-app \
    --network=prod-vpc --direction=INGRESS --action=ALLOW \
    --rules=tcp:8080 \
    --source-service-accounts=app-sa@PROJECT.iam.gserviceaccount.com \
    --target-service-accounts=db-sa@PROJECT.iam.gserviceaccount.com

# ── HA VPN (skeleton) ──
gcloud compute routers create prod-router --network=prod-vpc --region=europe-west3 --asn=65001
gcloud compute vpn-gateways create prod-vpn --network=prod-vpc --region=europe-west3
# (peer gateway, tunnels, BGP sessions follow)

# ── Cloud Router ──
gcloud compute routers add-bgp-peer prod-router --region=europe-west3 \
    --peer-name=onprem --peer-asn=65010 --peer-ip-address=169.254.0.2 --interface=if-0

# ── Load balancer (global external Application LB, simplified) ──
gcloud compute health-checks create http web-hc --port=80
gcloud compute backend-services create web-bs --global --protocol=HTTP --health-checks=web-hc
gcloud compute backend-services add-backend web-bs --global \
    --instance-group=web-mig --instance-group-region=europe-west3
gcloud compute url-maps create web-url --default-service=web-bs
gcloud compute target-http-proxies create web-proxy --url-map=web-url
gcloud compute forwarding-rules create web-fr --global \
    --target-http-proxy=web-proxy --ports=80

# ── Network Service Tier ──
gcloud compute project-info update --default-network-tier=PREMIUM
```

## 6. Exam gotchas

- **VPCs are global, subnets are regional.** This is the #1 GCP networking fact. Many questions hinge on it.
- **Auto-mode VPCs are convenient but discouraged.** If a question says "production", assume custom mode.
- **VPC Peering is non-transitive.** A↔B and B↔C does **not** give A↔C — that's a frequent trap.
- **Overlapping CIDRs break peering.** Plan IP space upfront.
- **Default firewall behaviour is allow-egress, deny-ingress.** Many failure scenarios are "we forgot to add an ingress allow".
- **Network tags vs. secure tags vs. service accounts** — the modern guidance is *secure tags or service accounts* as firewall targets. Network tags are still on the exam but the *recommended* answer leans modern.
- **Premium tier is required** for global external Application LBs and Cloud CDN.
- **HA VPN gives 99.99% SLA**; Classic VPN gives 99.9%. If a scenario insists on the higher SLA, that's HA VPN.
- **Interconnect requires colocation** (Dedicated) or a partner (Partner). It is **not** something you set up in a day; the exam will test that.
- **Cross-region internal LB** exists only at L7 (Application LB). Internal passthrough Network LB is regional only.
- **Shared VPC roles** — Compute Shared VPC Admin must be granted at the **org** (or folder) level, not the host project, for the initial setup.
- **Cloud Router uses BGP** to dynamically advertise routes between your VPC and on-prem; without it you'd need static custom routes.

## 6.5 Named scenarios

These are the named "Practical Scenario" stories from the Udemy curriculum. Each is the canonical recognizable shape — when you see a question that fits, the answer should snap into place.

### Scenario A — Identity-Based Defense

**Story.** A retail company is moving from a flat VPC where every VM had a network tag like `db-client` and the firewall allowed `tcp:5432` from anything tagged `db-client` → anything tagged `db-server`. A red-team review found that any developer with `compute.instances.setTags` could add `db-client` to their dev VM and reach prod databases. Security wants the rule to enforce **identity**, not a self-assignable string.

**Design.**
- Create two service accounts: `app-sa@…` (attached to app VMs) and `db-sa@…` (attached to DB VMs).
- Rewrite the firewall rule to target by service account, not tag:
  ```bash
  gcloud compute firewall-rules create allow-app-to-db \
      --network=prod-vpc --direction=INGRESS --action=ALLOW \
      --rules=tcp:5432 \
      --source-service-accounts=app-sa@PROJECT.iam.gserviceaccount.com \
      --target-service-accounts=db-sa@PROJECT.iam.gserviceaccount.com
  ```
- Lock down `iam.serviceAccounts.actAs` on `app-sa` so only the app team can attach it to a VM. Without `actAs`, a developer cannot create or modify a VM to *be* `app-sa`, so they cannot impersonate their way into the firewall rule.
- Optional: replace any remaining tag-based rules with **secure tags** (Resource Manager tags), which are IAM-controlled at create/attach time.

**Why it works.** Network tags are free-form strings; secure tags and service accounts are IAM-bound. The firewall now matches *who* the VM is, not *what label* it wears, so rule authority lives with IAM admins instead of any VM editor.

**Recognize it.** Words like "self-assigned tag", "identity-based", "least privilege at the network layer", or "compliance audit said tags aren't access-controlled" → this scenario. Answer is **secure tags** or **service-account-targeted firewall rules**, never network tags.

### Scenario B — Centralized Network Management

**Story.** An enterprise has 15 application teams. Each team wants its own GCP project for IAM isolation, billing, and quota — but the network team must own all VPCs, subnets, firewall policies, and the on-prem Interconnect connection. Teams should be able to deploy VMs and GKE clusters into shared subnets without being able to alter routes, peerings, or firewall rules.

**Design.**
- Create a **host project** (`netcorp-shared-host`) that owns the VPC, subnets, Cloud Router, Interconnect attachments, and hierarchical firewall policies.
- Enable Shared VPC: `gcloud compute shared-vpc enable netcorp-shared-host`.
- For each application team, create a **service project** (`team-payments`, `team-orders`, …) and attach it: `gcloud compute shared-vpc associated-projects add team-payments --host-project=netcorp-shared-host`.
- Grant the network team **Compute Shared VPC Admin** at the **organization** (or folder) level — not at the host project, since it's an org-level role.
- Grant each team **Compute Network User** on the specific subnet(s) they're allowed to use (per-subnet IAM, not whole-VPC).
- Apply a **hierarchical firewall policy** at the folder level for guardrails (e.g., always-deny egress to known-bad CIDRs, always-allow IAP SSH).

**Why it works.** Service projects' VMs/GKE pods get IPs from the host project's subnets, so all traffic is governed by the host's VPC, routes, and firewall policies. Application teams keep project-level IAM and quota independence; network team keeps centralized control of the wire.

**Recognize it.** "Central security/network team owns the network", "many application teams in their own projects", "single place to manage firewall policies and Interconnect" → **Shared VPC**, with hierarchical firewall policies for org-wide guardrails.

### Scenario C — Going Global

**Story.** A media startup launches a video-on-demand site. Users are in North America, Europe, and South-East Asia. They want one DNS name (`watch.example.com`), HTTPS termination, content cached at the edge, and DDoS protection. Latency targets: <100 ms TTFB worldwide. Cost is secondary to user experience.

**Design.**
- **Frontend.** Reserve a **global** static external IP on **Premium tier** (`gcloud compute addresses create vod-ip --global --network-tier=PREMIUM`). Premium tier is required for global anycast and is the only tier compatible with global LBs and Cloud CDN.
- **Load balancer.** **Global external Application Load Balancer** with a Google-managed SSL certificate (auto-renewing) for `watch.example.com`. Anycast: a single IP, served from the Google PoP nearest each user.
- **Backends.** Regional MIGs in `us-central1`, `europe-west3`, and `asia-southeast1`, each running the video-origin service. The LB picks the closest healthy backend by latency.
- **Cloud CDN.** Enable on the backend service so HLS chunks and posters are cached at Google's ~180 edge PoPs. Set cache-control headers on origin responses; CDN respects them.
- **Cloud Armor.** Attach a security policy to the backend service with rate limiting, geo-blocking (if needed), and the OWASP Top-10 preconfigured rules.
- **DNS.** Point `watch.example.com` (A record) at the LB's static IP via Cloud DNS.

**Why it works.** Premium tier puts traffic onto Google's private backbone end-to-end, so a user in Singapore reaches the closest Google PoP within milliseconds; the LB then proxies to the closest healthy backend (or serves from CDN). One IP, one cert, one config — multi-region high availability for free if any region fails.

**Recognize it.** "Global users", "single IP / single domain", "low latency worldwide", "CDN", "DDoS / WAF" → **Global external Application LB + Premium tier + Cloud CDN + Cloud Armor**. If the question says Standard tier, that's a trap — Standard tier locks you out of global LBs.

## 7. Practice scenarios

### Q1 — Cross-project private connectivity
Project A and project B (same org) need their internal IPs to talk privately. What's the simplest mechanism?

A. **VPC Network Peering.**
B. Shared VPC.
C. Cloud VPN between the two VPCs.
D. Cloud Interconnect.

**Answer: A.** VPC Peering is the lightweight, cheap, non-transitive connection between two VPCs. B is heavier and centralizes networking under a host project (good if you have many service projects). C/D are for hybrid (GCP↔on-prem), not GCP↔GCP.

### Q2 — Hybrid connectivity SLA
A company needs an on-prem ↔ GCP link with 99.99% SLA, ~1 Gbps bandwidth, encryption, no colocation. What's the right product?

A. Classic Cloud VPN with two tunnels.
B. **HA VPN.**
C. Dedicated Interconnect.
D. Partner Interconnect.

**Answer: B.** HA VPN gives 99.99% SLA over the internet with IPsec encryption — no colocation required. Classic VPN (A) is 99.9%. C requires colocation. D is bandwidth-flexible but doesn't necessarily need encryption.

### Q3 — Firewall target choice
A security review says "the firewall rule that allows database traffic targets VMs by network tag, but anyone with edit on the VM can self-assign that tag." What's the recommended remediation?

A. Move all targeted VMs to a separate VPC.
B. Use **secure tags** or a **service account** as the firewall target.
C. Add the rule at higher priority.
D. Switch from ingress to egress.

**Answer: B.** Secure tags are IAM-controlled (resource-manager scoped); service accounts are also IAM-bound. Both prevent unauthorized self-tagging. The exam guide explicitly steers toward this.

### Q4 — Load balancer choice
You need a public, global, HTTPS-terminating load balancer for a multi-region web app, with Cloud CDN. Which LB and tier?

A. Regional external Application LB on Standard tier.
B. **Global external Application LB on Premium tier.**
C. External passthrough Network LB on Premium tier.
D. Internal Application LB.

**Answer: B.** Global external Application LB is the L7 product for public web apps and is required by Cloud CDN. Premium tier is required for global LBs. A is regional only. C is L4 passthrough, no HTTP/CDN. D is internal.

### Q5 — Non-transitive peering trap
VPCs A↔B are peered, B↔C are peered. A team in VPC A reports they can't reach a VM in VPC C. Why?

A. Wrong CIDRs.
B. **VPC Peering is non-transitive — A doesn't see C's networks via B.**
C. Firewall rules in B are blocking.
D. The peering is broken.

**Answer: B.** Peering does not propagate routes through intermediates. To reach C from A, peer A↔C directly, or use a hub-and-spoke topology with a VPN/router VM as the hub.

## 8. Hands-on labs

### Lab 1 — Create a custom VPC with subnets in two regions
**Goal:** build a `prod-vpc` with subnets in `europe-west3` and `us-central1`, and confirm cross-region internal connectivity.

**Console:**
1. *Navigation menu → VPC network → VPC networks → Create VPC network*.
2. **Name:** `prod-vpc`. **Subnet creation mode:** *Custom*.
3. Add **Subnet 1**: name `prod-eu`, region `europe-west3`, IP range `10.10.0.0/20`. Click **Done**.
4. Click **Add subnet** → **Subnet 2**: name `prod-us`, region `us-central1`, IP range `10.20.0.0/20`. **Done**.
5. **Dynamic routing mode:** *Global* (so routes propagate across regions). *Create*.
6. *Compute Engine → VM instances → Create instance*. Name `vm-eu`, region `europe-west3-a`, network `prod-vpc`, subnet `prod-eu`. *Create*.
7. Repeat for `vm-us` in `us-central1-a`, network `prod-vpc`, subnet `prod-us`.
8. SSH into `vm-eu` and run `ping -c 3 <internal-ip-of-vm-us>`. Expect replies (after firewall lab below).

**gcloud:**
```bash
gcloud compute networks create prod-vpc --subnet-mode=custom --bgp-routing-mode=global
gcloud compute networks subnets create prod-eu --network=prod-vpc --region=europe-west3 --range=10.10.0.0/20
gcloud compute networks subnets create prod-us --network=prod-vpc --region=us-central1 --range=10.20.0.0/20
```

### Lab 2 — Firewall rule using a service account as target
**Goal:** allow SSH only from IAP and HTTP only to VMs whose service account is `web-sa`. No legacy network tags.

**Console:**
1. *IAM & Admin → Service Accounts → Create service account*. Name `web-sa`. Skip role grants. *Done*. (Used purely as a firewall identity.)
2. *VPC network → Firewall → Create firewall rule*.
3. **Name:** `prod-allow-iap-ssh`. **Network:** `prod-vpc`. **Direction:** *Ingress*. **Action:** *Allow*.
4. **Targets:** *All instances in the network*. **Source IP ranges:** `35.235.240.0/20` (IAP range). **Protocols and ports:** `tcp:22`. *Create*.
5. **Create firewall rule** again. **Name:** `prod-allow-http-to-web-sa`. **Network:** `prod-vpc`.
6. **Targets:** *Specified service account*. **Service account scope:** *In this project*. **Target service account:** `web-sa@${PROJECT}.iam.gserviceaccount.com`. **Source IP:** `0.0.0.0/0`. **Ports:** `tcp:80`. *Create*.
7. Edit a VM (`vm-eu`) → *Identity and API access* → set service account to `web-sa`. Save & restart. The rule now applies only to that VM.

**gcloud:**
```bash
gcloud iam service-accounts create web-sa
gcloud compute firewall-rules create prod-allow-iap-ssh \
    --network=prod-vpc --direction=INGRESS --action=ALLOW \
    --rules=tcp:22 --source-ranges=35.235.240.0/20
gcloud compute firewall-rules create prod-allow-http-to-web-sa \
    --network=prod-vpc --direction=INGRESS --action=ALLOW \
    --rules=tcp:80 --source-ranges=0.0.0.0/0 \
    --target-service-accounts=web-sa@$DEVSHELL_PROJECT_ID.iam.gserviceaccount.com
```

### Lab 3 — VPC Peering between two VPCs
**Goal:** peer `prod-vpc` with a new `data-vpc` so their internal IPs reach each other.

**Console:**
1. *VPC network → VPC networks → Create*. Name `data-vpc`, custom mode, one subnet `data-eu` `10.30.0.0/20` in `europe-west3`. *Create*.
2. *VPC network → VPC network peering → Create peering connection*.
3. **Name:** `prod-to-data`. **Your VPC network:** `prod-vpc`. **Peered VPC network:** *In project* → same project → `data-vpc`. *Create*.
4. *Create peering connection* again, this time reverse: **Name:** `data-to-prod`, **Your VPC:** `data-vpc`, **Peered VPC:** `prod-vpc`. Both sides must exist.
5. Confirm both rows show **Active** with green check.
6. Create a VM in `data-vpc/data-eu` and ping it from `vm-eu` in `prod-vpc/prod-eu` (after adding an internal-allow firewall rule on both sides).

```bash
gcloud compute networks peerings create data-to-prod --network=data-vpc --peer-network=prod-vpc
gcloud compute firewall-rules create prod-allow-internal --network=prod-vpc \

gcloud compute firewall-rules create data-allow-internal --network=data-vpc \

```

### Lab 4 — Egress firewall rule (deny outbound to a CIDR)
**Goal:** add an explicit egress *deny* rule that prevents `vm-eu` (tagged `restricted`) from reaching `203.0.113.0/24`. Default egress is allow-all, so deny is the operational lever.

**Console:**
1. *VPC network → Firewall → Create firewall rule*.
2. **Name:** `prod-deny-egress-203`. **Network:** `prod-vpc`. **Direction:** *Egress*. **Action:** *Deny*. **Priority:** `900` (beats the default allow-all egress at 65535).
3. **Targets:** *Specified target tags*. **Target tags:** `restricted`.
4. **Destination filters → Destination IP ranges:** `203.0.113.0/24`.
5. **Protocols and ports:** *all*. *Create*.
6. *Compute Engine → vm-eu → Edit*. Under **Network tags** add `restricted`. *Save*.
7. SSH `vm-eu` → `curl -m 5 203.0.113.10` blocks; `curl -m 5 8.8.8.8` still works.

**gcloud:**
```bash
gcloud compute firewall-rules create prod-deny-egress-203 \
    --network=prod-vpc --direction=EGRESS --action=DENY --priority=900 \
    --rules=all --destination-ranges=203.0.113.0/24 \
    --target-tags=restricted

gcloud compute instances add-tags vm-eu --tags=restricted --zone=europe-west3-a
```

### Lab 5 — Global external Application Load Balancer fronting a MIG
**Goal:** stand up a public global HTTPS LB that routes `/` to a regional MIG; reserve a static IP for DNS.

**Prerequisites:** the `web-mig` MIG from §2.1 Lab 13 (or any MIG with port 80 exposed) and an `http-server` firewall rule that allows `0.0.0.0/0:80` to those instances.

**Console (reserve static IP):**
1. *VPC network → IP addresses → Reserve external static address*.
2. **Name:** `lb-ip`. **Network Service Tier:** *Premium*. **IP version:** IPv4. **Type:** *Global*. *Reserve*.

**Console (create the LB):**
3. *Network services → Load balancing → Create load balancer*.
4. **Type:** *Application Load Balancer (HTTP/S)*. **Public facing or internal:** *Public facing*. **Global or Regional:** *Best for global workloads* (= Global external Application LB). *Configure*.
5. **Name:** `web-lb`.
6. **Frontend configuration → Add frontend IP and port**:
   - **Name:** `https-frontend`. **Protocol:** HTTPS. **Port:** 443. **IP version:** IPv4. **IP address:** `lb-ip`.
   - **Certificate:** *Create new* → **Google-managed**. Add a domain you control (or skip this and use HTTP for the lab — switch protocol to HTTP and Port 80).
7. **Backend configuration → Create a backend service**:
   - **Name:** `web-bs`. **Backend type:** *Instance group*. **Protocol:** HTTP. **Port:** 80.
   - **Backends → Add a backend** — instance group `web-mig`, **Port numbers:** `80`, **Balancing mode:** *Utilization*, **Maximum backend utilization:** `80%`.
   - **Health check:** *Create* → **Name:** `web-lb-hc`, port `80`, request path `/`. *Save*.
   - (Optional) Enable **Cloud CDN** on the backend service.
8. **Routing rules → Host and path rules** — leave default *Match all* → `web-bs`.
9. *Create*. Wait ~3–5 min for the LB IP to become reachable.
10. Browse to `http://<lb-ip>/` (or the HTTPS URL) — load reaches one of the MIG VMs round-robin.

**gcloud (HTTP variant for brevity):**
```bash
gcloud compute addresses create lb-ip --global --network-tier=PREMIUM
gcloud compute health-checks create http web-lb-hc --port=80 --request-path=/
gcloud compute backend-services create web-bs --global --protocol=HTTP \
    --health-checks=web-lb-hc --enable-cdn
gcloud compute backend-services add-backend web-bs --global \
    --instance-group=web-mig --instance-group-region=europe-west3 \
    --balancing-mode=UTILIZATION --max-utilization=0.8

gcloud compute url-maps create web-url --default-service=web-bs
gcloud compute target-http-proxies create web-proxy --url-map=web-url
gcloud compute forwarding-rules create web-fr --global \
    --address=lb-ip --target-http-proxy=web-proxy --ports=80

curl http://$(gcloud compute addresses describe lb-ip --global --format='value(address)')
```

**Cleanup:**
```bash
gcloud compute forwarding-rules delete web-fr --global --quiet
gcloud compute target-http-proxies delete web-proxy --quiet
gcloud compute url-maps delete web-url --quiet
gcloud compute backend-services delete web-bs --global --quiet
gcloud compute health-checks delete web-lb-hc --quiet
gcloud compute addresses delete lb-ip --global --quiet
```
