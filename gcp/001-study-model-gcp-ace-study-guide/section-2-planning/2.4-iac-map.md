# 2.4 -- Visual Map: Infrastructure as Code

---

## 1. The IaC Idea

```
  ┌──────────────────────────────────────────────────────────────────────┐
  │                    WHY INFRASTRUCTURE AS CODE?                       │
  ├──────────────────────────────────────────────────────────────────────┤
  │  - Declarative: state your desired infra, tool figures out how       │
  │  - Versioned in Git: review, blame, rollback                         │
  │  - Reproducible: dev / staging / prod from the same modules          │
  │  - Auditable: every change goes through PR + plan + apply            │
  │  - Drift detection: tool compares state vs. reality                  │
  └──────────────────────────────────────────────────────────────────────┘
```

### State Management

```
                              ┌── LOCAL STATE  (avoid)
                              │     - file on your laptop, no team sharing
        Terraform State ──────┤
                              ├── REMOTE STATE in GCS bucket  (CORRECT)
                              │     - VERSIONING enabled on the bucket
                              │     - State locking via the GCS object
                              │     - One bucket per env (or workspace)
                              │
                              └── State commands (surgical, sparing)
                                    import / mv / rm / show
```

```
  WHY remote + locking?
  ─────────────────────
  Two engineers running `terraform apply` on the same state simultaneously
  is the classic infra disaster: races, partial writes, corrupted state.
  GCS backend with locking + versioning prevents this AND lets you roll
  back to an earlier state revision if you nuke production.
```

### Versioning Discipline

```
  ┌──────────────────────────────────────────────────────────────────────┐
  │  PIN provider versions in `required_providers`                       │
  │  COMMIT the .terraform.lock.hcl                                      │
  │  USE modules with versioned releases (Git tag or Registry version)   │
  │  PROMOTE the same module across envs by changing INPUTS, not code    │
  └──────────────────────────────────────────────────────────────────────┘
```

## 4. Fabric FAST -- the Stage Map

```
                              ┌── 0. bootstrap   (org IAM, billing, seed)
                              │
                              ├── 1. resman      (folder + project factory)
                              │
        Fabric FAST stages ───┤── 2. networking  (Shared VPC, hybrid)
                              │
                              ├── 3. security    (org policies, KMS, VPC-SC)
                              │
                              └── 4. data platform / project factory
                                    extensible for product teams
```

```
  Use Fabric FAST when you're standing up a NEW GCP org and want
  Google's opinionated layout (folder hierarchy, IAM, network) without
  writing it from scratch. It IS Terraform underneath.
```

## 5. Config Connector & Helm

```
                            ┌── Config Connector
                            │     - GCP CRDs in your GKE cluster
                            │     - Reconciliation loop applies desired state
                            │     - For shops where K8s is the control plane
                            │
   Other GCP-related ───────┤
                            └── Helm
                                  - K8s package manager
                                  - For deploying APPLICATIONS to K8s
                                  - Not for provisioning GCP resources
```

## 6. IaC Workflow (CI/CD)

```
  ┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐   ┌──────────┐
  │  Code   │ ─►│  Pull   │ ─►│  Plan   │ ─►│  Apply  │ ─►│  Drift   │
  │  module │   │ Request │   │ in CI   │   │ via SA  │   │  check   │
  └─────────┘   └─────────┘   └────┬────┘   └────┬────┘   └────┬─────┘
                                   │             │             │
                                   ▼             ▼             ▼
                              Reviewer        Promote      Schedule
                              sees plan        across       periodic
                              diff             envs         plan-only
```

### Promotion across environments

```
                           ┌── dev      (vars-dev.tfvars)
                           │
        Module             ├── staging  (vars-staging.tfvars)
        (one source) ──────┤
                           │
                           └── prod     (vars-prod.tfvars)

  Same code, different inputs / workspaces / state files.
  Avoid copy-pasting whole stacks per environment.
```

## 7. Section 2.4 Cheat Sheet

```
  ┌──────────────────────────────────────────────────────────────────────────────┐
  │  2.4 QUICK REFERENCE                                                         │
  ├──────────────────────────────────────────────────────────────────────────────┤
  │  TERRAFORM      Default IaC tool for GCP and beyond                          │
  │  STATE          REMOTE in GCS bucket; versioning + locking ON                │
  │  PROVIDER       Pin versions; commit .terraform.lock.hcl                     │
  │  WORKFLOW       init / plan / apply / destroy                                │
  │  PROMOTION      Same modules, different vars/workspace per env               │
  │  DRIFT          Re-run plan periodically; never edit infra in console        │
  │  FABRIC FAST    Google-opinionated GCP org bootstrap (Terraform under hood)  │
  │  CONFIG CONN.   Manage GCP via K8s CRDs in GKE                               │
  │  HELM           K8s app packaging, NOT infra                                 │
  │  CI ROLE        Apply via dedicated service account, never user creds        │
  │  STATE COMMANDS import / mv / rm — surgical, document why you used them      │
  └──────────────────────────────────────────────────────────────────────────────┘
```
