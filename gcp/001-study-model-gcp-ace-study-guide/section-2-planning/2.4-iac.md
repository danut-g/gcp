# 2.4 — Planning and implementing resources through infrastructure as code

> **Exam guide reference:** Section 2.4. Sub-topics: IaC tooling (Fabric FAST, Config Connector, Terraform, Helm), planning and executing IaC deployments — versioning, state management, updates.

---

## 1. Why this matters for the exam

The exam doesn't expect you to write Terraform from scratch, but it does expect you to know:

- **What IaC is for** — repeatable, versioned, reviewable provisioning, instead of clicking in the console.
- **The four tools** Google calls out: **Terraform**, **Fabric FAST**, **Config Connector**, **Helm**.
- **State management** — what state is, why it's sensitive, where to keep it.
- **The workflow** — plan → apply → modules → versioning.

Expect questions that compare approaches ("we want IaC for our Kubernetes clusters" — Terraform vs. Config Connector vs. Helm) and questions about state management mistakes ("our team keeps overwriting each other's changes" — remote state with locking).

---

## 2. Core concepts

### 2.1 What infrastructure as code means on Google Cloud

Instead of clicking in the console, you write declarative files (HCL, YAML, Kubernetes manifests) that describe the desired state, commit them to git, and run a tool that reconciles real cloud resources against the spec.

Benefits the exam likes to see: **versioning**, **peer review via PRs**, **repeatability across environments**, **disaster recovery from code**, **drift detection**.

### 2.2 Terraform

The de-facto standard. Cross-cloud, declarative HCL syntax.

- **Providers** — the `google` and `google-beta` providers cover almost every GCP service.
- **State file** — Terraform's source of truth about what it manages. Sensitive (contains resource IDs and sometimes secrets).
- **Modules** — reusable units of HCL. The exam may mention modules from the Cloud Foundation Toolkit (CFT).
- **Workflow** — `terraform init` → `terraform plan` → `terraform apply` → `terraform destroy`.

#### State management
- **Local state** — file on disk. Fine for solo experimentation, **dangerous** for teams.
- **Remote state** — kept in a Cloud Storage bucket with versioning enabled. The recommended pattern.
- **Locking** — Terraform locks the state during `apply` so two teammates can't run apply simultaneously. With the GCS backend, locking is built in via object metadata.
- **Backups** — turning on bucket versioning gives you state-file history automatically.

A typical `backend` block:

```hcl
terraform {
  backend "gcs" {
    bucket = "tf-state-myorg"
    prefix = "prod/network"
  }
}
```

#### Versioning and updates
- Pin provider versions (`required_providers`) so a sudden upstream release doesn't break you.
- Use modules with a version constraint, ideally referenced from a registry or a tagged git ref.
- For environments, the common pattern is one root module per environment, calling shared child modules (so dev and prod look the same except for variables).

### 2.3 Fabric FAST

A **Google-published, opinionated Terraform reference** for end-to-end org bootstrapping. Stands for **Fabric Foundation for Accelerated Setup with Terraform**.

- It's a set of stages: bootstrap (org policies, billing), resource hierarchy, networking, security, multi-tenant projects, etc.
- The point: take it as a starting blueprint instead of building org foundations from scratch.
- For the exam, recognize the name and that it's *Terraform-based, opinionated, and Google-blessed*.

### 2.4 Config Connector

Lets you **manage Google Cloud resources from inside a Kubernetes cluster** using Kubernetes manifests.

- You install Config Connector as a controller in GKE (often via the GKE add-on).
- You then write `kind: ContainerCluster` or `kind: PubSubTopic` YAML resources, apply them with `kubectl`, and the controller talks to the GCP API to create them.
- Use case: when a team is already managing everything via Kubernetes manifests + GitOps (e.g. with **Config Sync** or Argo CD), it's natural to manage cloud resources the same way.
- The exam wants you to recognize this as the answer for "we want IaC, but our team lives in `kubectl`".

### 2.5 Helm

A **package manager for Kubernetes**. Not really IaC for Google Cloud resources — it's IaC for **Kubernetes workloads**.

- A **chart** is a templated bundle of Kubernetes manifests with values you can override.
- Use it to install third-party software (NGINX, Prometheus, …) or to template your own Kubernetes deployments across environments.
- On the exam, "Helm" is the right answer when the question is "deploy this app to GKE consistently across dev/staging/prod" or "install Prometheus on our GKE cluster".

### 2.6 The four tools side by side

| Tool | What it provisions | Where it runs | Sweet spot |
|---|---|---|---|
| **Terraform** | GCP resources (and almost anything else) | CLI, CI/CD | General IaC across the cloud |
| **Fabric FAST** | GCP foundations (org, IAM, networks, security) | Terraform under the hood | Bootstrapping a new org |
| **Config Connector** | GCP resources, but written as K8s manifests | GKE cluster | GitOps teams already on Kubernetes |
| **Helm** | Kubernetes workloads | A K8s cluster | Packaging and templating apps on K8s |

### 2.7 The IaC workflow

A healthy IaC pipeline:

1. **Source control** — code in git, branch per change.
2. **Code review** — PR with `terraform plan` output attached.
3. **CI** — runs `fmt`, `validate`, `plan` on PRs.
4. **CD** — runs `apply` on merge to main, often via Cloud Build / Jenkins / GitHub Actions.
5. **Drift detection** — periodic `plan` to catch manual console changes.
6. **State** — remote, versioned, encrypted, locked.

The **same code, different variables** pattern: one module, one set of variables per environment.

## 3. Decision criteria

| Question | Answer |
|---|---|
| Brand new GCP organization, want a Google-blessed starting point | **Fabric FAST** |
| General-purpose IaC for any GCP resource | **Terraform** |
| Manage GCP resources from a Kubernetes cluster (GitOps) | **Config Connector** |
| Package and deploy a Kubernetes application | **Helm** |
| Multiple engineers running Terraform | **Remote state in GCS** with versioning + locking |
| Worried about secrets in state | Use Cloud Storage with CMEK + IAM-restricted access |
| Promotion across dev/staging/prod | **One module, multiple variable sets** (or workspaces) |
| Manual changes are sneaking in | Add **drift detection** to CI (`terraform plan -detailed-exitcode`) |

## 4. Console walkthrough

There isn't a single "IaC" page in the console; the relevant places are:

- **Cloud Build** — *Cloud Build → Triggers / History*. Common host for `terraform plan`/`apply` pipelines.
- **Artifact Registry** — *Artifact Registry → Repositories*. Stores Helm charts (Helm OCI repos) and container images.
- **Cloud Storage bucket for state** — *Cloud Storage → Buckets*. Create the bucket with **uniform access**, **versioning on**, and locked-down IAM.
- **Config Connector add-on** — *Kubernetes Engine → Clusters → (your cluster) → Edit → Config Connector*.
- **Anthos Config Management / Config Sync** — *Anthos → Config*. Used together with Config Connector for GitOps.
- **Resource Manager** — useful to inspect what Terraform actually built in the hierarchy.

## 5. CLI / tool reference

Not strictly `gcloud` — the relevant CLIs are `terraform`, `kubectl`, `helm`.

```bash
# ── Terraform ──
terraform init                    # downloads providers, configures backend
terraform fmt                     # standard formatting
terraform validate                # syntax + provider checks
terraform plan -out plan.tfplan   # preview changes
terraform apply plan.tfplan       # execute the plan
terraform destroy                 # tear down

# Workspaces (lightweight env separation, sharing one backend)
terraform workspace new prod
terraform workspace select dev

# State commands (for surgical fixes — use sparingly)
terraform state list
terraform state show google_compute_instance.web
terraform state mv ...
terraform import google_compute_instance.web projects/PROJECT/zones/ZONE/instances/web

# ── Helm ──
helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update
helm install web bitnami/nginx --namespace web --create-namespace
helm upgrade web bitnami/nginx -f values.yaml
helm uninstall web --namespace web
helm list --all-namespaces

# ── Config Connector (after enabling on the cluster) ──
kubectl apply -f - <<'EOF'
apiVersion: pubsub.cnrm.cloud.google.com/v1beta1
kind: PubSubTopic
metadata:
  name: orders
  namespace: prod
EOF

kubectl get pubsubtopics -A

# ── Fabric FAST (just Terraform under the hood) ──
git clone https://github.com/GoogleCloudPlatform/cloud-foundation-fabric.git
cd cloud-foundation-fabric/fast/stages/0-bootstrap
terraform init && terraform plan
```

A handy `gcloud` snippet for setting up a state bucket:

```bash
gcloud storage buckets create gs://tf-state-myorg \
    --location=eu --uniform-bucket-level-access
gcloud storage buckets update gs://tf-state-myorg --versioning
```

## 6. Exam gotchas

- **Local Terraform state is dangerous.** "Two engineers ran apply at the same time" → remote state in GCS with locking is the answer.
- **Versioning the bucket** is the simple way to get state backups; don't write a custom backup script.
- **Terraform state can contain secrets.** Restrict IAM on the bucket to the CI service account; do not give human users blanket read.
- **Config Connector is for GCP resources from K8s, not for K8s workloads.** Don't confuse it with Helm.
- **Helm doesn't manage GCP resources.** If a question is "deploy a Cloud SQL instance with Helm", that's wrong (Config Connector or Terraform are correct).
- **Fabric FAST is opinionated.** It's a *foundation*, not a generic library. Pick it when bootstrapping; for ad-hoc resources, plain Terraform.
- **`terraform plan` doesn't change anything.** It's safe to run on a PR. Apply requires explicit approval.
- **Drift** = real cloud differs from state. The fix is typically `import` + remove the manual change, not "force apply".
- **Pin provider versions.** A new `google` provider release breaking your code is a real risk; the exam expects you to know `required_providers`.
- **Workspaces** are for *minor* environmental differences sharing the same code; they are **not** a hard isolation boundary. For real isolation, use separate state files per environment.
- **The GCS backend supports state locking out of the box.** No DynamoDB-style external lock service is needed (that's an AWS thing).

## 6.5 Named scenarios

### Scenario A — Scaling Team Collaboration

**Story.** A growing platform team starts with one engineer running Terraform from a laptop. State lives in `terraform.tfstate` in the repo. Three months later there are five engineers, three environments (dev/staging/prod), and roughly weekly incidents: state-file merge conflicts on PRs, two `apply`s racing and corrupting the deployment, a junior engineer accidentally pushing a state file with a service-account key inside it, and a console-side firewall change that quietly drifted from code. Leadership asks: how do we run Terraform safely as a team?

**Design.**

1. **Move state to a remote, locked, versioned GCS backend.**
   ```bash
   gcloud storage buckets create gs://acme-tfstate \
       --location=eu --uniform-bucket-level-access
   gcloud storage buckets update gs://acme-tfstate --versioning
   ```
   Then add the backend block (per environment, with distinct prefixes):
   ```hcl
   terraform {
     backend "gcs" {
       bucket = "acme-tfstate"
       prefix = "prod/network"   # one prefix per env+stack
     }
   }
   ```
   The GCS backend handles **locking** automatically (no DynamoDB-equivalent needed) — concurrent applies serialize. Versioning gives you state-file history for free; rollback is `gsutil cp` of an older generation.

2. **Restrict who can read state.** Terraform state can contain secrets (DB passwords, SA keys it generated, etc.). Grant **Storage Object Admin** on the bucket only to the CI service account; humans get **Storage Object Viewer** at most, and only those who need it. Encrypt the bucket with **CMEK** if compliance requires.

3. **One root module per environment, calling shared child modules.**
   ```
   envs/
     dev/main.tf      → module "network" { source = "../../modules/network", env = "dev" }
     staging/main.tf  → module "network" { source = "../../modules/network", env = "staging" }
     prod/main.tf     → module "network" { source = "../../modules/network", env = "prod" }
   modules/
     network/
   ```
   Each environment has its own backend prefix → its own state file → blast radius is one env. Workspaces are tempting but considered too lightweight for production isolation.

4. **CI pipeline.** On PR open: `terraform fmt -check`, `terraform validate`, `terraform plan` (post the plan as a PR comment). On merge to main: `terraform apply` for the affected env, gated on a manual approval for prod. The CI service account is the only identity with `roles/owner` (or scoped equivalents) on the target projects.

5. **Pin versions.** In every root: `required_version = ">= 1.6, < 2.0"` and `required_providers { google = { version = "~> 5.0" } }`. Renovate/Dependabot opens PRs for upgrades so they're reviewed, not stealth-applied.

6. **Drift detection.** A nightly Cloud Scheduler job runs `terraform plan -detailed-exitcode` per environment; non-zero exit posts to Slack. The fix is "decide whether the manual change is intended; if yes, port it into code; if no, run apply to restore".

**Why it works.** The locked remote backend kills concurrency bugs; per-env state files isolate blast radius; CI-mediated apply makes the audit trail the merge log; pinned versions make builds reproducible; nightly drift detection turns the "someone clicked in the console" surprise into a daily question instead of a quarterly incident.

**Recognize it.** "Two engineers ran apply at the same time", "we keep overwriting each other's state", "state file accidentally committed", "manual changes are sneaking in", "promote the same code across dev/staging/prod" → **GCS remote backend + per-env root modules + CI-gated apply + drift detection**. Workspaces alone are *not* the right answer for hard environment isolation.

## 7. Practice scenarios

### Q1 — Choosing the IaC tool
A team running everything on GKE wants to manage Cloud SQL instances and Pub/Sub topics declaratively, alongside their Kubernetes manifests, in the same GitOps pipeline. Which tool fits best?

A. Helm.
B. **Config Connector.**
C. Terraform run from a local machine.
D. Cloud Deployment Manager.

**Answer: B.** Config Connector lets you express GCP resources as Kubernetes CRDs, which slots into a GitOps workflow with kubectl/Argo CD/Config Sync. A (Helm) packages K8s workloads, not GCP resources. C is fine but doesn't integrate with GitOps as cleanly. D is deprecated.

### Q2 — Terraform state for a team
Two engineers ran `terraform apply` simultaneously and corrupted the deployment. What's the recommended fix?

A. Add a CI gate that serialises applies.
B. **Use a remote backend (GCS) — locking and versioning come built in.**
C. Run `terraform refresh` after every apply.
D. Switch to `terraform.tfstate.local`.

**Answer: B.** GCS backend supports locking automatically; bucket versioning gives state history. A could help but is fragile and not the recommended primary fix. C doesn't address concurrency. D is the *cause*.

### Q3 — Org bootstrap
Your company is starting a new GCP organization and wants a Google-recommended starting point with Terraform code for org policies, hierarchy, networking, IAM. What do you adopt?

A. Cloud Foundation Toolkit (CFT) modules only.
B. Custom Terraform written from scratch.
C. **Fabric FAST.**
D. Helm charts.

**Answer: C.** Fabric FAST (Foundation for Accelerated Setup with Terraform) is the Google-published opinionated Terraform reference for new org foundations. CFT (A) is a useful library of modules but not an end-to-end blueprint. B duplicates work. D is for K8s.

### Q4 — Promoting an environment
You have one Terraform module describing a service and want to deploy it to dev/staging/prod separately, with isolated state files. What's the cleanest pattern?

A. One root module with `terraform.workspace` switches.
B. **Separate root modules per environment, each with its own backend prefix, calling the same shared module.**
C. Apply the same code three times in the same backend.
D. Helm charts per environment.

**Answer: B.** Workspaces (A) are convenient but considered too lightweight for production-grade isolation; the recommended pattern is per-environment root modules. C collides state between environments. D is irrelevant (Helm is for K8s workloads).

### Q5 — Manual changes
Someone changed a firewall rule via the console and now `terraform plan` shows a diff. What is happening, and what is the right action?

A. Run `terraform apply` immediately to push the change back.
B. Run `terraform refresh` and accept the new state.
C. **Decide whether the manual change is intended; if yes, update the Terraform code; if no, run `apply` to restore the desired state.**
D. Delete the state and re-import.

**Answer: C.** This is "drift". Terraform tells you about it; the correct response depends on intent. Blindly applying (A) erases possibly valid manual changes; B accepts changes silently and loses the source-of-truth property; D is a destructive overreach.

## 8. Hands-on labs

### Lab 1 — Provision a VM with Terraform using a GCS remote backend
**Goal:** create a state bucket, write a minimal Terraform config, and apply it from Cloud Shell.

**Console (state bucket):**
1. *Cloud Storage → Buckets → Create*. **Name:** `${PROJECT}-tfstate`. **Location type:** *Region* / `europe-west3`. **Storage class:** Standard. **Access control:** Uniform.
2. *Protection tools:* check **Enable object versioning**. *Create*.
3. *IAM & Admin → IAM*. Grant the user (or CI service account) **Storage Object Admin** on the bucket only (not project-wide).

**Cloud Shell (Terraform):**
```bash
mkdir tf-demo && cd tf-demo
cat > main.tf <<'EOF'
terraform {
  required_version = ">= 1.6"
  required_providers {
    google = { source = "hashicorp/google", version = "~> 5.0" }
  }
  backend "gcs" {
    bucket = "PROJECT-tfstate"   # replace with your bucket
    prefix = "demo/vm"
  }
}

provider "google" {
  project = "PROJECT"
  region  = "europe-west3"
  zone    = "europe-west3-a"
}

resource "google_compute_instance" "demo" {
  name         = "tf-demo-vm"
  machine_type = "e2-small"
  boot_disk {
    initialize_params { image = "debian-cloud/debian-12" }
  }
  network_interface {
    network = "default"
    access_config {}
  }
}
EOF

# Substitute the project id
sed -i "s/PROJECT/$DEVSHELL_PROJECT_ID/g" main.tf

terraform init        # downloads google provider, configures gcs backend
terraform plan        # shows the create
terraform apply       # type "yes"
```

**Verify:**
1. *Compute Engine → VM instances* — `tf-demo-vm` is green.
2. *Cloud Storage → Buckets → ${PROJECT}-tfstate → demo/vm/* — a `default.tfstate` object exists; the **Versions** tab shows history.

**Cleanup:**
```bash
terraform destroy   # remove the VM
gcloud storage rm -r gs://$DEVSHELL_PROJECT_ID-tfstate
```
