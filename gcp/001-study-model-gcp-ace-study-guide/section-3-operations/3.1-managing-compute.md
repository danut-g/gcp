## 2. Core concepts

### 2.1 Connecting to a Compute Engine instance

Three ways:

| Method | When to use |
|---|---|
| **SSH from the console** (the *SSH* button on the instance row) | Quick access; uses ephemeral browser keys, no local setup |
| **`gcloud compute ssh`** | From your terminal; auto-handles keys, OS Login, IAP |
| **Custom SSH client** (`ssh user@ip`) | Only when you've manually placed keys; rarely the right exam answer |

Two important access patterns:

- **OS Login** — IAM-controlled SSH. Roles: `roles/compute.osLogin` (login) and `roles/compute.osAdminLogin` (sudo). When OS Login is on (project or instance metadata), individual SSH keys are ignored.
- **Identity-Aware Proxy (IAP) for TCP** — SSH to a VM **without an external IP**. The VM has only an internal IP; IAP tunnels SSH (port 22) through Google's identity-aware proxy. The CLI flag is `--tunnel-through-iap`. The role `roles/iap.tunnelResourceAccessor` is required.

### 2.2 Viewing running instances

- *Compute Engine → VM instances* — list with status, zone, machine type, IPs.
- `gcloud compute instances list` — same, scriptable.
- For at-scale visibility, **Cloud Asset Inventory** can answer "every instance in the org".

### 2.3 Snapshots and images

Both are point-in-time captures of a Persistent Disk, but they serve different purposes:

| | Snapshot | Image |
|---|---|---|
| Primary purpose | Backup of a disk | Template for creating new disks/VMs |
| Storage | Cloud Storage, multi-region by default | Cloud Storage, project-scoped |
| Incremental? | Yes — only changed blocks since the previous snapshot | No — full image |
| Can be used as boot template? | Indirectly (create a disk from a snapshot) | Yes, directly when launching a VM |
| Used in instance templates? | Rare | Common |

#### Snapshot schedules
A **snapshot schedule** (a *resource policy*) attached to a disk runs snapshots automatically — daily/weekly/hourly — with a configurable retention. The standard answer for "we need automated VM backups".

#### Custom images
Built from an existing disk or imported. Used when you've baked an image with your stack pre-installed (e.g. "golden image" workflow). Often combined with **Packer** to automate.

#### Machine images
A separate object that captures **everything about a VM** — disks, instance properties, attached metadata. Useful for full-VM cloning, but most exam questions still revolve around disks/snapshots/images.

### 2.4 GKE — running it

#### Inventory
- **Nodes** — `kubectl get nodes` or *Kubernetes Engine → Clusters → Nodes*.
- **Pods, Services, Deployments, etc.** — `kubectl get pods,svc,deploy -A`. The console exposes them under *Workloads*, *Services & Ingress*, *ConfigMaps*, etc.

#### Pulling images from Artifact Registry
GKE's node service account needs read access to the registry. Grant `roles/artifactregistry.reader` on the registry (or the project) to the **node service account** (the SA used by the node VM, *not* a workload service account).

If you use **Workload Identity** (recommended) and pull from the workload service account, grant the role to that SA instead.

#### Securely accessing GCP services from GKE Pods

Two patterns; only one is exam-correct for new clusters:

- **Node service account** (legacy) — every Pod on a node inherits the node's GCE SA. Coarse: any Pod on the node has every API permission the node does.
- **Workload Identity** (recommended) — each Pod runs as a Kubernetes service account that is bound to a Google service account. Tokens come from a per-Pod metadata server, scoped per workload. **No JSON keys.** See §4.2 for the binding steps.

If a question says "the team is mounting JSON keys as Secrets" or "node SA has too many permissions", the answer is *Workload Identity*.

#### Node pools
- A cluster has one or more node pools, each independently configured (machine type, autoscaling, disk, image, taints/labels).
- **Add a pool** when you need different hardware (GPU, larger memory) or to gradually migrate to a new config.
- **Cluster autoscaler** scales node pools up and down based on pending pods.
- Node pools can be marked as **spot** to use Spot VMs as cheap nodes for fault-tolerant work.

#### Kubernetes resources you must know
- **Pod** — smallest deployable unit; one or more containers.
- **Deployment** — manages a replica set of Pods, supports rolling updates.
- **Service** — stable virtual IP / DNS in front of Pods. Types: `ClusterIP` (internal), `NodePort`, `LoadBalancer` (external IP, provisions a Google LB), `ExternalName`.
- **StatefulSet** — Pods with stable identity and persistent volumes; for databases and stateful apps. Each Pod gets a deterministic name (`mysql-0`, `mysql-1`, …), a stable DNS entry through a *headless* Service, and its own PersistentVolumeClaim that survives Pod restarts. Updates and scaling happen **in order** (one Pod at a time). Use it for databases, message brokers, leader-elected clusters — not for stateless web apps.
- **DaemonSet** — one Pod per node (logging agents, metrics).
- **Job / CronJob** — run-to-completion / scheduled work.
- **ConfigMap / Secret** — configuration and credentials, mounted or env-injected.
- **Ingress** — HTTP routing into a cluster, often backed by an HTTP Load Balancer in GKE.

#### HPA, VPA, Cluster Autoscaler
- **HPA (Horizontal Pod Autoscaler)** — scales the **number of Pods** in a Deployment based on CPU, memory, or custom metrics.
- **VPA (Vertical Pod Autoscaler)** — adjusts a Pod's **CPU/memory requests**, restarting it. Cannot be used with HPA on the same metric.
- **Cluster Autoscaler** — adds/removes **nodes** in a node pool when Pods can't be scheduled.

A clean order of operations: HPA reacts first (more pods); if no node has room, cluster autoscaler adds a node; VPA adjusts requests over time so HPA's signals are accurate.

#### GKE Autopilot pod resource requests
In Autopilot you don't manage nodes — billing is per Pod's **resource requests**. The exam wants you to know:
- You **must** set CPU/memory requests; Autopilot enforces minimums and ratios.
- Autopilot rejects unsafe configs (privileged containers, non-namespaced) by default.
- You can still set HPA; you just can't run a DaemonSet that touches node internals.

### 2.5 Cloud Run — running it

#### Deploying new versions
Each `gcloud run deploy` creates a new **revision**. By default the new revision serves 100% of traffic immediately, but you can deploy with `--no-traffic` and then explicitly split.

#### Traffic splitting
Cloud Run is built around **revisions** and **traffic splits**. Patterns:

- **Canary** — `update-traffic` to send 5%/10%/etc. to the new revision, observe, then ramp.
- **Blue/green** — deploy with `--no-traffic`, validate, then `update-traffic` to 100%.
- **Rollback** — `update-traffic` back to the previous revision.

The same model exists in **Cloud Run functions** (which is now Cloud Run under the hood) and in **GKE** (where you typically achieve traffic splitting via a service mesh, or the LB's URL maps).

#### Autoscaling
Cloud Run autoscales based on **concurrent requests per instance**. Knobs:
- **Concurrency** — max requests per instance (default 80).
- **Min instances** — keep N warm to avoid cold starts.
- **Max instances** — cap on scale-out.
- **CPU allocation** — `default` (CPU only during requests) vs. `always` (CPU during background work).
- **Startup CPU boost** — extra CPU for the first few seconds, helping cold starts.

A single instance can handle many concurrent requests; if your code is single-threaded and slow, lower concurrency to spread load over more instances.

## 3. Decision criteria

| Question | Answer |
|---|---|
| Need SSH into a VM with no external IP | **IAP TCP forwarding** (`--tunnel-through-iap`) |
| Need automated daily disk backups | **Snapshot schedule** (resource policy) on the disk |
| Need a reusable boot template | **Custom image** (sometimes a snapshot if used as boot disk source) |
| Pods crashing for OOM | Increase memory request (or VPA in recommend mode) |
| Cluster cost too high during off-hours | Cluster autoscaler **min** count low, or schedule-based scaling on node pools |
| Sudden traffic spike | HPA on relevant metric, plus cluster autoscaler |
| Cloud Run cold starts hurting latency | Set **min instances** > 0 and consider **startup CPU boost** |
| Need to roll back a Cloud Run release fast | `gcloud run services update-traffic --to-revisions=PREV=100` |
| Need different hardware on GKE for one workload | New **node pool** with the hardware + node selector / taint on the pool |
| Sharing a registry across multiple GKE clusters | Grant `roles/artifactregistry.reader` to each cluster's node SA |

## 4. Console walkthrough

- **SSH a VM** — *Compute Engine → VM instances* → click **SSH** on the row. For IAP tunneling, the same button works as long as IAP is configured.
- **Snapshots** — *Compute Engine → Snapshots*. Tabs for snapshots and *Snapshot schedules* (resource policies).
- **Custom images** — *Compute Engine → Images → Custom images → Create image* (from disk or from a snapshot).
- **GKE inventory** — *Kubernetes Engine → Clusters → (cluster) → Nodes / Workloads / Services & Ingress / Storage / Config*.
- **Node pools** — *Kubernetes Engine → Clusters → (cluster) → Nodes → Add node pool* (or edit/delete).
- **HPA** — *Kubernetes Engine → Workloads → (deployment) → Actions → Autoscale*.
- **Cloud Run revisions / traffic** — *Cloud Run → Services → (service) → Revisions* tab. *Manage traffic* button to set splits.
- **Cloud Run scaling** — *Cloud Run → (service) → Edit & deploy new revision → Container, Networking & Security → Capacity*: min/max instances, concurrency, CPU allocation.

## 5. gcloud / kubectl reference

```bash
# ── Compute Engine SSH ──
gcloud compute ssh web-1 --zone=europe-west3-a
gcloud compute ssh internal-vm --zone=europe-west3-a --tunnel-through-iap

# Add an OS Login SSH key
gcloud compute os-login ssh-keys add --key-file=~/.ssh/id_ed25519.pub

# ── Snapshots and images ──
gcloud compute disks snapshot data-1 --snapshot-names=data-1-2026-04-27 --zone=europe-west3-a
gcloud compute snapshots list
gcloud compute snapshots delete data-1-2026-04-27

gcloud compute images create golden-app-v1 --source-disk=base-disk --source-disk-zone=europe-west3-a --family=app

# Snapshot schedule (resource policy) and attach to disk
gcloud compute resource-policies create snapshot-schedule daily-7d \
    --region=europe-west3 --max-retention-days=7 --daily-schedule --start-time=02:00
gcloud compute disks add-resource-policies data-1 \
    --resource-policies=daily-7d --zone=europe-west3-a

# ── GKE inventory & node pools ──
gcloud container clusters get-credentials std-cluster --region=europe-west3
kubectl get nodes
kubectl get pods,svc,deploy -A

gcloud container node-pools list --cluster=std-cluster --region=europe-west3
gcloud container node-pools create batch-pool --cluster=std-cluster --region=europe-west3 \
    --machine-type=e2-standard-4 --enable-autoscaling --min-nodes=0 --max-nodes=20 --spot
gcloud container node-pools delete old-pool --cluster=std-cluster --region=europe-west3

# ── Kubernetes operations ──
kubectl create deployment web --image=europe-docker.pkg.dev/PROJECT/repo/web:1.0
kubectl expose deployment web --type=LoadBalancer --port=80 --target-port=8080
kubectl scale deployment web --replicas=5

# HPA
kubectl autoscale deployment web --cpu-percent=60 --min=2 --max=10

# StatefulSet (typical pattern is via YAML; quick imperative not standard)

# ── GKE Artifact Registry pull ──
NODE_SA=$(gcloud iam service-accounts list --filter="email~compute@" --format="value(email)")
gcloud artifacts repositories add-iam-policy-binding repo \
    --location=europe-west3 --member=serviceAccount:$NODE_SA \
    --role=roles/artifactregistry.reader

# ── Cloud Run deployments and traffic ──
gcloud run deploy api --image=...:1.1 --region=europe-west3 --no-traffic
gcloud run revisions list --service=api --region=europe-west3
gcloud run services update-traffic api --region=europe-west3 \
    --to-revisions=api-00003-abc=10,api-00002-abc=90    # 10% canary

# Roll back to previous revision
gcloud run services update-traffic api --region=europe-west3 \
    --to-revisions=api-00002-abc=100

# Cloud Run scaling settings
gcloud run services update api --region=europe-west3 \
    --min-instances=2 --max-instances=50 --concurrency=40 --cpu-boost
```

## 6. Exam gotchas

- **IAP tunneling vs. external IP.** A VM without an external IP isn't unreachable — IAP TCP forwarding is the answer for SSH/management.
- **Snapshots are incremental, but charges show per-snapshot.** Deleting an old snapshot doesn't necessarily free up its full size; the data is shared with newer snapshots.
- **Snapshots are stored in Cloud Storage**, but you don't see them as objects in a bucket — they're managed automatically.
- **Custom images are project-scoped.** To share across projects, share via IAM (or use an organization image).
- **Schedule snapshots via a resource policy**, not a cron job in a VM. The exam tests this.
- **Pulling from Artifact Registry on GKE** — grant `roles/artifactregistry.reader` to the **node service account**, not a workload SA, unless you're using Workload Identity.
- **HPA + VPA on the same metric is forbidden.** They will fight. Use VPA in *recommend* mode if you also use HPA.
- **Autopilot enforces resource requests.** No requests, no scheduling. Reasonable defaults, but don't expect "just deploy without limits".
- **Cloud Run rollbacks are traffic shifts**, not redeploys. The old revision is still there; you point traffic at it.
- **Min instances cost money even when idle** — they're paying for warmth. Mention this for cold-start questions.
- **Concurrency = 1** turns Cloud Run into per-request scaling (one container per request) — useful for non-thread-safe code, but expensive.
- **Scaling Cloud Run functions** uses the same model as Cloud Run since 2nd gen runs on Cloud Run.
- **`kubectl expose ... --type=LoadBalancer`** on GKE provisions a real Network LB. Don't be surprised by the bill.

## 7. Practice scenarios

### Q1 — SSH to a private VM
A VM has only an internal IP. You need to SSH from your laptop. Which approach?

A. Add an external IP temporarily.
B. **Use IAP TCP forwarding with `gcloud compute ssh --tunnel-through-iap`.**
C. Set up a bastion host with a public IP and SSH-jump.
D. Use the Cloud Shell.

**Answer: B.** IAP TCP forwarding tunnels SSH through Google's identity-aware proxy without giving the VM a public IP. A defeats the security posture. C works but is more infrastructure than needed. D is closer in spirit but still routes through your project — IAP is the canonical, exam-correct answer.

### Q2 — Automated VM backups
You need every production VM disk backed up daily, with 14-day retention, with no manual intervention. Which feature?

A. A cron job inside each VM that runs `gcloud compute disks snapshot`.
B. **A snapshot schedule (resource policy) attached to each disk.**
C. Custom images created weekly.
D. Cloud Storage `gcloud storage cp` of `/dev/sda`.

**Answer: B.** Snapshot schedules (resource policies) are the managed way to schedule and retain snapshots — daily/weekly/hourly with retention. A works but is fragile. C creates *images* (templates) not backups. D is wrong on multiple levels.

### Q3 — GKE node pool for GPU workloads
Your GKE Standard cluster needs to run a few GPU jobs occasionally without paying for GPUs all the time. What's the right approach?

A. Add GPUs to the default node pool.
B. **Add a separate GPU node pool with autoscaling, min=0, max=N, with taints so only GPU-tolerant pods schedule there.**
C. Switch the entire cluster to GPU machine types.
D. Use Autopilot.

**Answer: B.** A dedicated node pool with autoscaling-to-zero (`min=0`) means you only pay when GPU jobs run; taints and tolerations keep regular pods off. A wastes GPUs. C massively over-provisions. D Autopilot supports GPUs, but the question implies retaining Standard.

### Q4 — Cloud Run rollback
A new Cloud Run revision (`rev-12`) has a serious bug. The previous revision was `rev-11`. What's the fastest, safest action?

A. Redeploy the previous container image as `rev-13`.
B. **`gcloud run services update-traffic --to-revisions=rev-11=100`.**
C. Delete `rev-12`.
D. Recreate the service from scratch.

**Answer: B.** Cloud Run keeps revisions; the rollback is a traffic shift to the prior revision — instantaneous, no rebuild, no risk. A creates an unnecessary new revision. C may break, and you cannot delete a revision serving traffic. D is dramatic.

### Q5 — Cloud Run cold starts
Users complain about latency spikes for the first request after idle periods. Which combination of settings reduces cold starts?

A. Increase max instances.
B. Decrease concurrency to 1.
C. **Set min instances ≥ 1 and enable startup CPU boost.**
D. Switch to Cloud Run jobs.

**Answer: C.** Min instances keep N warm; startup CPU boost gives extra CPU for the first few seconds. A doesn't help cold starts (it just allows more parallel scaling). B *hurts* — you'll spawn more cold instances per request. D is for batch, not online traffic.

## 8. Hands-on labs

### Lab 1 — Take a manual snapshot of a Persistent Disk
**Goal:** snapshot a running VM's boot disk, then restore by creating a new disk and VM from that snapshot.

**Console (snapshot):**
1. *Compute Engine → Snapshots → Create snapshot*.
2. **Name:** `web-1-2026-04-27`. **Source disk:** select `web-1`. **Location:** Multi-regional (default).
3. *Create*. After ~1 min status is **Ready**.

**Console (restore):**
1. *Compute Engine → Disks → Create disk*.
2. **Name:** `web-1-restored`. **Type:** Balanced PD. **Source type:** *Snapshot*. Pick `web-1-2026-04-27`. **Zone:** `europe-west3-a`. *Create*.
3. *VM instances → Create instance*. Boot disk **Change → Existing disks** → select `web-1-restored`. *Create*.

**gcloud:**
```bash
gcloud compute disks snapshot web-1 --snapshot-names=web-1-2026-04-27 --zone=europe-west3-a
gcloud compute disks create web-1-restored --source-snapshot=web-1-2026-04-27 --zone=europe-west3-a
gcloud compute instances create web-1-restored --disk=name=web-1-restored,boot=yes --zone=europe-west3-a
```

### Lab 2 — Create a snapshot schedule and attach it to a disk
**Goal:** automate daily snapshots with 7-day retention.

**Console:**
1. *Compute Engine → Snapshots → Snapshot schedules → Create snapshot schedule*.
2. **Name:** `daily-7d`. **Region:** `europe-west3`. **Schedule type:** Daily, **Start time:** 02:00.
3. **Auto-delete after:** 7 days. **Snapshot location:** Multi-regional. *Create*.
4. *Compute Engine → Disks → web-1*. Click **Edit**. Under **Snapshot schedule**, pick `daily-7d`. *Save*.

**gcloud:**
```bash
gcloud compute resource-policies create snapshot-schedule daily-7d \
    --region=europe-west3 --max-retention-days=7 --daily-schedule --start-time=02:00
gcloud compute disks add-resource-policies web-1 \
    --resource-policies=daily-7d --zone=europe-west3-a
```

### Lab 3 — Create a custom image from a disk
**Goal:** bake a "golden" image you can launch new VMs from.

**Console:**
1. Stop the VM whose disk you want to image (preferred for consistency): *VM instances → web-1 → Stop*.
2. *Compute Engine → Images → Create image*.
3. **Name:** `golden-web-v1`. **Source:** *Disk*. **Source disk:** `web-1`. **Family:** `web` (optional). *Create*.
4. *VM instances → Create instance → Boot disk → Change → Custom images*. Pick `golden-web-v1`. *Create*.

**gcloud:**
```bash
gcloud compute instances stop web-1 --zone=europe-west3-a
gcloud compute images create golden-web-v1 --source-disk=web-1 --source-disk-zone=europe-west3-a --family=web
gcloud compute instances create web-2 --image=golden-web-v1 --zone=europe-west3-a
```

### Lab 4 — Add an autoscaling node pool to a GKE cluster
**Goal:** add a dedicated `e2-standard-4` autoscaled pool with min 0, max 5, with a label so workloads can target it.

**Console:**
1. *Kubernetes Engine → Clusters → std-cluster → Nodes → Add node pool*.
2. **Name:** `batch-pool`. **Number of nodes (per zone):** `0`. Check **Enable autoscaling**, **Min:** `0`, **Max:** `5`.
3. **Nodes → Machine type:** `e2-standard-4`.
4. **Metadata → Kubernetes labels:** `workload=batch`. *Create*.
5. Verify in Cloud Shell:
   ```bash
   kubectl get nodes -L workload
   ```
6. Schedule a test pod that targets the label:
   ```bash
   kubectl run batch-test --image=alpine --restart=Never \
       --overrides='{"spec":{"nodeSelector":{"workload":"batch"}}}' -- sleep 30
   ```
   The cluster autoscaler will scale `batch-pool` from 0 → 1 then back to 0 once the pod completes.

**gcloud:**
```bash
gcloud container node-pools create batch-pool --cluster=std-cluster --region=europe-west3 \
    --machine-type=e2-standard-4 --enable-autoscaling --min-nodes=0 --max-nodes=5 \
    --node-labels=workload=batch
```

### Lab 5 — Configure Horizontal Pod Autoscaler
**Goal:** scale a Deployment from 2 to 10 replicas based on CPU.

**Cloud Shell:**
```bash
kubectl create deployment cpu-load --image=k8s.gcr.io/hpa-example
kubectl set resources deployment cpu-load --requests=cpu=200m,memory=128Mi
kubectl expose deployment cpu-load --port=80 --target-port=80
kubectl autoscale deployment cpu-load --cpu-percent=50 --min=2 --max=10
kubectl get hpa cpu-load -w
```

In another shell, drive load:
```bash
kubectl run -it loader --image=busybox --restart=Never --rm -- \
    /bin/sh -c "while true; do wget -q -O- http://cpu-load; done"
```

Watch `REPLICAS` climb. Stop the loader and observe scale-down (after the cool-down).

**Console verification:** *Workloads → cpu-load → Actions → Autoscale* shows the same HPA.

### Lab 6 — Deploy a new Cloud Run revision and split traffic
**Goal:** push a `:2.0` revision with `--no-traffic`, then canary 10%, then promote to 100%.

**Cloud Shell:**
```bash
gcloud run deploy hello-run \
    --image=europe-west3-docker.pkg.dev/$DEVSHELL_PROJECT_ID/apps/hello:2.0 \
    --region=europe-west3 --no-traffic

REV=$(gcloud run revisions list --service=hello-run --region=europe-west3 \
    --filter="metadata.labels.serving.knative.dev/configurationGeneration=2" \
    --format="value(metadata.name)")

# 10% canary
gcloud run services update-traffic hello-run --region=europe-west3 \
    --to-revisions=$REV=10
```

**Console:**
1. *Cloud Run → hello-run → Revisions tab*.
2. Confirm a new revision shows `10%` traffic; the previous one shows `90%`.
3. Click **Manage traffic**. Drag the new revision slider to `100`. *Save*.
4. Click **Manage traffic** again, choose the previous revision and set `100` to roll back instantly.

### Lab 7 — Pull images from Artifact Registry on GKE
**Goal:** grant the GKE node service account read on the registry so deployments can pull private images.

**Console:**
1. *IAM & Admin → IAM* — find the entry that ends in `-compute@developer.gserviceaccount.com`. That's the default Compute Engine SA used by GKE nodes.
2. *Artifact Registry → Repositories → apps → Permissions tab → Add principal*.
3. **New principal:** the node SA email. **Role:** *Artifact Registry Reader*. *Save*.
4. Re-deploy a Pod referencing `europe-west3-docker.pkg.dev/$PROJECT/apps/hello:1.0`. Pod transitions from `ImagePullBackOff` (if it was) to `Running`.

**gcloud:**
```bash
NODE_SA="$(gcloud iam service-accounts list --filter='email~compute@' --format='value(email)')"
gcloud artifacts repositories add-iam-policy-binding apps \
    --location=europe-west3 --member="serviceAccount:$NODE_SA" \
    --role=roles/artifactregistry.reader
```
