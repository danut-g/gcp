# 3.2 — Managing storage and data solutions

> **Exam guide reference:** Section 3.2. Sub-topics: managing/securing objects in Cloud Storage buckets, object lifecycle management, executing queries (Cloud SQL, BigQuery, Bigtable, Spanner, Firestore, AlloyDB), estimating costs of data storage, backing up and restoring databases (Cloud SQL, Firestore, Spanner, AlloyDB, Bigtable), reviewing job status (Dataflow, BigQuery), Database Center.

---

## 1. Why this matters for the exam

Section 2.2 was *picking* a data product; section 3.2 is **operating** it. The exam will put you in the day-2 seat: a bucket needs lifecycle policies, a BigQuery job is stuck, a Cloud SQL DB needs a point-in-time restore, a finance team wants cost estimates.

You don't need to be a DBA, but you do need to know **what each product's backup story looks like**, **how to query it**, and **how to monitor jobs**.

## 2. Core concepts

### 2.1 Managing Cloud Storage objects

The key operational responsibilities:

#### Access control
Two models — pick **one** per bucket:
- **Uniform Bucket-Level Access (UBLA)** — IAM only, applied at bucket level. **Strongly preferred** and the default for new buckets.
- **Fine-grained ACLs** — legacy per-object access lists. Avoid unless explicitly required.

To make an object publicly readable with UBLA, the canonical pattern is a binding for `allUsers` with `roles/storage.objectViewer` on the bucket — but you almost always **don't** want this. Public buckets are a top finding for compliance scans.

**Signed URLs** are the right answer for "give a third party temporary access to one object" — they bake an expiring URL with embedded credentials.

#### Object lifecycle management
Rules on a bucket that fire automatically. Conditions can include:
- `age` in days
- `createdBefore` / `customTimeBefore`
- `numNewerVersions`
- `matchesStorageClass`
- `isLive` (current vs. non-current versions)

Actions:
- `SetStorageClass` — transition to Nearline / Coldline / Archive.
- `Delete` — permanent.
- `AbortIncompleteMultipartUpload`.

The classic "tiering" recipe: live for 30 days → Nearline; 90 days → Coldline; 365 days → Archive; older non-current versions → delete.

#### Versioning + retention + holds
- **Versioning** — keep prior versions on overwrite/delete. Combined with lifecycle, gives a soft delete.
- **Retention policy** — bucket-level; objects can't be deleted before N seconds since creation. Can be **locked** for compliance — irrevocable.
- **Object holds** (event-based / temporary) — pin an individual object against deletion.

#### Encryption (operational)
- Default = Google-managed keys.
- **CMEK** — `gcloud storage buckets update --default-kms-key=...`. Re-encrypting existing objects requires a rewrite.
- **CSEK** — supplied per request; not commonly an exam answer beyond "we want to keep keys ourselves".

### 2.2 Querying data instances

You should know the **standard query interface** for each:

| Product | Interface |
|---|---|
| **Cloud SQL** / **AlloyDB** | SQL via `psql`, `mysql`, or a JDBC/ODBC client; Cloud SQL Studio in the console |
| **Spanner** | SQL (with extensions) via the console **Studio** or `gcloud spanner databases execute-sql` |
| **BigQuery** | SQL in the console **Studio**, `bq query`, or via the API/SDK; supports legacy & GoogleSQL (use GoogleSQL) |
| **Firestore** | Limited, document-style queries via SDKs / console; no general SQL (Firestore in Datastore mode has GQL) |
| **Bigtable** | No SQL — key-prefix scans via `cbt` CLI, HBase-compatible APIs, BigQuery external tables, or the console *Tables* view |

### 2.3 Backups and restores

Every database has a backup story; they differ.

| Product | Built-in backup | Restore type |
|---|---|---|
| **Cloud SQL** | Automated daily backups + on-demand; **PITR** if WAL/binlog archive enabled | Restore to a new instance, or PITR clone |
| **AlloyDB** | Automated continuous backups + on-demand; PITR within window | Restore to a new cluster |
| **Spanner** | On-demand backups; **point-in-time recovery** within version retention (default 1h, up to 7d) | New database from backup or PITR |
| **Firestore** | Scheduled exports to Cloud Storage; or Native managed backups (newer) | Import to a new (or same) database |
| **Bigtable** | Per-table on-demand backups (in cluster); cross-region via export | Restore to same or different cluster |
| **BigQuery** | "Time travel" 7 days by default; table snapshots; dataset copy | Query at a past timestamp; restore from snapshot |
| **Cloud Storage** | Versioning + lifecycle as the closest equivalent | Restore by listing/getting a previous version |

#### Point-in-time recovery (PITR)
On Cloud SQL, you must enable **automated backups** + **point-in-time recovery (binary logs / WAL)**. PITR creates a *new* instance restored to the chosen timestamp; it does not overwrite the original.

### 2.4 Reviewing job status

#### BigQuery jobs
- *BigQuery → Job history* — every query, load, copy, export job is listed.
- Or `bq ls -j` and `bq show -j JOB_ID` for details.
- `bq cancel JOB_ID` to stop a running job.

#### Dataflow jobs
- *Dataflow → Jobs* — visualises the pipeline graph, watermark, throughput, lag.
- `gcloud dataflow jobs list` / `describe` / `cancel` / `drain` for CLI ops.
- Drain = stop accepting new work but finish in-flight; Cancel = terminate.

#### Database Center
A newer single pane of glass for the **entire database fleet** across Cloud SQL, AlloyDB, Spanner, Bigtable, Firestore, Memorystore. Look for it under *Database Center* in the console — surfaces health, recommendations, vulnerabilities, upgrades.

### 2.5 Estimating storage costs

Two tools:

- **Pricing calculator** (`cloud.google.com/products/calculator`) — pre-purchase forecasting. Pick service, region, quantities; get an estimate.
- **Cost reports / billing exports** — actual spend, sliced by service and SKU. The right answer for "what did this dataset cost us last month".

For Cloud Storage the main cost components are:
1. **Storage** (per GB-month, depends on class).
2. **Network egress** (especially internet egress).
3. **Operations** (Class A and Class B requests; not free).
4. **Retrieval fees** (Nearline / Coldline / Archive).
5. **Early-deletion fees** (if you delete before the minimum duration).

For BigQuery:
1. **Active storage** vs. **long-term storage** (auto-discounted after 90 days untouched).
2. **Query cost** — on-demand (per TB scanned) vs. capacity (slot reservations).
3. **Streaming inserts / Storage Write API** charges.

## 3. Decision criteria

| Question | Answer |
|---|---|
| Restore a Cloud SQL DB to 2 hours ago | Enable PITR ahead of time; then restore to a new instance at that timestamp |
| Keep Cloud Storage objects undeletable for 7 years | Bucket retention policy with `--retention-period=220752000s` and locked |
| Move infrequently-accessed data to cheaper storage | Lifecycle rule: age > 30d → Nearline, age > 365d → Archive |
| Audit who changed an object | Object versioning + IAM Audit Logs |
| Query BigQuery at yesterday's state | Time-travel: `FOR SYSTEM_TIME AS OF TIMESTAMP` |
| Stop a BigQuery query that's costing too much | `bq cancel JOB_ID` |
| Pause a streaming Dataflow job for an upgrade | **Drain** (not cancel) so in-flight work completes |
| Cross-region backup of Bigtable | Export to Cloud Storage, or replicate to a multi-cluster instance |
| Check fleet-wide DB health | **Database Center** |

## 4. Console walkthrough

- **Cloud Storage object operations** — *Cloud Storage → Buckets → (bucket)*. Each row has overflow actions: change class, edit metadata, edit permissions, set retention, manage holds.
- **Lifecycle** — bucket page → *Lifecycle* tab → *Add rule*.
- **Permissions** — bucket page → *Permissions* tab. UBLA bucket: only IAM section. Fine-grained: ACLs section appears too.
- **Cloud SQL backups** — *SQL → (instance) → Backups*. Toggle automated backups, run on-demand, restore from a backup.
- **Cloud SQL Studio** — *SQL → (instance) → Cloud SQL Studio*. Browser-based SQL client.
- **BigQuery Studio** — *BigQuery* (the whole product is now "BigQuery Studio"). Query editor, dataset explorer, job history left panel.
- **BigQuery snapshots** — *BigQuery → (table) → Snapshot*. Time-travel works in `FROM` clauses.
- **Spanner Studio** — *Spanner → (database) → Studio*.
- **Firestore exports** — *Firestore → Import/Export*.
- **Bigtable backups** — *Bigtable → (instance) → (cluster) → Backups*.
- **Dataflow jobs** — *Dataflow → Jobs*. Click a job for the live graph and metrics.
- **Database Center** — *Database Center* in the navigation menu.

## 5. gcloud / CLI reference

```bash
# ── Cloud Storage operations ──
gcloud storage ls gs://my-bucket/
gcloud storage cp gs://my-bucket/file.csv .
gcloud storage rm gs://my-bucket/old-file.csv
gcloud storage objects describe gs://my-bucket/file.csv

# Object class change
gcloud storage objects update gs://my-bucket/old.bin --storage-class=COLDLINE

# Lifecycle (apply a JSON rule file)
gcloud storage buckets update gs://my-bucket --lifecycle-file=lifecycle.json

# Versioning, retention, hold
gcloud storage buckets update gs://my-bucket --versioning
gcloud storage buckets update gs://my-bucket --retention-period=2592000s
gcloud storage buckets update gs://my-bucket --lock-retention-period
gcloud storage objects update gs://my-bucket/important.dat --temporary-hold

# Signed URL (15-minute download link)
gcloud storage sign-url gs://my-bucket/file.csv \
    --duration=15m --private-key-file=sa-key.json

# ── Cloud SQL backups & PITR ──
gcloud sql backups list --instance=db-1
gcloud sql backups create --instance=db-1 --description="pre-deploy"
gcloud sql instances clone db-1 db-1-restored \
    --point-in-time="2026-04-27T12:00:00Z"
gcloud sql instances restore-backup db-1 --backup-id=...

# ── BigQuery jobs & queries ──
bq ls -j --max_results=20                   # recent jobs
bq show -j JOB_ID
bq cancel JOB_ID
bq query --use_legacy_sql=false 'SELECT 1'
bq query --use_legacy_sql=false \
  "SELECT * FROM mydataset.mytable FOR SYSTEM_TIME AS OF TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 1 HOUR)"

# Table snapshot
bq cp --snapshot mydataset.mytable mydataset.mytable_snap_2026_04_27

# ── Spanner queries ──
gcloud spanner databases execute-sql app --instance=main --sql="SELECT 1"

# ── Bigtable ──
cbt -instance main lookup users user-123
cbt -instance main read users prefix=user-

# ── Firestore export/import ──
gcloud firestore export gs://my-bucket/firestore-backup-2026-04-27
gcloud firestore import gs://my-bucket/firestore-backup-2026-04-27

# ── Dataflow jobs ──
gcloud dataflow jobs list --region=europe-west3 --status=active
gcloud dataflow jobs describe JOB_ID --region=europe-west3
gcloud dataflow jobs drain   JOB_ID --region=europe-west3
gcloud dataflow jobs cancel  JOB_ID --region=europe-west3
```

## 6. Exam gotchas

- **UBLA is preferred.** If a question describes per-object ACL juggling, the answer is usually "switch to UBLA + IAM".
- **Public buckets** = `allUsers` granted `roles/storage.objectViewer`. The exam loves this scenario as a security finding.
- **Signed URLs** are the right "share temporarily" answer — not making the bucket public, not changing IAM.
- **Lifecycle policies are async.** Don't expect immediate transition; ~24 hours.
- **Locked retention policy is irrevocable.** Don't lock unless legally required.
- **Cloud SQL PITR requires it to be enabled in advance.** You can't retroactively enable PITR for a moment in the past.
- **Cloud SQL restore creates a new instance.** It doesn't overwrite the source.
- **BigQuery time travel is 7 days by default**, configurable up to 7 days (and not more — for older data you need snapshots).
- **BigQuery long-term storage** is automatic — touched tables stay "active"; untouched > 90 days get the discount.
- **Drain vs. cancel a Dataflow job** — drain finishes in-flight, cancel kills. Use drain for clean upgrades.
- **Bigtable backups are per-cluster.** Cross-cluster requires replication or export.
- **Firestore backups are exports to Cloud Storage** by default; the newer managed backup service is the one to mention if available.
- **Database Center** is a relatively new exam term — recognize it as the cross-database fleet console.
- **Pricing calculator is for forecasting; cost reports are for actuals.** Don't mix them up.

## 7. Practice scenarios

### Q1 — Sharing a single file
A partner needs read access to one specific object in a private bucket for the next 4 hours, without a Google account. What's the secure, idiomatic approach?

A. Make the bucket public.
B. Add `allUsers` as `roles/storage.objectViewer` on the object.
C. **Generate a signed URL with a 4-hour expiration.**
D. Email the partner the SA key file.

**Answer: C.** Signed URLs are the canonical "temporary access without an identity" mechanism. A and B make it world-readable indefinitely. D leaks long-lived credentials catastrophically.

### Q2 — Lifecycle policy
You want objects in a bucket to transition to Coldline at 90 days and be deleted at 365 days. The objects are versioned, and you want non-current versions deleted after 30 days. Which feature?

A. Cloud Functions triggered by Cloud Storage events.
B. **Object Lifecycle Management with multiple rules.**
C. A scheduled BigQuery query.
D. Manual review monthly.

**Answer: B.** Lifecycle rules cover age-based transitions, deletions, and version cleanups in one declarative config. A overengineers. C and D are manual.

### Q3 — Cloud SQL recovery
At 14:30 someone ran a `DELETE FROM orders WHERE 1=1` on the prod database. You realise at 15:00. What's the recovery path, and what must already be enabled?

A. Restore from the most recent automated backup; PITR not needed.
B. **Use point-in-time recovery to a timestamp just before 14:30 — PITR (binary logs/WAL) must have been enabled in advance.**
C. Replay manual backups.
D. Use Database Migration Service.

**Answer: B.** PITR provides minute-level recovery via continuously archived WAL/binlogs. It must be enabled *before* the incident. A only goes to nightly granularity. C is operational nightmare. D is for migrations.

### Q4 — BigQuery time travel
A table was overwritten 3 days ago. You want to query its previous state. Which approach?

A. Restore from a Cloud Storage backup.
B. **`SELECT * FROM dataset.table FOR SYSTEM_TIME AS OF TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 3 DAY)`.**
C. Re-run the original ingest job.
D. Use Database Migration Service.

**Answer: B.** BigQuery time travel keeps 7 days of history by default; `FOR SYSTEM_TIME AS OF` is the SQL syntax. A and C are unnecessary. D doesn't apply.

### Q5 — Dataflow pause for upgrade
A streaming Dataflow pipeline must pause while you deploy a new pipeline version, with **no data loss**. Which action?

A. `gcloud dataflow jobs cancel`.
B. **`gcloud dataflow jobs drain`.**
C. Stop the source Pub/Sub subscription.
D. Delete the BigQuery sink.

**Answer: B.** Drain stops new ingestion but lets in-flight elements finish — no data loss. Cancel kills mid-flight. C/D break the pipeline shape but don't help with safe shutdown.

## 8. Hands-on labs

### Lab 1 — Manage object lifecycle and versioning
**Goal:** turn on versioning and add a rule that deletes non-current versions older than 30 days.

**Console:**
1. Open the bucket → *Protection* tab → **Edit object versioning** → *Enable* → *Save*.
2. *Lifecycle* tab → **Add a rule**. **Action:** *Delete object*. *Continue*.
3. **Conditions:** *Age* `30`. *Match Object state* → *Noncurrent*. *Create*.
4. Test: upload a file twice (same name). Toggle *Show noncurrent versions* in the Objects view — both versions are listed.

**gcloud:**
```bash
gcloud storage buckets update gs://$BUCKET --versioning
cat > nc-lifecycle.json <<EOF
{"lifecycle": {"rule": [
  {"action":{"type":"Delete"},
   "condition":{"age":30,"isLive":false}}
]}}
EOF
gcloud storage buckets update gs://$BUCKET --lifecycle-file=nc-lifecycle.json
```

### Lab 2 — Generate a Signed URL for a single object
**Goal:** create a 15-minute, no-account, read-only download link.

**Console:** *(Signed URLs are gcloud-only; the console can grant the SA but the URL itself is generated via CLI/SDK.)*
1. *IAM & Admin → Service Accounts → Create*. Name `signer-sa`. *Done*.
2. *Cloud Storage → Buckets → ${BUCKET} → Permissions → Grant access*. **Principal:** `signer-sa@…`. **Role:** *Storage Object Viewer*. *Save*.
3. *Service Accounts → signer-sa → Keys → Add key → Create new key → JSON*. Save `signer-sa.json`.

**gcloud:**
```bash
gcloud storage sign-url gs://$BUCKET/file.csv \
    --duration=15m --private-key-file=signer-sa.json
# share the resulting https://… URL
```

### Lab 3 — Cloud SQL: enable PITR, take a backup, restore to a new instance
**Goal:** prove you can recover a Cloud SQL DB to a moment in time.

**Console (enable PITR + on-demand backup):**
1. *SQL → pg-1 → Edit*. Expand **Data Protection**.
2. Check **Automate backups** and **Enable point-in-time recovery**. *Save & Restart* (Postgres restarts).
3. *SQL → pg-1 → Backups → Create backup*. Description `pre-deploy`. *Create*.

**Console (restore to a new instance):**
1. *SQL → pg-1 → Operations → Clone*.
2. **Clone instance ID:** `pg-1-restored`. **Clone from:** *Specific point in time* → choose a timestamp 10 minutes ago.
3. *Create clone*. After ~5 min you have a separate restored instance.

**gcloud:**
```bash
gcloud sql instances patch pg-1 --backup --enable-point-in-time-recovery
gcloud sql backups create --instance=pg-1 --description=pre-deploy
gcloud sql instances clone pg-1 pg-1-restored \
    --point-in-time="2026-04-27T13:30:00Z"
```

### Lab 4 — Run BigQuery query, view job history, time-travel
**Goal:** run a query, then re-query the table as it was 1 hour ago.

**Console:**
1. *BigQuery → Studio*. Run:
   ```sql
   UPDATE `analytics.us_states` SET name = 'TEMP' WHERE post_abbr='WY';
   ```
2. Run a normal `SELECT` to verify the change.
3. Click **Job history** in the left rail to see UPDATE and SELECT jobs, durations, bytes processed.
4. Run a time-travel query for the prior state:
   ```sql
   SELECT name, post_abbr
   FROM `analytics.us_states`
       FOR SYSTEM_TIME AS OF TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 1 HOUR)
   WHERE post_abbr='WY';
   ```
5. Compare results — original `Wyoming` is back.

**bq:**
```bash
bq query --use_legacy_sql=false \
  "SELECT * FROM \`analytics.us_states\` FOR SYSTEM_TIME AS OF TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 1 HOUR)"
bq ls -j --max_results=10
```

### Lab 5 — Estimate storage cost in the Pricing Calculator
**Goal:** forecast what 5 TB in Standard + 50 TB in Coldline costs in `europe-west3` for a year.

**Console (web):**
1. Open `https://cloud.google.com/products/calculator`.
2. *Add to estimate → Cloud Storage*.
3. **Location type:** Region → `europe-west3`. **Storage class:** Standard. **Total amount:** 5 TB. **Average duration:** 12 months.
4. **Add to estimate → Cloud Storage** again with same location, class **Coldline**, 50 TB, 12 months. Add a small egress estimate.
5. Save the estimate URL — it's the artefact you share with finance.

(No gcloud equivalent — the calculator is a web tool.)

### Lab 6 — Inspect a Dataflow job and drain it for an upgrade
**Goal:** start a streaming Dataflow template, view its graph, then drain it.

**Console (start a sample job):**
1. *Dataflow → Jobs → Create job from template*.
2. **Job name:** `pubsub-to-bq`. **Region:** `europe-west3`.
3. **Dataflow template:** *Pub/Sub Subscription to BigQuery*.
4. Fill in any test Pub/Sub subscription and BigQuery table. *Run job*.
5. After it transitions to **Running**, click the job to see the graph (read → transform → write), the watermark and throughput on the right.

**Drain:**
1. *Top bar → STOP → Drain*. The graph keeps draining in-flight elements until 0, then the job state becomes **Drained**.
2. Or via CLI:
   ```bash
   gcloud dataflow jobs list --region=europe-west3 --status=active
   gcloud dataflow jobs drain JOB_ID --region=europe-west3
   ```

### Lab 7 — Execute basic queries against a Cloud SQL database
**Goal:** create a schema, insert rows, run SELECT/UPDATE/JOIN queries via Cloud SQL Studio, then via the auth proxy.

**Console (Cloud SQL Studio — browser-based SQL):**
1. *SQL → pg-1 → Cloud SQL Studio* (left tab).
2. **Database:** `app`. **User:** `appuser`. **Password:** the one set in 2.2 Lab 3. *Authenticate*.
3. Run, one at a time:
   ```sql
   CREATE TABLE customers (
     id     SERIAL PRIMARY KEY,
     name   TEXT NOT NULL,
     email  TEXT UNIQUE NOT NULL,
     joined DATE DEFAULT CURRENT_DATE
   );

   INSERT INTO customers (name, email) VALUES
     ('Alice','alice@example.com'),
     ('Bob','bob@example.com'),
     ('Carol','carol@example.com');

   SELECT id, name, email FROM customers ORDER BY id;
   UPDATE customers SET name = 'Alice Smith' WHERE id = 1;
   SELECT * FROM customers WHERE name LIKE 'Alice%';
   ```
4. Use the **Explain** button on a SELECT to see the query plan.
5. *Query history* tab (left rail) shows duration, rows returned, status.

**Cloud Shell (`gcloud sql connect` — auth proxy, no exposed IP):**
```bash
gcloud sql connect pg-1 --user=appuser --database=app
# you're now in psql:
\dt
SELECT count(*) FROM customers;
\q
```

**App-side (Cloud SQL Auth Proxy as a sidecar):**
```bash
# Download and run the proxy locally; the app connects to 127.0.0.1:5432
./cloud-sql-proxy $DEVSHELL_PROJECT_ID:europe-west3:pg-1 &
psql "host=127.0.0.1 port=5432 user=appuser dbname=app"
```

The proxy authenticates via your `gcloud` credentials (or a service account) — no SSL certs to manage, no public IP needed.
