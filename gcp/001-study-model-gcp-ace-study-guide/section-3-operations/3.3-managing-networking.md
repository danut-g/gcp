# 3.3 — Managing networking resources

> **Exam guide reference:** Section 3.3. Sub-topics: adding a subnet to an existing VPC, expanding a subnet to have more IPs, reserving static external/internal IPs, adding custom static routes, working with Cloud DNS and Cloud NAT.

---

## 1. Why this matters for the exam

This section is **smaller in scope** than 2.3 (which covered the big design decisions). Here you're managing an existing VPC: growing it, allocating IPs, adding routes, configuring DNS, getting outbound internet access through NAT. These are the everyday networking tasks the exam puts you in front of.

## 2. Core concepts

### 2.1 Adding a subnet

A VPC can have many subnets, each in a region with a non-overlapping CIDR. Adding a subnet to a custom-mode VPC is straightforward — pick a region and a CIDR.

Things to watch:
- **Auto-mode VPC** subnets cannot be customized; convert to custom mode if you need to add a custom subnet.
- **Private Google Access** can be enabled per subnet so VMs without external IPs can reach Google APIs (`*.googleapis.com`).
- **Flow Logs** are enabled per subnet (off by default).

### 2.2 Expanding a subnet's IP range

You can **grow** a subnet (expand its CIDR to a larger block); you **cannot shrink** it.

- The new range must be a superset of the existing one.
- Existing VMs keep their IPs; new IPs come from the expanded range.
- The expansion doesn't disrupt running workloads.

If you need to *change* a subnet's CIDR (not just grow it), the answer is to create a new subnet, migrate workloads, then delete the old one.

#### Secondary IP ranges (alias IP ranges)

A subnet can have **secondary ranges** in addition to the primary. They're used by:
- **GKE** — pod IPs and service IPs come from secondary ranges (VPC-native clusters).
- **Alias IP** — assigning extra IPs to a VM (e.g. for multiple containers on a single VM with their own IPs).

### 2.3 Static IP addresses

VMs and load balancers can have either **ephemeral** or **static** IPs.

| | Ephemeral | Static |
|---|---|---|
| Lifetime | Tied to the resource — released when the VM stops or the LB is deleted | Reserved separately, persists |
| Naming | None | Has a name in the project |
| Use case | Disposable infra | Anything DNS-pointed, VPN endpoints, LB frontends |

Two flavours:

- **External static IP** — public, anycast or regional. Required for any DNS-stable internet endpoint.
- **Internal static IP** — within a subnet. Required when peers need a stable internal address (e.g. an HA proxy, a database replica).

Reserved IPs that aren't attached **still cost money** — Google bills idle IPs to discourage hoarding.

### 2.4 Routes

Routes in a VPC tell traffic where to go. You see them under *VPC network → Routes*.

- **System-generated routes** — auto-created for each subnet (so VMs in the subnet can talk to each other) and a default route to the internet.
- **Custom static routes** — you add them. Common cases:
  - Force traffic for a specific CIDR through a NAT gateway VM.
  - Send traffic for an on-prem CIDR through a VPN/Interconnect tunnel.
  - Send traffic for the public internet through a security appliance ("next hop = instance").

Routes have:
- **Destination** — CIDR.
- **Next hop** — internet gateway, an instance, an internal LB, a VPN tunnel, etc.
- **Priority** — lower = higher priority. Multiple matching routes use the most specific match, then priority.
- **Tags** — apply only to instances with matching network tags.

**Dynamic routes** come from Cloud Router (BGP) and are managed automatically; you don't add them by hand.

### 2.5 Cloud DNS

Managed authoritative DNS service.

- **Public zones** — answer queries from the internet (`example.com`).
- **Private zones** — answer queries only from authorized VPCs (`internal.example.com`). The standard pattern for service discovery.
- **DNSSEC** — sign zones for tamper-evidence; supported on public zones.
- **Forwarding zones** — route queries for a domain to specific resolvers (e.g. for hybrid: forward `corp.example.com` to on-prem DNS over VPN/Interconnect).
- **Peering zones** — let one VPC's queries see another VPC's private zones.

Records you'll create most often: `A` / `AAAA` / `CNAME` / `MX` / `TXT` / `SRV`.

The **TTL** governs caching; lower it before a planned cutover.

### 2.6 Cloud NAT

NAT gateway as a service. Provides **outbound** internet access to VMs that have no external IP.

- **Regional** — one Cloud NAT per region per VPC, attached to a Cloud Router.
- **Manual or automatic IP allocation** — you can pin static external IPs (so the outside world sees a stable source IP for outbound calls) or let Google manage them.
- **Scales automatically** — but be aware of **port allocation**: each NAT IP supports a finite number of TCP/UDP source ports per VM. High concurrent connections may need more IPs or per-VM port reservation.
- **Logging** — Cloud NAT logs (translation events) can go to Cloud Logging.

Cloud NAT is **the** modern answer for "private VMs that need to reach the internet" — don't roll your own NAT VM.

### 2.7 Private Google Access

A subnet-level toggle: VMs without external IPs can still reach Google APIs (`*.googleapis.com`, `gcr.io`, `*.pkg.dev`) without going through NAT or the internet. Works because Google routes those domains internally when the toggle is on.

If your private GKE cluster needs to pull images, the answer is *Private Google Access* + (sometimes) a route, not Cloud NAT.

## 3. Decision criteria

| Question | Answer |
|---|---|
| Need more IPs in a subnet | **Expand the subnet** (cannot shrink) |
| Need to change CIDR drastically | New subnet, migrate, delete old |
| Stable public IP for an LB / VPN gateway | **Reserve a static external IP** |
| Stable internal IP for a database failover | **Reserve a static internal IP** |
| Send all `0.0.0.0/0` traffic through a security appliance | Custom static route, next hop = instance, higher priority than the default |
| Internal name resolution between services | **Cloud DNS private zone** scoped to the VPC(s) |
| On-prem hostnames must resolve from GCP | **Forwarding zone** to on-prem resolvers |
| Private VMs need to reach `pypi.org` for `pip install` | **Cloud NAT** in the region |
| Private VMs need to reach Cloud Storage / APIs only | **Private Google Access** on the subnet |
| Outbound calls from GCP must come from a known IP for an external API | **Cloud NAT** with a reserved external IP pinned |

## 4. Console walkthrough

- **Add a subnet** — *VPC network → VPC networks → (your VPC) → Add subnet*.
- **Expand a subnet** — *VPC network → VPC networks → (your VPC) → (subnet) → Edit → IP address range* (you can only enter a larger range).
- **Static IPs** — *VPC network → IP addresses → Reserve external static address* / *Reserve internal static address*.
- **Custom routes** — *VPC network → Routes → Create route*. Pick destination CIDR, priority, next hop type.
- **Cloud DNS** — *Network services → Cloud DNS → Create zone* (Public / Private / Forwarding / Peering). Add record sets in the zone.
- **Cloud NAT** — *Network services → Cloud NAT → Create gateway*. Attach to a Cloud Router; pick which subnets are NAT'd.
- **Private Google Access** — *VPC network → (subnet) → Edit → Private Google access: On*.

## 5. gcloud reference

```bash
# ── Add / expand subnets ──
gcloud compute networks subnets create prod-eu \
    --network=prod-vpc --region=europe-west3 --range=10.10.0.0/20 \
    --enable-private-ip-google-access --enable-flow-logs

gcloud compute networks subnets expand-ip-range prod-eu \
    --region=europe-west3 --prefix-length=18

# Secondary range (e.g. for GKE pods)
gcloud compute networks subnets update prod-eu \
    --region=europe-west3 \
    --add-secondary-ranges=pods=10.20.0.0/16,services=10.30.0.0/20

# ── Static IPs ──
gcloud compute addresses create web-ip --region=europe-west3
gcloud compute addresses create global-lb-ip --global
gcloud compute addresses create db-internal --region=europe-west3 \
    --subnet=prod-eu --addresses=10.10.0.50
gcloud compute addresses list

# ── Custom routes ──
gcloud compute routes create to-onprem \
    --network=prod-vpc --destination-range=10.100.0.0/16 \
    --next-hop-vpn-tunnel=tunnel-1 --next-hop-vpn-tunnel-region=europe-west3

gcloud compute routes create via-firewall-vm \
    --network=prod-vpc --destination-range=0.0.0.0/0 \
    --next-hop-instance=fw-vm --next-hop-instance-zone=europe-west3-a \
    --priority=900   # beats the default route at priority 1000

# ── Cloud DNS ──
gcloud dns managed-zones create prod-private \
    --dns-name=internal.example.com. --description="" --visibility=private \
    --networks=prod-vpc

gcloud dns record-sets transaction start --zone=prod-private
gcloud dns record-sets transaction add 10.10.0.50 \
    --name=db.internal.example.com. --ttl=60 --type=A --zone=prod-private
gcloud dns record-sets transaction execute --zone=prod-private

# Forwarding zone to on-prem
gcloud dns managed-zones create corp-forward \
    --dns-name=corp.example.com. --visibility=private \
    --networks=prod-vpc \
    --forwarding-targets=192.168.0.10,192.168.0.11

# ── Cloud NAT ──
gcloud compute routers create nat-router --network=prod-vpc --region=europe-west3
gcloud compute routers nats create prod-nat --router=nat-router --region=europe-west3 \
    --nat-all-subnet-ip-ranges --auto-allocate-nat-external-ips

# Pin a known external IP
gcloud compute addresses create nat-fixed-ip --region=europe-west3
gcloud compute routers nats update prod-nat --router=nat-router --region=europe-west3 \
    --nat-external-ip-pool=nat-fixed-ip
```

## 6. Exam gotchas

- **Subnets can grow but not shrink.** Plan your CIDRs accordingly.
- **Reserved IPs cost money even when idle.** Question scenario: "we have unused static IPs and don't want to pay" → release them.
- **Cloud NAT vs. Private Google Access** — Cloud NAT for *general* internet egress, Private Google Access for *only Google APIs*. Many questions test this.
- **Cloud NAT is regional.** A multi-region VPC needs a Cloud NAT per region.
- **Custom routes need a priority tighter than 1000** to beat the default route. The exam loves "we added a route and it's not picking up".
- **Private DNS zones must be authorized to the VPC(s)** that should resolve them. Forgetting this is a common failure.
- **Forwarding zones** require IP connectivity (VPN/Interconnect) and the on-prem resolvers must accept Google's source ranges (`35.199.192.0/19`).
- **Peering zones** are how you share a private zone across VPCs without duplicating the records.
- **Default routes** include `0.0.0.0/0 → default-internet-gateway`. Removing them removes internet access for all VMs in the VPC, which is sometimes intentional (purely internal VPC).
- **Alias IPs / secondary ranges** are how GKE VPC-native clusters work; they aren't "extra IPs for fun" — they're load-bearing for Kubernetes.
- **NAT IP exhaustion** is real: lots of VMs × lots of connections × few NAT IPs = port exhaustion. The fix is more NAT IPs or per-VM port reservation, not "scale Cloud NAT".

## 7. Practice scenarios

### Q1 — Subnet capacity
A subnet `10.10.0.0/24` is running out of IPs. You need to grow it without downtime to existing VMs. Which action?

A. Delete and recreate the subnet with `/22`.
B. **Run `gcloud compute networks subnets expand-ip-range` to a larger CIDR like `/22`.**
C. Add a secondary range.
D. Migrate VMs to a new subnet.

**Answer: B.** Subnets can be expanded (grown), and existing VMs keep their IPs. A causes downtime and is unnecessary. C provides additional ranges (used for GKE pods) but doesn't grow the primary range. D is a workaround when you need to *change* CIDR, not when you need to grow.

### Q2 — Outbound internet for private VMs
A subnet of private-only VMs needs to install OS updates from `apt.example.com`. Which is the simplest correct configuration?

A. Add external IPs to all VMs.
B. **Configure Cloud NAT in the region for the subnet.**
C. Enable Private Google Access.
D. Build a NAT VM by hand.

**Answer: B.** Cloud NAT provides outbound internet egress for VMs without external IPs. A breaks the security posture. C only helps for `*.googleapis.com` (Google services). D is the legacy DIY approach.

### Q3 — Internal name resolution
Microservices in a VPC need to resolve each other by names like `orders.internal.example.com`. What do you set up?

A. A public Cloud DNS zone for `internal.example.com`.
B. **A Cloud DNS private zone authorized to the VPC, with A records for each service.**
C. `/etc/hosts` files on every VM.
D. Cloud NAT.

**Answer: B.** Private zones are scoped to authorised VPCs and resolve only from inside them. A leaks internal names publicly. C is unmanageable. D is unrelated.

### Q4 — Static IP for an LB
A global external Application Load Balancer needs a stable IPv4 address that you can put in DNS. Which type of address?

A. Ephemeral external IP.
B. **Global external static IPv4 address.**
C. Internal static IP.
D. Anycast IP from your registrar.

**Answer: B.** Global external Application LBs require a global external static address; ephemeral can change on rebuild. C is internal-only. D is unrelated.

### Q5 — Custom static route
You need to send all traffic for `10.100.0.0/16` (on-prem) over a VPN tunnel. The default route to the internet should not be touched. Which is correct?

A. Replace the default route with the VPN tunnel.
B. **Add a custom static route with destination `10.100.0.0/16`, next hop = VPN tunnel.**
C. Add a firewall rule allowing `10.100.0.0/16`.
D. Enable Cloud Router but no static route.

**Answer: B.** Custom static routes target specific destination CIDRs. A breaks general internet access. C is a firewall, not a routing decision. D — Cloud Router would handle it dynamically *if* BGP is configured; if not, you need a static route.

## 8. Hands-on labs

### Lab 1 — Cloud NAT for private VMs + Cloud DNS private zone
**Goal:** create a private subnet, attach Cloud NAT so VMs reach the internet without external IPs, and add a private DNS zone for service discovery.

**Console (subnet + private VM):**
1. *VPC network → VPC networks → prod-vpc → Add subnet*. Name `prod-private-eu`, region `europe-west3`, range `10.40.0.0/20`. Check **Private Google access: On**. *Add*.
2. *Compute Engine → VM instances → Create*. Name `private-vm`, zone `europe-west3-a`, network `prod-vpc`, subnet `prod-private-eu`. Expand **Networking** → **External IPv4 address:** *None*. *Create*.

**Console (Cloud Router + Cloud NAT):**
3. *Hybrid connectivity → Cloud Routers → Create router*. Name `prod-router`, region `europe-west3`, network `prod-vpc`, ASN `65001`. *Create*.
4. *Network services → Cloud NAT → Get started* (or *Create gateway*).
5. **Gateway name:** `prod-nat`. **Network:** `prod-vpc`. **Region:** `europe-west3`. **Cloud Router:** `prod-router`.
6. **Source endpoint type:** *Cloud NAT for VMs*. **Cloud NAT mapping:** *All subnets' primary and secondary ranges*. **NAT IP addresses:** *Automatic*. *Create*.
7. SSH into `private-vm` via IAP and run `curl https://example.com` — should succeed via NAT.

**Console (private DNS zone):**
8. *Network services → Cloud DNS → Create zone*.
9. **Zone type:** Private. **Zone name:** `prod-private`. **DNS name:** `internal.example.com.`. **Networks:** `prod-vpc`. *Create*.
10. Click the zone → **Add record set**. **DNS name:** `db`. **Type:** A. **TTL:** 60. **IPv4:** `10.10.0.50`. *Create*.
11. From `private-vm`: `getent hosts db.internal.example.com` resolves to `10.10.0.50`.

**gcloud:**
```bash
gcloud compute networks subnets create prod-private-eu \
    --network=prod-vpc --region=europe-west3 --range=10.40.0.0/20 \
    --enable-private-ip-google-access
gcloud compute instances create private-vm --zone=europe-west3-a \
    --subnet=prod-private-eu --no-address

gcloud compute routers create prod-router --network=prod-vpc --region=europe-west3 --asn=65001
gcloud compute routers nats create prod-nat \
    --router=prod-router --region=europe-west3 \
    --nat-all-subnet-ip-ranges --auto-allocate-nat-external-ips

gcloud dns managed-zones create prod-private \
    --dns-name=internal.example.com. --visibility=private --networks=prod-vpc \
    --description="internal services"
gcloud dns record-sets create db.internal.example.com. \
    --zone=prod-private --type=A --ttl=60 --rrdatas=10.10.0.50
```

### Lab 2 — Expand a subnet's IP range
**Goal:** grow `prod-eu` from `/20` to `/18` without touching running VMs.

**Console:**
1. *VPC network → VPC networks → prod-vpc → Subnets → prod-eu → Edit*.
2. **IP address range:** change from `10.10.0.0/20` to `10.10.0.0/18`. (The new range must contain the old one.)
3. *Save*. The change is **online** — existing VMs keep their IPs.
4. Verify: *Subnets → prod-eu* shows the new range and a larger pool of usable addresses (`16,381` for `/18`).

**Console (negative test — try to shrink):**
5. *Edit* again, try `/22`. Save fails with "Range can only be expanded" — proving subnets cannot shrink.

**gcloud:**
```bash
gcloud compute networks subnets describe prod-eu --region=europe-west3 \
    --format="value(ipCidrRange)"
gcloud compute networks subnets expand-ip-range prod-eu \
    --region=europe-west3 --prefix-length=18
gcloud compute networks subnets describe prod-eu --region=europe-west3 \
    --format="value(ipCidrRange)"
```

**Note:** if you need to *change* (not grow) a CIDR, the playbook is: create a new subnet, migrate VMs to it (recreate VMs in the new subnet), delete the old one.
