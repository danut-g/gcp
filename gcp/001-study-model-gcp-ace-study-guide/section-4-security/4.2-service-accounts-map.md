# 4.2 -- Visual Map: Managing Service Accounts

---

## 1. What a Service Account Is

```
  ┌──────────────────────────────────────────────────────────────────────┐
  │  SERVICE ACCOUNT (SA)                                                │
  │                                                                      │
  │   - Non-human identity used by workloads                             │
  │   - Belongs to a project                                             │
  │   - Email format: NAME@PROJECT_ID.iam.gserviceaccount.com            │
  │   - Used to authenticate calls to GCP APIs                           │
  │                                                                      │
  └──────────────────────────────────────────────────────────────────────┘
```

### Default SAs You'll See

```
                              ┌── Compute Engine default SA
                              │     PROJECT_NUMBER-compute@developer
                              │     ─► EDITOR by default — REPLACE IT
                              │
                              ├── App Engine default SA
        Default SAs ──────────┤
                              ├── Google APIs Service Agent
                              │     internal Google use
                              │
                              └── Per-service agents
                                    e.g. service-PROJECT_NUMBER@compute-system
```

## 2. The Dual Nature of Service Accounts

```
  ┌──────────────────────────────────────────────────────────────────────┐
  │           A SERVICE ACCOUNT IS BOTH ...                              │
  ├──────────────────────────────────────────────────────────────────────┤
  │                                                                      │
  │   ╔═══════════════════════╗          ╔═══════════════════════╗       │
  │   ║      MEMBER           ║          ║      RESOURCE         ║       │
  │   ║                       ║          ║                       ║       │
  │   ║  SA acts on OTHER     ║          ║  Humans/SAs act ON    ║       │
  │   ║  resources            ║          ║  this SA              ║       │
  │   ║                       ║          ║                       ║       │
  │   ║  e.g.                 ║          ║  e.g.                 ║       │
  │   ║   roles/storage.      ║          ║   roles/iam.          ║       │
  │   ║     objectViewer      ║          ║     serviceAccountUser│       │
  │   ║     ON a bucket       ║          ║     (attach to res)   ║       │
  │   ║                       ║          ║                       ║       │
  │   ║                       ║          ║   roles/iam.          ║       │
  │   ║                       ║          ║     serviceAccount    ║       │
  │   ║                       ║          ║     TokenCreator      ║       │
  │   ║                       ║          ║     (impersonate)     ║       │
  │   ╚═══════════════════════╝          ╚═══════════════════════╝       │
  │                                                                      │
  └──────────────────────────────────────────────────────────────────────┘
```

## 3. Attaching SAs to Resources

```
                            ┌── Compute Engine VM
                            │     gcloud compute instances create
                            │       --service-account=SA_EMAIL
                            │
                            ├── Cloud Run (service or job)
                            │     gcloud run deploy ... --service-account=
        Attach SA to ───────┤
                            ├── Cloud Run functions (gen 2)
                            │     gcloud functions deploy ... --service-account=
                            │
                            └── GKE Pod (via Workload Identity)
                                  K8s SA bound to Google SA


   To attach an SA you need roles/iam.serviceAccountUser ON the SA.
```

## 4. Impersonation (Short-Lived Tokens, No Keys)

```
                                       ┌──────────────────┐
                                       │  Service Account │
                                       │  prod-deploy@... │
                                       └─────────▲────────┘
                                                 │
                                                 │ mints SHORT-LIVED tokens
                                                 │
        ┌────────────────────────────────────────┴─────────────────┐
        │                                                          │
   ┌────┴───────────────┐                                  ┌───────┴─────────┐
   │  user:alice@co.com │ ─── must hold ─────────────────► │ roles/iam.      │
   │                    │     this on the SA               │ serviceAccount  │
   │                    │                                  │ TokenCreator    │
   └────────────────────┘                                  └─────────────────┘

   gcloud --impersonate-service-account=prod-deploy@PROJECT.iam...
   gcloud iam service-accounts get-access-token ... (mint explicitly)


   WHY impersonation > SA keys
   ───────────────────────────
   - No long-lived secret to leak
   - Token expires (1h default)
   - Action audit-logged as the human + the SA
```

## 5. Service Account Keys -- Avoid

```
                                       ┌── Long-lived JSON file
                                       │     contains private key
                                       │
        SA Keys ───────────────────────┤── RISKS
                                       │     - Sprawl (everywhere)
                                       │     - Leaks via Git, logs, laptops
                                       │     - Hard to rotate
                                       │
                                       └── ORG-WIDE LOCK
                                             constraint:
                                             iam.disable
                                               ServiceAccountKeyCreation


   USE A KEY ONLY WHEN ...
   ────────────────────────
   No alternative exists (rare). Even on-prem workloads can usually use
   Workload Identity Federation (WIF) instead of a long-lived key.
```

### Better Alternatives

```
                            ┌── Workload Identity (GKE)         IN GCP
                            │
        Instead of keys ────┤── Attached SA on VM/CR/Function   IN GCP
                            │
                            └── Workload Identity Federation    OUTSIDE GCP
                                  - AWS / Azure / GitHub Actions
                                  - On-prem with OIDC/SAML provider
```

## 6. Workload Identity (GKE)

```
  ┌───────────────────────────────────────────────────────────────────────┐
  │  GKE WORKLOAD IDENTITY                                                │
  ├───────────────────────────────────────────────────────────────────────┤
  │                                                                       │
  │   Step 1: Enable WI on cluster + each node pool                       │
  │   Step 2: Create Google SA (GSA) with the IAM roles your app needs    │
  │   Step 3: Bind a Kubernetes SA (KSA) → GSA                            │
  │   Step 4: Pod uses serviceAccountName: KSA in its spec                │
  │                                                                       │
  └───────────────────────────────────────────────────────────────────────┘

  ┌─────────────────┐                       ┌──────────────────────┐
  │  Kubernetes SA  │   IAM binding         │  Google SA           │
  │   wi-ksa        │   roles/iam.workload  │   sa@PROJECT.iam     │
  │   (in default)  │  ◄─────────────────►  │                      │
  └─────────┬───────┘   IdentityUser        └──────────────────────┘
            │                                          │
            ▼                                          ▼
  ┌───────────────────────────┐         ┌─────────────────────────┐
  │  Pod with                 │         │  Has roles like         │
  │  serviceAccountName: wi-ksa│        │   roles/storage.        │
  │  ─► acts as the GSA        │         │     objectViewer       │
  └───────────────────────────┘         └─────────────────────────┘

  RESULT: pods reach GCS / BigQuery / Pub/Sub WITHOUT any key file.
```

## 7. Decision Quick Picks

```
  ┌──────────────────────────────────────┬──────────────────────────────┐
  │  Task                                │  Action                      │
  ├──────────────────────────────────────┼──────────────────────────────┤
  │  Pod calls BigQuery                  │  Workload Identity binding   │
  │  Human runs as SA temporarily        │  Impersonation, Token Creator│
  │  Attach SA to a new VM               │  Service Account User on SA  │
  │  Block long-lived keys org-wide      │  Org policy:                 │
  │                                      │  iam.disableSAKeyCreation    │
  │  External workload to GCP            │  Workload Identity Federation│
  │  Replace Compute default SA          │  Custom SA on instance       │
  │  Audit who acted as an SA            │  Audit logs (data access on  │
  │                                      │  iam.tokens)                 │
  └──────────────────────────────────────┴──────────────────────────────┘
```

## 8. Section 4.2 Cheat Sheet

```
  ┌──────────────────────────────────────────────────────────────────────────────┐
  │  4.2 QUICK REFERENCE                                                         │
  ├──────────────────────────────────────────────────────────────────────────────┤
  │  SA EMAIL       NAME@PROJECT_ID.iam.gserviceaccount.com                      │
  │  DUAL NATURE    Member (acts ON resources) + Resource (acted ON by humans)   │
  │  ATTACH         Need roles/iam.serviceAccountUser on the SA                  │
  │  IMPERSONATE    Need roles/iam.serviceAccountTokenCreator                    │
  │  DEFAULT GCE SA Editor by default — replace with least-privilege SA          │
  │  KEYS           AVOID; org policy iam.disableServiceAccountKeyCreation       │
  │  ALTERNATIVE    Attached SA in GCP; WIF outside GCP                          │
  │  GKE WI         KSA ↔ GSA binding via roles/iam.workloadIdentityUser         │
  │  GKE WI ENABLE  Cluster + node pool level                                    │
  │  AUDIT          Cloud Audit logs surface impersonation actions               │
  └──────────────────────────────────────────────────────────────────────────────┘
```
