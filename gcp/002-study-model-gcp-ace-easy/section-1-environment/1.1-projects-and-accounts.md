# 1.1 — Setting up cloud projects and accounts (easy version)

> **What the official exam guide calls this:** Section 1.1 — resource hierarchy, organization policies, IAM roles in a project, Cloud Identity users/groups, enabling APIs, Cloud Observability, quotas, standalone organizations, networking, geographic availability, Cloud Asset Inventory, Gemini Cloud Assist.

## 1. Why this matters for the exam

Almost every other topic on the exam **assumes** you already understand:

1. **The resource hierarchy** (organization → folders → projects → resources).
2. **How permissions and rules flow down** that hierarchy.

If you can't answer *"where do I put this rule, and what does it cover?"*, you'll lose points on questions that *look* like Compute or BigQuery questions but are really hierarchy questions in disguise.

Three question patterns the exam loves:

- A diagram of an org / folders / projects, asking **where to apply** a policy.
- A multi-team setup asking which **Cloud Identity** structure (groups vs. users) is most maintainable.
- *"Why does this API call fail?"* — usually because the API isn't enabled, a quota is full, or an org policy blocks it.

## 2. Core concepts

### 2.1 The resource hierarchy

#### The problem it solves

Imagine you work at a company with 200 engineers. Everyone is creating VMs, databases, and storage buckets in the cloud.

- How do you make sure the marketing team's bills don't get mixed up with engineering's?
- How do you stop one wrong click from deleting the production database?
- How do you give the security team read-only access to *everything*, but only allow each product team to touch their own stuff?

The answer is to **organize cloud stuff into a tree**, with rules that flow down. That tree is called the **resource hierarchy**.

#### The tree, in pictures

```
Organization                ← the whole company (mycompany.com)
  └── Folder(s)             ← departments / environments
       └── Project(s)       ← actual containers for resources
            └── Resources   ← VMs, buckets, databases, etc.
```

#### A real-world analogy

| GCP thing | Like a... | What lives there |
|---|---|---|
| **Organization** | Whole company building | All the rules and people |
| **Folder** | A floor or department | Groups of related projects |
| **Project** | A locked office | Actual cloud stuff (resources) |
| **Resource** | The chairs, computers, files | A VM, a bucket, a database |

#### What you have to remember

- **Organization** — the root. There is exactly one per company domain. It's the *only* place where you can set rules that apply to **everything below**.
- **Folders** — optional. You use them to group projects by department, environment (prod / staging / dev), or business unit. Folders can hold other folders, **up to 10 levels deep**.
- **Projects** — every resource lives in **exactly one project**. A project is the unit for billing, API on/off, quotas, and most permissions.
- **Resources** — VMs, buckets, datasets, etc. They inherit settings from their project, on up the tree.

> **Micro-summary:** *Org = root. Folders = optional grouping. Projects = mandatory container for stuff. Everything inherits from above.*

### 2.2 Three project IDs — and why one is "forever"

Every project has **three** identifiers. Don't let this trip you up — the exam will ask.

| Identifier | Can you change it? | Globally unique? | Example |
|---|---|---|---|
| **Project name** | ✅ Yes (just a label) | ❌ No | `My Web App` |
| **Project ID** | ❌ **NEVER** | ✅ Yes | `my-web-app-12345` |
| **Project number** | ❌ No (auto-set) | ✅ Yes | `123456789012` |

**Memory trick:**
- **Name** = your *nickname* (you can change it).
- **ID** = your *social security number* (forever).
- **Number** = a *barcode* the system stuck on you.

> **The thing people get wrong:** "Can I rename a Project ID?" → **No.** If you typo it, your only fix is to create a new project, move resources over, and delete the old one.

### 2.3 What happens when you delete a project

```
ACTIVE  →  DELETE_REQUESTED  →  (30 days pass)  →  gone forever
              │
              └── you can "undelete" within those 30 days and restore it
```

After 30 days, the data is gone for good. The Project ID is released — and even then, it's often never reusable.

> **Micro-summary:** *Delete is reversible for 30 days. Project IDs are forever.*

### 2.4 How rules flow down — the most important rule on the exam

Two kinds of rules flow down the tree. They flow in the same direction but they **combine in opposite ways**. This is the #1 thing that confuses people.

| Rule type | What it controls | How it combines as it flows down |
|---|---|---|
| **IAM policy** | *Who* can do *what* | **UNION** — most permissive wins. Grants stack. |
| **Org policy** | *What is allowed* on resources | **INTERSECTION** — most restrictive wins. Locks tighten. |

#### A grandma analogy that always works

- **IAM** = "If grandma gave you permission, mom can't take it back." (Grants only add up.)
- **Org policy** = "If grandma said no, mom can't say yes." (Restrictions only get tighter.)

#### Two examples to lock this in

- *"I added Editor to a user at the folder level. Can the project below remove it?"*
  - **No.** IAM is *additive only*. Removing it requires removing the binding at the folder.
- *"The org disabled external IPs. Can a single project re-enable them?"*
  - **No.** Org policies *only get tighter* down the tree (unless the constraint explicitly allows overrides).

> **Micro-summary:** *IAM = union (more permissive wins). Org policy = intersection (more restrictive wins).*
>
> If I allow something that is not explicity denied on a superior lvl, the inferior levels can only accept it and if I deny something at a superior level it cannot be allowed at an inferior lvl.

### 2.5 Organization policies — the company-wide guardrails

#### What they are

An org policy is a rule that says *"this kind of thing is not allowed here."* Examples in plain English:

- *"No public buckets anywhere in our company."*
- *"Only EU regions allowed in this folder."*
- *"Nobody can create service-account keys."*

Each rule has a technical name called a **constraint**, e.g.:
- `compute.vmExternalIpAccess` (allow/deny external IPs on VMs)
- `iam.disableServiceAccountKeyCreation` (block service-account key creation)

#### Two flavours of constraint

- **List constraint** — an allow list or deny list of values.
  *"Only allow these regions: europe-west1, europe-west3."*
- **Boolean constraint** — an on/off switch.
  *"External IPs allowed: false."*

#### Where you can set them

You can set a constraint at any level (org / folder / project). Lower levels can:

- **Inherit** from above (default), or
- **Override** (only if the parent allows it), or
- **Merge** with the parent's values.

> **Micro-summary:** *Org policies = company-wide "no" rules. They get tighter as they flow down.*

### 2.6 Cloud Identity — where humans live

#### The single most important distinction

People constantly confuse Cloud Identity with IAM. The exam will test this.

- **Cloud Identity** = the **list of people** (the user directory).
- **IAM** = **what each person is allowed to do** in GCP.

> **Memory trick:** Cloud Identity is the *guest list at the door*. IAM is *what each guest is allowed to do at the party*.

#### Where it lives

You manage Cloud Identity in a **separate UI**: `admin.google.com` (the Admin Console), **not** the GCP console. This is a frequent source of confusion in exam scenarios.

#### Free vs. Premium

- **Cloud Identity Free** — basic users and groups.
- **Cloud Identity Premium** — adds enterprise SSO, mobile device management, advanced security.

#### Best practice: groups, not individual users

Always grant roles to **groups**, never to individual users. Why?

- One person joins the team → add them to a group, done. No new IAM bindings to manage.
- One person leaves → remove from group, done. They lose all their access in one step.
- If you grant 50 individual users on a project, you have 50 bindings to maintain by hand.

#### "Standalone organization" — a piece of exam vocabulary

If a company doesn't use Google Workspace, they can still sign up for **Cloud Identity Free** just to get an organization node. That's called a **standalone organization**.

#### Auto-syncing users from elsewhere

Big companies usually already have a user directory and want to copy it into Cloud Identity:

- **Google Cloud Directory Sync (GCDS)** — for on-prem LDAP / Active Directory.
- **SCIM provisioning** — for external identity providers like Okta or Azure AD.

> **Micro-summary:** *Cloud Identity = the user list. IAM = what they can do. Always grant roles to groups, never individuals.*

### 2.7 Enabling APIs — every service has its own on/off switch

#### The problem

You write a script that talks to BigQuery. It fails with `SERVICE_DISABLED`. What happened?

The BigQuery API isn't enabled in this project. Every Google Cloud service is gated behind an API, and **APIs are turned on per project**.

#### Things to remember

- New projects start with a small default set of APIs enabled.
- Enabling an API may also create a default service account for that service.
- Some APIs require **billing to be enabled** on the project before you can turn them on.
- **You can't enable an API at the org node.** It must be done in each project.

> **Micro-summary:** *APIs are per-project. `SERVICE_DISABLED` error → enable the API in that project.*

### 2.8 Cloud Observability — your eyes and ears

#### What it is

**Cloud Observability** is the umbrella name for the five tools that help you see what's going on:

| Tool | Purpose |
|---|---|
| **Cloud Monitoring** | Metrics and dashboards |
| **Cloud Logging** | Log collection and search |
| **Cloud Trace** | Request latency tracing |
| **Cloud Profiler** | CPU / memory profiling |
| **Error Reporting** | Groups errors automatically |

#### What you need to know for the exam

- Most services give you logs and metrics by default in each project.
- For monitoring, projects send metrics into a thing called a **Metrics Scope**.
- A scope can read from **many projects at once** — that's how you get one dashboard across an entire org.
- The project that hosts a scope is called the **scoping project** — that's the one you log into.

> **Micro-summary:** *Observability = monitoring + logging + tracing + profiling + error reporting. Use a Metrics Scope to see many projects in one place.*

### 2.9 Quotas — speed limits and capacity caps

#### What they are

Quotas are **per-project, per-region** limits on how much of something you can use. There are two types.

| Type | Limits | Example |
|---|---|---|
| **Rate quota** | Requests per minute | API calls per minute |
| **Allocation quota** | Total amount | Number of CPUs in `us-central1` |

#### What happens when you hit a quota

You **request an increase** through the console (or via support). It is **not instant** — Google reviews each request.

> **Exam trap:** A question says *"we need more capacity by tomorrow's launch."* → The right answer involves *requesting the increase now*, not *"just enable it."*

> **Micro-summary:** *Quotas = per-project/per-region limits. Increases must be requested and reviewed by Google.*

### 2.10 Where things live geographically

#### The three tiers

| Tier | Lives where | Example |
|---|---|---|
| **Global** | Outside any region | IAM, Cloud DNS, global load balancers |
| **Regional** | One region, spread across zones | Regional Persistent Disk, regional Cloud Storage |
| **Zonal** | One zone only | Default Compute Engine VM, zonal Persistent Disk |

The official truth about which service is in which region is the **Cloud locations** page: `cloud.google.com/about/locations`.

#### Regions

- A region is a geographic area. Examples:
  - `europe-west3` = Frankfurt
  - `us-central1` = Iowa
  - `asia-southeast1` = Singapore
- 40+ regions worldwide.
- **Each region is isolated** from the others — a region-wide outage doesn't spread.
- How to pick one:
  - **Distance to your users** (latency).
  - **Data-residency rules** (GDPR, sovereignty).
  - **Service availability** (not every product is in every region).
  - **Price** (regions vary by 10–30%).

#### Zones

- A zone is an **independent failure box** inside a region — its own power, cooling, and network.
- Most regions have **3 zones** (a few have 4); they're named like `europe-west3-a`, `-b`, `-c`.
- Think of a zone as one or more data-center rooms.
- Two zones in the same region are roughly *less than 1 ms apart* — close enough for synchronous replication.
- **Zonal resources die with their zone.** Regional resources spread across zones to survive a single zone failure.

#### The single most important deployment rule

> - **2+ zones for HA** (high availability) inside a region.
> - **2+ regions for DR** (disaster recovery) across regions.

#### Multi-region locations

A logical group of regions on a continent: `us`, `eu`, `asia`.

- Cloud Storage multi-region buckets, BigQuery multi-region datasets, and Spanner multi-region configs replicate **automatically** across the regions inside.
- Use them when you want continent-wide availability without managing replication yourself.

#### Edge locations (PoPs)

180+ network edge points where Google connects to ISPs around the world.

- You **don't deploy resources here**. They're just entry/exit points for traffic.
- Used by:
  - **Cloud CDN** — caches content close to users.
  - **Global external Application Load Balancer** — accepts user requests at the nearest edge, then carries them over Google's private fibre to the backend region. That's what **Premium tier** networking buys you.
  - **Cloud Armor** — DDoS / WAF protection at the edge.
  - **Google's private backbone** — the dedicated fibre and submarine cables that link all regions and PoPs.

#### Quick mental map

```
Continent (multi-region: us / eu / asia)
   └── Region (europe-west3 — Frankfurt)
        └── Zone (europe-west3-a, -b, -c)            ← place VMs / zonal disks here
             └── Resources (VMs, PDs, GKE nodes)
   ─── connected by ───
Google's private global backbone
   ─── reaches users via ───
Edge PoPs (180+) ← Cloud CDN, global LB frontends, Cloud Armor
```

> **Exam shortcut:** *Global users + low latency + DDoS protection* = global LB on Premium tier + Cloud CDN + backends in one or more regions.

> **Micro-summary:** *Regions = where resources live. Zones = HA inside a region. Multi-region = continent-wide. Edge = serve users close to them.*

### 2.11 Cloud Asset Inventory — the searchable catalog

#### What it does

A read-only catalog of every resource and IAM policy across your org / folder / project, with a **5-week (35-day) history**. Use it to:

- **Search.** *"Find every public bucket in the org."*
- **Export.** Snapshot to BigQuery or Cloud Storage for an audit.
- **Watch for changes.** Set up a Pub/Sub feed that fires when a resource is created / changed / deleted.

> **Exam trap:** If a question asks *"audit what changed last quarter"* (more than 35 days ago), the answer is **export to BigQuery** — don't look directly in Asset Inventory.

> **Micro-summary:** *Asset Inventory = "what do we have, who can touch it." 35-day history. For longer audits, export to BigQuery.*

### 2.12 Gemini Cloud Assist — the built-in AI helper

A built-in AI assistant in the GCP console. For the exam, just know:

- It exists.

- It uses Cloud Asset Inventory and other signals to answer.

## 3. Decision criteria — when to choose what

| Question | Rule of thumb |
|---|---|
| Where do I apply this policy? | At the **highest node** where it should be true everywhere. At the **lowest node** when only one team needs it. |
| Should I grant this role to a user or a group? | **Always a group**, except for emergency "break-glass" identities. |
| Folders by environment or by team? | Most companies do **team / business unit at the top**, then **environment underneath**. Either works — just be consistent. |
| Do I need an organization node? | Yes for any non-trivial setup. It's required for org policies, central IAM, and folders. Standalone Cloud Identity gets you one for free. |
| Quota request or design change? | Hit it occasionally → request increase. Hit it constantly → architecture is wrong (split projects, switch regions, redesign). |

## 5. gcloud reference — the small CLI cheat sheet

Pattern: `gcloud <service> <verb>`. If you understand the concept, the command is usually obvious.

```bash
# Hierarchy
gcloud organizations list
gcloud resource-manager folders list --organization=ORG_ID
gcloud resource-manager folders create --display-name="prod" --organization=ORG_ID

gcloud projects list
gcloud projects create my-project-id --name="My Project" --folder=FOLDER_ID
gcloud projects describe PROJECT_ID
gcloud projects delete PROJECT_ID
gcloud projects undelete PROJECT_ID            # within the 30-day window

# Active context
gcloud config set project PROJECT_ID
gcloud config list

# IAM at any level (same verb pattern, different parent flag)
gcloud projects       add-iam-policy-binding PROJECT_ID \
    --member=user:alice@example.com --role=roles/viewer
gcloud resource-manager folders add-iam-policy-binding FOLDER_ID \
    --member=group:devs@example.com --role=roles/editor
gcloud organizations  add-iam-policy-binding ORG_ID \
    --member=user:cto@example.com --role=roles/resourcemanager.organizationAdmin

# Organization policies
gcloud resource-manager org-policies list --project=PROJECT_ID
gcloud resource-manager org-policies set-policy POLICY.yaml --project=PROJECT_ID

# APIs
gcloud services list --available
gcloud services list --enabled
gcloud services enable compute.googleapis.com
gcloud services disable compute.googleapis.com

# Quotas (read-only via CLI; increases are requested in the console)
gcloud compute regions describe us-central1   # shows quotas + usage

# Asset Inventory
gcloud asset search-all-resources --scope=organizations/ORG_ID --query="state:ACTIVE"
gcloud asset search-all-iam-policies --scope=projects/PROJECT_ID --query="policy:roles/owner"
```

The CLI mirrors the console: every console screen has a `gcloud` equivalent. Once you spot the pattern (`gcloud <thing> list / describe / create / delete`), you can guess most commands.

## 6. Common confusions — the things people mix up

These are the traps the exam will set for you. Re-read this section the night before.

### "IAM" vs "Cloud Identity"

- **Cloud Identity** = the *list of people*. Lives in `admin.google.com`.
- **IAM** = *what those people are allowed to do*. Lives in GCP console.

Editing a Cloud Identity group does **not** require IAM. But you reference the group as `group:devs@example.com` in any IAM binding.

### "IAM = union" vs "Org policy = intersection"

- **IAM**: more permissive wins. A folder grant **adds**; a project can't remove it.
- **Org policy**: more restrictive wins. An org-level deny **locks**; a project can't unlock it (unless overrides allowed).

### "Project ID" vs "Project name" vs "Project number"

- **Name** is mutable, not unique. (Just a label.)
- **ID** is **immutable**, globally unique. (Forever.)
- **Number** is auto-assigned, globally unique.

### "API enabled" vs "permission granted"

- An API call can fail two main ways:
  - The **API is disabled** in this project → enable it in *APIs & Services*.
  - You **lack the IAM permission** → ask an admin for the right role.
- These look similar in error messages but have different fixes.

### "Folders are optional" vs "projects are mandatory"

- You don't *need* folders, but every resource must live in a project.

### "Asset Inventory history = 35 days only"

- For audits older than 5 weeks, you must have *exported* to BigQuery beforehand.

## 7. Exam gotchas — the subtle traps

- **Project ID is forever.** It can't be renamed. It stays reserved for ~30 days after deletion before it can be reused (and even then, sometimes never).
- **IAM = union, org policy = intersection.** The single most common confusion.
- **Cloud Identity ≠ IAM.** Cloud Identity is the user directory. IAM is what users can do.
- **APIs are per-project, not per-organization.** Each project must have it enabled.
- **Quota increases are not instant.** They go through Google support.
- **Standalone organization** = Cloud Identity Free tenant just to get an org node, no Workspace.
- **Folders are optional. Projects are mandatory.**
- **Editing a Cloud Identity group does NOT require IAM** — happens in the Admin Console.
- **Asset Inventory history is 35 days.** Older audits → export to BigQuery.

## 8. Named scenarios — deeper design walk-throughs

These are the kind of design questions the exam asks, told as little stories.

### Scenario A — Designing for compliance and availability

**Context.** A European fintech is moving its first workload to GCP. Three constraints:
1. All customer data must stay inside the EU (GDPR Article 44).
2. The service must survive a single data-centre fire with **≤ 1 minute downtime**.
3. A single Frankfurt region is fine for now, but the company plans an EU-wide product within 12 months.

**Recommended design.**
- **Region:** start in `europe-west3` (Frankfurt). Confirm chosen services (Cloud SQL, Cloud Run, Cloud Storage) are listed for that region on `cloud.google.com/about/locations`.
- **Zonal redundancy:** every stateful service gets multi-zone replication inside the region:
  - Cloud SQL with `--availability-type=REGIONAL` (synchronous standby in another zone).
  - Regional Managed Instance Group spread across `-a`, `-b`, `-c`.
  - Regional Persistent Disks for self-managed databases.
- **Storage bucket:** dual-region `eu-west3 + eu-west4` for documents — keeps data inside the EU while surviving a region-level outage.
- **Org-policy guardrail:** at the org node, set `gcp.resourceLocations` to `in:eu-locations` so no engineer can accidentally deploy in `us-*` or `asia-*`. This is enforced **above** IAM — even Owners can't bypass it.
- **Future-proofing:** when expanding EU-wide, migrate to a multi-region Cloud Storage `EU` location, a Spanner EU multi-region instance, and a global external Application Load Balancer (Premium tier) fronting backends in two EU regions.

**Why this works.** *Zones for HA → regions for DR → multi-region for global availability* maps directly to the three constraints. The org-policy lock is the single durable artefact that prevents one wrong gcloud command from breaking compliance.

### Scenario B — Hierarchy & guardrails

**Context.** A 200-person engineering org has 12 product teams, each with three environments (dev / staging / prod). New teams arrive every quarter. Security wants:
1. The same org policies applied to every prod project automatically.
2. Data-platform team: read-only across everything. Each product team: only their own projects.
3. Only SecOps can create new billing accounts.

**Recommended design.**
- **Folder layout:**
  ```
  Organization
    ├── prod/
    │     ├── team-checkout/
    │     ├── team-search/        (≈12 product folders)
    │     └── …
    ├── nonprod/
    │     └── (same shape)
    └── shared/
          └── security/, networking/, billing-ops/
  ```
  Two top-level folders (`prod` / `nonprod`) make it trivial to apply prod-only org policies (deny external IPs, lock CMEK, require VPC-SC). Every project beneath inherits them. New teams = new folders, never new policies.
- **IAM grants:**
  - `data-platform@` → `roles/viewer` at the **org** node (universal read).
  - `team-checkout@` → predefined per-service roles (`roles/run.admin`, `roles/cloudsql.editor`, …) at the `team-checkout` folder (covers all three of their envs).
  - SecOps → `roles/billing.creator` at the org; everyone else: nothing on billing.
- **Quota & API guardrails:** enable required APIs once at project-template time (a Terraform module under `prod/team-*`); each team can request additional APIs via PR.

**Why this works.** Two principles do most of the work: **apply IAM at the highest node where the rule is universally true**, and **let the folder structure mirror the policy structure**. Adding a 13th team is a single folder + a single IAM binding — no per-project copy-paste.

## 9. Practice scenarios — try these before reading the answers

### Q1 — Hierarchy and inheritance
Your company has the resource hierarchy: Organization → "Engineering" folder → 5 production projects. The security team must have *Viewer* across every Engineering project, with the **minimum number of bindings**. Where do you grant the role?

A. Grant `roles/viewer` to the security group on every project individually.
B. Grant `roles/viewer` to the security group on the Engineering folder.
C. Grant `roles/viewer` to the security group on the organization.
D. Add each security team member individually to each project as Viewer.

**Answer: B.** A folder-level binding is inherited by every child project — one binding covers all five. Granting at the org node (C) over-scopes. A and D violate "minimum bindings" and "groups over users".

### Q2 — Project ID
You created project `proj-prod-2024` and accidentally typed it instead of `proj-prod-app`. You want to rename the Project ID. What's the correct action?

A. Use `gcloud projects update --new-id=proj-prod-app`.
B. Edit the project in the console under *Project Settings*.
C. Create a new project with the desired ID; migrate resources; delete the old one.
D. Rename the Project Name; the Project ID will follow.

**Answer: C.** Project IDs are **immutable**. There is no rename feature. Project Name (D) is mutable but unrelated to the ID. A and B don't exist.

### Q3 — IAM vs. org policy
A user with `roles/owner` on a project complains they cannot create a VM with an external IP. Which is the most likely cause?

A. The Compute Engine API is disabled.
B. An organization policy `compute.vmExternalIpAccess` is restricting external IPs.
C. The user is missing `roles/compute.networkAdmin`.
D. Quota for external IPs is exhausted.

**Answer: B.** Owner cannot bypass an org policy. IAM (C) is moot since Owner already has all permissions. A would block any VM creation, not just external IP. D would surface a quota error.

### Q4 — Cloud Identity and groups
A new engineering group of 12 people needs *Editor* on a development project. What is the recommended approach?

A. Add each user as Editor on the project.
B. Create a Google Group, add users to it, and bind the group to `roles/editor` on the project.
C. Use the default service account to act on their behalf.
D. Add `allAuthenticatedUsers` as Editor.

**Answer: B.** Always grant roles to groups. D (`allAuthenticatedUsers`) makes the project accessible to *every* Google account on the internet — disastrous.

### Q5 — Asset Inventory
Compliance asks you to produce a list of every Cloud Storage bucket in the entire organization that is publicly accessible. The fastest single action is:

A. Run `gcloud storage buckets list` in every project.
B. Use Cloud Asset Inventory to search all IAM policies in the org for bindings of `allUsers` on storage resources.
C. Enable Data Access audit logs for Cloud Storage and review them.
D. Open each project's Cloud Storage page in the console and inspect bucket permissions.

**Answer: B.** Asset Inventory's `search-all-iam-policies` answers org-wide questions in one call. C is for *who accessed what*. A and D are unscalable.

## 10. Hands-on labs

Console steps first, gcloud at the end of each lab.

### Lab 1 — Console tour: orient yourself

**Goal:** Recognize every place referenced in the rest of the guide.

1. Sign in at `console.cloud.google.com`.
2. **Top bar (left):** the **Project picker** — click it to switch project / org / folder context. Pin frequent projects with the star icon.
3. **Top bar (right):** the **Cloud Shell** icon (`>_`) opens a free Linux shell with `gcloud`, `kubectl`, `terraform` pre-installed. **Notifications**, **Help**, and **Avatar** icons are next to it.
4. **Hamburger menu (☰)** at top-left: the navigation menu. Pin your top services by hovering and clicking the pin.
5. The **search bar** in the top center is the fastest way to jump anywhere.
6. Settings live under the **avatar** in the top-right.

### Lab 2 — Check service availability by region

**Goal:** Confirm a product is offered in a region before designing for it.

1. Open `cloud.google.com/about/locations` (the source of truth).
2. Find your target region (e.g. `europe-west3 — Frankfurt`).
3. Cross-reference the service: search for "BigQuery", "Spanner", "Cloud Run", etc.
4. In the console: when creating any resource, the region/zone dropdowns only show valid options for that service — a quick sanity check.

### Lab 3 — Three ways to interact with GCP

**Console:** the GUI at `console.cloud.google.com`.

**Cloud Shell** (no install):
1. Click the `>_` icon in the top bar.
2. A terminal opens with you already authenticated. First launch creates a 5 GB persistent home dir.
3. Try `gcloud projects list`, `gcloud auth list`, `gcloud config list`.
4. Cloud Shell **Editor** opens a VS Code-like editor in the same panel.

**Local gcloud SDK:**
1. Install: `brew install --cask google-cloud-sdk` on macOS, or download from `cloud.google.com/sdk/docs/install`.
2. Authenticate: `gcloud auth login` (opens a browser).
3. Set defaults: `gcloud config set project PROJECT_ID`, `gcloud config set compute/region europe-west3`.
4. Sanity check: `gcloud projects list`.

### Lab 4 — Create and manage projects

**Console:**

### Lab 5 — Apply an organization policy

**Goal:** Restrict external IPs at the organization level.

**Console:**
1. Switch the project picker to the **organization** scope.
2. *IAM & Admin → Organization policies*.
3. Search for `compute.vmExternalIpAccess`.
4. Click the policy → **Manage policy**.
5. Set **Policy enforcement** to *Replace*.
6. Choose **Deny all** (or define an allow list).
7. **Save**. Inheritance now blocks external-IP VM creation in every project under the org.

**gcloud:**
```bash
gcloud resource-manager org-policies set-policy policy.yaml --organization=ORG_ID
# policy.yaml:
# constraint: constraints/compute.vmExternalIpAccess
# listPolicy:
#   allValues: DENY
```

### Lab 6 — Enable APIs in a project

**Console:**

4. Click → **Enable**.
5. To audit: *APIs & Services → Enabled APIs & services*.
6. Disable: same screen → click → **Disable API** (careful — breaks running workloads).

### Lab 7 — Create a user and a group in Cloud Identity

**In `admin.google.com`:**
1. Sign in with a Cloud Identity admin account.
2. *Directory → Users → Add new user*. Fill name, primary email, set a temporary password. **Add new user**.
3. *Directory → Groups → Create group*. Name, email (`devs@example.com`), description. Save.
4. Open the group → **Members → Add members** → add the user.

**Then in GCP:**
1. *IAM & Admin → IAM → Grant access*.
2. **New principals:** `devs@example.com`. **Role:** `roles/viewer`.
3. **Save**. The user inherits via group membership.

**gcloud:**
```bash
gcloud projects add-iam-policy-binding PROJECT_ID \
    --member=group:devs@example.com --role=roles/viewer
```

### Lab 8 — Day-to-day Cloud Identity management

In `admin.google.com`:
- **Add to a group:** *Groups → (group) → Members → Add members*.
- **Remove:** same page → tick member → **Remove members**.
- **Suspend a user:** *Users → (user) → More options → Suspend user*. Keeps data; can't sign in. Reverse with **Reactivate**.
- **Reset password:** *Users → (user) → Reset password*. Force change on next sign-in.
- **Bulk:** *Users → Bulk update users* (CSV upload).

For automation across many users:
- **Google Cloud Directory Sync (GCDS)** — for on-prem LDAP / Active Directory.
- **SCIM provisioning** — for Okta / Azure AD.

### Lab 9 — Discover resources with Cloud Asset Inventory & Gemini

**Console (Asset Inventory):**
1. *IAM & Admin → Asset Inventory*.
2. Tabs: **Resource**, **IAM Policy**, **Org Policy**, **Access Policy**, **Resource search**.
3. In **Resource search**, try `name:web-* AND state:ACTIVE`.
4. **Export** → Cloud Storage or BigQuery (for audits).
5. **Feeds** → create a Pub/Sub feed for change notifications.

**Gemini Cloud Assist:**
1. Click the spark icon (★) at the top of any console page.
2. Ask: *"Show me the buckets in this project that are publicly accessible."*
3. The assistant summarizes and provides deep links.

**gcloud:**
```bash
gcloud asset search-all-resources --scope=organizations/ORG_ID --query="state:ACTIVE"
gcloud asset search-all-iam-policies --scope=projects/PROJECT_ID --query="policy:roles/owner"
gcloud asset feeds create my-feed --organization=ORG_ID \
    --asset-types=storage.googleapis.com/Bucket --content-type=resource \
    --pubsub-topic=projects/PROJECT_ID/topics/asset-feed
```

## 11. TL;DR — what to remember if you only have 5 minutes before the exam

1. **Hierarchy:** Organization → Folder(s) → Project(s) → Resources. Folders optional, projects mandatory.
2. **Project ID is forever** (immutable). Project Name is just a label.
3. **IAM = union (most permissive wins). Org policy = intersection (most restrictive wins).**
4. **Cloud Identity = the user list. IAM = what they can do.** Don't confuse them.
5. **APIs are per-project** — enable in each one.
6. **Quota increases are not instant** — request through Google.
7. **Zones for HA inside a region. Regions for DR across regions. Multi-region for continent-wide.**
8. **Asset Inventory = 35-day history.** For older audits, export to BigQuery.
9. **Always grant roles to groups, not individuals.**
10. **Standalone organization** = Cloud Identity Free, no Workspace.
