# 1.2 — Managing billing configuration (easy version)

> **What the official exam guide calls this:** Section 1.2 — creating billing accounts, linking projects to a billing account, billing budgets and alerts, billing exports.

---

## 1. Why this matters for the exam

Billing questions on the exam are **not about cost engineering** — they are about **structure and control**:

- *Who pays?*
- *How are costs visible?*
- *How do you stop surprises?*

You need to know:
- The difference between a billing account and a project.
- What permissions are needed to link them.
- How to set up alerts and exports so an organization can monitor spend.

Question patterns to expect:

- A new project was created and no resources can be provisioned. Why? → Billing not linked, or the linker didn't have permission.
- A team needs to know when they reach 50% of their monthly budget. → Budget alert via Pub/Sub or email.
- Finance wants every line item from every project in BigQuery for analysis. → Billing export to BigQuery.

## 2. Core concepts

### 2.1 Billing accounts vs. projects

#### The problem this solves

Imagine your company has 30 projects in GCP. Some are run by the engineering team, some by marketing, some are internal R&D experiments. **Who pays for what?** And how do you change who pays without rebuilding everything?

The answer: a **billing account** holds the payment method. **Projects** consume resources. You **link** projects to billing accounts, and you can change the link later.

#### How they relate

- **Billing account** = where the credit card lives. Pays the bill.
- **Project** = where resources live. Generates the bill.
- A project must be linked to a billing account, or it cannot use paid services.

```
Billing Account (credit card)
   ├── Project A   ← uses VMs, BigQuery, etc. → charges flow up
   ├── Project B
   └── Project C
```

Key rules:

- One billing account can pay for **many projects**.
- A project is linked to **exactly one** billing account at a time. (You can switch it, but not split it.)
- Billing accounts live **outside** the project hierarchy. They have their own permissions surface, separate from project IAM.
- Billing accounts can be **owned** by an organization (so they're managed centrally).

#### Two kinds of billing accounts

| Type | Who pays | How you create it |
|---|---|---|
| **Self-serve** (online) | Credit card on file | Sign up at `console.cloud.google.com` |
| **Invoiced** | Monthly invoice from Google | Negotiated with Google sales (common for big companies) |

> **Micro-summary:** *Billing account = the wallet. Project = where stuff runs. One wallet pays many projects. Each project has only one wallet at a time.*

### 2.2 Billing IAM roles

#### Why a separate set of roles?

Because billing accounts live outside the project hierarchy, project Owner does **not** automatically give you billing powers. You need separate roles on the billing account.

#### The roles you need to know

| Role | What it lets you do |
|---|---|
| **Billing Account Creator** (org-level) | Create new billing accounts under the org |
| **Billing Account Administrator** | Manage everything: payment methods, users, link/unlink projects |
| **Billing Account User** | Link projects to **this** billing account (but cannot manage it) |
| **Billing Account Viewer** | See charges and reports |
| **Project Billing Manager** (project-level) | Attach/detach a billing account from a single project |

#### The classic exam scenario

> *"To link a new project to an existing billing account, what's the minimum role combination?"*

**Answer:** **Billing Account User** on the billing account **PLUS** **Project Billing Manager** on the project.

Why two roles? Because linking is a cross-resource action — you need permission on **both sides** (the billing account *and* the project).

> **Micro-summary:** *Linking project ↔ billing account requires two roles: Billing Account User (on the billing account) + Project Billing Manager (on the project).*

### 2.3 Budgets and alerts

#### The most important thing to know

> **A budget does NOT stop spending. It only sends an alert.**

This is the #1 trap on exam questions about budgets. Read it again. It does *not* shut anything off automatically.

#### What a budget actually is

- A monitoring tool that watches spending and sends notifications.
- Targets a **billing account**, optionally narrowed to specific projects, services, or labels.
- Has **thresholds** (percentages of the budget amount). Defaults are 50%, 90%, 100% — but you set them.

#### Where alerts can go

- **Email** — to billing admins / users.
- **Pub/Sub topic** — for programmatic action. (This is how you build automation.)

#### How to actually cap spending

The supported "auto-shutoff" pattern:

```
Budget threshold crossed
   → Pub/Sub message
      → Cloud Function listens
         → calls Billing API to disable billing on the project
            → resources stop running
```

#### Two amount styles

- **Specified amount** — flat dollar number (e.g., $1,000/month).
- **Last month's spend** — a rolling target that adjusts each month.

> **Micro-summary:** *Budgets ALERT, they don't CAP. To actually cap, build a Pub/Sub → Cloud Function automation that disables billing.*

### 2.4 Billing exports

#### Why you need them

The billing console gives you nice reports, but for **deep analysis** (e.g., joining cost data with internal team data, building custom dashboards) you need the raw data. **Exports** stream every line item out to BigQuery or Cloud Storage.

#### Two destinations

| Destination | Best for |
|---|---|
| **BigQuery** | Detailed cost analytics, custom dashboards, joining with internal data |
| **Cloud Storage** | Long-term archive, compliance retention |

You can do both at once.

#### Three BigQuery export schemas

| Schema | Granularity | Cost |
|---|---|---|
| **Standard usage cost** | Per-SKU charges (the everyday format) | Cheaper to store |
| **Detailed usage cost** | Adds **per-resource** detail (e.g. per-VM costs) | Larger and more expensive |
| **Pricing data** | The price list itself, not your usage | Useful for "what-if" cost modelling |

Choose **Detailed** only when you genuinely need per-VM attribution; otherwise **Standard** is enough.

> **Micro-summary:** *Exports = stream every line item to BigQuery (analysis) or Cloud Storage (archive). Standard = per-SKU. Detailed = per-resource.*

### 2.5 Cost reports and the billing console

These are built-in tools you should know exist.

| Tool | What it does |
|---|---|
| **Reports** | Interactive cost breakdown by project, service, SKU, region, label, time range |
| **Cost table** | Flat table view, exportable as CSV |
| **Cost breakdown** | Separates list price, discounts, credits, taxes |
| **Pricing calculator** | Estimates costs *before* you provision (`cloud.google.com/products/calculator`) |

> **Memory trick:** *Reports = past actuals. Calculator = future estimates. The exam likes to mix these up.*

### 2.6 Labels and cost allocation

#### The problem

You have one big project shared across teams. The bill says "$5,000 on VMs." How do you split that bill back to teams?

#### The answer: labels

**Labels** are simple key/value pairs you attach to resources (and to projects). Examples:

- `team:checkout`
- `env:prod`
- `cost-center:engineering`

Labels are **the standard mechanism for chargeback/showback**. The billing export carries them through — so you can group costs in BigQuery by team, environment, etc.

#### Don't confuse labels with tags

> **Important:** *Labels* (used for billing/organization) and *tags* (used for IAM and firewall rules) are different things in GCP. The exam will try to mix them up.

| Concept | Use case | Propagates to billing? |
|---|---|---|
| **Labels** | Cost allocation, organization | ✅ Yes |
| **Tags** | IAM bindings, firewall rules | ❌ No |

> **Micro-summary:** *Labels = key/value pairs for cost allocation. They propagate to billing exports. Tags do NOT propagate to billing.*

## 3. Decision criteria — when to choose what

| Question | Rule of thumb |
|---|---|
| One billing account or many? | One per **legal entity / cost centre**. Multiple accounts are rarely necessary; multiple projects under one account is the norm. |
| How do I cap spending? | You don't, directly. Use a budget alert + Pub/Sub + Cloud Function that disables billing on the project. |
| BigQuery or Cloud Storage export? | BigQuery for analysis, Cloud Storage for archive. You can do both. |
| Standard or detailed export? | Standard for most teams. Detailed only if you need per-resource attribution. |
| Per-team chargeback — labels or projects? | Projects = cleanest boundary. Labels work when one project is shared across teams. |

## 5. gcloud reference

Most billing operations are console-driven, but the CLI covers the essentials.

```bash
# List billing accounts you can see
gcloud billing accounts list

# Describe a billing account
gcloud billing accounts describe BILLING_ACCOUNT_ID

# Link / unlink a project
gcloud billing projects link    PROJECT_ID --billing-account=BILLING_ACCOUNT_ID
gcloud billing projects unlink  PROJECT_ID

# Show which billing account a project uses
gcloud billing projects describe PROJECT_ID

# Budgets (Cloud Billing Budgets API — the gcloud verbs live under `billing budgets`)
gcloud billing budgets list   --billing-account=BILLING_ACCOUNT_ID
gcloud billing budgets create --billing-account=BILLING_ACCOUNT_ID \
    --display-name="monthly-prod" --budget-amount=1000USD \
    --threshold-rule=percent=0.5 --threshold-rule=percent=0.9 --threshold-rule=percent=1.0
```

> **Important exam fact:** *Billing exports are ONLY configurable in the console, not via gcloud.*

## 6. Common confusions — the things people mix up

### "Budget" vs "Quota"

- **Budget** = a *cost* alert (in dollars).
- **Quota** = a *resource count* limit (e.g., max VMs in a region).
- Budgets don't stop spending. Quotas can stop creation.

### "Labels" vs "Tags"

- **Labels** = key/value pairs for cost & organization. **Propagate to billing.**
- **Tags** = used in IAM and firewall rules. **Do NOT propagate to billing.**

### "Disable billing" vs "Delete project"

- **Disable billing**: project stays, resources stop running. Reversible.
- **Delete project**: starts the 30-day deletion clock. Recoverable for 30 days, then gone.

### "Pricing Calculator" vs "Cost Reports"

- **Calculator** = forecasts *future* costs (before you build).
- **Reports** = shows *actual* past costs (after you ran).

## 7. Exam gotchas — the subtle traps

- **A budget does NOT stop spending.** It only alerts. Auto-shutoff requires Pub/Sub + Cloud Function.
- **Two roles are needed to link a project to a billing account:** Billing Account User on the billing side + Project Billing Manager on the project side.
- **A project links to ONE billing account at a time.** Switching is allowed; splitting between two is not.
- **Billing accounts are NOT inside the resource hierarchy.** Org IAM doesn't automatically grant billing roles.
- **Disabling billing** on a project doesn't delete it; resources stop running but the project still exists.
- **Labels propagate to billing exports.** **Tags do not.**
- **Exports are forward-only.** Turning on a BigQuery export today does not back-populate historical data.
- **Pricing calculator** = forecast; **Cost reports** = actuals. The exam likes to mix these up.

## 8. Practice scenarios

### Q1 — Linking a project to a billing account

A new engineer was given `roles/owner` on a project. They cannot link the project to the company's existing billing account. What additional role is required and where?

A. `roles/billing.user` on the project.
B. `roles/billing.user` on the billing account, plus `roles/billing.projectManager` on the project.
C. `roles/billing.admin` on the organization.
D. Owner is sufficient — there must be a billing account problem.

**Answer: B.** Linking a project to a billing account is an explicitly cross-resource action: the user needs **Billing Account User** on the billing account *and* **Project Billing Manager** on the project. Owner does not include billing-account-side permissions because billing accounts live outside the project hierarchy.

### Q2 — Capping spend

Management says *"we cannot exceed $10,000 per month on this project under any circumstances."* Which configuration delivers this?

A. Set a budget of $10,000 with a 100% threshold email alert.
B. Set a budget of $10,000 and configure a Pub/Sub notification that triggers a Cloud Function which disables billing on the project.
C. Set a quota on the project.
D. Use a billing alert with SMS notification.

**Answer: B.** Budgets in GCP **never cap spending automatically** — they only alert. The supported pattern for hard cutoff is budget → Pub/Sub → Cloud Function that disables billing. A and D notify but don't stop spend. C confuses quotas (resource counts) with cost.

### Q3 — Detailed cost analysis

The finance team wants to attribute costs at the level of individual virtual machines, by team. What's the correct configuration?

A. Enable BigQuery export with the Standard usage cost schema and group by project.
B. Enable BigQuery export with the **Detailed usage cost** schema and use **labels** like `team:checkout`.
C. Use the Pricing Calculator to estimate per-VM costs.
D. Export billing to Cloud Storage and parse the CSVs in a spreadsheet.

**Answer: B.** Detailed usage cost gives per-resource granularity; labels propagate into the export and provide the team-level grouping. A's standard schema doesn't reach per-VM granularity. C forecasts, not actuals. D would work in theory but is far more cumbersome than BigQuery.

### Q4 — Multi-team billing

A startup wants one billing account but needs each team's costs separated for chargeback. What's the recommended structure?

A. One billing account, one project per team, billing export to BigQuery.
B. One billing account per team.
C. One project, multiple billing accounts (one per team).
D. Apply tags to resources by team.

**Answer: A.** Projects are the cleanest cost boundary; billing export already breaks costs out by project. B is unnecessary overhead. C is impossible (project ↔ one billing account). D *tags* are an IAM/firewall concept and do not propagate to billing exports — **labels** do.

### Q5 — Budget alert recipients

A budget reaches 90%; you want the alert to go to the cost-engineering team via Slack. What is required?

A. Configure email recipients on the budget.
B. Configure a Pub/Sub topic on the budget; subscribe a Cloud Function that posts to Slack.
C. Use the Slack-native budget integration in the GCP console.
D. Export billing to BigQuery and run a scheduled query that posts to Slack.

**Answer: B.** Budgets support email and Pub/Sub. There is no first-party Slack integration; the standard pattern is Pub/Sub → Cloud Function → Slack webhook. A only emails billing admins/users. D is far more roundabout.

## 9. Hands-on labs

### Lab 1 — Verify and manage project billing

**Goal:** See which billing account a project uses, and link/unlink projects.

**Console:**
1. Confirm the project context (top bar).
2. *Navigation menu → Billing*.
3. If the project has no billing account, click **Link a billing account** → pick the account → **Set account**.
4. To unlink: *Billing → Account management → Manage billing account → Disable billing*. Resources stop running but the project still exists.
5. To switch the linked billing account: *Billing → Account management → Change billing account*.

To see all projects under one billing account:
1. Switch the billing context (top bar) to the billing account.
2. *Account management → Projects*. Lists name, ID, and link state.

**gcloud:**
```bash
gcloud billing projects describe PROJECT_ID
gcloud billing projects link   PROJECT_ID --billing-account=BILLING_ACCOUNT_ID
gcloud billing projects unlink PROJECT_ID
gcloud billing accounts list
```

### Lab 2 — Create a budget with thresholds and Pub/Sub alerting

**Goal:** Get alerts at 50/90/100% with Pub/Sub for programmatic action.

**Console:**
1. *Billing → (billing account) → Budgets & alerts → Create budget*.
2. **Scope:** select project(s) / service(s) / label(s). Default = whole account.
3. **Amount:** *Specified amount* `$1,000` (or *Last month's spend* for a rolling target).
4. **Thresholds:** form pre-fills 50/90/100% — adjust as needed.
5. **Notifications:**
   - Tick **Email alerts to billing admins and users**.
   - For Pub/Sub: tick **Connect a Pub/Sub topic** → pick or create one (e.g., `billing-alerts`).
6. **Finish**.

To turn that Pub/Sub topic into automatic billing-disable, deploy a Cloud Function with a Pub/Sub trigger that calls the Cloud Billing API to unlink the project.

**gcloud:**
```bash
gcloud billing budgets create \
    --billing-account=BILLING_ACCOUNT_ID \
    --display-name="prod-monthly" \
    --budget-amount=1000USD \
    --threshold-rule=percent=0.5 \
    --threshold-rule=percent=0.9 \
    --threshold-rule=percent=1.0 \
    --notifications-rule-pubsub-topic=projects/PROJECT_ID/topics/billing-alerts

gcloud billing budgets list   --billing-account=BILLING_ACCOUNT_ID
gcloud billing budgets describe BUDGET_ID --billing-account=BILLING_ACCOUNT_ID
gcloud billing budgets delete   BUDGET_ID --billing-account=BILLING_ACCOUNT_ID
```

### Lab 3 — Enable billing export to BigQuery

**Goal:** Stream every line item to a BigQuery dataset for analysis.

**Console only — exports are NOT configurable via gcloud:**
1. Create the destination dataset first: *BigQuery → (project) → Create dataset*. Pick a multi-region (`EU` or `US`); friendly ID like `billing_export`.
2. Switch context to the **billing account** (top bar).
3. *Billing → Billing export*.
4. Tabs: **BigQuery export** (Standard / Detailed / Pricing data).
5. **Edit settings** on *Standard usage cost*.
6. Choose the project and dataset.
7. **Save**. Future usage flows in (no historical backfill).

> **Tip:** Enable both Standard and Detailed if you need per-resource cost — they go into separate tables (`gcp_billing_export_v1_*` and `gcp_billing_export_resource_v1_*`).

### Lab cleanup
- Budgets are free to keep.
- BigQuery export datasets store data and incur storage costs — delete the dataset if you stop the export and want to clean up.

## 10. TL;DR — what to remember if you only have 5 minutes before the exam

1. **Billing account = the wallet.** Project = where resources run.
2. **One billing account → many projects. One project → one billing account.**
3. **Link requires TWO roles:** Billing Account User on the account + Project Billing Manager on the project.
4. **Budgets ALERT, they don't CAP.** Auto-shutoff = Pub/Sub → Cloud Function.
5. **Exports are forward-only.** No historical backfill.
6. **Standard export** = per-SKU. **Detailed export** = per-resource. Both go to BigQuery / Cloud Storage.
7. **Labels propagate to billing. Tags do NOT.**
8. **Pricing Calculator** = forecast. **Reports** = actuals.
9. **Disabling billing ≠ deleting project.** Resources stop, project remains.
10. **Billing exports are console-only.** No gcloud configuration.
