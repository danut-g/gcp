# 1.3 — Cloud SDK and Cloud Shell (easy version)

> **What the official exam guide calls this:** Section 1 — installing and configuring the command line interface (CLI), in particular the Cloud SDK (e.g., setting the default project), using Cloud Shell, and managing `gcloud` configurations.

---

## 1. Why this matters for the exam

The exam will **not** ask you to type commands from memory. But it *will*:

1. Show you a `gcloud` command and ask **what it does** or **why it fails**.
2. Describe a situation ("a developer needs to manage two projects from one laptop") and ask **which gcloud feature** solves it — the answer is usually *configurations*.
3. Test whether you know **what Cloud Shell gives you for free** (and what its limits are).
4. Test the difference between **your credentials** and a **service account's credentials** on the same machine.

If you understand the *shape* of `gcloud` commands and the handful of `config` / `auth` / `components` subcommands, you can decode any command the exam throws at you — even ones you've never seen.

---

## 2. Plain-English intro

Think of Google Cloud as a huge office building you can control three ways:

- **The Console** (web UI) — walking around and flipping switches by hand.
- **The CLI (`gcloud` and friends)** — phoning the building manager and giving precise instructions.
- **Client libraries / APIs** — hiring a robot (your code) to make those calls for you.

The **Google Cloud CLI** (historically called the **Cloud SDK**) is the "phone": a set of command-line tools you install on your laptop. The main one is `gcloud`, plus a few specialists (`bq` for BigQuery, `kubectl` for Kubernetes).

**Cloud Shell** is the same phone, but pre-installed, pre-authenticated, and living **in your browser** — Google gives you a small temporary Linux machine with all the tools ready, for free.

## 3. Core concepts

### 3.1 The tools in the box

| Tool | What it talks to | Example |
|---|---|---|
| **`gcloud`** | Almost everything (Compute, IAM, Cloud Run, GKE, networking…) | `gcloud compute instances list` |
| **`gcloud storage`** | Cloud Storage (the modern way) | `gcloud storage cp file.txt gs://my-bucket/` |
| **`gsutil`** | Cloud Storage (the *legacy* way — still appears in exam answers!) | `gsutil cp file.txt gs://my-bucket/` |
| **`bq`** | BigQuery | `bq query 'SELECT ...'` |
| **`kubectl`** | Kubernetes clusters (GKE) | `kubectl get pods` |

> **The thing people get wrong:** `kubectl` is **not** a Google tool — it's the standard Kubernetes CLI. You install it *through* gcloud (`gcloud components install kubectl`), and you point it at your cluster with `gcloud container clusters get-credentials`.

> **Micro-summary:** *`gcloud` = almost everything. `bq` = BigQuery. `gsutil`/`gcloud storage` = buckets. `kubectl` = inside a GKE cluster.*

---

### 3.2 The anatomy of a gcloud command

Every `gcloud` command follows the same grammar. Learn the grammar and you can read any command:

```
gcloud  <product>  <resource>   <verb>     <name>      --flags
gcloud  compute    instances    create     my-vm       --zone=europe-west1-b
gcloud  storage    buckets      create     gs://my-b   --location=EU
gcloud  projects   list
gcloud  iam        service-accounts  create  build-sa
```

**Reading trick:** read it backwards as a sentence — *"create an instance, in compute, using gcloud."*

Three flags work **everywhere** and the exam loves them:

| Flag | What it does | Example |
|---|---|---|
| `--project` | Override the default project *for this one command* | `--project=other-proj` |
| `--format` | Change output (json, yaml, table, value) | `--format=json` |
| `--filter` | Show only matching rows | `--filter="zone:europe-west1-b"` |

### 3.3 Installing and updating the SDK — components

The SDK is modular. The core install gives you `gcloud`; everything else is a **component** you add:

```bash
gcloud components list                # what's installed / available
gcloud components install kubectl    # add a tool
gcloud components update              # update everything
```

Common components: `kubectl`, `app-engine-python`, `cloud-datastore-emulator`, and the **`alpha`** and **`beta`** command groups.

#### Alpha and beta commands

- `gcloud beta compute instances ...` — newer features, almost stable.
- `gcloud alpha ...` — early, may change or disappear.

> **Exam pattern:** *"The command `gcloud beta X` fails with 'Invalid choice'"* → the **beta component isn't installed** → `gcloud components install beta`.

> **The thing people get wrong:** in **Cloud Shell** you *can't* use `gcloud components install` the usual way (the package is managed by Google and already includes almost everything). On your own laptop, you can.

> **Micro-summary:** *SDK = core + components. `components install/update/list`. Alpha/beta are components too.*

### 3.4 Initial setup: `gcloud init` vs `gcloud auth login`

| Command | What it actually does |
|---|---|
| **`gcloud init`** | The full welcome wizard: log in **and** pick default project **and** (optionally) default region/zone. Creates/updates a configuration. |
| **`gcloud auth login`** | *Only* logs you in (opens a browser, stores your user credentials). |
| **`gcloud config set project my-proj`** | *Only* sets the default project. |

So: `init` ≈ `auth login` + `config set project` + `config set compute/region|zone`, wrapped in a wizard.

---

### 3.5 Defaults: `gcloud config` — stop typing the same flags

Without defaults, every command needs `--project`, `--zone`, etc. With defaults, gcloud fills them in for you:

```bash
gcloud config set project my-web-app-12345
gcloud config set compute/region europe-west1
gcloud config set compute/zone europe-west1-b
gcloud config list                    # see current defaults
```

**Where do these live?** In a **configuration** — a named bundle of settings.

#### Configurations: the "profiles" feature

The problem: you manage a **work** project with `you@company.com` and a **personal** project with `you@gmail.com`, from the same laptop. Re-typing `gcloud config set ...` four times a day is misery.

The answer: one **configuration per context**, and you flip between them:

```bash
gcloud config configurations create work
gcloud config configurations create personal
gcloud config configurations activate work     # now all defaults = work
gcloud config configurations list
```

Each configuration stores its own account, project, region/zone. The default one is called `default`.

**One-off override without switching:** add `--configuration=personal` (or just `--project=...`) to a single command.

> **Memory trick:** configurations are like **browser profiles** — same browser, different person/context, switch with one click.

> **Micro-summary:** *`config set` = defaults. `config configurations` = named bundles of defaults. Activate to switch context.*

### 3.6 Who am I? — `gcloud auth` and the two kinds of credentials

```bash
gcloud auth list                              # which accounts are logged in, which is active
gcloud auth login                             # log in as a HUMAN (browser flow)
gcloud auth activate-service-account --key-file=key.json   # log in as a SERVICE ACCOUNT
gcloud auth application-default login         # credentials for YOUR CODE running locally
```

The distinction the exam tests:

| Command | Whose identity? | Used by |
|---|---|---|
| `auth login` | You (human) | `gcloud` commands you type |
| `auth activate-service-account` | A robot (service account, via key file) | `gcloud` commands on a server/CI |
| `auth application-default login` | You, but exposed to **code** | Apps/scripts using client libraries on your laptop |

> **The thing people get wrong:** `gcloud auth login` and `gcloud auth application-default login` are **different credential stores**. Your `gcloud` CLI working fine does *not* mean your Python script can authenticate — the script needs Application Default Credentials (ADC).

> **Micro-summary:** *`auth list` = who am I. Human login vs service-account key vs ADC for code.*

### 3.7 Cloud Shell — the zero-install option

**What it is:** click the `>_` icon in the Console and Google starts a **small temporary Linux VM** in your browser, already logged in as you, with `gcloud`, `kubectl`, `bq`, `git`, `terraform`, editors, and language runtimes pre-installed.

**The facts to memorise:**

| Property | Value |
|---|---|
| Cost | **Free** (with any Google account) |
| Your files | **5 GB persistent disk** mounted at `$HOME` — survives between sessions |
| The VM itself | **Ephemeral** — recycled when your session ends; anything *outside* `$HOME` is lost |
| Inactivity | Session ends after ~**20 minutes** idle |
| Usage quota | Weekly usage limit (about **50 hours/week**) |
| Long inactivity | Don't use it for ~**120 days** → Google may wipe the home disk |
| Authentication | Automatic — you're already logged in as the Console user |
| Extras | **Cloud Shell Editor** (VS Code-like), **Web Preview** on ports 8080+, **Boost mode** for a beefier VM |

**When the exam wants "Cloud Shell" as the answer:**
- *"…without installing anything locally"*
- *"…from any machine / a borrowed laptop"*
- *"…company policy forbids installing SDKs"*
- *"…fastest way to run one gcloud command"*

**When the exam does NOT want Cloud Shell:**
- Long-running jobs (the session times out) → use a real VM.
- Heavy builds / big data moves → real VM or Cloud Build.
- Anything that must run unattended on a schedule → not Cloud Shell.

> **Micro-summary:** *Cloud Shell = free ephemeral VM + 5 GB persistent `$HOME` + pre-installed, pre-authenticated tools. Great for admin, wrong for long-running work.*

### 3.8 Enabling APIs from the CLI

You met this in lesson 1.1 — here is the CLI side, because it shows up in command-reading questions:

```bash
gcloud services list --enabled            # what's on in this project
gcloud services list --available          # everything you could turn on
gcloud services enable compute.googleapis.com
```

> **Exam pattern:** a command fails with *"API not enabled"* → the fix is `gcloud services enable <api>` (or clicking Enable in the Console) — **not** an IAM change.

## 4. gcloud commands you'll see

Memorize these **for recognition**, not for typing:

```bash
# Setup & identity
gcloud init
gcloud auth login
gcloud auth list
gcloud auth activate-service-account --key-file=key.json
gcloud auth application-default login

# Defaults & profiles
gcloud config list
gcloud config set project PROJECT_ID
gcloud config set compute/zone europe-west1-b
gcloud config configurations create NAME
gcloud config configurations activate NAME
gcloud config configurations list

# Components (laptop only, not Cloud Shell)
gcloud components list
gcloud components install kubectl
gcloud components update

# APIs
gcloud services list --enabled
gcloud services enable SERVICE_NAME.googleapis.com

# Useful everywhere
gcloud projects list
gcloud compute instances list --filter="zone:europe-west1-b" --format=json
ANY_COMMAND --project=OTHER_PROJECT        # one-off project override
```

## 5. Common confusions

| Confusion | The truth |
|---|---|
| "`gcloud init` vs `gcloud auth login`" | `init` is the **wizard** (login + project + region defaults). `auth login` **only** authenticates. |
| "`config set` vs `configurations`" | `config set` changes a value **inside** the active configuration. `configurations` create/switch **whole profiles**. |
| "CLI auth vs code auth" | `auth login` serves `gcloud`. Your **code** needs `auth application-default login` (ADC). Two separate stores. |
| "Cloud Shell loses my files" | Only files **outside `$HOME`**. The 5 GB home directory persists. |
| "kubectl is part of gcloud" | No — it's the standard K8s tool, installed *as a component*, wired to GKE via `gcloud container clusters get-credentials`. |
| "`gsutil` is wrong/old so it won't appear" | It still appears in questions and answers. `gsutil` and `gcloud storage` do the same job. |
| "Switching projects needs re-login" | No — same login can span many projects. Switch with `config set project` or `--project`. |

## 6. Worked scenarios

**Scenario 1.** *A developer manages two unrelated clients from one laptop: client A (account `dev@a.com`, project `a-prod`) and client B (account `dev@b.com`, project `b-prod`). They keep accidentally creating resources in the wrong project. What's the cleanest fix?*

→ Two **gcloud configurations** (one per client), each storing its own account + project + defaults. Switch with `gcloud config configurations activate clientA`. The "accidentally wrong project" symptom is the classic configurations trigger.

**Scenario 2.** *You're at a conference on a borrowed laptop and must urgently restart a VM. Company policy forbids installing software. What do you do?*

→ Open the Console in a browser → **Cloud Shell** → `gcloud compute instances reset my-vm --zone=...`. Nothing to install, already authenticated.

**Scenario 3.** *On a CI server, `gcloud compute instances list` returns "You do not currently have an active account selected." What's the fix?*

→ The server has no credentials. Authenticate as a robot: `gcloud auth activate-service-account --key-file=key.json` (or better, run CI on infrastructure with an attached service account — see lesson 4.2).

**Scenario 4.** *`gcloud beta run jobs create ...` fails with "Invalid choice: 'beta'". Why?*

→ The **beta component** isn't installed → `gcloud components install beta`.

**Scenario 5.** *A script using the Python client library fails to authenticate on your laptop, even though `gcloud projects list` works fine. Why?*

→ The CLI uses your `auth login` credentials; the **library** looks for **Application Default Credentials**. Run `gcloud auth application-default login`.

## 7. Mini-Q&A

- **Q: What persists between Cloud Shell sessions?** → The 5 GB disk at `$HOME`. Everything else on the VM is recycled.
- **Q: One command to see your active account and project?** → `gcloud config list` (account, project, region/zone of the active configuration).
- **Q: How does `kubectl` get access to a GKE cluster?** → `gcloud container clusters get-credentials CLUSTER --zone=...` writes the kubeconfig entry.
- **Q: How do you run one command against a different project without changing defaults?** → Add `--project=OTHER_ID`.
- **Q: What's the modern replacement for `gsutil`?** → `gcloud storage`.
- **Q: Where do you set a default zone?** → `gcloud config set compute/zone ZONE`.
- **Q: Is Cloud Shell good for an 8-hour batch job?** → No — sessions time out; use a Compute Engine VM.
- **Q: What does `gcloud auth list` show?** → All credentialed accounts on this machine, with a star on the active one.

## 8. Hands-on lab (optional, ~20 min)

1. Open **Cloud Shell** from the Console. Run `gcloud config list` — notice you're already authenticated and the project is set.
2. Create a file in your home dir: `echo hello > ~/persist-test.txt`. Close Cloud Shell, reopen later, confirm the file is still there.
3. On your **own machine**, install the Google Cloud CLI, then run `gcloud init` and walk the wizard.
4. Create a second configuration: `gcloud config configurations create lab`, set a project on it, then `activate` back and forth and watch `gcloud config list` change.
5. Run `gcloud compute instances list --format=json` and then with `--format="table(name,zone,status)"` — see how `--format` reshapes output.
6. Run `gcloud services list --enabled` and count how many APIs a fresh project really has.

## 9. Exam gotchas

- `gcloud init` = wizard; `gcloud auth login` = login **only**.
- Configurations are the answer to any "multiple projects/accounts from one machine" scenario.
- Cloud Shell: free, **5 GB persistent `$HOME`**, ephemeral VM, ~20 min idle timeout, weekly usage cap — wrong tool for long-running jobs.
- You **cannot** add components inside Cloud Shell; on a laptop you can (`gcloud components install`).
- "Invalid choice: beta/alpha" → install the component, it's not a permissions problem.
- CLI credentials ≠ ADC (code) credentials — two different `auth` commands.
- `kubectl` needs `gcloud container clusters get-credentials` first.
- "API not enabled" errors are fixed with `gcloud services enable`, **not** with IAM roles.
- `--project` on any command beats the configured default — handy and exam-tested.

---

## 10. TL;DR recap

> The **Google Cloud CLI** gives you `gcloud` (plus `bq`, `gsutil`/`gcloud storage`, and `kubectl` as a component). Commands follow `gcloud <product> <resource> <verb>`. Set defaults with `gcloud config set`, and bundle defaults into **configurations** when you juggle multiple projects or accounts. Humans log in with `auth login`, robots with `auth activate-service-account`, and your local code with `auth application-default login`. **Cloud Shell** is a free, browser-based, pre-authenticated terminal with a 5 GB persistent home — perfect for quick admin from anywhere, wrong for long-running work.
