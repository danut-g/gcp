## 1. Why this matters for the exam

Section 2 is the **biggest part** of the exam (~30%) and **compute is the heart of it**.

The single most common question is: *"Given this workload, which compute service?"* If you can confidently pick between Compute Engine, GKE, and Cloud Run for a described workload, you'll get a lot of points easily.

Beyond the *choice*, the exam tests whether you understand the **operational model** of each:

- *Who patches the OS?*
- *Who scales the nodes?*
- *What triggers an autoscale?*
- *What happens when an instance dies?*

## 2. Core concepts

### 2.1 The four compute options — pick the right tool for the job

#### The problem this solves

Imagine you have to run code in the cloud. You could:

- Get a virtual machine and run anything you want (most control, most work).
- Run containers on managed Kubernetes (medium control, medium work).
- Just upload a container and let Google handle the rest (least control, least work).
- Just upload a function and let Google build the container for you (least of all).

GCP gives you all four options. Knowing which to pick is the most exam-tested skill in this section.

#### The continuum

```
Compute Engine  →  GKE Standard  →  GKE Autopilot  →  Cloud Run  →  Cloud Run functions
   most control                                                       least control
   most ops work                                                      least ops work
```

#### The four options at a glance

| Service | Abstraction | You manage | Google manages | Sweet spot |
|---|---|---|---|---|
| **Compute Engine** | Virtual machine | OS, runtime, app, scaling logic | Hypervisor, hardware | Lift-and-shift, custom OS, GPU/TPU workloads, anything that won't fit a container |
| **GKE Standard** | Kubernetes cluster | Cluster config, node pools, workloads | Control plane (master) | Microservices at scale, complex orchestration, when you want Kubernetes APIs |
| **GKE Autopilot** | Kubernetes workloads | Workloads only | Everything below the workload, including nodes | Kubernetes without operating nodes; pay per pod |
| **Cloud Run** | Container as a service | The container image | Everything else, including scale-to-zero | Stateless web apps and APIs, event-driven services |
| **Cloud Run functions** (formerly Cloud Functions) | A single function | Source code | Build, deploy, runtime, scaling | Glue code, single-purpose handlers, light event processing |

> **Vocabulary note:** *Knative serving* is the open-source spec that Cloud Run implements. You'll occasionally see it in the exam guide as a reminder that Cloud Run runs Knative-compatible containers.

> **Micro-summary:** *More control = more work. Compute Engine is most flexible, Cloud Run functions is least work. Pick by what the workload needs.*

### 2.2 Compute Engine — VM fundamentals

#### What defines a VM

A VM is described by these attributes:

| Attribute | What it is |
|---|---|
| **Machine type** | The shape: how many vCPUs, how much RAM |
| **Image** | The boot disk template (OS) |
| **Boot disk** | The disk where the OS lives |
| **Network** | VPC + subnet + zone, optional external IP |
| **Service account** | The identity the VM uses to call other GCP APIs |

#### Machine type families — pick the right shape

| Family | Optimised for | Use cases |
|---|---|---|
| `e2` | Cost | Small workloads, dev/test |
| `n2`, `n2d` | General purpose | Most workloads |
| `c2`, `c3` | Compute | CPU-heavy work |
| `m2`, `m3` | Memory | In-memory databases |
| `a2`, `a3` | GPU/AI | Training, inference |

You can also use **custom machine types** to pick exact vCPU + memory amounts within family limits — useful when off-the-shelf shapes are wasteful.

#### Availability policy

Two settings to know:

- **On host maintenance:**
  - `MIGRATE` (default) — Google live-migrates the VM to another host.
  - `TERMINATE` — VM stops during maintenance. Required for some configs (sole-tenant, some GPU types, Spot VMs).
- **Automatic restart** (default on) — restart the VM if it crashes.

#### SSH access — two ways

| Method | How it works | Recommended? |
|---|---|---|
| **OS Login** | SSH controlled by IAM. The VM looks up your IAM identity | ✅ Yes — centralised, audit-logged, supports 2FA |
| **Metadata SSH keys** | Old method. Keys stored in project or instance metadata | ❌ Old; managed in two places |

Two relevant OS Login roles:
- `roles/compute.osLogin` — login.
- `roles/compute.osAdminLogin` — login + sudo.

#### Spot VMs — discounted but interruptible

| Type | Discount | Catch |
|---|---|---|
| **Spot VM** | Up to 91% off | Google can preempt at any time, with 30-second shutdown signal |
| **Preemptible VM** (older) | Up to 91% off | Same as Spot, but capped at 24-hour lifetime |

For the exam, treat them as roughly equivalent. Both are great for **fault-tolerant batch work**: CI runners, render farms, ML training that can resume.

#### Sole-tenant nodes

Your VMs run on hardware that hosts no one else's workloads. Usually a **licensing or compliance requirement**.

#### Storage for VMs — five options

| Option | Performance | Persistence | Use case |
|---|---|---|---|
| **Zonal Persistent Disk** | Standard, balanced, SSD, extreme | Survives VM deletion | The default; lives in one zone |
| **Regional Persistent Disk** | Same tiers | **Synchronously replicated to a 2nd zone** | HA: failover with no data loss |
| **Local SSD** | Highest IOPS / lowest latency | **Ephemeral!** Lost when VM stops | Caches, temp scratch space |
| **Hyperdisk** | Newer, **tunable** IOPS + throughput separately from size | Persistent | High-performance workloads on newer machine families |
| **Cloud Storage FUSE / NetApp / Filestore** | File-level access | External | Network file system; not a boot disk |

Important facts:
- Persistent Disks can be **resized while attached** (you cannot shrink, only grow).
- **Snapshots are incremental** and stored as Cloud Storage objects.

> **Memory trick for Local SSD:** "Local" sounds nice and fast, but it dies when the VM stops. The exam loves this trap.

#### VM Manager — fleet-level OS operations

VM Manager automates OS operations across many Compute Engine VMs (and Anthos on-prem):

| Tool | What it does |
|---|---|
| **OS Inventory Management** | Collects installed packages, kernel, OS metadata for every VM |
| **OS Patch Management** | Schedules and runs patch jobs across thousands of VMs (Linux + Windows). Can target by zone/label, roll out in batches |
| **OS Configuration Management** | Declarative desired state for packages, files, services (think small Ansible inside Google Cloud) |

Enable VM Manager on the project. The **OS Config agent** must be running on each VM (it ships with most public images and the Ops Agent installer).

> **Exam phrasing hints:**
> - *"We need to know what's installed on every VM"* → OS Inventory.
> - *"We need to apply security patches in waves"* → OS Patch.

> **Micro-summary:** *VMs need machine type + image + disk + network + service account. OS Login is the modern SSH way. Spot VMs are cheap but preemptible. Local SSD is fast but ephemeral. VM Manager handles OS-level operations at fleet scale.*

### 2.3 Managed Instance Groups (MIGs)

#### The problem this solves

Imagine you need 10 identical web-server VMs. You could create them one by one, but then:
- If one dies, you have to manually replace it.
- If traffic spikes, you have to manually create more.
- If you need a new image, you have to update each one.

A **MIG** automates all of that. It's a fleet of identical VMs that GCP creates, replaces, and scales for you.

#### How it works

```
Instance Template (immutable spec)
       │
       ▼
       MIG (zonal or regional)
       │
       ├── VM 1   ← all identical, all built from the template
       ├── VM 2
       └── VM 3
```

Key concepts:

| Term | What it is |
|---|---|
| **Instance template** | An **immutable** spec: machine type, image, network, startup script, service account, etc. To change anything, create a new template and roll it out |
| **Zonal MIG** | VMs in a single zone |
| **Regional MIG** | VMs spread across multiple zones in a region (better availability; the MIG balances zones for you) |

#### Autoscaling triggers — what makes it grow/shrink

A MIG can scale based on:

- **CPU utilization**
- **HTTP load-balancer serving capacity** (RPS or backend utilization)
- **Cloud Monitoring metric** (any metric)
- **Pub/Sub queue depth** (via metric)
- **Schedule** (e.g., bigger during business hours)

Autoscaling **adds and removes** VMs (horizontal). To **change machine size** (vertical), you have to recreate the instances.

#### Auto-healing — replacing dead VMs

A MIG can replace VMs that fail a health check. **Important**: this is a *separate concept* from load-balancer health checks (though they often share configuration).

#### Rolling updates

You can change to a new template with controls for:
- **Max surge** — how many extra VMs during the update.
- **Max unavailable** — how many can be down.
- **Canary distribution** — % of traffic to the new version.

> **Micro-summary:** *MIG = fleet of identical VMs from an immutable template. It autoscales, auto-heals, and supports rolling updates. Instance templates can never be edited — to change, make a new one.*

---

#### Containers vs. VMs (the analogy)

| | VM | Container |
|---|---|---|
| **What's virtualised** | Hardware | The process tree |
| **OS kernel** | Each VM has its own | Many containers share the host kernel |
| **Boot time** | Minutes | Seconds |
| **Density** | Dozens per host | Hundreds per host |
| **Image size** | Gigabytes | Megabytes |
| **Isolation** | Hardware-level | Kernel-level (namespaces, cgroups) |

#### Containerizing an app with Docker (standard packaging)

The standard packaging step before GKE / Cloud Run:

1. Write a **Dockerfile** (`FROM`, `COPY`, `RUN`, `CMD` instructions).
2. `docker build -t IMAGE:TAG .` produces a local image.
3. `docker run IMAGE:TAG` to verify locally.
4. Tag and push to **Artifact Registry**: `docker push REGION-docker.pkg.dev/PROJECT/REPO/IMAGE:TAG`.
5. Deploy that image to GKE / Cloud Run / Cloud Run functions.

For multi-language stacks, **Cloud Buildpacks** (`pack` CLI) can produce an image **without a Dockerfile** by detecting the language and applying Google-maintained build steps.

### 2.4 GKE essentials

#### Two flavours of GKE

| Mode | You pay for | You configure | Best for |
|---|---|---|---|
| **GKE Standard** | Nodes (VMs in your project) + control plane fee per cluster | Node pools, networking, autoscaling, node OS | When you want full control over nodes |
| **GKE Autopilot** | Pods (CPU/memory requested) | Workloads only — no nodes to see | Hands-off Kubernetes |

#### Cluster topologies

| Type | Control plane | Nodes | When to use |
|---|---|---|---|
| **Zonal** | 1 zone | 1 zone | Simple, cheap, weakest availability |
| **Regional** | Replicated across 3 zones | Spread across zones | **Production** |
| **Private cluster** | Private endpoint | Internal IPs only | Keep cluster off the public internet |

#### Node pools (a group of nodes with the same setup)— different machine types in one cluster

- A cluster has one or more **node pools**, each with its own machine type, autoscaling config, and labels/taints.
- You scale node pools, not the cluster as a whole.
- Different workloads can target different pools (e.g., GPU pool for ML, small pool for batch).

#### Three autoscalers in GKE — they each do different things

| Autoscaler | What it scales |
|---|---|
| **Cluster autoscaler** | Nodes (adds/removes VMs in the pool) |
| **Horizontal Pod Autoscaler (HPA)** | Number of pod replicas in a deployment |
| **Vertical Pod Autoscaler (VPA)** | Pod resource requests (CPU/memory per pod) |

> **Memory trick:** *Cluster autoscaler = nodes. HPA = pod count. VPA = pod size.*

#### kubectl setup for GKE

`kubectl` is the Kubernetes CLI. To use it with a GKE cluster:

1. Install `gke-gcloud-auth-plugin` (required for kubectl to auth via gcloud).
2. `gcloud container clusters get-credentials NAME --region=REGION` — writes a kubeconfig entry.
3. `kubectl get nodes` to confirm.

> **Exam trap:** If the question says "kubectl returns auth errors after `get-credentials`", the cause is the missing `gke-gcloud-auth-plugin`.

> **Micro-summary:** *Standard = you manage nodes. Autopilot = pay per pod. Regional = HA control plane. Private = no public IPs. kubectl needs the auth plugin.*

### 2.5 Serverless: Cloud Run and Cloud Run functions

#### Cloud Run — containers as a service

Run **stateless containers**. You give it an image, a port, and a region. Google handles the rest.

Key knobs:

| Knob | What it does |
|---|---|
| **Concurrency** | Multiple requests can hit the same container (default 80, configurable) |
| **CPU allocation** | `default` (CPU only during requests) or `always` (background work allowed) |
| **Min instances** | Keep N warm; default is 0 (scale-to-zero) |
| **Traffic splitting** | Each deployment is a **revision**; route 50/50 between revisions for canaries or rollbacks |

A “knob” = a configurable parameter or setting that you can adjust to change how a system behaves. ￼
Think of it like:
🔧 a dial you can turn to fine‑tune performance, cost, or behavior.
￼
✅ In a GCP context
When someone says “GCP knobs”, they usually mean:
• Configuration options in GCP services
• Tunable parameters for performance, scaling, or security
• Settings exposed by managed services (sometimes limited)
￼
🔍 Examples of “knobs” in GCP
Compute / GCE
• Machine type (CPU/RAM)
• Autoscaling settings
• Preemptible vs standard VMs
GKE (Kubernetes)
• Node pool size
• Pod resource limits (CPU/memory)
• Autoscaler thresholds


#### Two execution environments

| Type | What it is |
|---|---|
| **Cloud Run service** | Long-running web service, handles HTTP requests |
| **Cloud Run job** | Runs to completion, like a batch job. Can be triggered manually, scheduled, or invoked |

#### Cloud Run functions — upload code, not a container

The next generation of Cloud Functions, built on top of Cloud Run.

- You upload **source code** (not a container image).
- Google builds the container automatically.
- The rest works like Cloud Run.

> **Exam tip:** There are still two generations in the docs (`1st gen` Cloud Functions and `2nd gen` Cloud Run functions). Always pick **Cloud Run functions / 2nd gen** unless told otherwise.

> **Micro-summary:** *Cloud Run = run stateless containers. Cloud Run functions = upload code, Google builds the container. Scale to zero by default; min-instances eliminates cold starts.*

### 2.6 Eventing — Pub/Sub, Cloud Storage triggers, Eventarc

Serverless workloads are usually **triggered by events**, not just HTTP requests.

| Trigger | What fires it |
|---|---|
| **HTTP** | A direct HTTP request |
| **Pub/Sub** | A message arrives on a topic |
| **Cloud Storage object change** | An object is created/deleted/updated in a bucket |
| **Eventarc** | The unified event router |

#### Eventarc — the modern unified router

What is Eventarc: A centralized event router that connects everything that produces events to everything that consumes them.
Eventarc acts as an internal hub that manages events and  routes them to services that perform the actions.
What does it do exactly   --- Collects events from sources
                          --- Standardizes them (Converts everything into CloudEvents format)
                          --- Routes events

Eventarc standardises events from many sources (Audit Logs, Pub/Sub, Cloud Storage, third-party SaaS) into the **CloudEvents** format and delivers them to:

- Cloud Run
- Cloud Run functions
- GKE
- Workflows

> **Exam tip:** When you see both "direct Pub/Sub trigger" and "Eventarc" as options, **Eventarc** is the modern recommended pattern. Direct triggers still exist for simple cases.

> **Micro-summary:** *Events drive serverless. Eventarc = unified event router using CloudEvents format. Modern best practice.*

## 3. Decision criteria — which compute?

The "which compute?" question shows up many times. A simple decision flow:

1. **Need a specific OS, kernel, GPU/TPU, or licensed software?** → **Compute Engine**.
2. **Running an existing Kubernetes cluster, or need full Kubernetes APIs?** → **GKE** (Autopilot for hands-off, Standard for full control).
3. **Stateless container workload?** → **Cloud Run** (a service or a job).
4. **Single-purpose handler responding to an event?** → **Cloud Run functions**.

Side-by-side cheat sheet:

| Concern | Pick |
|---|---|
| Long-running stateful service | Compute Engine, or GKE with StatefulSet |
| Spiky traffic, scale-to-zero acceptable | Cloud Run |
| Predictable traffic, want a fleet of identical VMs | Compute Engine + MIG |
| Event-driven glue (object lands → process) | Cloud Run functions |
| Heterogeneous microservices in containers | GKE |
| 30-second handlers, no infrastructure to manage | Cloud Run functions |
| Need root / kernel modules | Compute Engine |
| Batch job that must run to completion | Cloud Run job, or a Compute Engine MIG with custom logic |

## 6. Common confusions — the things people mix up

### "Spot VM" vs "Preemptible VM"

- Both are heavily discounted (up to 91%) and can be preempted.
- Spot is the **newer** name. Preemptible has the older 24-hour cap.
- For the exam, treat them as roughly equivalent — Spot is preferred.

### "Local SSD" vs "Persistent Disk SSD"

- **Local SSD** = fast but **ephemeral** (lost when VM stops).
- **Persistent Disk SSD** = persistent, survives VM deletion.
- Don't be fooled by "SSD" in both names.

### "Zonal MIG" vs "Regional MIG"

- **Zonal** = all VMs in one zone (cheap, weak HA).
- **Regional** = VMs spread across zones in a region (HA, recommended for prod).

### "GKE Standard" vs "GKE Autopilot"

- **Standard** = you manage nodes, pay for nodes.
- **Autopilot** = Google manages nodes, you pay per pod.

### "Cloud Run service" vs "Cloud Run job"

- **Service** = always-on web service (HTTP).
- **Job** = runs to completion (batch).

### "Cluster autoscaler" vs "HPA" vs "VPA"

- **Cluster autoscaler** = adds/removes **nodes**.
- **HPA** = adds/removes **pod replicas**.
- **VPA** = adjusts **pod resource requests**.

## 7. Exam gotchas — the subtle traps

- **GKE Autopilot pricing is per-pod**, not per-node. If a question says *"paying for unused node capacity"*, the answer is Autopilot or Cloud Run, not "fix the autoscaler".
- **Spot VMs can be preempted at any time.** The 24-hour cap was for the older preemptible model.
- **Regional Persistent Disks** synchronously replicate across two zones. Snapshots replicate across regions but they are *backups*, not real-time replicas.
- **Local SSD is ephemeral.** A VM stop/restart loses the data.
- **Custom machine types** still have ratio constraints (memory per vCPU).
- **OS Login** doesn't work cleanly if metadata SSH keys are in use — best practice is OS Login project-wide and remove metadata keys.
- **Instance templates are immutable.** "Update the MIG to use a new image" → create a new template and roll it out.
- **Cloud Run scales to zero by default** = cold starts on first request. Fix with **min instances**.
- **Cloud Run requires a stateless container.** Persistent state goes in Cloud SQL, Cloud Storage, etc.
- **Eventarc vs. direct triggers** — Eventarc is the unified, future-proof choice.
- **GKE private cluster** still needs egress to pull container images (Cloud NAT or Private Google Access).
- **kubectl needs `gke-gcloud-auth-plugin`** with recent gcloud versions.

## 8. Named scenarios — deeper design walk-throughs

These are the kind of design questions the exam asks, told as little stories.

### Scenario A — Cost optimisation & workload types

**Context.** A startup is over-spending on compute. Three workloads dominate the bill:
1. A Python web API serving variable traffic (peaks at lunch, near-zero overnight).
2. A nightly ML training batch that takes 6 hours on 32 vCPUs and tolerates restarts.
3. A long-running self-managed PostgreSQL on a single n2-standard-8 VM running 24/7 because they need a Postgres extension Cloud SQL doesn't support.

**Recommended design.**

| Workload | Right answer | Why it saves money |
|---|---|---|
| Python web API | **Cloud Run** with `min-instances=0`, concurrency 80 | Scale-to-zero overnight = $0; pay only for request seconds |
| ML batch | **Spot VMs** in a regional MIG, instance template with the training image, `--instance-termination-action=STOP` | Up to 91% discount; restartable code makes preemption a non-event |
| Self-managed Postgres | Keep on Compute Engine but **right-size** to a custom machine type (e.g. 4 vCPU / 32 GB if memory-bound), enable **committed-use discount** for 1 year | Custom shape removes wasted vCPU; CUD trims another 25–37% on steady-state |

**Why this works.** Each workload picks the *cheapest service that fits its tolerance for disruption*. Stateless + bursty → Cloud Run. Stateful + restartable → Spot. Long-running + can't move to managed → CUD + right-sizing. Lifting all three to "always-on n2 VMs" was the original mistake.

### Scenario B — Building a scalable web application

**Context.** End-to-end design for a public web app that should survive a zone failure, scale automatically, and serve users worldwide.

**Architecture.**
```
Users  →  Cloud DNS  →  Global external Application LB (Premium tier)
                              │  + Cloud Armor (WAF/DDoS) + Cloud CDN
                              ▼
                       Regional MIG (web tier, e2-medium)
                          • Instance template w/ startup script
                          • Auto-healing on HTTP /health
                          • Autoscaling on backend utilization 60%
                          • Spread across europe-west3-a/b/c
                              │
                              ▼
                       Cloud SQL Postgres (Regional HA) + Read Replica
                              │
                              ▼
                       Cloud Storage (eu multi-region) for user uploads
```

**Build order.**
1. Custom-mode VPC with one subnet in `europe-west3` (`/20`); enable Private Google Access.
2. Instance template `web-tmpl-v1` (e2-medium, Debian, startup script, attached to a least-privileged service account).
3. Health check `web-hc` → `/health` on port 80.
4. **Regional MIG** `web-mig` (3 zones, autoscaling 2–10, auto-healing with the health check, initial delay 60 s).
5. Reserve a global static external IPv4 → create global external Application LB with a Google-managed cert and the MIG as backend; enable Cloud CDN.
6. Add `roles/storage.objectAdmin` on the uploads bucket to the MIG's SA.
7. (Optional) Cloud Armor security policy on the LB backend service.

**Why this works.** Each layer covers one concern: LB = global entry + TLS. MIG = horizontal scale + auto-heal. Regional Cloud SQL = stateful HA. Multi-region bucket = continent-wide static-asset durability. Adding a second region later = clone the MIG into another region and add as backend on the same LB.

### Scenario C — Infrastructure as a Service (when to pick GCE)

**Context.** A team is debating whether to lift-and-shift a Windows + .NET Framework 4.7 app that depends on a custom kernel-level USB driver and a per-CPU licensed library.

**Recommended pick: Compute Engine (IaaS).**

Three constraints rule out the alternatives:
- **Custom kernel driver** → containers/serverless can't load arbitrary kernel modules. GKE / Cloud Run are out.
- **Licensed library priced per CPU** → you need a *predictable CPU shape*. Cloud Run / Autopilot autoscale CPU, breaking the license model.
- **Windows + .NET Framework 4.7** → the simplest path is a Windows Server VM.

**Operational pattern.** Build a **golden image** (custom image baked from a configured VM). Put it behind an instance template + small MIG (size 2 for HA across zones). Front with internal/external LB. Use **Sole-tenant nodes** if the license requires "no shared hardware". Schedule daily disk snapshots via a resource policy. *Exactly* the IaaS sweet spot.

### Scenario D — Security & private clusters

**Context.** A regulated SaaS company runs workloads on GKE. Audit findings require:
1. Control plane must not be reachable from the public internet.
2. Worker nodes must have no external IPs.
3. The cluster must still pull container images from Artifact Registry and call Google APIs.
4. Operators on corporate laptops must still administer via `kubectl`.

**Recommended design.**
- **Regional Standard cluster** (control-plane HA across 3 zones) with **Private nodes: Enabled** and **Private endpoint** for the control plane. Public endpoint **disabled**.
- **Master authorized networks**: add the corporate egress CIDR (or, better, the IAP TCP forwarding range `35.235.240.0/20`).
- **Egress for image pulls and APIs**: enable **Private Google Access** on the node subnet. Artifact Registry, `*.googleapis.com`, and `gcr.io` resolve to private VIPs. No Cloud NAT needed unless workloads also call third-party HTTPS endpoints.
- **Workload Identity** enabled cluster-wide.
- **kubectl access**: operators use `gcloud container clusters get-credentials … --internal-ip` and connect through an **IAP TCP tunnel** to a small bastion VM.

**Why this works.** Private nodes + private endpoint solve constraints 1 and 2. Private Google Access satisfies 3 without re-exposing the cluster. IAP + master authorized networks satisfy 4 with identity-aware, audit-logged access.

### Scenario E — GKE: pods & nodes

**Context.** A workload owner says: *"My pods are stuck in `Pending` and the cluster autoscaler isn't adding nodes. Some pods OOM-kill mid-day. We pay too much for nodes overnight."*

**Diagnosis & fix, in order.**

1. **Pending pods** — `kubectl describe pod <p>` shows `0/3 nodes are available: insufficient memory`. The pods request 8 Gi each but the existing pool is `e2-standard-4` (16 Gi total, only ~12 Gi usable for pods). Two fixes: shrink the request or add a pool with a larger machine type.
2. **Cluster autoscaler not scaling** — check the pool's max-nodes setting. If max is reached, raise the cap or move workload to a pool that can grow.
3. **OOM at midday** — set a sensible **memory limit** AND raise the **request**. Use **VPA in `recommend` mode** to get Google-recommended values; bake them into the deployment YAML.
4. **Overnight overpay** — set min-nodes=0 on a separate "burst" pool with a taint, and put workloads there with a matching toleration. Cluster autoscaler scales that pool to 0 overnight.
5. **Steady-state efficiency** — switch the burst pool to **Spot VMs**, then add a **PodDisruptionBudget** to keep at least one replica during preemptions.

**Why this works.** Each symptom maps to the *correct autoscaler*: HPA scales pods, VPA tunes requests, cluster autoscaler scales nodes — all three are needed for an efficient cluster.

### Scenario F — Serverless computing with Cloud Run

**Context.** A team has a small Node.js HTTP API. Latency requirement: p99 < 400 ms warm, < 2 s cold. Traffic: 0–500 RPS, very spiky. Deploy in `europe-west3`, bill back per request.

**Recommended design.**
- **Cloud Run service** with a container built via Cloud Buildpacks (no Dockerfile needed for vanilla Node).
- **Concurrency 50** — Node is single-threaded; tune below the default 80 to avoid event-loop saturation.
- **Min instances = 1** — keeps one warm to absorb the first request after idle.
- **Max instances = 50** — caps blast radius if a runaway client floods the service.
- **CPU allocation = "CPU only during requests"** — no background work. Use **Startup CPU boost** to shrink warm-up time for any cold instance.
- **Autoscaling signal** is implicit (concurrent requests / instance), not configurable.
- **Deploy with `--no-traffic`**, then `update-traffic --to-revisions=<new>=10` for a 10% canary, watch SLO dashboards in Cloud Monitoring, then ramp to 100%. Roll back instantly with another `update-traffic`.
- **Per-team chargeback**: tag the service with `--labels=team=growth,env=prod`. Labels propagate to the billing export.

**Why this works.** The default Cloud Run knobs are tuned for stateless web traffic; the only intentional changes (min instances, concurrency, CPU boost) directly address the latency SLO. Revisions + traffic splits give zero-downtime rollouts and rollbacks.

## 9. Practice scenarios

### Q1 — Picking the right compute service

A team is migrating a stateless Python web API. Traffic is highly variable: bursts during work hours, near-zero overnight. They want minimum operations and the lowest cost during idle periods. Which service?

A. Compute Engine with a managed instance group.
B. GKE Standard with HPA.
C. **Cloud Run.**
D. App Engine standard.

**Answer: C.** Stateless + scale-to-zero + minimum ops = Cloud Run. A and B don't scale to zero (you keep paying nodes). D is acceptable but Cloud Run is the modern recommended answer for new containerised workloads.

### Q2 — VM availability policy

You're running a CPU-intensive batch job that tolerates restarts but you want it cheaper. Which configuration?

A. n2-standard-4 with `--maintenance-policy=MIGRATE`.
B. n2-standard-4 Spot VM with `--maintenance-policy=TERMINATE`.
C. e2-medium with `--maintenance-policy=MIGRATE`.
D. n2-standard-4 with sole-tenant.

**Answer: B.** Spot VMs are deeply discounted (up to 91%) and require `TERMINATE` (they're preemptible). Sole-tenant (D) is *more* expensive. A is fine but full price. C downgrades CPU/memory but pays full price.

### Q3 — MIG vs. instance template

You want to update the boot image on every VM in a regional MIG. What's the correct workflow?

A. SSH each VM and update the OS in place.
B. Modify the existing instance template's image.
C. Create a new instance template referencing the new image; configure a rolling update on the MIG to use it.
D. Delete the MIG and recreate with the new image.

**Answer: C.** Instance templates are **immutable** — you cannot modify (B). A is unscalable and breaks the MIG model. D causes downtime. The correct pattern is "new template + rolling update".

### Q4 — Persistent Disk choice for an HA database

A self-managed PostgreSQL VM must survive a zone failure with no data loss. What disk type?

A. Local SSD.
B. Zonal Persistent Disk standard.
C. **Regional Persistent Disk SSD.**
D. Zonal Persistent Disk SSD with daily snapshot schedule.

**Answer: C.** Regional PD synchronously replicates across two zones in the same region — the requirement is "no data loss across zone failure". A loses data on stop. B and D are zonal; snapshots provide point-in-time recovery, not zero-data-loss failover.

### Q5 — GKE cluster type for a regulated workload

A GKE cluster must be unreachable from the public internet (control plane and nodes). The team also wants the highest control-plane availability. Which configuration?

A. Zonal cluster with private nodes.
B. **Regional cluster with private nodes and private endpoint for the control plane.**
C. Autopilot cluster with public endpoint disabled.
D. Regional Standard cluster with public endpoint and authorized networks.

**Answer: B.** Regional gives multi-zone control-plane HA; private nodes have no external IPs; private endpoint blocks public access to the control plane. A is single-zone (less HA). D leaves a public endpoint, just IP-restricted — not "unreachable".

## 11. TL;DR — what to remember if you only have 5 minutes before the exam

1. **Compute continuum:** Compute Engine → GKE Standard → GKE Autopilot → Cloud Run → Cloud Run functions. (Most control → least control.)
2. **Spot VMs:** up to 91% off, can be preempted any time. Great for batch.
3. **Local SSD = ephemeral!** Lost when VM stops.
4. **Regional Persistent Disk** = synchronously replicated across two zones for HA.
5. **Instance templates are immutable.** To change, create a new one + rolling update.
6. **MIG autoscale signals:** CPU, LB capacity, custom metric, schedule.
7. **GKE 3 autoscalers:** Cluster autoscaler (nodes), HPA (pod count), VPA (pod size).
8. **GKE Autopilot:** pay per pod, Google manages nodes.
9. **Cloud Run:** scales to zero by default → cold starts. Use **min instances** to keep warm.
10. **Cloud Run functions = 2nd gen.** Always pick this on the exam.
11. **Eventarc** = unified event router (CloudEvents format). Modern best practice.
12. **OS Login:** SSH controlled by IAM. Better than metadata SSH keys.
13. **VM Manager:** OS Inventory + OS Patch + OS Config — manage OS at fleet scale.
