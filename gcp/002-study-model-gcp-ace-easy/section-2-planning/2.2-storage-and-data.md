# 2.2 — Planning and implementing storage and data solutions (easy version)

> **What the official exam guide calls this:** Section 2.2 — choosing data products (Cloud SQL, BigQuery, Firestore, Spanner, Bigtable, AlloyDB, Dataflow, Pub/Sub, Managed Service for Apache Kafka, Memorystore), choosing storage products (Cloud Storage, Filestore, NetApp Volumes), Cloud Storage classes (Standard / Nearline / Coldline / Archive), loading data (CLI, Cloud Storage, Storage Transfer Service), maintaining multi-region redundancy.

---

## 1. Why this matters for the exam

GCP has **a lot** of storage and data products. Almost every exam scenario says something like:

> *"We need to store / query / move data of this shape — what do we use?"*

The exam doesn't really test how to write SQL or design a schema. It tests whether you can **pick the right product**.

You need two skills:

1. **Pattern-match the workload** to the product:
   - Relational? OLAP? Key-value? Document? Streaming? Files? Blobs?
2. Understand **redundancy and locality**:
   - Regional vs. multi-region, replication, backup.

## 2. Core concepts

### 2.1 The data product map — knowing what each one is for

Group GCP's data products by what they actually are. This is the most important table in the section.

#### Object storage — Cloud Storage

Buckets of arbitrary blobs. Use for: images, videos, backups, ML training data, static website assets — **any binary blob**.

#### File storage — Filestore, NetApp Volumes

NFS-style network file systems. Use when an application **must see a POSIX filesystem** (legacy apps, lift-and-shift, shared scratch space across VMs).

**Filestore — Google's managed NFS (NFSv3).** Picked by service tier:

| Tier | Performance | Availability | Use case |
|---|---|---|---|
| **Basic HDD** | Low IOPS, cheap | Zonal | Cold home directories, archive shares |
| **Basic SSD** | Higher IOPS | Zonal | General-purpose POSIX share |
| **Zonal** (formerly High Scale) | Up to 920k IOPS | Zonal | High-throughput analytics, render farms |
| **Regional** | Same as Zonal but replicated | Regional (synchronous) | Production workloads needing zone-failure resilience |
| **Enterprise** | High IOPS, low latency | Regional | SAP, EDA, mission-critical apps |

Filestore exposes an internal IP. Clients mount with `mount -t nfs IP:/SHARE /mnt/...`. Cross-VPC access uses peering or private service connection.

**NetApp Volumes (Google Cloud NetApp Volumes) — Google-managed ONTAP.** Supports:
- **NFS (v3, v4.1)**
- **SMB (v2/v3)** — *the only Google-managed file service that does this*
- **Dual-protocol** (NFS + SMB on the same volume)

Pick NetApp when:
- You already run NetApp on-prem (use SnapMirror to replicate into Google).
- You need SMB shares (Filestore can't do SMB).
- You need ONTAP features (snapshots, FlexClone, dedup).

> **Memory trick:** *Filestore = NFS only. NetApp Volumes = NFS + SMB + ONTAP magic.*

#### Relational databases — Cloud SQL, AlloyDB, Spanner

| Product | What it is | When to pick |
|---|---|---|
| **Cloud SQL** | Managed MySQL / PostgreSQL / SQL Server | Default "I need a relational DB" |
| **AlloyDB** | PostgreSQL-compatible, faster + analytics-friendly | PostgreSQL workload too big/slow for Cloud SQL |
| **Spanner** | Globally distributed, strongly consistent, horizontally scalable relational | When you need **global ACID** transactions |

**Cloud SQL — HA vs. read replicas (very different things):**

| Feature | What it is | What it gives you |
|---|---|---|
| **HA (Regional)** | Synchronous standby in another zone in the same region | Auto-failover, RPO=0, RTO~minute |
| **Read replicas** | Async read-only copies | Offload read traffic; or DR copy in another region |

Important details:
- In a regional HA pair, the standby is **NOT queryable**. Only the primary serves traffic.
- Need read scale-out → add **explicit** read replicas.
- Cross-region read replicas exist but **promotion is manual** — that's the DR pattern for a regional outage.

> **Rule of thumb:** *Cloud SQL until it stops working. Then think AlloyDB. Pick Spanner only when global ACID is genuinely required.*

#### NoSQL — Firestore, Bigtable

| Product | Type | When to pick |
|---|---|---|
| **Firestore** | Document database, low-latency, mobile/web SDKs | App data, user profiles, shopping carts |
| **Bigtable** | Wide-column, petabyte-scale, single-digit-ms latency | Time-series, IoT, ad tech, financial ticks |

Don't pick Bigtable for a typical app DB — it has no free tier and is built for at-scale workloads.

#### Analytical — BigQuery

Serverless data warehouse. Columnar storage. Runs SQL over **petabytes**. Used for analytics, dashboards, BI, large-scale reporting.

Two pricing models:

| Model | How you pay | Good for |
|---|---|---|
| **On-demand** | Per TB scanned | Variable / unpredictable usage |
| **Capacity** (slot-based) | Flat-rate reservations | Predictable, heavy usage |

Storage and compute are **separated** — you pay storage even when not querying.

#### Caching — Memorystore

Managed **Redis** or **Memcached**. In-memory cache for sub-millisecond reads. Use for:
- Sessions
- Leaderboards
- Rate-limiting counters

#### Messaging & streaming — Pub/Sub, Managed Kafka

| Product | When to pick |
|---|---|
| **Pub/Sub** | Default for event-driven architecture. Global, fully managed |
| **Pub/Sub Lite** | Cheaper, zonal, lower-throughput variant |
| **Managed Service for Apache Kafka** | When you specifically need Kafka APIs (existing Kafka clients) |

#### Stream and batch processing — Dataflow

Managed **Apache Beam**. Runs ETL pipelines for both streaming AND batch. Often pairs with Pub/Sub (input) and BigQuery / Cloud Storage (output).

> **Micro-summary:** *Pick by workload shape: blobs → Cloud Storage. Files → Filestore (NFS) or NetApp (SMB). Relational → Cloud SQL → AlloyDB → Spanner. Documents → Firestore. Wide-column at scale → Bigtable. Analytics → BigQuery. Cache → Memorystore. Events → Pub/Sub. ETL → Dataflow.*

### 2.2 Cloud Storage in detail

A **bucket** holds **objects**. Bucket names are **globally unique** — once taken, gone.

#### Location types

| Type | Replicated where | Use case |
|---|---|---|
| **Region** | One region (multiple zones) | Most workloads — low latency near compute |
| **Dual-region** | Two specific regions, synchronously replicated | HA across regions you choose |
| **Multi-region** | Multiple regions in a continent (`eu`, `us`, `asia`) | Globally served content, max availability |

#### Storage classes — chosen per object (or as bucket default)

| Class | Min storage duration | Retrieval cost | Access pattern |
|---|---|---|---|
| **Standard** | none | none | Hot data, frequent access |
| **Nearline** | 30 days | per-GB retrieval fee | Once a month |
| **Coldline** | 90 days | higher retrieval fee | A few times a year |
| **Archive** | 365 days | highest retrieval fee | Compliance, "almost never" |

> **Trap:** *Min storage duration is enforced.* Putting an object into Coldline and deleting it after 10 days **still costs you 90 days of storage**. The exam loves this.

#### Object Lifecycle Management

You can switch classes per object — manually or via lifecycle rules like:
- *"After 30 days → transition to Nearline"*
- *"After 365 days → delete"*

Lifecycle policies are evaluated **roughly daily**, not in real-time.

#### Versioning

- Enable at the bucket level.
- Each overwrite or delete keeps the prior copy (called a "non-current version").
- Combined with lifecycle rules ("delete non-current versions older than 30 days"), this gives you a **soft-delete system**.

#### Object holds and retention policies — for compliance

| Mechanism | What it does |
|---|---|
| **Retention policy** | Bucket-level. Objects can't be deleted before N seconds since creation |
| **Object holds** (event-based / temporary) | Pin an individual object against deletion |
| **Object versioning** | Soft delete via version history |

> **Important:** Once a retention policy is **locked**, you cannot reduce or remove it until the period passes. Built specifically for compliance.

#### Encryption

Google encrypts at rest **by default**. Three options:

| Option | Acronym | Who controls the key |
|---|---|---|
| **Google-managed** | GMEK | Google (default) |
| **Customer-managed** | CMEK | You, in Cloud KMS |
| **Customer-supplied** | CSEK | You, supplied on every request. Google never stores it |

> **Micro-summary:** *Bucket location: region/dual-region/multi-region. Storage classes: Standard → Nearline → Coldline → Archive. Lifecycle moves objects automatically. Versioning + retention policies = soft delete + compliance. Encryption is GMEK by default; CMEK or CSEK if you need control.*

### 2.3 Loading data — how to get data IN

Multiple options. Pick by **size** and **how often**.

| Tool | Use for |
|---|---|
| `gcloud storage cp` (or older `gsutil cp`) | One-off uploads / downloads, scripts |
| **Cloud Storage console upload** | Small ad-hoc files |
| **Storage Transfer Service** | Scheduled transfers from S3, Azure Blob, on-prem (via agent), or GCS-to-GCS |
| **Transfer Appliance** | Petabyte-scale offline transfer — Google ships a physical box |
| **BigQuery Data Transfer Service** | Scheduled imports into BigQuery from SaaS sources (YouTube, Google Ads, S3, etc.) |
| **Database Migration Service** | Online migration of MySQL/PostgreSQL/SQL Server/Oracle into Cloud SQL or AlloyDB |
| **bq load** | Load files from Cloud Storage into BigQuery |

#### Storage Transfer Service in detail

Three source families:

| Source | Auth pattern |
|---|---|
| **Cloud-to-cloud** | AWS S3 (access key or AWS WIF), Azure Blob (SAS token), other GCS buckets |
| **Public URL list** | TSV file with HTTPS URLs and MD5/sizes |
| **On-prem (any POSIX filesystem)** | Install **Transfer Service for on-prem agents** (Docker container); agents stream over TLS |

Job options:
- **Schedule** — one-shot, daily, hourly.
- **Filters** — include/exclude prefixes, modified-since timestamps.
- **Overwrite policy** — when destination has the file, overwrite vs. skip.
- **Bandwidth limit** — cap MB/s.
- **Notifications** — Pub/Sub topic on completion.

#### When to pick Transfer Appliance instead

For **>50 TB on a slow link**, Transfer Appliance is the answer. Google ships a 7 TB / 40 TB / 300 TB device, you load it, ship back, they upload to your bucket.

> **Trap:** *Storage Transfer Service ≠ Transfer Appliance.* Service is online; Appliance is a literal box for huge offline migrations.

#### For Cloud Storage → BigQuery

- **`bq load`** — batch.
- **Streaming inserts** / **Storage Write API** — continuous.

> **Micro-summary:** *Small/scripted = `gcloud storage cp`. Recurring = Storage Transfer Service. Petabytes offline = Transfer Appliance. Database migrations = Database Migration Service. SaaS → BigQuery = BigQuery Data Transfer Service.*

### 2.4 Multi-region redundancy

Each data product has its own redundancy story:

| Product | How redundancy works |
|---|---|
| **Cloud Storage** | Pick a multi-region or dual-region bucket; replication is automatic |
| **Cloud SQL** | HA = synchronous standby in another zone (same region). Cross-region replicas exist for DR but failover is manual |
| **Spanner** | Multi-region instance config; replication built in |
| **Firestore** | Pick multi-region location at database creation (permanent) |
| **BigQuery** | Dataset location is permanent. To "move", you copy |
| **Bigtable** | Replication with cluster copies in additional regions |
| **Pub/Sub** | Already global; messages stored in closest region by default |

> **Important:** *Backups vs. replication.* Replication = availability. Backups = "oops, I deleted the table". A real scenario needs both.

| Workload description | Pick |
|---|---|
| Petabytes of analytical SQL queries | **BigQuery** |

| Enterprise wants ONTAP / SMB | **NetApp Volumes** |

## 6. Common confusions — the things people mix up

### "Cloud SQL HA" vs "Cloud SQL read replicas"

- **HA** = synchronous standby, auto-failover. Standby is **not queryable**.
- **Read replicas** = async read-only copies. Used for offloading reads or DR.

### "Spanner" vs "AlloyDB"

- **Spanner** = global distribution + strong consistency + horizontal scale. Expensive.
- **AlloyDB** = single-region, faster PostgreSQL. Cheaper. Pick this unless the question explicitly says "global ACID".

### "Filestore" vs "NetApp Volumes"

- **Filestore** = NFS only.
- **NetApp Volumes** = NFS + SMB + ONTAP features.

### "Storage Transfer Service" vs "Transfer Appliance"

- **Service** = online, scheduled, over-the-wire.
- **Appliance** = physical box, for petabytes when bandwidth isn't enough.

### "Versioning" vs "Backups" vs "Retention policy"

- **Versioning** = soft delete (keeps overwritten/deleted versions).
- **Backups** = separate snapshots for restore.
- **Retention policy** = hard prevention of delete (compliance lock).

### "Firestore Native" vs "Firestore Datastore mode"

- **Native** = the modern one. Use this.
- **Datastore mode** = for legacy GAE apps. Don't pick on the exam unless told.
- **Permanent choice at database creation.**

## 7. Exam gotchas — the subtle traps

- **Bucket names are globally unique.** Once taken, gone forever.
- **Storage class min-duration charges are per-object.** Switching to Coldline and deleting next day still costs 90 days.
- **Object Lifecycle is async** — ~daily, not real-time.
- **Versioning + lifecycle = "soft delete"** pattern. Costs storage.
- **Retention policy locks you in.** Once locked, you cannot reduce it until period passes.
- **Cloud Storage default access** in new projects is **Uniform Bucket-Level Access**. Don't reach for ACLs unless explicitly mentioned.
- **Cloud SQL HA ≠ read replicas.** HA = automatic regional failover; replicas = manual.
- **Spanner is expensive** — only the right answer for global strong consistency.
- **Firestore Native vs. Datastore mode** is permanent at creation. Native is modern.
- **Bigtable has no free tier** and isn't for "small app DB".
- **BigQuery dataset location is permanent** — to "move" a dataset, copy it.
- **Pub/Sub is global** but has a regional storage policy if data residency matters.
- **Storage Transfer Service ≠ Transfer Appliance.**
- **Database Migration Service** = right answer for online MySQL/Postgres/Oracle migrations. Not "use mysqldump".
- **Memorystore Basic is single-zone.** Standard tier for HA.

## 8. Named scenarios — deeper design walk-throughs

### Scenario A — The "Waterfall" lifecycle strategy

**Context.** A media company keeps user-uploaded video. Access pattern is well-known:
- Day 0–30: heavy access (just uploaded, hot in feeds).
- Day 31–90: occasional access (some users come back to share).
- Day 91–365: rare access (≈ once or twice a year).
- After 1 year: legal hold for 7 years, almost never read but **must be retrievable** within 12 hours.
- Versions kept on overwrite for 30 days, then deleted.

**Recommended design — a "waterfall" of lifecycle rules on a single bucket:**

```yaml
lifecycle:
  rule:
    - action:    {type: SetStorageClass, storageClass: NEARLINE}
      condition: {age: 30,  matchesStorageClass: [STANDARD]}
    - action:    {type: SetStorageClass, storageClass: COLDLINE}
      condition: {age: 90,  matchesStorageClass: [NEARLINE]}
    - action:    {type: SetStorageClass, storageClass: ARCHIVE}
      condition: {age: 365, matchesStorageClass: [COLDLINE]}
    - action:    {type: Delete}
      condition: {age: 30,  isLive: false}          # non-current versions
```

Plus: enable **versioning** (so the non-current rule has something to delete), and lock a **bucket retention policy** of 7 years (`220752000s`) — the lock is irrevocable and exactly satisfies the legal hold.

**Why this works.** Each rule fires when the *previous* tier is no longer cost-justified. The min-storage-duration penalties (30/90/365) align naturally with transition ages — you never delete a Coldline object before its 90 days are up. Lifecycle is async (~daily). Roughly 1/10th the cost of leaving everything in Standard for 7 years.

### Scenario B — Global scale & consistency

**Context.** A global ride-hailing app needs a single source of truth for trips. Requirements:
- Drivers and riders in 30+ countries; users may move between regions mid-trip.
- Reads must reflect writes immediately, **everywhere** (driver reassignments must be globally consistent).
- 50,000 writes/sec at peak; horizontal scale required.
- SQL workload — joins across `trips`, `drivers`, `riders`, `payments`.

**Right answer: Spanner**, in a multi-region instance config (e.g. `nam3` for North America or `eur6` for Europe + secondary).

**Why not the alternatives?**

| Option | Why it doesn't work |
|---|---|
| Cloud SQL with cross-region read replicas | Replicas are async read-only; promotion is manual. No global writes |
| AlloyDB | Scales reads, but primary is single-region. Writes don't scale globally |
| Bigtable | Wide-column, no SQL joins; wrong query model for trip ledger |
| Firestore (multi-region) | Strongly consistent but document-oriented, not relational |

**Trade-offs.** Spanner is **expensive** — minimum 1 PU per region in multi-region; budget hundreds of $/month at the smallest size. The exam loves to lay out scenarios that *seem* to need Spanner but actually fit AlloyDB; read carefully for "globally consistent" or "strongly consistent across regions".

### Scenario C — The processing engine choice

**Context.** A retail company has three distinct data jobs:
1. **Streaming clickstream → real-time dashboard** — every click in mobile app published to Pub/Sub; near-real-time funnel.
2. **Nightly batch ETL** — yesterday's transactions land in Cloud Storage as JSON; clean/aggregate, load into BigQuery.
3. **Scheduled SQL transforms** — once daily, recompute "customer lifetime value" from existing BigQuery tables.

**Right pick per job:**

| Job | Service | Why |
|---|---|---|
| Streaming clickstream | **Dataflow (streaming)** with Pub/Sub → BigQuery | Beam handles windowing, watermarks, exactly-once into BigQuery. Auto-scaling absorbs spikes |
| Nightly batch ETL | **Dataflow (batch)**, or **bq load** if no transforms needed | Dataflow if you need transforms; plain `bq load` for trivial schema-already-matches |
| In-warehouse SQL transform | **BigQuery scheduled queries** (or **Dataform** for managed dbt-style) | Data is already in BigQuery — Dataflow is overkill |

**Why this works.** Each engine has a sweet spot: Dataflow for stream + complex transforms; BigQuery scheduled queries / Dataform for in-warehouse SQL; Pub/Sub as the streaming bus; bq load for trivial ingest. Don't reach for Managed Service for Apache Kafka unless you specifically need Kafka APIs.

### Scenario D — The Windows migration challenge

**Context.** A company is migrating an on-prem Windows-based app that:
- Uses **SMB shares** between multiple Windows VMs.
- Runs SQL Server (already migrated to Cloud SQL for SQL Server).
- Has a single .NET app server group needing the SMB share for documents and report templates.

**The trap.** Filestore is the obvious "managed file storage" answer — but **Filestore is NFS-only**. Windows can technically mount NFS, but it's awkward.

**Right answer: Google Cloud NetApp Volumes.** It's the only Google-managed file service that supports **SMB (v2/v3)** natively and can do dual-protocol if you ever add Linux access.

**Architecture.**
- **NetApp Volumes capacity pool** in `europe-west3` with the *Premium* service level (or *Extreme* for higher IOPS) inside the same VPC as the Windows VMs.
- **SMB volume** with Active Directory integration (NetApp can join your AD so file-level ACLs work like on-prem).
- Windows VMs `net use Z: \\<volume-host>\share` — looks identical to on-prem.
- Snapshots and SnapMirror replication built-in for backup/DR.

**Why not Filestore?** SMB is unsupported. Forcing Windows to use NFS would lose proper ACL semantics and surprise the Windows ops team.

## 9. Practice scenarios

### Q1 — Picking the right database

An application needs to store millions of small JSON documents (user profiles), with low-latency reads from web/mobile SDKs and minimal operations overhead. Which database?

A. Cloud SQL for MySQL.
B. BigQuery.
C. **Firestore (Native mode).**
D. Bigtable.

**Answer: C.** Firestore Native is the document DB designed for app data with mobile/web SDKs and simple queries. A would work but requires schema. B is analytical, not OLTP. D is for huge wide-column workloads (IoT/ad-tech), not user profiles.

### Q2 — Storage class for archival

A team has 50 TB of compliance archives that must be retained for 7 years and accessed *less than once a year*. Cost is the priority. Which storage class?

A. Standard.
B. Nearline.
C. Coldline.
D. **Archive.**

**Answer: D.** Archive is for compliance data accessed almost never; min 365-day storage. C targets a few times a year. B is roughly monthly access.

### Q3 — Loading data

An on-prem team has 200 TB of historical logs to move into Cloud Storage. Bandwidth is limited (50 Mbps WAN) and they need it in 1 week. Which approach?

A. Scripted `gcloud storage cp` with parallelism.
B. Storage Transfer Service with on-prem agents.
C. **Transfer Appliance.**
D. Database Migration Service.

**Answer: C.** 200 TB at 50 Mbps takes ~370 days — hopeless over the wire. Transfer Appliance is the physical-shipping solution. B is the *online* equivalent, would saturate the link. D is for databases.

### Q4 — BigQuery cost

A team's monthly BigQuery on-demand bill is dominated by repeated queries scanning the same large tables. They want predictable cost. The recommended action:

A. **Switch to BigQuery capacity (slot-based) reservations.**
B. Move data to Cloud Storage and query as external tables.
C. Increase the dataset's time-travel window.
D. Switch tables to long-term storage.

**Answer: A.** Capacity pricing (slot reservations) is the predictable, flat-rate alternative to on-demand. B usually performs worse and still scans bytes. C is unrelated to query cost. D affects storage cost, not query.

### Q5 — Multi-region resilience for a relational DB

A globally distributed e-commerce platform requires single SQL queries to be strongly consistent across regions, with horizontal scale to thousands of writes per second. Which database?

A. Cloud SQL with cross-region read replicas.
B. **Spanner.**
C. AlloyDB.
D. Bigtable.

**Answer: B.** Spanner is the only managed database that combines global distribution with strong consistency and horizontal write scale. A's cross-region replicas are read-only. C scales reads but is regional. D is non-relational.

### Lab 5 — Manage objects with the `gcloud storage` CLI

```bash
BUCKET=$DEVSHELL_PROJECT_ID-demo-bucket

# Listing
gcloud storage ls -l gs://$BUCKET/
gcloud storage ls -lr gs://$BUCKET/**

# Copy local → bucket (parallel, recursive)
mkdir -p site && for i in 1 2 3; do echo "page $i" > site/page$i.html; done
gcloud storage cp -r site/ gs://$BUCKET/site/

# Copy bucket → bucket (server-side)
gcloud storage cp gs://$BUCKET/site/page1.html gs://$BUCKET/archive/

# Move (rename) — server-side
gcloud storage mv gs://$BUCKET/archive/page1.html gs://$BUCKET/archive/page1-renamed.html

# Change storage class
gcloud storage objects update gs://$BUCKET/archive/page1-renamed.html --storage-class=COLDLINE

# Custom metadata
gcloud storage objects update gs://$BUCKET/site/page1.html \
    --custom-metadata=owner=alice,env=dev

# Inspect
gcloud storage objects describe gs://$BUCKET/site/page1.html

# Delete
gcloud storage rm gs://$BUCKET/archive/page1-renamed.html
gcloud storage rm -r gs://$BUCKET/site/

# Note: `gsutil` is the older CLI; same verbs but different flags. Migrate to `gcloud storage`.
gsutil ls gs://$BUCKET/   # still works
```

## 11. TL;DR — what to remember if you only have 5 minutes before the exam

1. **Workload → product** is the most-tested skill. Memorize the decision table in section 3.
2. **Cloud Storage classes:** Standard → Nearline (≥30 d) → Coldline (≥90 d) → Archive (≥365 d). Min-duration is enforced.
3. **Bucket location:** Region / Dual-region / Multi-region. Permanent.
4. **Cloud SQL HA = synchronous standby.** Standby is NOT queryable. Read replicas are different.
5. **Spanner = global ACID + horizontal scale.** Expensive — only when explicitly needed.
6. **Firestore Native vs Datastore mode** = permanent at creation. Native is modern.
7. **Bigtable** for petabyte-scale wide-column. Not for small app DBs.
8. **BigQuery dataset location is permanent.** To move = copy.
9. **Filestore = NFS only. NetApp Volumes = NFS + SMB.**
10. **Storage Transfer Service = online. Transfer Appliance = physical box.**
11. **Database Migration Service** = online MySQL/PG/Oracle migrations.
12. **Versioning + lifecycle = soft-delete pattern.** Locked retention policy = compliance lock.
13. **Encryption:** GMEK (default) → CMEK (your KMS key) → CSEK (your key on every request).
