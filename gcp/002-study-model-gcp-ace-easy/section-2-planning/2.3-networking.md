# 2.3 — Planning and implementing networking resources (easy version)

> **What the official exam guide calls this:** Section 2.3 — VPC with subnets (custom mode, Shared VPC), Cloud Next Generation Firewall (Cloud NGFW) ingress/egress policies and attributes, Tags (secure Tags) and service accounts in firewall rules, network connectivity (Cloud VPN, VPC Network Peering, Cloud Interconnect), choosing/deploying load balancers, Network Service Tiers.

---

## 1. Why this matters for the exam

Networking on GCP is **different** from AWS or on-prem in important ways:

- **VPCs are global.**
- **Subnets are regional.**
- Firewalls and routes work at the VPC level, not subnet.

Many exam questions test whether you understand these defaults, plus:
- Choosing connectivity (peering / VPN / Interconnect).
- Choosing the right load balancer.

Common scenarios:
- *"A team can't reach a resource"* → diagnose firewall, route, or service-IP issue.
- *"On-prem to GCP"* → pick VPN vs. Interconnect by bandwidth/SLA.
- *"App needs a load balancer"* → match traffic type and scope to the right LB product.

## 2. Core concepts

### 2.1 VPC fundamentals — "global VPC, regional subnets"

#### The single most important fact

> **VPCs are global. Subnets are regional.**
>
> One VPC spans every region. Inside it, you create subnets in whichever regions you need.

This is unlike AWS, where VPCs are regional. The exam assumes you know this.

#### What lives at the VPC level

- **Routes** — default routes go to the internet gateway, default gateway, etc. Custom routes are added at the VPC level.
- **Firewall rules** — rules attach to the VPC but can target subnets, tags, or service accounts.
- **Internal IPs route freely** between subnets in the same VPC, **across regions**, with no extra config.

#### VPC modes

| Mode | Behaviour | When |
|---|---|---|
| **Auto** | Subnet automatically created in every region with Google-chosen CIDRs | Demos. Not recommended for prod |
| **Custom** | You create subnets explicitly with the CIDRs you want | **Production** — exam expects this |

#### Default VPC

Each new project gets a `default` VPC in **auto mode** with permissive firewall rules:
- Allow internal
- Allow ICMP
- Allow SSH/RDP from any source

For production: **delete it** and build a custom VPC.

> **Micro-summary:** *VPC = global. Subnets = regional. Routes/firewalls live on the VPC. Auto mode is for demos; production = custom mode.*

---

### 2.2 Shared VPC — central network team owns the network

#### The problem this solves

You have many app teams in different projects, but you want **one** central network team to own all the networking (VPCs, subnets, firewall policies, Interconnect). App teams should deploy VMs and GKE clusters in shared subnets without being able to mess with routes or firewalls.

#### How it works

- A **host project** owns the VPC and its subnets.
- One or more **service projects** are attached to the host project.
- Their resources (VMs, GKE nodes) live in the **host's network**.
- Network admins manage networking in one place; app teams operate in their own projects.

```
Host project (owns VPC + subnets)
   │
   ├── Service project A   ← VMs use the host VPC
   ├── Service project B
   └── Service project C
```

#### Required role

**Compute Shared VPC Admin** at the **org level** (or folder), not on the host project, for the initial setup.

> **Micro-summary:** *Shared VPC = host project owns the network, service projects use it. Right answer when one team owns the network and many teams build apps.*

---

### 2.3 VPC Peering — connect two VPCs

#### What it does

Connects two VPCs (in the same or different orgs) so their internal IPs can reach each other directly.

#### Important rules

- **Non-transitive.** A peered with B and B peered with C does **NOT** let A reach C. (Frequent exam trap!)
- **No overlapping CIDRs allowed.** Plan IP space upfront.
- **Cheaper than VPN** — traffic stays on Google's network and isn't encrypted.
- Perfect for "two GCP projects, internal traffic only".

> **Trap:** *Peering is non-transitive.* Triangle topology requires A↔C peering directly, or hub-and-spoke with a router VM as the hub.

> **Micro-summary:** *Peering = direct VPC-to-VPC link. Non-transitive. No overlapping CIDRs. Cheaper than VPN.*

---

### 2.4 Hybrid connectivity — VPN and Interconnect

#### The problem this solves

You have on-prem infrastructure (or another cloud) and need to connect it privately to a GCP VPC.

#### Four options

| Product | Bandwidth | SLA | When to use |
|---|---|---|---|
| **Cloud VPN** (Classic / HA) | Up to ~3 Gbps per tunnel | 99.9% (Classic) / 99.99% (HA) | Quick, traffic over public internet, IPsec encrypted |
| **Dedicated Interconnect** | 10 / 100 Gbps per circuit | 99.9% / 99.99% with redundancy | High bandwidth, private fibre to a Google PoP, requires colocation |
| **Partner Interconnect** | 50 Mbps – 50 Gbps | 99.9% / 99.99% with redundancy | Through a service provider, no colocation needed |
| **Cross-Cloud Interconnect** | 10 / 100 Gbps | 99.9% / 99.99% | Direct private link to AWS / Azure / Oracle / Alibaba |

> **HA VPN** is the modern variant — two tunnels for active/active redundancy and the higher SLA. **Use HA VPN unless told otherwise.**

#### Cloud Router

For routing across these links, you typically use **Cloud Router** with **BGP**, which dynamically learns and announces routes between your VPC and on-prem.

> **Micro-summary:** *Quick + IPsec = HA VPN (99.99% SLA). High bandwidth + colocation = Dedicated Interconnect. Through a telco = Partner Interconnect. Cloud Router does dynamic BGP routing.*

### 2.5 Firewall — Cloud NGFW

Google's firewall product is now called **Cloud Next Generation Firewall (Cloud NGFW)**. Two layers:

| Layer | Scope | Order of evaluation |
|---|---|---|
| **VPC firewall rules** (classic) | Single VPC | Applied at VPC level |
| **Firewall policies** | Hierarchical: org / folder / regional | Applied **above** VPC rules, before VPC rules |

#### What's in a rule

| Attribute | Values |
|---|---|
| **Direction** | `INGRESS` or `EGRESS` |
| **Action** | `ALLOW`, `DENY`, or (NGFW) `GOTO_NEXT` to chain policies |
| **Source / destination** | CIDRs, secure tags, service accounts |
| **Targets** | Which instances the rule applies to (tag or service account) |
| **Protocol & ports** | `tcp:80,443`, `udp:53`, `icmp`, `all`, etc. |
| **Priority** | 0–65535 (lower = higher priority) |

#### Default behaviour

- Default ingress: **deny** from anywhere.
- Default egress: **allow** to anywhere.
- Two implicit rules sit at priority 65535: allow all egress + deny all ingress.

> **Common failure mode:** *"Why can't I reach my VM?"* — you forgot to add an ingress allow rule.

#### Three ways to identify "which VMs this rule applies to"

| Identifier | Scope | Notes |
|---|---|---|
| **Network tags** (legacy) | Per-VM, free-form strings | Simple but **not access-controlled** — anyone with edit on the VM can self-assign |
| **Secure tags** (Resource Manager tags) | Org/folder/project/resource scoped, **IAM-controlled** | The modern choice — auditable and restrict-able |
| **Service accounts** | Identity attached to the VM | Often the cleanest — tie firewall rules to identity |

> **Exam steer:** The exam guide explicitly mentions **secure Tags and service accounts** in firewall rules. Google is steering you **away from network tags**.

> **Micro-summary:** *Cloud NGFW = the firewall. Default deny ingress, allow egress. Modern targets = secure tags or service accounts (NOT network tags).*

### 2.6 Load balancers — pick the right one

Google's load balancers are a family. The exam tests **which one to pick**.

#### Three big questions

1. **Where is the LB?** Global vs. regional.
2. **What traffic?** HTTP(S) / TCP / UDP / SSL passthrough / proxy.
3. **External (internet-facing)** or **internal (within VPC)**.

#### The list

| LB | Layer | Scope | Traffic | Use case |
|---|---|---|---|---|
| **Global external Application Load Balancer** | L7 (HTTP/S) | Global, anycast | HTTPS | Public websites/APIs, multi-region apps |
| **Regional external Application Load Balancer** | L7 | Regional | HTTPS | App in a single region, public-facing |
| **Internal Application Load Balancer** | L7 | Regional | HTTPS | Microservices inside a VPC |
| **Cross-region internal Application Load Balancer** | L7 | Multi-region | HTTPS | Internal services across regions |
| **Global external Proxy Network Load Balancer** | L4 (TCP/SSL proxy) | Global | TCP / SSL | Non-HTTP TCP to a global frontend |
| **External passthrough Network Load Balancer** | L4 | Regional | TCP / UDP | Preserves client IP — game servers, custom protocols |
| **Internal passthrough Network Load Balancer** | L4 | Regional | TCP / UDP | Internal L4 LB, preserves client IP |

#### Decision flow

1. **HTTP/S?** → Application Load Balancer.
2. **TCP/UDP and need to preserve client IP?** → Passthrough Network LB.
3. **TCP/SSL but want global anycast and proxy termination?** → Proxy Network LB.
4. **Public or private?** → external vs. internal flavour.
5. **Single region or multi-region?** → regional vs. global.

> **Micro-summary:** *Application LB = L7 / HTTP. Network LB = L4 / TCP/UDP. Passthrough preserves client IP. Proxy terminates connections. Global = anycast (Premium tier required).*

### 2.7 Network Service Tiers — Premium vs. Standard

How traffic exits Google's network.

| Tier | Path | Cost | When |
|---|---|---|---|
| **Premium** (default) | Through Google's global private backbone end-to-end, exits as close to the user as possible | Higher | Production user-facing traffic; required for global LBs |
| **Standard** | Exits Google near the source region; traverses the public internet | Lower | Cost-sensitive, regional workloads, dev/test |

> **Important:** **Premium tier is required for global external Application Load Balancers and Cloud CDN.** Standard tier locks you to regional LBs only.

> **Micro-summary:** *Premium = Google's private network end-to-end (default, required for global LBs). Standard = cheaper, public internet, regional only.*

## 3. Decision criteria — the cheat sheet

| Question | Answer |
|---|---|
| Two GCP projects need internal connectivity | **VPC Peering** (or Shared VPC if same org) |
| 10+ teams, central network control | **Shared VPC** |
| On-prem to GCP, fast to set up, < 3 Gbps | **HA VPN** |
| On-prem to GCP, need 10 Gbps+ and physical isolation | **Dedicated Interconnect** |
| On-prem to GCP through an existing telco | **Partner Interconnect** |
| Public website with global users | **Global external Application LB + Premium tier** |
| TCP gaming traffic preserving client IP | **External passthrough Network LB** |
| Internal microservice fronting | **Internal Application LB** |
| Cost > performance, single region | **Standard tier** |
| Replace network tags with something controllable | **Secure tags** (or service-account targets) |

## 5. gcloud reference

```bash
# ── VPC & subnets ──
gcloud compute networks create prod-vpc --subnet-mode=custom
gcloud compute networks subnets create prod-eu \
    --network=prod-vpc --region=europe-west3 --range=10.10.0.0/20
gcloud compute networks subnets expand-ip-range prod-eu --region=europe-west3 --prefix-length=18

# ── Shared VPC ──
gcloud compute shared-vpc enable HOST_PROJECT_ID
gcloud compute shared-vpc associated-projects add SERVICE_PROJECT_ID --host-project=HOST_PROJECT_ID

# ── VPC Peering ──
gcloud compute networks peerings create prod-to-data \
    --network=prod-vpc --peer-network=data-vpc --peer-project=other-project

# ── Firewall rules ──
gcloud compute firewall-rules create allow-http \
    --network=prod-vpc --direction=INGRESS --action=ALLOW \
    --rules=tcp:80,tcp:443 --source-ranges=0.0.0.0/0 --target-tags=http-server

gcloud compute firewall-rules create allow-internal \
    --network=prod-vpc --direction=INGRESS --action=ALLOW \
    --rules=all --source-ranges=10.10.0.0/16

# Service-account-targeted rule (no tags)
gcloud compute firewall-rules create allow-from-app \
    --network=prod-vpc --direction=INGRESS --action=ALLOW \
    --rules=tcp:8080 \
    --source-service-accounts=app-sa@PROJECT.iam.gserviceaccount.com \
    --target-service-accounts=db-sa@PROJECT.iam.gserviceaccount.com

# ── HA VPN (skeleton) ──
gcloud compute routers create prod-router --network=prod-vpc --region=europe-west3 --asn=65001
gcloud compute vpn-gateways create prod-vpn --network=prod-vpc --region=europe-west3
# (peer gateway, tunnels, BGP sessions follow)

# ── Cloud Router ──
gcloud compute routers add-bgp-peer prod-router --region=europe-west3 \
    --peer-name=onprem --peer-asn=65010 --peer-ip-address=169.254.0.2 --interface=if-0

# ── Load balancer (global external Application LB, simplified) ──
gcloud compute health-checks create http web-hc --port=80
gcloud compute backend-services create web-bs --global --protocol=HTTP --health-checks=web-hc
gcloud compute backend-services add-backend web-bs --global \
    --instance-group=web-mig --instance-group-region=europe-west3
gcloud compute url-maps create web-url --default-service=web-bs
gcloud compute target-http-proxies create web-proxy --url-map=web-url
gcloud compute forwarding-rules create web-fr --global \
    --target-http-proxy=web-proxy --ports=80

# ── Network Service Tier ──
gcloud compute project-info update --default-network-tier=PREMIUM
```

## 6. Common confusions — the things people mix up

### "VPC" vs "subnet"

- **VPC** = global, holds routes and firewall rules.
- **Subnet** = regional, holds a CIDR range.

### "VPC Peering" vs "Shared VPC"

- **Peering** = two VPCs, equal partners, light setup, non-transitive.
- **Shared VPC** = one host VPC owned by the network team, used by many service projects.

### "Cloud VPN" vs "Cloud Interconnect"

- **VPN** = quick, encrypted over the public internet.
- **Interconnect** = private fibre, requires colocation (Dedicated) or telco (Partner).

### "HA VPN" vs "Classic VPN"

- **HA VPN** = two tunnels, 99.99% SLA. Modern, default choice.
- **Classic VPN** = single tunnel, 99.9% SLA.

### "Application LB" vs "Network LB"

- **Application LB** = L7 (HTTP/HTTPS).
- **Network LB** = L4 (TCP/UDP).

### "Passthrough" vs "Proxy"

- **Passthrough** = preserves client IP. Connection goes directly to the backend.
- **Proxy** = LB terminates the connection and starts a new one to the backend. Lose client IP unless you read the X-Forwarded-For header.

### "Network tags" vs "Secure tags" vs "Service accounts"

- **Network tags** = legacy, free-form strings, **not** IAM-controlled.
- **Secure tags** = Resource Manager tags, IAM-controlled.
- **Service accounts** = identity attached to a VM.

### "Premium tier" vs "Standard tier"

- **Premium** = Google's private backbone end-to-end. Required for global LBs and CDN.
- **Standard** = exits to public internet near source region. Cheaper but regional only.

## 7. Exam gotchas — the subtle traps

- **VPCs are global, subnets are regional.** The #1 GCP networking fact.
- **Auto-mode VPCs are convenient but discouraged.** Production = custom mode.
- **VPC Peering is non-transitive.** A↔B and B↔C does NOT give A↔C.
- **Overlapping CIDRs break peering.**
- **Default firewall: allow egress, deny ingress.**
- **Network tags vs. secure tags vs. service accounts** — modern answer is **secure tags or service accounts**, not network tags.
- **Premium tier is required** for global external Application LBs and Cloud CDN.
- **HA VPN gives 99.99% SLA**; Classic VPN gives 99.9%.
- **Interconnect requires colocation (Dedicated) or a partner (Partner).** Not set up in a day.
- **Cross-region internal LB exists only at L7.** Internal passthrough Network LB is regional only.
- **Shared VPC roles** must be granted at **org/folder** level, not the host project.
- **Cloud Router uses BGP** to dynamically advertise routes.

## 8. Named scenarios — deeper design walk-throughs

### Scenario A — Identity-Based Defense

**Story.** A retail company is moving from a flat VPC where every VM had a network tag like `db-client` and the firewall allowed `tcp:5432` from anything tagged `db-client` → anything tagged `db-server`. A red-team review found that any developer with `compute.instances.setTags` could add `db-client` to their dev VM and reach prod databases.

**Design.**
- Create two service accounts: `app-sa@…` (attached to app VMs) and `db-sa@…` (attached to DB VMs).
- Rewrite the firewall rule to **target by service account**:
  ```bash
  gcloud compute firewall-rules create allow-app-to-db \
      --network=prod-vpc --direction=INGRESS --action=ALLOW \
      --rules=tcp:5432 \
      --source-service-accounts=app-sa@PROJECT.iam.gserviceaccount.com \
      --target-service-accounts=db-sa@PROJECT.iam.gserviceaccount.com
  ```
- Lock down `iam.serviceAccounts.actAs` on `app-sa` so only the app team can attach it to a VM.
- Optionally replace any remaining tag-based rules with **secure tags**.

**Why it works.** Network tags are free-form strings; secure tags and service accounts are IAM-bound. The firewall now matches *who* the VM is, not *what label* it wears.

**Recognize it.** "Self-assigned tag", "identity-based", "least privilege at the network layer", "compliance audit said tags aren't access-controlled" → **secure tags** or **service-account-targeted rules**.

### Scenario B — Centralized Network Management

**Story.** An enterprise has 15 application teams. Each team wants its own GCP project for IAM isolation, billing, and quota — but the network team must own all VPCs, subnets, firewall policies, and the on-prem Interconnect.

**Design.**
- Create a **host project** (`netcorp-shared-host`) that owns the VPC, subnets, Cloud Router, Interconnect, and hierarchical firewall policies.
- Enable Shared VPC: `gcloud compute shared-vpc enable netcorp-shared-host`.
- For each team, create a **service project** and attach it: `gcloud compute shared-vpc associated-projects add team-payments --host-project=netcorp-shared-host`.
- Grant the network team **Compute Shared VPC Admin** at the **org level** (not host project — it's an org-level role).
- Grant each team **Compute Network User** on the specific subnet(s) they're allowed to use.
- Apply a **hierarchical firewall policy** at the folder level for guardrails (deny egress to known-bad CIDRs, allow IAP SSH).

**Why it works.** Service projects' VMs and pods get IPs from the host project's subnets. All traffic is governed by the host's VPC, routes, and firewall policies. App teams keep project-level IAM and quota independence; network team keeps centralized control.

**Recognize it.** "Central security/network team owns the network", "many teams in their own projects", "single place for firewall policies and Interconnect" → **Shared VPC + hierarchical firewall policies**.

### Scenario C — Going Global

**Story.** A media startup launches a VOD site. Users are in NA, EU, SE-Asia. They want one DNS name (`watch.example.com`), HTTPS termination, edge caching, DDoS protection. Latency targets: <100 ms TTFB worldwide.

**Design.**
- **Frontend.** Reserve a **global** static external IP on **Premium tier** (`gcloud compute addresses create vod-ip --global --network-tier=PREMIUM`).
- **Load balancer.** **Global external Application LB** with a Google-managed SSL certificate for `watch.example.com`.
- **Backends.** Regional MIGs in `us-central1`, `europe-west3`, `asia-southeast1`. The LB picks the closest healthy backend.
- **Cloud CDN.** Enable on the backend service so HLS chunks and posters cache at Google's ~180 edge PoPs.
- **Cloud Armor.** Attach a security policy with rate limiting, geo-blocking, OWASP Top-10 preconfigured rules.
- **DNS.** Point `watch.example.com` (A record) at the LB's static IP via Cloud DNS.

**Why it works.** Premium tier puts traffic on Google's private backbone end-to-end. A user in Singapore reaches the closest Google PoP within milliseconds. The LB then proxies to the closest healthy backend. One IP, one cert, one config — multi-region HA built in.

**Recognize it.** "Global users", "single IP / single domain", "low latency worldwide", "CDN", "DDoS / WAF" → **Global external Application LB + Premium tier + Cloud CDN + Cloud Armor**. Standard tier is a trap.

## 9. Practice scenarios

### Q1 — Cross-project private connectivity

Project A and project B (same org) need their internal IPs to talk privately. What's the simplest mechanism?

A. **VPC Network Peering.**
B. Shared VPC.
C. Cloud VPN between the two VPCs.
D. Cloud Interconnect.

**Answer: A.** VPC Peering is the lightweight, cheap, non-transitive connection. B is heavier and centralizes networking under a host project. C/D are for hybrid (GCP↔on-prem).

### Q2 — Hybrid connectivity SLA

A company needs an on-prem ↔ GCP link with 99.99% SLA, ~1 Gbps bandwidth, encryption, no colocation. What's the right product?

A. Classic Cloud VPN with two tunnels.
B. **HA VPN.**
C. Dedicated Interconnect.
D. Partner Interconnect.

**Answer: B.** HA VPN gives 99.99% SLA over the internet with IPsec encryption — no colocation. Classic VPN (A) is 99.9%. C requires colocation. D is bandwidth-flexible but doesn't necessarily encrypt.

### Q3 — Firewall target choice

A security review says *"the firewall rule that allows database traffic targets VMs by network tag, but anyone with edit on the VM can self-assign that tag."* What's the recommended fix?

A. Move all targeted VMs to a separate VPC.
B. **Use secure tags or a service account as the firewall target.**
C. Add the rule at higher priority.
D. Switch from ingress to egress.

**Answer: B.** Secure tags are IAM-controlled; service accounts are IAM-bound. Both prevent unauthorized self-tagging. The exam guide explicitly steers toward this.

### Q4 — Load balancer choice

You need a public, global, HTTPS-terminating load balancer for a multi-region web app, with Cloud CDN. Which LB and tier?

A. Regional external Application LB on Standard tier.
B. **Global external Application LB on Premium tier.**
C. External passthrough Network LB on Premium tier.
D. Internal Application LB.

**Answer: B.** Global external Application LB is the L7 product for public web apps and is required by Cloud CDN. Premium tier is required for global LBs.

### Q5 — Non-transitive peering trap

VPCs A↔B are peered, B↔C are peered. A team in VPC A reports they can't reach a VM in VPC C. Why?

A. Wrong CIDRs.
B. **VPC Peering is non-transitive — A doesn't see C's networks via B.**
C. Firewall rules in B are blocking.
D. The peering is broken.

**Answer: B.** Peering does not propagate routes through intermediates. Peer A↔C directly, or use hub-and-spoke with a VPN/router VM.

## 10. Hands-on labs

### Lab 1 — Create a custom VPC with subnets in two regions

**Goal:** build a `prod-vpc` with subnets in `europe-west3` and `us-central1` and confirm cross-region internal connectivity.

**Console:**
1. *VPC network → VPC networks → Create VPC network*.
2. **Name:** `prod-vpc`. **Subnet creation mode:** *Custom*.
3. **Subnet 1:** name `prod-eu`, region `europe-west3`, range `10.10.0.0/20`. **Done**.
4. **Add subnet → Subnet 2:** name `prod-us`, region `us-central1`, range `10.20.0.0/20`. **Done**.
5. **Dynamic routing mode:** *Global*. *Create*.
6. *Compute Engine → VM instances → Create instance*. `vm-eu` in `europe-west3-a`, network `prod-vpc`, subnet `prod-eu`.
7. Repeat for `vm-us` in `us-central1-a`.
8. SSH into `vm-eu` → `ping -c 3 <internal-ip-of-vm-us>` (after firewall lab).

**gcloud:**
```bash
gcloud compute networks create prod-vpc --subnet-mode=custom --bgp-routing-mode=global
gcloud compute networks subnets create prod-eu --network=prod-vpc --region=europe-west3 --range=10.10.0.0/20
gcloud compute networks subnets create prod-us --network=prod-vpc --region=us-central1 --range=10.20.0.0/20
```

### Lab 2 — Firewall rule using a service account as target

**Goal:** allow SSH only from IAP and HTTP only to VMs whose service account is `web-sa`. No legacy network tags.

**Console:**
1. *IAM & Admin → Service Accounts → Create service account*. Name `web-sa`. Skip role grants.
2. *VPC network → Firewall → Create firewall rule*.
3. **Name:** `prod-allow-iap-ssh`. **Network:** `prod-vpc`. **Direction:** *Ingress*. **Action:** *Allow*.
4. **Targets:** *All instances*. **Source IP:** `35.235.240.0/20` (IAP). **Ports:** `tcp:22`. *Create*.
5. **Create firewall rule** again. **Name:** `prod-allow-http-to-web-sa`.
6. **Targets:** *Specified service account*. Target: `web-sa@${PROJECT}.iam.gserviceaccount.com`. **Source IP:** `0.0.0.0/0`. **Ports:** `tcp:80`. *Create*.
7. Edit `vm-eu` → *Identity and API access* → set service account to `web-sa`. Save & restart.

**gcloud:**
```bash
gcloud iam service-accounts create web-sa
gcloud compute firewall-rules create prod-allow-iap-ssh \
    --network=prod-vpc --direction=INGRESS --action=ALLOW \
    --rules=tcp:22 --source-ranges=35.235.240.0/20
gcloud compute firewall-rules create prod-allow-http-to-web-sa \
    --network=prod-vpc --direction=INGRESS --action=ALLOW \
    --rules=tcp:80 --source-ranges=0.0.0.0/0 \
    --target-service-accounts=web-sa@$DEVSHELL_PROJECT_ID.iam.gserviceaccount.com
```

### Lab 3 — VPC Peering between two VPCs

**Goal:** peer `prod-vpc` with a new `data-vpc` so their internal IPs reach each other.

**Console:**
1. *VPC network → VPC networks → Create*. `data-vpc`, custom mode, subnet `data-eu` `10.30.0.0/20` in `europe-west3`.
2. *VPC network → VPC network peering → Create peering connection*.
3. **Name:** `prod-to-data`. **Your VPC:** `prod-vpc`. **Peered VPC:** same project → `data-vpc`. *Create*.
4. **Create** again, reverse: `data-to-prod`, **Your VPC:** `data-vpc`, **Peered VPC:** `prod-vpc`. **Both sides must exist.**
5. Confirm both rows show **Active**.
6. Create a VM in `data-vpc/data-eu` and ping from `vm-eu` (after adding internal-allow firewall on both sides).

**gcloud:**

### Lab 4 — Egress firewall rule (deny outbound to a CIDR)

**Goal:** add an explicit egress *deny* rule that prevents `vm-eu` (tagged `restricted`) from reaching `203.0.113.0/24`.

**Console:**
1. *VPC network → Firewall → Create firewall rule*.
2. **Name:** `prod-deny-egress-203`. **Direction:** *Egress*. **Action:** *Deny*. **Priority:** `900` (beats default at 65535).
3. **Targets:** *Specified target tags*. **Tag:** `restricted`.
4. **Destination IPs:** `203.0.113.0/24`. **Ports:** *all*. *Create*.
5. Edit `vm-eu` → **Network tags** → add `restricted`. *Save*.
6. SSH `vm-eu` → `curl -m 5 203.0.113.10` blocks; `curl -m 5 8.8.8.8` still works.

**gcloud:**

### Lab 5 — Global external Application Load Balancer fronting a MIG

**Goal:** stand up a public global HTTPS LB that routes `/` to a regional MIG.

**Prerequisites:** the `web-mig` MIG from §2.1 Lab 13 (or any MIG with port 80 exposed) and an `http-server` firewall rule.

**Console (reserve static IP):**
1. *VPC network → IP addresses → Reserve external static address*.
2. **Name:** `lb-ip`. **Tier:** *Premium*. **IP version:** IPv4. **Type:** *Global*. *Reserve*.

**Console (create the LB):**
3. *Network services → Load balancing → Create load balancer*.
4. **Type:** *Application Load Balancer (HTTP/S)*. **Public-facing**. **Best for global workloads** (= Global external Application LB). *Configure*.
5. **Name:** `web-lb`.
6. **Frontend → Add frontend IP and port:**
   - **Name:** `https-frontend`. **Protocol:** HTTPS. **Port:** 443. **IP:** `lb-ip`.
   - **Certificate:** *Create new* → **Google-managed**. (Or use HTTP/Port 80 for the lab.)
7. **Backend → Create a backend service:**
   - **Name:** `web-bs`. **Type:** *Instance group*. **Protocol:** HTTP. **Port:** 80.
   - **Backends → Add backend** — `web-mig`, **Port:** `80`, **Mode:** *Utilization*, **Max:** `80%`.
   - **Health check:** *Create* → `web-lb-hc`, port `80`, path `/`. *Save*.
   - (Optional) Enable **Cloud CDN**.
8. **Routing rules** — leave default *Match all* → `web-bs`.
9. *Create*. Wait ~3–5 min.
10. Browse to `http://<lb-ip>/`.

**gcloud (HTTP variant):**
```bash
gcloud compute addresses create lb-ip --global --network-tier=PREMIUM
gcloud compute health-checks create http web-lb-hc --port=80 --request-path=/
gcloud compute backend-services create web-bs --global --protocol=HTTP \
    --health-checks=web-lb-hc --enable-cdn
gcloud compute backend-services add-backend web-bs --global \
    --instance-group=web-mig --instance-group-region=europe-west3 \
    --balancing-mode=UTILIZATION --max-utilization=0.8

gcloud compute url-maps create web-url --default-service=web-bs
gcloud compute target-http-proxies create web-proxy --url-map=web-url
gcloud compute forwarding-rules create web-fr --global \
    --address=lb-ip --target-http-proxy=web-proxy --ports=80

curl http://$(gcloud compute addresses describe lb-ip --global --format='value(address)')
```

**Cleanup:**
```bash

gcloud compute target-http-proxies delete web-proxy --quiet
gcloud compute url-maps delete web-url --quiet
gcloud compute backend-services delete web-bs --global --quiet
gcloud compute health-checks delete web-lb-hc --quiet

```

## 11. TL;DR — what to remember if you only have 5 minutes before the exam

1. **VPC = global. Subnet = regional.** The most important fact.
2. **Custom mode VPC** for production. Auto mode for demos.
3. **Shared VPC** = host project owns network, service projects use it.
4. **VPC Peering = non-transitive.** No overlapping CIDRs.
5. **Hybrid connectivity:** HA VPN (99.99%, encrypted) → Dedicated Interconnect (10/100 Gbps, colocation) → Partner Interconnect (telco) → Cross-Cloud Interconnect (to AWS/Azure/etc.).
6. **Default firewall:** allow egress, deny ingress.
7. **Firewall targets** — modern: secure tags or service accounts. Legacy: network tags.
8. **Cloud Router** = dynamic BGP routing.
9. **Application LB** = L7 / HTTP. **Network LB** = L4 / TCP/UDP.
10. **Passthrough** = preserves client IP. **Proxy** = terminates.
11. **Premium tier** = required for global LBs and Cloud CDN.
12. **Standard tier** = cheaper, regional only.
