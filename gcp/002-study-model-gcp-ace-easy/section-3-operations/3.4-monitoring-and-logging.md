# 3.4 — Monitoring and logging (the easy version)

> **What the official exam guide calls this:** Section 3.4 — "Monitoring and logging". Sub-topics: Cloud Monitoring alerts on resource metrics, custom metrics (from apps or logs), exporting logs (on-prem, BigQuery), log buckets/log analytics/log routers, viewing/filtering logs, viewing log message details, cloud diagnostics (Cloud Trace, Cloud Profiler, Query Insights, index advisor), Personalized Service Health dashboard, Ops Agent, Managed Service for Prometheus, audit logs, Gemini Cloud Assist for Cloud Monitoring, Active Assist for resource optimization.

---

## 1. Why this matters for the exam

This is one of the broader topics on the exam. Google Cloud Observability has many surfaces (Monitoring, Logging, Trace, Profiler, Error Reporting), and you need to know which one solves which problem.

Expect questions that test whether you can:
- Set up a useful **alert** on a resource metric.
- Build **custom metrics** from logs or app instrumentation.
- Route logs to the right destination (BigQuery, Cloud Storage, Pub/Sub, on-prem).
- Recognise each diagnostic tool and what it's for.
- Read **audit logs** to answer "who did what".

## 2. Core concepts

### 2.0 The Google Cloud Observability suite — pick the right tool

Half the exam in this section is "match the question to the tool".

| Sub-product | Answers |
|---|---|
| **Cloud Monitoring** | "Is something broken right now?" — metrics, dashboards, alerts, uptime checks |
| **Cloud Logging** | "What did a system print?" — text/structured logs, retention, routing, audit trail |
| **Cloud Trace** | "Where did time go in this request?" — distributed tracing across services |
| **Cloud Profiler** | "Which function burns CPU/memory?" — continuous production profiling |
| **Error Reporting** | "What new errors are users hitting?" — error grouping and alerts |
| **Service Health** (Personalized) | "Is Google itself broken?" — incidents that affect *your* projects |

All of them are project-scoped by default. You aggregate via a **metrics scope** (Monitoring) or **log routers** (Logging).

*Micro-summary: Monitoring = metrics. Logging = text. Trace = distributed timing. Profiler = function-level CPU/heap. Error Reporting = error groups. Service Health = is Google broken (for you).*

### 2.1 Cloud Monitoring fundamentals

#### Metrics scope — "one dashboard for many projects"

**The problem this solves.** A central SRE team needs one dashboard showing 25 application projects. They don't want to flip between 25 consoles.

A **metrics scope** is a project that aggregates metrics from one or more **monitored projects**. Dashboards and alerts live in the scoping project; data flows in from the others.

By default, a project is its own scope. To consolidate, attach app projects to a central scoping project.

#### Alerting policies

An **alerting policy** = condition(s) + duration + notification channel(s).

- **Condition** — usually a metric threshold (`compute.googleapis.com/instance/cpu/utilization > 0.8 for 5 minutes`).
- **Duration** — how long the condition must be true before it fires.
- **Notification channels** — email, SMS, Slack, PagerDuty, webhooks, Pub/Sub.
- **Auto-close** — alerts close automatically once healthy for a set duration.
- **Documentation field** — Markdown sent with the alert; use it for runbooks.

**Gotcha:** If your duration is 5 minutes, a condition that's true for 1 minute won't fire. The exam tests this.

#### Uptime checks — synthetic black-box probes

**The problem this solves.** Your platform metrics look fine, but customers are complaining. The reason is a backend dependency, or DNS, or TLS — none of which platform metrics see. Probe from outside.

Cloud Monitoring's **uptime check** is a synthetic HTTP/HTTPS/TCP probe run from multiple Google-owned global locations.

- **Target types:** URL (HTTP/HTTPS), Compute Engine VM, App Engine service, generic TCP host.
- **Frequency:** every 1, 5, 10, or 15 minutes.
- **Locations:** any 3+ of US / Europe / South America / Asia Pacific.
- **Validation:** response code (`2xx` by default) plus optional **content match** (substring or regex in the body).
- **Authentication:** Basic auth or Bearer token for protected endpoints.
- **Alerting:** convert failures to an alert with a one-click *Create alert* on the uptime-check page.

Uptime checks are billed per check; very cheap. Canonical answer for "we want to be paged when the public site is down" without instrumenting the app.

#### Custom metrics — bring your own data

Two ways to get your own data into Cloud Monitoring:

1. **Application code** — call the Monitoring API (`monitoring_v3`) or use OpenCensus / OpenTelemetry SDKs. Metric type is `custom.googleapis.com/...`.
2. **Logs-based metrics** — define a metric that counts (or extracts a value from) log entries matching a filter. Cheap and powerful — great for "errors per minute" or "checkout latency p50".

Two flavours of logs-based metrics:
- **Counter** — counts matching log entries.
- **Distribution** — extracts a numeric value from each entry (for percentiles).

*Micro-summary: alerts = metric + duration + channel. Uptime checks = synthetic probes with content match. Logs-based metrics convert log lines into a time-series you can alert on.*

### 2.2 Cloud Logging — buckets, routing, and analytics

#### Log buckets (different from Cloud Storage buckets!)

Logs are stored in **log buckets**. Each project has two by default:

- `_Required` — admin-activity audit logs and access-transparency. **Retention 400 days. Cannot be modified or deleted.**
- `_Default` — everything else. **Retention 30 days** (configurable).

You can create **user-defined log buckets** with custom retention (1–3650 days) and route specific logs into them.

#### Log Router and sinks

The **Log Router** decides what happens to each log entry. It runs **sinks**: rules that say "match these logs, send them to this destination".

| Destination | Use case |
|---|---|
| Another **log bucket** | Long retention, separate access controls |
| **BigQuery dataset** | SQL analytics over logs |
| **Cloud Storage bucket** | Cheap long-term archive |
| **Pub/Sub topic** | **Stream** logs to external systems (SIEM, on-prem SOC) |
| Another **project**'s logging | Centralised logging across the org |

**Two important behaviours:**
- Sinks have **filters** (CEL-like) that select which entries match.
- The `_Default` sink ingests into the `_Default` bucket. You can disable it to *exclude* certain logs entirely.
- Sinks define **inclusion**; **exclusion filters** prevent matching logs from being stored.

#### Log Analytics — SQL over logs in place

A feature on log buckets: enables **SQL queries** against the bucket's logs. Once a bucket is upgraded to Log Analytics, you write standard SQL (and can **link** it to a BigQuery dataset for unified querying).

Often the right answer for "we want to query our logs with SQL without setting up a BigQuery sink" — Log Analytics keeps logs in their bucket and still lets you SQL them.

#### Exporting logs

"Export" is exam shorthand for routing through the Log Router. Common targets:

- **BigQuery** — analytics. Sinks create date-partitioned tables.
- **Cloud Storage** — cheap archive. Files written hourly/daily.
- **Pub/Sub** — streaming to an external SIEM or on-prem.
- **Log bucket in another project** — centralised logging.

*Micro-summary: log buckets store logs (different from Cloud Storage). Log Router + sinks route logs out. Pub/Sub for streaming, BigQuery for SQL, GCS for archive, log buckets for retention. Log Analytics = SQL in place.*

### 2.3 Viewing and filtering logs (Logs Explorer)

The **Logs Explorer** is the primary UI:

- A **query bar** uses the Logging query language (`resource.type="gce_instance" AND severity>=ERROR`).
- **Severity levels** — `DEFAULT`, `INFO`, `WARNING`, `ERROR`, `CRITICAL`, `ALERT`, `EMERGENCY`.
- **Histogram** — frequency over time; click a bucket to zoom in.
- **Saved queries** and **shared queries** for reuse.

For investigations across many resources, combine resource type filters with text search.

### 2.4 Audit logs — four types, know all four

| Type | Captures | On by default? | Where it goes |
|---|---|---|---|
| **Admin Activity** | API calls that modify metadata/configuration | **Yes** | `_Required` (free, 400-day retention) |
| **System Event** | Google-system actions (e.g. live migrate) | **Yes** | `_Required` (free, 400-day retention) |
| **Data Access** | **Reads** of user data (and writes for some services) | **Mostly off**, must enable | `_Default` (charges apply) |
| **Policy Denied** | Denied access attempts (e.g. VPC-SC violation) | Yes | `_Default` |

**Classic exam scenario:** "We need to know who **read** this BigQuery table" → enable **Data Access** audit logs for BigQuery (off by default because high-volume and chargeable). If a question proposes Admin Activity for read auditing, that's the trap — Admin Activity captures *changes*, not reads.

*Micro-summary: Admin Activity = changes (free, on by default). Data Access = reads (off by default, costs money). Always ask: "is this about a change or a read?".*

### 2.5 Cloud diagnostics

#### Cloud Trace
**Distributed tracing.** Propagates request IDs across services so you can see where time is spent. Best with OpenTelemetry instrumentation. App Engine and Cloud Run auto-trace HTTP requests.

#### Cloud Profiler
**Continuous CPU + heap profiling** of running applications. Low-overhead, production-safe profiling for Go, Java, Node, Python. Use to find hot functions or memory leaks.

#### Error Reporting
Aggregates errors from logs (and from explicit `report` calls) into groups. Alerts on new error groups.

#### Query Insights / index advisor (Cloud SQL, AlloyDB, Spanner)

- **Query Insights** — slow query analysis and load patterns inside the DB console.
- **Index advisor** — recommends indexes that would speed up specific slow queries (Cloud SQL Postgres, Spanner).

When the exam asks "DB is slow, what tool?": **Query Insights** for the analysis, **index advisor** for recommendations.

### 2.6 Personalized Service Health

A console dashboard that shows **incidents on Google Cloud services that affect your specific projects**. More relevant than the public status page because it's filtered to your usage.

Available under *Service Health*. Recognise the name.

### 2.7 Ops Agent

The **Ops Agent** is the unified Google-supplied agent for VMs (Compute Engine, GKE-on-VMs, on-prem). It collects:
- **System metrics** (CPU, memory, disk, network).
- **Logs** (system, custom application logs).

It **replaces** the older Logging Agent + Monitoring Agent. Install it on VMs that should send rich telemetry; without it, you only get the host-level metrics Compute Engine provides automatically.

### 2.8 Google Cloud Managed Service for Prometheus

A Google-managed Prometheus stack. Accepts standard Prometheus metrics (Prometheus exposition format), stores them, queries with **PromQL**. Native integration with GKE.

Use when:
- Your team is already on Prometheus and wants long-term storage with managed scaling.
- You want PromQL queries alongside Cloud Monitoring metrics.

### 2.9 Gemini Cloud Assist for Cloud Monitoring

Gemini-powered assistant inside the Monitoring console: ask natural-language questions ("why are my errors spiking?"), get summaries, generate alert policies from descriptions.

Recognise the name.

### 2.10 Active Assist (recommendations)

A family of recommendations across Google Cloud:
- **IAM Recommender** — flags over-permissive bindings.
- **Compute Engine sizing recommendations** — over/underprovisioned VMs.
- **Idle resources** — unused IPs, disks, instances.
- **Unattended project recommender** — projects with no activity.
- **Firewall insights** — overlapping or unused firewall rules.

Surfaces in the **Recommendations Hub**. Use for the exam-guide phrasing "optimize resource utilization".

## 5. gcloud / CLI reference

```bash
# ── Logs explorer & queries ──
gcloud logging read 'resource.type="gce_instance" AND severity>=ERROR' --limit=20
gcloud logging read 'resource.type="cloud_run_revision" AND textPayload:"timeout"' \
    --freshness=1h --limit=50

# ── Log buckets ──
gcloud logging buckets create long-term --location=global --retention-days=400
gcloud logging buckets update _Default --location=global --retention-days=90
gcloud logging buckets list --location=global

# ── Log sinks (Log Router) ──
gcloud logging sinks create to-bq \
    bigquery.googleapis.com/projects/PROJECT/datasets/log_archive \
    --log-filter='resource.type="cloud_run_revision"'

gcloud logging sinks create to-gcs \
    storage.googleapis.com/log-archive-bucket \
    --log-filter='severity>=WARNING'

gcloud logging sinks create to-pubsub \
    pubsub.googleapis.com/projects/PROJECT/topics/siem-feed \
    --log-filter='logName:"cloudaudit.googleapis.com"'

# After creating a sink, grant the sink's writer SA permission on the destination
gcloud logging sinks describe to-bq      # shows the writerIdentity SA
# Then grant BigQuery Data Editor on the dataset to that SA

# ── Logs-based metrics ──
gcloud logging metrics create checkout_errors \
    --description="Failed checkouts" \
    --log-filter='resource.type="cloud_run_revision" AND severity=ERROR AND textPayload:"checkout failed"'

# ── Alerting (typically done via console; CLI is via the Monitoring API) ──
gcloud alpha monitoring policies list
gcloud alpha monitoring policies create --policy-from-file=policy.json

# ── Ops Agent ──
# Install on a Compute Engine VM (Linux):
curl -sSO https://dl.google.com/cloudagents/add-google-cloud-ops-agent-repo.sh
sudo bash add-google-cloud-ops-agent-repo.sh --also-install

# ── Managed Service for Prometheus on GKE ──
gcloud container clusters update std-cluster --region=europe-west3 \
    --enable-managed-prometheus

# ── Audit logs config ──
# Data Access logging is enabled per service via IAM policy; typically managed in the console
# or via `gcloud projects get-iam-policy / set-iam-policy` editing audit configs.
```

## 6. Common confusions

- **Log buckets vs Cloud Storage buckets.** Different products. Log buckets store logs (queried in Logs Explorer). GCS buckets store objects. A sink can route logs *to* a GCS bucket.
- **Admin Activity vs Data Access logs.** Admin = changes (writes, config). Data Access = reads. Different defaults: Admin is on; Data Access is mostly off.
- **`_Required` vs `_Default`.** `_Required` is locked (admin-activity audits, 400 days, free, can't modify). `_Default` is everything else (30 days by default, configurable).
- **Log Analytics vs BigQuery sink.** Log Analytics = SQL in place (logs stay in the log bucket). BigQuery sink = streams logs out into a BigQuery dataset (dual storage cost).
- **Pub/Sub sink vs BigQuery sink.** Pub/Sub for **streaming** (real-time SIEM). BigQuery for **batch SQL analytics**. Different problems.
- **Sink writerIdentity needs IAM on the destination.** Creating a sink isn't enough — you have to grant the sink's SA write permission on the target. Forgetting this is the #1 reason a sink "silently drops" logs.
- **Ops Agent vs the old agents.** Ops Agent replaces the legacy Logging Agent + Monitoring Agent. Modern answer.
- **Personalized Service Health vs the public status page.** Personalized = filtered to *your* projects. Public status = generic.
- **Cloud Trace requires instrumentation.** It's not magical — your app must propagate trace context (OpenTelemetry/OpenCensus). Cloud Run / App Engine give you HTTP traces for free.

## 7. Exam gotchas

- **`_Required` log bucket cannot be modified.** Don't try to redirect or delete admin-activity audit logs from it. (You can copy via a sink to *additional* destinations.)
- **Data Access audit logs are off by default** for most services (BigQuery's are off in particular). Turning them on costs money but is the right answer for "we need to know who read this".
- **`_Default` retention is 30 days** out of the box; for longer retention, either change it or sink to a longer-retention bucket / GCS.
- **Sinks need permission on the destination.** Cloud Logging creates a `writerIdentity` service account when you create the sink — you must grant it `roles/bigquery.dataEditor`, `roles/storage.objectCreator`, or `roles/pubsub.publisher` accordingly. Forgetting this is a top failure scenario.
- **Logs-based metrics are project-scoped** and counter or distribution. If a question describes "count specific log lines as a metric for an alert", that's the answer.
- **Log Analytics ≠ BigQuery export.** Log Analytics keeps logs in the log bucket and lets you SQL them in place; BigQuery export streams them out.
- **Ops Agent replaces** the legacy Logging + Monitoring agents. If a question mentions both, the modern answer is Ops Agent.
- **Managed Service for Prometheus** is not a replacement for Cloud Monitoring; it's a Prometheus-native ingestion path that *also* feeds Cloud Monitoring.
- **Personalized Service Health is not the public status page.** It's project-aware; the public page is generic.
- **Cloud Trace requires instrumentation** (OpenTelemetry / OpenCensus) — it doesn't magically get traces from arbitrary apps. Cloud Run / App Engine give you HTTP traces for free.
- **Alert duration matters.** A condition that is true for 1 minute won't fire if your duration is 5 minutes — frequent gotcha.
- **Active Assist / Recommender** is the right answer for "find unused IPs / right-size VMs / unused IAM permissions".

## 8. Named scenarios

### Scenario A — The Invisible Outage

**Story.** A SaaS company's checkout API was down for 47 minutes last quarter before anyone noticed. The Cloud Run service itself was healthy — every revision served 200s on `/healthz` — but a backend dependency (a third-party payment gateway) was timing out, so user checkouts hung. Cloud Monitoring's default VM/Cloud Run dashboards looked fine. The incident was discovered when a customer emailed support. Leadership wants: "we should never learn about an outage from a customer again."

**Design.**

1. **Synthetic black-box probe.** Create an **uptime check** against the user-facing URL (`https://api.example.com/checkout/dry-run`) that exercises the full path — including the dependency call — and asserts on a content match (`"status":"ok"` in the response body), not just `200 OK`. Run it from 4 global locations every 1 minute. The check fails if *any* configured location reports failure for the configured number of consecutive runs.
2. **Logs-based counter metric.** Define `checkout_5xx_per_min` filtering `resource.type="cloud_run_revision" AND severity>=ERROR AND jsonPayload.endpoint="/checkout"`. This converts log spikes into a time-series.
3. **Two alerting policies, layered.**
   - *Fast detection (cheap, noisy):* `checkout_5xx_per_min > 5` for 1 minute → page on-call.
   - *Slow confirmation (quiet, true-positive):* uptime-check failure for 2 consecutive minutes → also page on-call.
   Either signal alone fires; together they corroborate.
4. **Notification channels.** PagerDuty for the page; Slack `#incidents` channel for the heads-up; email for the asynchronous record. Add a **Documentation** field on each policy with a Markdown runbook: which dashboard to open, which gateway status page to check, how to fail over to the secondary processor.
5. **Personalized Service Health.** Subscribe the on-call to incidents on the dependent Google services (Pub/Sub, Cloud Run) so a Google-side outage is correlated immediately, not investigated from scratch.
6. **Auto-close** alerts after 30 minutes healthy so closed incidents don't linger in the queue.

**Why it works.** Default platform metrics measure platform health, not *your* user journey. The uptime check is the user; the logs-based metric is the symptom; the layered alerts trade off latency vs. false-positive rate. Now you learn about outages from your monitoring before customers email.

**Recognize it.** "Service was down and we didn't know", "alerts only fire after customers complain", "platform looked healthy but the user journey was broken" → **uptime check with content match + logs-based metric + alerting policy + Personalized Service Health**.

### Scenario B — The Blind Spot

**Story.** A regulated company is preparing for a SOC-2 audit. Auditors ask: "Show me every read of the `customers.pii_export` BigQuery table over the last 90 days." The team opens the Logs Explorer, queries audit logs… and finds nothing for read events. Admin Activity logs show table *creation*, *schema changes*, *deletion* — but no reads. Meanwhile, the security team wants logs streamed off-platform to their on-prem Splunk SIEM in near real time, retained for 7 years. Today nothing is exported anywhere; logs sit in `_Default` and age out after 30 days.

**Design.**

1. **Enable Data Access audit logs for BigQuery** (and any other service touching PII). Admin Activity is on by default; **Data Access is off by default** because it's high-volume and chargeable. Turn it on per service via *IAM & Admin → Audit Logs* (or by editing the project's IAM policy `auditConfigs`). Now every `BigQuery.JobService.InsertJob` and `BigQuery.TableService.GetTable` is captured with the principal email.
2. **Stream to Splunk via Pub/Sub.** Create a Log Router sink:
   ```bash
   gcloud logging sinks create audit-to-siem \
       pubsub.googleapis.com/projects/PROJECT/topics/siem-feed \
       --log-filter='logName:"cloudaudit.googleapis.com"'
   ```
   Grab the sink's `writerIdentity` and grant it `roles/pubsub.publisher` on the topic — forgetting this step is the #1 reason sinks silently drop logs. The Splunk side runs the **Splunk Add-on for Google Cloud Platform** as a Pub/Sub subscriber.
3. **Long-term cheap archive in GCS.** A second sink to a Coldline bucket with a 7-year **bucket lock** retention policy:
   ```bash
   gcloud storage buckets create gs://acme-audit-archive \
       --location=eu --default-storage-class=COLDLINE --uniform-bucket-level-access
   gcloud storage buckets update gs://acme-audit-archive --retention-period=7y
   gcloud storage buckets update gs://acme-audit-archive --lock-retention-policy
   ```
   Lock makes the retention immutable — even an org admin cannot shorten it, satisfying auditors.
4. **Log Analytics for ad-hoc SQL.** Upgrade the `_Default` log bucket to Log Analytics so the audit team can SQL recent logs in place without standing up a BigQuery export pipeline.
5. **Org-level sink for new projects.** Create the audit-export sink at the **organization** level with `--include-children` so future projects automatically export — no per-project configuration drift.

**Why it works.** Data Access logs answer "who *read* what"; Pub/Sub gives you streaming SIEM ingestion (BigQuery is for analytics, GCS for archive); locked-retention GCS is the compliance-grade durable copy; org-level sinks make the policy stick across the entire footprint.

**Recognize it.** "Audit who read this dataset", "stream logs to on-prem SIEM in real time", "7-year retention", "auditors need to see access history" → **enable Data Access audit logs + Pub/Sub sink to SIEM + GCS sink with locked retention + org-level sink with `--include-children`**. If the question proposes "Admin Activity logs" for read auditing, that's the trap — Admin Activity captures *changes*, not reads.

## 9. Practice scenarios

### Q1 — Logs-based metric for alerting
You need to be alerted when more than 5 entries with `severity=ERROR` appear in your Cloud Run service logs in any 1-minute window. The minimal configuration is:

A. Export logs to BigQuery and run a scheduled query.
B. **Create a logs-based counter metric on the matching filter; create an alerting policy on that metric.**
C. Configure Pub/Sub log routing and write a Cloud Function alerter.
D. Use `_Required` log bucket retention.

**Answer: B.** Logs-based metrics are designed for this — they convert log events to time-series, which you alert on like any other metric. A and C are heavier. D is unrelated to alerting.

### Q2 — Routing logs to a SIEM
Security wants every audit log streamed to an on-prem SIEM in near real time. Which Log Router destination?

A. BigQuery dataset.
B. Cloud Storage bucket.
C. **Pub/Sub topic** consumed by an on-prem subscriber over VPN.
D. Another log bucket.

**Answer: C.** Pub/Sub is the streaming-friendly export destination — the SIEM (or a forwarder on-prem) subscribes and gets logs as they arrive. A is for SQL analytics. B is for archive (batch files). D centralises but doesn't egress.

### Q3 — Audit "who read this BigQuery table?"
A finance dataset's table contents may have been viewed by an unauthorized user. You need to confirm. Which configuration is required, and is it on by default?

A. Admin Activity audit logs (always on).
B. **Data Access audit logs for BigQuery — must be enabled, not on by default.**
C. Cloud Trace.
D. Cloud Profiler.

**Answer: B.** Data Access audit logs cover read access to user data; they are *off by default* (high volume, costed). You must enable them per service before the access in question. A captures *changes*, not reads. C/D are diagnostics, not access auditing.

### Q4 — Multi-project monitoring
The SRE team wants a single dashboard showing CPU across 25 application projects. What's the right setup?

A. Build the dashboard in each project and switch between them.
B. **Use a metrics scope: pick one scoping project; add the 25 projects as monitored projects; build dashboards in the scoping project.**
C. Export metrics to BigQuery from each project; build a Looker dashboard.
D. Aggregate via Pub/Sub.

**Answer: B.** Metrics scopes were designed exactly for this. A doesn't scale. C/D are far more complex than needed.

### Q5 — Slow Cloud SQL query
A team complains about slow queries on a Cloud SQL Postgres instance. Which tools should they use to diagnose, and which to act?

A. Cloud Trace and Cloud Profiler.
B. **Query Insights to analyse slow queries; index advisor for actionable index recommendations.**
C. Personalized Service Health.
D. Active Assist for sizing recommendations.

**Answer: B.** Query Insights and the index advisor are the database-specific diagnostic tools that are exam-canonical for "DB is slow". A is for application-level tracing. C is for Google service incidents. D is generic resource sizing, not query tuning.

## 10. Hands-on labs

### Lab 1 — Create an alerting policy on VM CPU
**Goal:** alert when any VM's CPU is > 80% for 5 minutes; deliver to email.

**Console (notification channel):**
1. *Monitoring → Alerting → Edit notification channels*.
2. **Email** → *Add new*. Enter your email, display name `me`. *Save*. Confirm via email.

**Console (alerting policy):**
3. *Monitoring → Alerting → Create policy*.
4. **Select a metric:** *VM Instance → CPU → CPU utilization*. *Apply*.
5. **Filter:** none. **Aggregator:** mean. **Window:** 1 min. *Next*.
6. **Threshold:** *Above*, value `0.8`. **Trigger duration:** 5 min. *Next*.
7. **Notification channels:** select your email. **Alert name:** `vm-cpu-high`. **Documentation (Markdown):** `Runbook: log into the VM, run \`top\`, identify offending process.`. *Create policy*.
8. To test: SSH the VM, run `yes > /dev/null &` × 4 (or `stress` if available), wait 5–6 min — alert fires.

**gcloud:** alerting policies are typically defined in JSON/YAML and applied via the API.
```bash
gcloud alpha monitoring policies list
```

### Lab 2 — Logs-based counter metric + alert on errors
**Goal:** count Cloud Run ERROR logs and alert when > 5 / minute.

**Console (logs-based metric):**
1. *Logging → Logs-based metrics → Create metric*.
2. **Type:** Counter. **Name:** `cloud_run_errors`. **Filter:**
   ```
   resource.type="cloud_run_revision" AND severity=ERROR
   ```
3. *Create metric*.

**Console (alert on the metric):**
4. *Monitoring → Alerting → Create policy*.
5. **Select a metric:** search `cloud_run_errors` → *Logs-based metric*. *Apply*.
6. **Aggregation:** sum, **Alignment period:** 1 min.
7. **Condition:** above `5` for `1 min`. *Next*.
8. **Notification channel:** your email. **Name:** `cloud-run-error-spike`. *Create*.
9. Trigger one or more 5xx responses on your Cloud Run service to test.

**gcloud:**
```bash
gcloud logging metrics create cloud_run_errors \
    --description="Cloud Run ERROR logs" \
```

## 11. TL;DR (5-minute pre-exam recap)

1. **Cloud Observability suite:** Monitoring (metrics), Logging (text), Trace (timing), Profiler (CPU/heap), Error Reporting (error groups), Service Health (Google incidents).
2. **Alert policy = condition + duration + notification channel.** Add a Markdown runbook in the Documentation field.
3. **Uptime checks** = synthetic HTTP/TCP probes from global locations. Add **content match** to detect "200 OK but body is wrong".
4. **Logs-based metrics** = counter or distribution. Convert log lines to a time-series for alerting.
5. **Metrics scope** = one project aggregates metrics from many. Right answer for multi-project dashboards.
6. **Log buckets:** `_Required` (admin audits, 400 days, locked), `_Default` (everything else, 30 days). Create your own for custom retention.
7. **Log Router sinks** route logs to BigQuery (SQL), GCS (archive), Pub/Sub (streaming/SIEM), or another log bucket.
8. **Sinks need permission on the destination.** Grant the sink's `writerIdentity` SA the appropriate write role. #1 cause of "logs aren't arriving".
9. **Log Analytics** = SQL over logs in place. Don't need a BigQuery export.
10. **Audit logs:** Admin Activity (changes, on, free) vs Data Access (reads, **off by default**, costs money). Read auditing requires Data Access.
11. **Ops Agent** is the modern unified VM agent (replaces old Logging + Monitoring agents).
12. **Managed Service for Prometheus** = managed Prometheus on GKE; query with PromQL.
13. **Cloud Trace** needs instrumentation (OpenTelemetry). Cloud Run/App Engine give HTTP traces for free.
14. **Cloud SQL slow query?** → **Query Insights** (analysis) + **index advisor** (recommendation).
15. **Active Assist / Recommender** = "find idle/over-provisioned resources to save money".
16. **Personalized Service Health** = Google incidents that affect *your* projects (not the public status page).
