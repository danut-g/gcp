## 4. Inheritance (the most important rule)

```
           ┌──────────────────────────────────────┐
           │          ORGANIZATION                 │
           │  Editor for group:ops@co.com          │
           └──────────────────┬───────────────────┘
                              │ inherits down
                              ▼
           ┌──────────────────────────────────────┐
           │          FOLDER: Prod                 │
           │  Viewer for user:alice@co.com         │
           └──────────────────┬───────────────────┘
                              │ inherits down
                              ▼
           ┌──────────────────────────────────────┐
           │       PROJECT: web-app-prod           │
           │  (no extra binding here)              │
           └──────────────────┬───────────────────┘
                              │
                              ▼
           ┌──────────────────────────────────────┐
           │       RESOURCE: VM instance          │
           │                                      │
           │  Effective for alice = Viewer        │
           │  Effective for ops   = Editor        │
           └──────────────────────────────────────┘


  GOLDEN RULES
  ────────────
  1. Policies flow ONLY downward.
  2. UNION: more permissive wins. (parent Editor > child Viewer = Editor)
  3. Child CANNOT remove a parent's grant.
  4. Best practice: grant at the NARROWEST scope where universally true.
```

## 6. IAM Conditions

```
                            ┌── Time-bound
                            │     "until 2026-12-31"
                            │
        IAM Conditions ─────┤── Resource attribute
                            │     "only buckets named app-*"
                            │
                            └── Request attribute
                                  IP / region / time of day


  EXAMPLE: roles/storage.admin granted ONLY when
           resource.name.startsWith("projects/_/buckets/app-")
           AND request.time < timestamp("2026-12-31T00:00:00Z")
```

## 8. Org Policies vs IAM (recap)

```
  ┌──────────────────────────────────┬──────────────────────────────────┐
  │              IAM                 │       ORGANIZATION POLICY        │
  ├──────────────────────────────────┼──────────────────────────────────┤
  │  Controls WHO can do things      │  Controls WHAT can be done       │
  │  Permissive  (UNION)             │  Restrictive  (INTERSECTION)     │
  │  Owner can grant their peers     │  Owner CANNOT bypass org policy  │
  └──────────────────────────────────┴──────────────────────────────────┘

  EXAM PATTERN: "User has Owner but cannot create external-IP VM"
                ──► an org policy is blocking, not IAM.
```

## 10. Section 4.1 Cheat Sheet

```
  ┌──────────────────────────────────────────────────────────────────────────────┐
  │  4.1 QUICK REFERENCE                                                         │
  ├──────────────────────────────────────────────────────────────────────────────┤
  │  MODEL          WHO + ROLE + RESOURCE (+ optional CONDITION)                 │
  │  MEMBERS        user / group / serviceAccount / domain / allUsers etc.       │
  │  GROUPS         Always prefer over individual users                          │
  │  ROLE TYPES     Basic (avoid) / Predefined (preferred) / Custom              │
  │  INHERITANCE    Down only; UNION (most permissive wins)                      │
  │  GRANTING       Highest node where universally true; lowest for scope        │
  │  CONDITIONS     Time / resource / request attributes                         │
  │  TROUBLESHOOT   IAM Policy Troubleshooter for "why?"                         │
  │  ORG POLICY     INTERSECTION; owner cannot bypass                            │
  │  PUBLIC TRAP    allUsers makes resource public                               │
  │  DOMAIN POLICY  iam.allowedPolicyMemberDomains restricts external grants     │
  └──────────────────────────────────────────────────────────────────────────────┘
```
