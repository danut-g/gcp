# 4.1 — Identity and Access Management (the easy version)

> **What the official exam guide calls this:** Section 4.1 — "Managing Identity and Access Management (IAM)". Sub-topics: viewing and creating IAM policies, managing role types and defining custom IAM roles (basic, predefined, custom).

---

## 1. Why this matters for the exam

Section 4 is "only" 20% of the exam, but IAM **shows up everywhere** — in compute, storage, networking, observability scenarios. The exam tests whether you can:

- Read an IAM policy and decide whether a given identity can perform an action.
- Pick the **least-privileged** role for a job (basic vs. predefined vs. custom).
- Apply IAM at the **right node** of the hierarchy (project / folder / org / resource).
- Manage role bindings safely.

Most IAM questions are scenario-based: "this identity got an unexpected error" or "we want to grant the minimum permissions for X".

## 2. Core concepts

### 2.1 What is an IAM policy?

A **policy** is a collection of **bindings**, attached to a resource. A binding looks like:

```
{
  role:    "roles/storage.objectViewer",
  members: [ "user:alice@example.com",
             "group:devs@example.com",
             "serviceAccount:app@PROJECT.iam.gserviceaccount.com",
             "domain:example.com",
             "allAuthenticatedUsers",
             "allUsers" ],
  condition?: { ... }      // optional, IAM Conditions
}
```

A policy attaches to a node in the hierarchy (org / folder / project) **or** to many individual resources (a Cloud Storage bucket, a Pub/Sub topic, a BigQuery dataset, a VM).

#### Inheritance — the most important rule

IAM policies **inherit downward** and are **additive (union)**. A grant at the org node applies to every project below; **a child cannot remove a parent's grant**.

The effective permissions for an identity = the **union** of every binding from the resource up to the org node.

*Micro-summary: a policy = bindings (role + members + optional condition). It attaches at hierarchy nodes or specific resources. Inheritance is downward and additive.*

### 2.2 Members (principals) — the things you grant access to

| Type | Prefix | Example |
|---|---|---|
| User account | `user:` | `user:alice@example.com` |
| Group | `group:` | `group:devs@example.com` |
| Service account | `serviceAccount:` | `serviceAccount:app@my-project.iam.gserviceaccount.com` |
| Workspace / Cloud Identity domain | `domain:` | `domain:example.com` |
| All authenticated Google accounts | (special) | `allAuthenticatedUsers` |
| Anyone on the internet | (special) | `allUsers` |

**Always prefer groups** as the binding member. Individuals come and go; groups are stable.

`allUsers` and `allAuthenticatedUsers` make the resource public(ish). The exam frequently tests bucket/object exposure that boils down to one of these being present.

*Micro-summary: prefer `group:` over `user:`. `allUsers` = anyone on the internet. `allAuthenticatedUsers` = anyone with a Google account.*

### 2.3 Role types — three flavours

| Type | What it is | When to use |
|---|---|---|
| **Basic roles** (Owner, Editor, Viewer) | Legacy, **very broad** — Owner = total control, Editor = write everywhere, Viewer = read everywhere | **Avoid in production.** OK for sandboxes |
| **Predefined roles** | Maintained by Google per service (e.g. `roles/storage.objectViewer`, `roles/compute.instanceAdmin.v1`) | **The default** — pick the most specific predefined role |
| **Custom roles** | Roles you define from a list of permissions | **Only when predefined is too broad** and no narrower one exists |

#### Predefined naming pattern
`roles/<service>.<role>` — e.g. `roles/bigquery.dataEditor`, `roles/pubsub.subscriber`. Many services have an `Admin`, `User`, `Editor`, `Viewer` flavour, plus more specific ones.

#### Custom roles — the rules
- Defined at the **project** or **organization** level — **not at folder level**.
- A list of **permissions** (e.g. `compute.instances.start`, `compute.instances.stop`).
- Lifecycle states: `ALPHA` → `BETA` → `GA` → `DEPRECATED` → `DISABLED`.
- **Cannot include permissions you don't have.** No "create your own elevation" trick.

Use custom roles when:
- You want a tight "operator" role that can start/stop VMs but not create them.
- Compliance requires least-privilege documentation per role.

Avoid them when a predefined role already fits — they're more work to maintain.

*Micro-summary: walk down the ladder — basic (avoid) → predefined (default) → custom (gap-fill). Custom roles only at project/org level, never folder.*

### 2.4 Where to grant — the hierarchy choice

| Apply at | Effect |
|---|---|
| **Organization** | Every folder/project/resource inherits it. Reserve for org-wide identities (security team). |
| **Folder** | All projects in the folder. Ideal for env-wide grants ("all dev project Editor for the dev team"). |
| **Project** | The most common level. App teams typically operate here. |
| **Resource** | A single bucket, dataset, topic, instance, etc. The narrowest possible. |

**The rule:** apply at the **lowest level** that achieves the goal. A project-level Editor shouldn't be granted at the org node "to make life easier" — it leaks across every project.

### 2.5 IAM Conditions — gates on bindings

A binding can include a **condition** — a CEL expression that gates when the binding is active.

Common uses:
- **Time-bound access** — `request.time < timestamp("2026-12-31T00:00:00Z")` for a contractor.
- **Resource attributes** — `resource.name.startsWith("projects/X/buckets/public-")` to scope a role to specific resources.
- **Tag-based access** — match secure tags on the target.

Conditions only work with certain roles (those flagged "supports conditions"). For the exam: conditions = time-bounded access or granular resource scoping.

*Micro-summary: IAM Condition = a CEL filter on a binding. Use for time-bounded access (contractor for 6 months) without setting calendar reminders.*

### 2.6 Effective permissions and the IAM Policy Troubleshooter

The **Policy Troubleshooter** answers "can member X perform action Y on resource Z, and if not, why?". It walks the entire inheritance chain and reports which bindings would have applied.

The exam may describe a scenario where someone unexpectedly has access (or doesn't) — Policy Troubleshooter is often the right answer for "how do you investigate?".

### 2.7 Org policies vs. IAM (recap from 1.1)

These two coexist and are constantly confused:

- **IAM** says *who can do what*.
- **Organization policies** say *what is allowed at all*.

Even an Owner cannot create an external-IP VM if an org policy blocks `compute.vmExternalIpAccess`. IAM grants permission to perform an action *if the action is permitted by org policy in the first place*.

*Micro-summary: IAM (union of grants) determines who. Org policy (intersection of guardrails) determines what's allowed. Org policy can override IAM — but only to deny.*

## 3. Decision criteria

| Question | Answer |
|---|---|
| Pick a role for "read all BigQuery datasets" | Predefined `roles/bigquery.metadataViewer` or `roles/bigquery.dataViewer` (not Owner) |
| Read-only access to one bucket | `roles/storage.objectViewer` granted **on the bucket**, not the project |
| A new team needs all the standard developer powers in one project | Predefined "service-specific" roles, not basic Editor — but Editor is sometimes acceptable for sandboxes |
| Time-limited access for a contractor | Predefined role + **IAM Condition** with `request.time < ...` |
| Need to "start/stop VMs but not create them" | **Custom role** with `compute.instances.start`, `compute.instances.stop`, `compute.instances.list`, `compute.instances.get` |
| Investigate "Alice can't access X" | **IAM Policy Troubleshooter** |
| Audit role assignments | **IAM page** filtered to identity/role; or **Cloud Asset Inventory** for cross-project audit |
| Share access with a partner Google domain | `domain:partner.com` member on the relevant resource |
| Make a bucket world-readable | `allUsers` member with `roles/storage.objectViewer` (rarely the right answer; use Signed URLs instead) |

## 5. gcloud reference

```bash
# ── View policies ──
gcloud projects get-iam-policy PROJECT_ID                    # YAML dump
gcloud projects get-iam-policy PROJECT_ID --format=json
gcloud organizations get-iam-policy ORG_ID
gcloud resource-manager folders get-iam-policy FOLDER_ID

# Resource-level (varies by service)
gcloud storage buckets get-iam-policy gs://my-bucket
gcloud pubsub topics get-iam-policy orders
gcloud secrets get-iam-policy my-secret

# ── Add / remove a single binding ──
gcloud projects add-iam-policy-binding PROJECT_ID \
    --member=group:devs@example.com --role=roles/editor

gcloud projects remove-iam-policy-binding PROJECT_ID \
    --member=group:devs@example.com --role=roles/editor

# Resource-level bindings follow the same verb pattern
gcloud storage buckets add-iam-policy-binding gs://my-bucket \
    --member=user:alice@example.com --role=roles/storage.objectViewer

# ── IAM Conditions (time-bounded role) ──
gcloud projects add-iam-policy-binding PROJECT_ID \
    --member=user:contractor@example.com --role=roles/storage.admin \
    --condition='expression=request.time < timestamp("2026-12-31T00:00:00Z"),title=until_year_end'

# ── Roles catalogue ──
gcloud iam roles list                                          # predefined
gcloud iam roles list --project=PROJECT_ID                     # custom in project
gcloud iam roles describe roles/storage.objectViewer
gcloud iam roles describe MyCustomRole --project=PROJECT_ID

# ── Custom roles ──
gcloud iam roles create vmStartStop --project=PROJECT_ID \
    --title="VM Start/Stop" --description="Start/stop VMs only" \
    --permissions=compute.instances.start,compute.instances.stop,compute.instances.list,compute.instances.get \
    --stage=GA

gcloud iam roles update vmStartStop --project=PROJECT_ID \
    --add-permissions=compute.instances.reset

gcloud iam roles delete vmStartStop --project=PROJECT_ID

# ── Test what a member can do (Policy Troubleshooter via gcloud) ──
gcloud policy-troubleshoot iam \
    //cloudresourcemanager.googleapis.com/projects/PROJECT_ID \
    --principal=alice@example.com --permission=compute.instances.create

# ── Set policies wholesale (advanced — read-modify-write) ──
gcloud projects get-iam-policy PROJECT_ID > policy.yaml
# edit policy.yaml
gcloud projects set-iam-policy PROJECT_ID policy.yaml
```

## 6. Common confusions

- **Owner ≠ Editor.** Owner can change IAM (give roles, take them away). Editor can write to most resources but cannot change IAM.
- **Predefined ≠ basic.** Predefined roles are *per-service* (named like `roles/storage.objectViewer`). Basic roles are *project-wide* (Owner, Editor, Viewer).
- **Custom role ≠ predefined.** Custom roles are yours; you maintain them. Use only when no predefined role fits.
- **Inheritance is union, not max.** Grants from parent + child stack up. Removing a child binding doesn't undo a parent binding.
- **IAM condition vs Org policy.** Both restrict. Conditions sit on a binding (per-grant gate). Org policies sit on the hierarchy (constraint above IAM).
- **Resource-level IAM is *additive*, not exclusive.** A bucket-level Viewer binding doesn't restrict a user with project-level Editor — they're a Viewer on the bucket *and* an Editor everywhere else.
- **Custom roles can't be defined at folder level.** Project or org only.
- **`allUsers` is public.** It's not "users with accounts" — it's literally the open internet.
- **Service accounts are members in IAM (so you grant them roles), but they're also resources (so other people can be granted access *to* them).** This dual nature is covered in 4.2.

## 7. Exam gotchas

- **IAM is additive.** A child cannot remove a parent's binding. To restrict a user, remove the binding upstream — or use **Deny policies** (recent feature, mention if asked).
- **Basic roles are too broad.** "Editor" includes power to delete data in most services; the exam often asks you to *replace* basic roles with predefined ones.
- **Owner is more than Editor.** Owner can change IAM; Editor cannot.
- **Custom roles cannot be created at the folder level.** Project or org only.
- **`allUsers` makes things public.** A common security finding scenario.
- **Resource-level IAM beats project IAM in narrowness, not in priority.** Both apply (union) — granting `objectViewer` on a single bucket adds to whatever project IAM the user already has.
- **IAM Conditions are not supported on every role.** Some predefined roles still don't support conditions; the exam may mention this.
- **`gcloud projects set-iam-policy`** uses an etag for concurrency. Editing without re-getting the latest policy can cause a conflict — typical CI failure mode.
- **Policy Troubleshooter** is the canonical answer for "why does Alice not have access?" — not "look at IAM page manually".
- **Service accounts are members in IAM bindings.** They are *also* a resource you grant access *to* — see lesson 4.2 for the dual nature.
- **Org policies block actions even if IAM permits them.** "Why can't this Owner create a public bucket?" → org policy `storage.publicAccessPrevention`.
- **Group-of-groups works.** A group can be a member of another group; permissions cascade.

## 8. Named scenarios

### Scenario A — Least Privilege & Role Types

**Story.** A growing fintech is preparing for a SOC-2 audit. The auditor's first finding: "Your IAM is dominated by **basic roles** — 14 engineers have `Owner` on prod projects, 30+ have `Editor`. There is no separation between the developer who edits code and the operator who restarts VMs at 3 AM. Replace basic roles with least-privilege predefined or custom roles per job function." The team has 4 distinct personas:

1. **Application developer** — needs to read/write BigQuery datasets used by the service, deploy new Cloud Run revisions, read logs.
2. **Night-shift operator** — needs to start/stop/reset Compute Engine VMs but never create or delete them.
3. **Finance auditor** — read-only access to *one* specific BigQuery dataset (`finance.quarterly_close`), nothing else, and only until the end of the fiscal quarter.
4. **External partner team** — entire `partner.example.com` workspace needs viewer access to a single Cloud Storage bucket of shared data exports.

**Design.**

The exam wants you to walk down the role-type ladder and stop at the *narrowest* match.

| Persona | Wrong answer | Right answer | Why |
|---|---|---|---|
| **App developer** | `roles/editor` on the project | **Multiple predefined service-specific roles**: `roles/bigquery.dataEditor` + `roles/run.developer` + `roles/logging.viewer`, each at the **project** level | Predefined service roles are Google-maintained and least-privilege per service. Editor includes write to *every* service in the project — far too broad. |
| **Night operator** | `roles/compute.instanceAdmin.v1` | **Custom role** `vmStartStop` with `compute.instances.{start,stop,reset,get,list}` | No predefined role matches "start/stop only — never create/delete". Custom roles exist exactly for this gap. Define at the **project** level (custom roles cannot be defined at the folder level). |
| **Finance auditor** | `roles/bigquery.dataViewer` on the project (then remember to revoke later) | **Predefined `roles/bigquery.dataViewer`** granted **on the dataset only** (resource-level), with an **IAM Condition** `request.time < timestamp("2026-09-30T23:59:59Z")` | Resource-level grant scopes to one dataset; the condition auto-expires the access — no human reminder, no audit gap. |
| **Partner team** | Add each user individually as a member | **`domain:partner.example.com`** member with `roles/storage.objectViewer` on the **bucket only** | Domain principals cover an entire Google Workspace; new partner hires inherit access automatically; departing ones lose it when their account is removed at the partner. |

**The hierarchy choice for each grant.** Apply at the **lowest level that achieves the goal**:
- App developer roles → **project** (their work spans many resources in one project).
- Night operator role → **project** (any VM in scope, but not other projects).
- Finance auditor role → **resource** (single dataset only).
- Partner team role → **resource** (single bucket only).
- *Never* push these up to the folder/org level "to make it easier" — that's the basic-role trap in different clothing.

**Verification with the Policy Troubleshooter.** Before declaring the migration done, run the troubleshooter for each persona × representative action:
```bash
gcloud policy-troubleshoot iam \
    //cloudresourcemanager.googleapis.com/projects/PROD_PROJECT \
    --principal=operator@example.com --permission=compute.instances.delete
# Expected: NOT_GRANTED — the custom role omits this permission.

gcloud policy-troubleshoot iam \
    //bigquery.googleapis.com/projects/PROD_PROJECT/datasets/quarterly_close \
    --principal=auditor@example.com --permission=bigquery.tables.getData
# Expected: GRANTED until the condition expires, NOT_GRANTED afterwards.
```

**Cleanup of basic roles.** With the new bindings in place, remove `roles/editor` and `roles/owner` from individuals (keep one break-glass `roles/owner` group for emergencies, ideally with an IAM Condition + audit alerting on its use).

**Why it works.** Each persona gets the narrowest role that still lets them do their job: predefined service roles for normal developer work, custom roles for the gap predefined doesn't fill, resource-level grants when the scope is one bucket/dataset, IAM Conditions for time-bounded access, and `domain:` members for whole-organization partner access. Auditor finding addressed; "blast radius" of any one credential drops dramatically.

**Recognize it.** "Replace basic roles", "least privilege per job function", "operator can start/stop but not create", "contractor for 6 months", "external partner needs read access to one bucket" → walk the ladder: **predefined first, custom only if predefined doesn't fit, resource-level grant when scope is one resource, IAM Condition for time-bounded, `domain:` for whole-Workspace access**. If a question proposes Editor/Owner, that's almost always the wrong answer in a production scenario.

## 9. Practice scenarios

### Q1 — Least privilege for an operator
An operator must be able to start, stop, and view Compute Engine VMs in a project, but not create or delete them. Which role should they get?

A. `roles/compute.admin`.
B. `roles/editor`.
C. `roles/compute.instanceAdmin.v1`.
D. **A custom role with `compute.instances.start`, `compute.instances.stop`, `compute.instances.get`, `compute.instances.list`.**

**Answer: D.** None of the predefined roles match this exactly without granting more than the operator should have (instanceAdmin includes create/delete). Custom roles solve this precisely.

### Q2 — Time-limited access
A contractor needs Storage Admin on a project for 6 months only. The cleanest configuration?

A. Grant Storage Admin permanently and remove it later.
B. Grant Storage Admin and set a calendar reminder to remove it.
C. **Grant Storage Admin with an IAM Condition `request.time < timestamp("2026-12-31T00:00:00Z")`.**
D. Add the contractor to a special group; remove them after 6 months.

**Answer: C.** IAM Conditions enforce time-bounded access automatically. A and B rely on humans remembering. D works in practice but C is the recommended and exam-correct mechanism.

### Q3 — Investigating access
A user emails: "I can no longer access dataset X in BigQuery." You need to know which bindings (or absent bindings) explain it. Best tool?

A. Cloud Audit Logs.
B. **IAM Policy Troubleshooter.**
C. Manually inspect the IAM page at every level.
D. Cloud Asset Inventory.

**Answer: B.** Policy Troubleshooter walks the entire inheritance chain for (member, action, resource) and tells you exactly why access is or isn't granted. A shows past actions, not effective access. C is what Troubleshooter automates. D is good for inventory but not effective-access analysis.

### Q4 — Avoiding basic roles
A new dev team should be able to read and write data in BigQuery and to manage Cloud Run services in a project. Which is the most appropriate IAM grant?

A. `roles/editor` on the project.
B. `roles/owner` on the project.
C. **`roles/bigquery.dataEditor` and `roles/run.admin` on the project (predefined service-specific roles).**
D. Custom role combining all permissions.

**Answer: C.** Predefined per-service roles are the recommended path — they're maintained by Google and follow least privilege per service. A grants too much (write everywhere). B grants everything plus IAM control. D is unnecessary given good predefined options exist.

### Q5 — Public bucket trap
A bucket has a binding `allUsers` → `roles/storage.objectViewer`. Compliance flags this as a finding. The team objects: "We need this bucket reachable by external clients without Google accounts." Which is the recommended remediation that keeps external access while passing compliance?

A. Switch to ACLs.
B. Add `allAuthenticatedUsers`.
C. **Generate signed URLs for external clients; remove the public binding.**
D. Move the bucket to a different project.

**Answer: C.** Signed URLs grant time-limited access to specific objects without requiring identity, *and* keep the bucket private. A is regressive (UBLA is preferred). B still requires Google accounts and over-shares. D doesn't change the access posture.

## 10. Hands-on labs

### Lab 1 — Grant and revoke an IAM role in the console
**Goal:** Add a role to a group, verify it, then remove it.

**Console:**
1. Confirm the project context (top bar).
2. *IAM & Admin → IAM*.
3. Click **Grant access**.
4. **New principals:** enter the principal — `group:devs@example.com`, `user:alice@example.com`, or `serviceAccount:app@PROJECT.iam.gserviceaccount.com`.
5. **Assign roles:** choose a role from the list. Pick `Compute Viewer` (predefined `roles/compute.viewer`) for a low-risk demo.
6. (Optional) **Add condition** — give it a title and a CEL expression like `request.time < timestamp("2026-12-31T00:00:00Z")` for time-bounded access.
7. **Save**. The new binding appears in the IAM list, grouped under the principal.
8. To revoke: in the IAM list, click the **edit (pencil)** icon on the principal's row → **Delete (trash)** next to the role → **Save**.

Verify "effective" access:
- *IAM & Admin → Policy Troubleshooter*.
- Enter the principal email, the resource path, and the permission (e.g. `compute.instances.list`).
- The result tells you exactly which binding granted (or denied) access.

**gcloud:**
```bash
gcloud projects add-iam-policy-binding PROJECT_ID \
    --member=group:devs@example.com --role=roles/compute.viewer

gcloud projects remove-iam-policy-binding PROJECT_ID \
    --member=group:devs@example.com --role=roles/compute.viewer

# Same pattern at folder / org / resource scope
gcloud resource-manager folders add-iam-policy-binding FOLDER_ID --member=... --role=...
gcloud organizations add-iam-policy-binding ORG_ID --member=... --role=...
gcloud storage buckets add-iam-policy-binding gs://my-bucket --member=... --role=...
```

### Lab 2 — Create and use a custom IAM role
**Goal:** Build a "VM operator" role that can start/stop/list VMs but not create or delete them.

**Console:**
1. *IAM & Admin → Roles*.
2. Click **Create role**.
3. Fill **Title**: *VM Start/Stop*; **ID**: `vmStartStop`; **Description**: brief.
4. **Role launch stage:** *General Availability* (or Beta if you'll iterate).
5. **Add permissions** → search and tick:
   - `compute.instances.start`
   - `compute.instances.stop`
   - `compute.instances.reset`
   - `compute.instances.get`
   - `compute.instances.list`
6. **Create**. The role is now in the project's role catalogue.
7. Assign it: *IAM & Admin → IAM → Grant access* → *Custom roles → VM Start/Stop* (it appears alongside predefined roles).
8. Test: from a Cloud Shell impersonating the granted user, try `gcloud compute instances start my-vm` (should succeed) and `gcloud compute instances delete my-vm` (should fail with permission denied).

To revise: *IAM & Admin → Roles → (your role) → Edit*. Add or remove permissions; Save.

**gcloud:**
```bash
gcloud iam roles create vmStartStop --project=PROJECT_ID \
    --title="VM Start/Stop" --description="Start, stop, and view VMs only" \
    --permissions=compute.instances.start,compute.instances.stop,compute.instances.reset,compute.instances.get,compute.instances.list \
    --stage=GA

gcloud projects add-iam-policy-binding PROJECT_ID \
    --member=user:operator@example.com \
    --role=projects/PROJECT_ID/roles/vmStartStop

# Update / disable / delete
gcloud iam roles update vmStartStop --project=PROJECT_ID --add-permissions=compute.instances.osLogin
gcloud iam roles update vmStartStop --project=PROJECT_ID --stage=DISABLED
gcloud iam roles delete vmStartStop --project=PROJECT_ID
```
