# 4.2 — Service accounts (the easy version)

> **What the official exam guide calls this:** Section 4.2 — "Managing service accounts". Sub-topics: creating service accounts, using service accounts in IAM policies with minimum permissions, assigning service accounts to resources, managing IAM permissions of a service account, managing service account impersonation, creating and managing short-lived service account credentials, using a Google Cloud service account with a GKE application.

---

## 1. Why this matters for the exam

Service accounts (SAs) are the **identity that workloads (not humans) use** to call Google Cloud APIs:
- A VM hitting Cloud Storage.
- A Cloud Run service writing to Pub/Sub.
- A Dataflow job writing to BigQuery.

Almost every compute and data scenario on the exam quietly involves a service account.

**The single most important idea — and the most common exam trap:**

A service account has a **dual nature**:
1. It is a **member** in IAM policies (you grant it roles to access *other* resources).
2. It is also itself a **resource** (you grant *humans / other SAs* roles **on it** — to use it, manage it, or impersonate it).

Confusing those two is the #1 exam mistake.

---

## 2. Core concepts

### 2.1 What a service account is

An **identity** belonging to a project, with an email like:

```
NAME@PROJECT_ID.iam.gserviceaccount.com
```

Two flavours:

| Type | Created | Use |
|---|---|---|
| **User-managed** | You create them per workload | **The recommended pattern for production** |
| **Default service accounts** | Auto-created when you enable certain APIs | Convenience; should be replaced for production |

#### Default service accounts you'll see

- **Compute Engine default SA** — `PROJECT_NUMBER-compute@developer.gserviceaccount.com`. Created when Compute Engine API is enabled. Comes with the **Editor** role on the project — **wildly over-privileged**. Replace it on production VMs.
- **App Engine default SA** — `PROJECT_ID@appspot.gserviceaccount.com`.
- **Service agents** — `service-PROJECT_NUMBER@gcp-sa-<service>.iam.gserviceaccount.com`. Google's own SAs that act on your behalf for managed services. **Don't delete these.**

Classic exam scenario: "default Compute Engine SA has Editor — what's wrong, what should you do?" → **Create a user-managed SA with only the permissions the workload needs, and reassign it.**

*Micro-summary: prefer user-managed SAs. Default Compute Engine SA = Editor on the project = too much. Service agents (`gcp-sa-*`) belong to Google — leave them alone.*

### 2.2 The dual nature — member vs. resource

#### Service account as a **member**

You grant the SA roles on **other resources** so the workload can do its job:

> "Grant `serviceAccount:app@PROJECT.iam.gserviceaccount.com` the role `roles/storage.objectAdmin` on `gs://my-bucket`."

The SA can then read/write that bucket from any compute that runs as it.

#### Service account as a **resource**

You grant **humans (or other SAs)** roles **on the service account itself**:

> "Grant `user:alice@example.com` the role `roles/iam.serviceAccountUser` **on `app@PROJECT.iam.gserviceaccount.com`**."

Why? So Alice can attach this SA to a VM (or a Cloud Run service, etc.). The role on the SA controls **who can use it**, separately from what the SA itself can do.

**Three SA-as-a-resource roles you must know cold:**

| Role | What it grants on the SA |
|---|---|
| `roles/iam.serviceAccountUser` | The user can **attach** this SA to a resource (`actAs`) |
| `roles/iam.serviceAccountTokenCreator` | The user can **impersonate** the SA (mint short-lived tokens for it) |
| `roles/iam.serviceAccountAdmin` | The user can **manage** (create, delete, modify) SAs |

*Micro-summary: ServiceAccountUser = "I can attach this SA to a resource". TokenCreator = "I can impersonate it (mint tokens for it)". Admin = "I can manage SAs themselves". The exam tests the user-vs-tokenCreator distinction constantly.*

### 2.3 Assigning a service account to a resource

The principle: **one workload → one SA → minimum permissions**.

| Resource | Where you set the SA |
|---|---|
| Compute Engine VM | At create time (you can change later, but the VM must be **stopped**) |
| Compute Engine instance template | In the template definition; MIGs inherit it |
| GKE node pool | At create time; node SA — used for kubelet, image pulls |
| GKE pod (Workload Identity) | The pod's K8s SA is bound to a Google SA via Workload Identity |
| Cloud Run service / job | `--service-account` flag (or in console; defaults to App Engine SA if omitted) |
| Cloud Run functions | `--service-account` (in 2nd gen) |
| Cloud Build | The build's runtime SA — defaults to the Cloud Build SA, but you can override |
| Dataflow / Dataproc / Composer / Pub/Sub | Per-job or per-environment runtime SA |

A VM's SA is the identity it presents when it calls APIs from inside (via the metadata server) — **no JSON keys needed**.

### 2.4 Service account impersonation

**The problem this solves.** A human admin needs to do something with prod-deploy permissions, but their human account doesn't have those rights. You don't want to grant them the prod role permanently. You also don't want to hand them a JSON key.

**Impersonation** lets a human (or another SA) act as a target SA **without holding any keys**.

How it works:
1. Grant the caller `roles/iam.serviceAccountTokenCreator` **on the target SA**.
2. The caller asks the IAM Credentials API to mint a **short-lived token** for the SA.
3. The caller uses that token (effectively becomes the SA for ~1 hour).

`gcloud` has a first-class flag: `--impersonate-service-account=app@PROJECT.iam.gserviceaccount.com`. Add it to any command and the call goes out as the SA.

This is **the secure pattern** for human-to-SA elevation. Replaces handing out JSON keys.

*Micro-summary: impersonation = mint a 1-hour token for an SA. Requires `tokenCreator` on the target SA. Audit-logged. Always preferred over keys.*

### 2.5 Short-lived service account credentials

The IAM Credentials API mints several types of short-lived tokens:

| Type | Used for |
|---|---|
| **OAuth 2.0 access token** | Calling Google APIs as the SA |
| **OpenID Connect (OIDC) ID token** | Authenticating to systems that verify Google ID tokens (e.g. Cloud Run with auth required) |
| **Self-signed JWT** | Signing tokens locally with the SA's key |
| **Signed blob** | Signing arbitrary bytes |

**Default expiry: 1 hour.** Always prefer these over long-lived keys.

### 2.6 Service account keys — when (and when not) to use them

A **service account key** is a JSON file containing a private key for the SA. Anyone with the file can act as the SA, anywhere, until the key is rotated or disabled.

- They are powerful and **frequently leaked**. Many real-world incidents start with a key in a public repo.
- **Avoid them whenever possible.** Modern alternatives:
  - **Attach the SA** to a Google Cloud workload (no key needed; metadata server provides tokens).
  - **Workload Identity Federation** — for *external* workloads (AWS, on-prem, GitHub Actions) authenticating to GCP without keys.
  - **Workload Identity** — for GKE workloads.
  - **Impersonation** — for humans.
- The org policy `iam.disableServiceAccountKeyCreation` can ban key creation entirely; many enterprises set this.
- If you must use a key: rotate regularly, store in **Secret Manager**, never in code.

*Micro-summary: keys are the legacy / leaky path. The modern answers are Workload Identity (GKE), Workload Identity Federation (external), impersonation (humans), and "just attach the SA" (GCP workloads).*

### 2.7 Using a Google SA with a GKE application — Workload Identity

GKE has two ways for pods to authenticate as a Google SA:

| Approach | Description | Recommended? |
|---|---|---|
| **Node service account** | All pods on a node share the node's GCE SA. Coarse, leaks privilege across pods. | **No**, except for legacy clusters |
| **Workload Identity** | Each pod authenticates via its own **Kubernetes service account**, which is bound to a Google SA. Tokens come from a metadata server scoped to the pod. | **Yes** — the modern standard |

**Workload Identity setup in three steps:**
1. Enable Workload Identity on the cluster (or node pool).
2. Create a Google SA with the permissions the workload needs.
3. Bind the K8s SA to the Google SA: grant the K8s SA `roles/iam.workloadIdentityUser` on the Google SA, and annotate the K8s SA with the Google SA's email.

After that, pods running as the K8s SA are seen by Google APIs as the Google SA — **no JSON key**, scoped per workload.

**Gotcha:** A pod cannot use Workload Identity if its node pool doesn't have **GKE Metadata Server** enabled. Common misconfiguration.

### 2.8 Secret Manager — where passwords and API keys live

#### The problem it solves

Your app needs a database password. The bad options the exam loves to dangle in front of you:

- **Hardcoded in the source code** — anyone with repo access has prod credentials; rotating means redeploying.
- **In an environment variable set by hand** — invisible, unaudited, copied around in tickets and chat.
- **In a config file in the container image** — anyone who can pull the image has the secret.

**Secret Manager** is the purpose-built answer: a managed vault for small pieces of sensitive data (passwords, API keys, certificates, connection strings).

#### What you have to remember

- A **secret** is a named container; each update creates a new **version** (you can pin to a version or use `latest`). Old versions can be disabled/destroyed — that's your rotation story.
- Access is plain **IAM**: grant the app's **service account** `roles/secretmanager.secretAccessor` on *just that secret* (least privilege — not on the whole project).
- Every access is **audit-logged** — who read what, when.
- Data is **encrypted at rest** automatically (CMEK optional, for the "we must hold the keys" compliance scenario).
- Integrations the exam mentions: Cloud Run and Cloud Functions can mount secrets **as environment variables or files** natively; GKE reads them via Workload Identity + client library (or the Secret Manager CSI driver).

```bash
# Create a secret and add a version
gcloud secrets create db-password --replication-policy=automatic
echo -n "s3cr3t" | gcloud secrets versions add db-password --data-file=-

# Read it (needs secretAccessor on the secret)
gcloud secrets versions access latest --secret=db-password

# Let the app's SA read it — and nothing else
gcloud secrets add-iam-policy-binding db-password \
  --member="serviceAccount:app-sa@my-proj.iam.gserviceaccount.com" \
  --role="roles/secretmanager.secretAccessor"
```

#### Secret Manager vs. KMS — a classic confusion

| | **Secret Manager** | **Cloud KMS** |
|---|---|---|
| Stores | The secret **itself** (password, API key) | **Encryption keys** only — never your data |
| You use it to | *Fetch* a credential at runtime | *Encrypt/decrypt/sign* data with a key that never leaves KMS |
| Exam trigger | "Where do we keep the DB password?" | "We must manage our own encryption keys (CMEK)" |

> **Micro-summary:** *Passwords and API keys → Secret Manager (versioned, IAM-gated, audit-logged). Encryption keys → KMS. Never hardcode, never bake into images.*

## 3. Decision criteria

| Question | Answer |
|---|---|
| Production VM running an app | **User-managed SA** with only the roles the app needs |
| Default Compute Engine SA on a prod VM | **Replace it**; the default has Editor on the project |
| Human needs prod permissions occasionally | Grant `roles/iam.serviceAccountTokenCreator` on a target SA + use **impersonation** |
| Need to call Google APIs from outside GCP without keys | **Workload Identity Federation** (AWS, on-prem, GitHub Actions) |
| GKE pod needs to access a Google API | **Workload Identity** binding K8s SA → Google SA |
| User needs to attach an SA to a VM | Grant **`roles/iam.serviceAccountUser`** on the SA |
| User wants to mint tokens for an SA | Grant **`roles/iam.serviceAccountTokenCreator`** on the SA |
| Want to forbid keys entirely in the org | Org policy **`iam.disableServiceAccountKeyCreation`** |
| Stop using a key right now | **Disable** the key first, then delete after confirming nothing breaks |
| Where to store a DB password / API key | **Secret Manager** + `secretAccessor` for the app's SA on that secret |
| Company must manage its own encryption keys (CMEK) | **Cloud KMS** — keys, not secrets |

| What you want to do | Where to click |
|---|---|
| List / create SAs | *IAM & Admin → Service Accounts* |
| See an SA's details (permissions, keys, logs) | *Service Accounts → (the SA email)* |

| Cloud Run runtime SA | *Cloud Run → (service) → Edit & deploy → Container, Networking & Security → Security → Service account* |

| Create / disable / delete keys | *IAM & Admin → Service Accounts → (SA) → Keys* |
| Block key creation org-wide | *IAM & Admin → Organization Policies → iam.disableServiceAccountKeyCreation* |

## 5. gcloud reference

```bash
# ── Create / list / describe / delete SAs ──
gcloud iam service-accounts create app-sa \
    --display-name="App service account"
gcloud iam service-accounts list
gcloud iam service-accounts describe app-sa@PROJECT.iam.gserviceaccount.com
gcloud iam service-accounts disable app-sa@PROJECT.iam.gserviceaccount.com
gcloud iam service-accounts enable  app-sa@PROJECT.iam.gserviceaccount.com
gcloud iam service-accounts delete  app-sa@PROJECT.iam.gserviceaccount.com

# ── SA as a MEMBER (grant the SA roles on other resources) ──
gcloud projects add-iam-policy-binding PROJECT_ID \
    --member=serviceAccount:app-sa@PROJECT.iam.gserviceaccount.com \
    --role=roles/storage.objectAdmin

gcloud storage buckets add-iam-policy-binding gs://my-bucket \
    --member=serviceAccount:app-sa@PROJECT.iam.gserviceaccount.com \
    --role=roles/storage.objectViewer

# ── SA as a RESOURCE (grant humans/SAs roles ON the SA) ──
# Allow Alice to attach this SA to a resource
gcloud iam service-accounts add-iam-policy-binding \
    app-sa@PROJECT.iam.gserviceaccount.com \
    --member=user:alice@example.com --role=roles/iam.serviceAccountUser

# Allow Alice to impersonate the SA (mint short-lived tokens)
gcloud iam service-accounts add-iam-policy-binding \
    app-sa@PROJECT.iam.gserviceaccount.com \
    --member=user:alice@example.com --role=roles/iam.serviceAccountTokenCreator

# ── Attach an SA to a resource ──
# At VM create time:
gcloud compute instances create web-1 ... \
    --service-account=app-sa@PROJECT.iam.gserviceaccount.com \
    --scopes=cloud-platform

# Cloud Run service:
gcloud run deploy api --image=...:1.0 --region=europe-west3 \
    --service-account=app-sa@PROJECT.iam.gserviceaccount.com

# Cloud Run function (2nd gen):
gcloud functions deploy on-upload --gen2 ... \
    --service-account=app-sa@PROJECT.iam.gserviceaccount.com

# ── Impersonation ──
gcloud storage ls gs://my-bucket \
    --impersonate-service-account=app-sa@PROJECT.iam.gserviceaccount.com

# Mint a short-lived access token explicitly
gcloud auth print-access-token \
    --impersonate-service-account=app-sa@PROJECT.iam.gserviceaccount.com

# ── Service account keys (avoid; use only when no alternative) ──
gcloud iam service-accounts keys list \
    --iam-account=app-sa@PROJECT.iam.gserviceaccount.com
gcloud iam service-accounts keys create key.json \
    --iam-account=app-sa@PROJECT.iam.gserviceaccount.com
gcloud iam service-accounts keys disable KEY_ID \
    --iam-account=app-sa@PROJECT.iam.gserviceaccount.com
gcloud iam service-accounts keys delete KEY_ID \
    --iam-account=app-sa@PROJECT.iam.gserviceaccount.com

# ── GKE Workload Identity ──
# 1) Enable Workload Identity at cluster + node pool level
gcloud container clusters update std-cluster --region=europe-west3 \
    --workload-pool=PROJECT.svc.id.goog
gcloud container node-pools update default-pool --cluster=std-cluster --region=europe-west3 \
    --workload-metadata=GKE_METADATA

# 2) Create the Google SA and grant it whatever it needs (e.g. read GCS)
gcloud iam service-accounts create wi-app
gcloud projects add-iam-policy-binding PROJECT_ID \
    --member=serviceAccount:wi-app@PROJECT.iam.gserviceaccount.com \
    --role=roles/storage.objectViewer

# 3) Bind a Kubernetes SA in namespace `default` to the Google SA
gcloud iam service-accounts add-iam-policy-binding \
    wi-app@PROJECT.iam.gserviceaccount.com \
    --member=serviceAccount:PROJECT.svc.id.goog[default/wi-ksa] \
    --role=roles/iam.workloadIdentityUser

kubectl create serviceaccount wi-ksa
kubectl annotate serviceaccount wi-ksa \
    iam.gke.io/gcp-service-account=wi-app@PROJECT.iam.gserviceaccount.com
# Pods now reference `serviceAccountName: wi-ksa` to act as the Google SA
```

## 6. Common confusions

- **Member vs resource (the dual nature).** Granting a role *to* the SA = SA as member. Granting a role *on* the SA = SA as resource. The exam will phrase scenarios that test which one you need.
- **`serviceAccountUser` vs `serviceAccountTokenCreator`.** User = "I can attach this SA to a resource". TokenCreator = "I can impersonate it (mint tokens)". Different actions. Many exam questions hinge on this.
- **`roles/iam.serviceAccountAdmin` ≠ `roles/iam.serviceAccountUser`.** Admin = manage SAs themselves (create/delete). User = use a specific SA.
- **Workload Identity vs Workload Identity Federation.** Workload Identity = inside GKE (K8s SA → Google SA). Workload Identity Federation = external (AWS/on-prem/GitHub) → GCP without keys.
- **Default vs user-managed SAs.** Default Compute Engine SA = Editor on the project (too much). User-managed = scoped per workload (right way).
- **Service agents (`gcp-sa-*`) are Google's, not yours.** Don't grant random roles to them; don't delete them.
- **Disable before delete.** Disabling an SA or a key is reversible. Deletion of a key is permanent. Deletion of an SA can be undone within 30 days.
- **Cross-project SA usage.** An SA from project A can be granted roles in project B. The SA still *lives* in project A — deleting project A loses it everywhere.
- **A token is short-lived (1 hour).** Apps that fail after ~60 minutes often have a token refresh bug.

## 7. Exam gotchas

- **Default Compute Engine SA has Editor on the project.** Production: replace it with a least-privileged user-managed SA.
- **`serviceAccountUser` ≠ `serviceAccountTokenCreator`.** User = "I can attach this SA to a resource". TokenCreator = "I can impersonate it". Many exam questions hinge on the difference.
- **Attaching an SA to an existing VM** requires the VM to be stopped (and you can change SA only on stopped VMs).
- **`actAs` permission** — `roles/iam.serviceAccountUser` includes it. To deploy a Cloud Run service that runs as a given SA, the deployer needs `actAs` on that SA.
- **JSON keys are a security risk.** The exam-correct answer is almost always *Workload Identity*, *Workload Identity Federation*, or *impersonation* — not "create a key".
- **Org policy `iam.disableServiceAccountKeyCreation`** blocks key creation org-wide; common in regulated environments.
- **Disable before delete** for keys/SAs — disabling is reversible, deletion is not (within 30 days you *can* restore an SA, but the safer path is disable first).
- **Workload Identity is per-pod**, node SA is per-node. Workload Identity is the modern, recommended pattern.
- **Service agents (`gcp-sa-*`)** are owned by Google. Don't delete them.
- **Short-lived tokens default to 1 hour.** Apps that fail after ~60 minutes often have a token refresh bug.
- **Cross-project SA usage** — you can grant an SA from project A roles in project B. Just remember the SA still *lives* in project A.
- **Restoring a deleted SA** within 30 days uses the SA's unique numeric ID, and any IAM bindings that reference it by ID are recovered automatically.
- **A pod cannot use Workload Identity if its node pool doesn't have GKE Metadata Server enabled** — common misconfiguration.

## 8. Practice scenarios

### Q1 — Replacing the default Compute Engine SA
A production VM is using the default Compute Engine service account. Security flags it. What's the recommended remediation?

A. Restrict the default SA's permissions.
B. **Create a user-managed SA with only the roles the workload needs; stop the VM; switch the VM's SA; restart.**
C. Disable the default SA project-wide.
D. Use Workload Identity Federation.

**Answer: B.** The standard fix is one-workload-one-SA with least privilege. A may work but the default SA is per-project; reducing its permissions can break other VMs. C breaks every VM still using it. D is for *external* workloads, not GCE VMs.

### Q2 — Impersonation roles
Alice manages deploys; she should be able to deploy a Cloud Run service that runs as `deploy-sa@...`. Which role does Alice need on the SA?

A. `roles/iam.serviceAccountAdmin`.
B. **`roles/iam.serviceAccountUser`.**
C. `roles/iam.serviceAccountTokenCreator`.
D. `roles/owner` on the project.

**Answer: B.** `serviceAccountUser` includes the `actAs` permission required to attach an SA to a resource. A is for managing SAs themselves. C lets her *impersonate* to mint tokens — a different action. D is overprivileged.

### Q3 — GKE Workload Identity
A pod needs to read from Cloud Storage. You don't want to use a JSON key. Which configuration is correct?

A. Mount a key as a Kubernetes Secret.
B. **Enable Workload Identity on the cluster; create a Google SA with `roles/storage.objectViewer`; grant the K8s SA `roles/iam.workloadIdentityUser` on the Google SA; annotate the K8s SA with the Google SA email.**
C. Use the node SA with `roles/owner`.
D. Service account keys are unavoidable for GKE.

**Answer: B.** Workload Identity is the Google-recommended pattern for binding K8s SAs to Google SAs without keys. A is the legacy practice. C leaks privilege across all pods on a node. D is false.

### Q4 — Human-to-SA elevation
An on-call engineer occasionally needs prod-deploy permissions that her user account doesn't have. The correct mechanism?

A. Add her user to the Owner role temporarily.
B. **Grant her `roles/iam.serviceAccountTokenCreator` on `prod-deploy-sa`; she runs commands with `--impersonate-service-account`.**
C. Email her the SA's JSON key.
D. Grant `allAuthenticatedUsers` Editor.

**Answer: B.** Impersonation is the secure pattern: short-lived tokens, audit-logged, no keys, no permanent role escalation. A is over-broad. C is a security incident waiting to happen. D is catastrophic.

### Q5 — Disabling key creation org-wide
Compliance requires that no one in the organization can create new SA JSON keys. What's the right enforcement?

A. Remove `roles/iam.serviceAccountKeyAdmin` from every binding.
B. Audit periodically for new keys.
C. **Set the org policy `iam.disableServiceAccountKeyCreation` at the organization node.**
D. Delete all existing keys and hope no one rotates.

**Answer: C.** Org policies enforce at the API level — even Owners cannot bypass. A misses inherited bindings and is fragile. B detects after the fact. D is partial and reactive.

## 9. Hands-on labs

### Lab 1 — Create a least-privileged SA, attach to a VM, replace default SA
**Goal:** spin up a user-managed SA with only `storage.objectViewer`, attach it to a VM, and stop using the default Compute Engine SA.

**Console (create the SA):**
1. *IAM & Admin → Service Accounts → Create service account*.
2. **Name:** `web-sa`. **Description:** `Runtime SA for web tier`. *Create and continue*.
3. **Grant access to project:** add role *Storage Object Viewer*. *Continue → Done*. (Optional: skip the *Grant users access* step.)

**Console (replace default SA on a VM):**
4. *Compute Engine → VM instances → web-1 → Stop*. Wait until status is `TERMINATED`.
5. Click **Edit**. Scroll to **Identity and API access**.
6. **Service account:** change from *Compute Engine default service account* to `web-sa@${PROJECT}.iam.gserviceaccount.com`.
7. **Access scopes:** *Allow full access to all Cloud APIs* (the IAM grant is what actually limits access; broad scopes + narrow IAM is the modern pattern).
8. *Save*. *Start*.
9. SSH in and run `gcloud storage ls` against a bucket — works for read; writes fail (proves least privilege).

**gcloud:**
```bash
gcloud iam service-accounts create web-sa --display-name="Web tier SA"
gcloud projects add-iam-policy-binding $DEVSHELL_PROJECT_ID \
    --member="serviceAccount:web-sa@$DEVSHELL_PROJECT_ID.iam.gserviceaccount.com" \
    --role=roles/storage.objectViewer

gcloud compute instances stop web-1 --zone=europe-west3-a
gcloud compute instances set-service-account web-1 --zone=europe-west3-a \
    --service-account="web-sa@$DEVSHELL_PROJECT_ID.iam.gserviceaccount.com" \
    --scopes=cloud-platform
gcloud compute instances start web-1 --zone=europe-west3-a
```

### Lab 2 — Service account impersonation (without keys)
**Goal:** let your user account run commands as `web-sa` via short-lived tokens.

**Console (grant the role on the SA itself):**
1. *IAM & Admin → Service Accounts → web-sa@…*. Click the SA's row to open it.
2. *Permissions* tab → **Grant access**.
3. **New principals:** your user email. **Role:** *Service Account Token Creator* (`roles/iam.serviceAccountTokenCreator`). *Save*.

**Cloud Shell (use the impersonation):**
```bash
# This call runs as YOUR user — may fail if you lack the role
gcloud storage ls gs://some-private-bucket

# This one mints a token for web-sa and runs as it
gcloud storage ls gs://some-private-bucket \
    --impersonate-service-account="web-sa@$DEVSHELL_PROJECT_ID.iam.gserviceaccount.com"

# Print a 1-hour access token explicitly
gcloud auth print-access-token \
    --impersonate-service-account="web-sa@$DEVSHELL_PROJECT_ID.iam.gserviceaccount.com"
```

**Audit check:**
4. *Logging → Logs Explorer*, query:
   ```
   protoPayload.serviceName="iamcredentials.googleapis.com"
   AND protoPayload.methodName="GenerateAccessToken"
   ```
   Each impersonation is logged — that's why this is the secure pattern (no keys, full audit trail).

### Lab cleanup
```bash
gcloud iam service-accounts remove-iam-policy-binding \
    "web-sa@$DEVSHELL_PROJECT_ID.iam.gserviceaccount.com" \
    --member="user:$(gcloud config get-value account)" \
    --role=roles/iam.serviceAccountTokenCreator
gcloud projects remove-iam-policy-binding $DEVSHELL_PROJECT_ID \
    --member="serviceAccount:web-sa@$DEVSHELL_PROJECT_ID.iam.gserviceaccount.com" \
    --role=roles/storage.objectViewer
gcloud iam service-accounts delete \
    "web-sa@$DEVSHELL_PROJECT_ID.iam.gserviceaccount.com" --quiet
```

## 10. TL;DR (5-minute pre-exam recap)

1. **Service accounts are workload identities.** Email format: `NAME@PROJECT.iam.gserviceaccount.com`.
2. **Dual nature:** an SA is a **member** in IAM bindings (gets roles to access resources) AND a **resource** itself (people are granted roles ON it).
3. **`serviceAccountUser`** = I can **attach** this SA to a resource. **`serviceAccountTokenCreator`** = I can **impersonate** it. **`serviceAccountAdmin`** = I can manage SAs themselves.
4. **Default Compute Engine SA has Editor on the project.** Replace it with a least-privileged user-managed SA on prod VMs.
5. **One workload → one SA → minimum permissions.** The exam-canonical pattern.
6. **Changing an SA on an existing VM** requires the VM to be **stopped**.
7. **Service agents** (`gcp-sa-*`) are owned by Google. Don't delete them.
8. **Impersonation** = `--impersonate-service-account` flag mints a 1-hour token. Requires `tokenCreator` on the target SA. Audit-logged. The secure human-to-SA pattern.
9. **JSON keys are dangerous.** Modern alternatives: **Workload Identity** (GKE), **Workload Identity Federation** (external), **impersonation** (humans), **just attach the SA** (GCP workloads).
10. **Disable before delete** keys and SAs. Deleted SA can be restored within 30 days.
11. **Workload Identity** binds a K8s SA to a Google SA so GKE pods get scoped, keyless tokens. Three steps: enable on cluster + node pool, create the Google SA, bind via `workloadIdentityUser` + annotate K8s SA.
12. **Workload Identity Federation** is the equivalent for **external** workloads (AWS, on-prem, GitHub Actions) — no keys.
13. **Org policy `iam.disableServiceAccountKeyCreation`** = block key creation org-wide. The compliance-grade enforcement.
