# Cloud Logging: Log Types, Sinks, Log-Based Metrics, Audit Logs

## Overview

**Cloud Logging** (part of Google Cloud's operations suite) is the centralized log management service for GCP. It ingests, indexes, stores, and analyzes logs from GCP services, applications, and custom sources. Understanding log types, retention, routing, and audit logs is heavily tested in the ACE exam.

---

## Key Concepts

### Log Types

#### Platform Logs (GCP Service Logs)

- Automatically generated by GCP services
- Examples: Cloud Load Balancer access logs, Cloud SQL slow query logs, VPC Flow Logs, Firewall Rules Logging
- Must be explicitly enabled for many services (not all are on by default)

#### Audit Logs (Admin Activity, Data Access, System Event, Policy Denied)

The most exam-critical log type — see detailed section below.

#### Agent Logs (from VMs)

- Generated by Ops Agent installed on Compute Engine VMs
- Includes: syslog, application logs (Apache, Nginx, etc.), structured logs from apps
- Without Ops Agent, VM logs don't appear in Cloud Logging

#### User-defined Logs

- Logs written by applications using the Cloud Logging API or client libraries
- Can be structured (JSON) or unstructured text
- Structured logs are searchable with rich field filtering

---

### Audit Logs

The most important log type for compliance, security, and the ACE exam.

| Audit Log Type | Description | Enabled by Default |
|---------------|-------------|-------------------|
| **Admin Activity** | Who created/modified/deleted resources (API calls that modify configuration) | Always ON, cannot be disabled |
| **Data Access** | Who read resource data or metadata | OFF by default (except BigQuery) |
| **System Event** | GCP-internal administrative actions (live migration, etc.) | Always ON, cannot be disabled |
| **Policy Denied** | Access denied by VPC Service Controls or IAM | Always ON, cannot be disabled |

#### Admin Activity Audit Logs

- Captures: `CreateInstance`, `DeleteBucket`, `setIAMPolicy`, `create`, `update`, `delete` operations
- Always enabled; cannot be disabled
- Retained for 400 days (default); no charge
- Critical for: Security incidents, compliance audits, change tracking

#### Data Access Audit Logs

- Captures: `GetObject`, `ReadTable`, `list` operations on data
- Must be explicitly enabled per service or resource
- Three sub-types:
  - **DATA_READ**: Reading data (e.g., `storage.objects.get`)
  - **DATA_WRITE**: Writing data (e.g., `storage.objects.create`)
  - **ADMIN_READ**: Reading metadata/config of data resources
- Can generate very high volume — consider enabling only for sensitive resources
- Default retention: 30 days; charged after free tier

#### Retention Periods

| Log Type | Default Retention | Charge |
|----------|------------------|--------|
| Admin Activity | 400 days | Free |
| Data Access | 30 days | Free up to 1 GB/project/month |
| System Event | 400 days | Free |
| Policy Denied | 30 days | Free up to 1 GB/project/month |
| User-defined | 30 days | First 50 GiB/project/month free |

- **To increase retention**: Configure a log sink to Cloud Storage, BigQuery, or Pub/Sub

### Log Router and Log Sinks

The **Log Router** controls where logs go. By default, logs are stored in `_Default` and `_Required` log buckets.

#### Log Buckets (Storage)

- `_Required`: Admin Activity and System Event logs; 400-day retention; cannot delete
- `_Default`: All other logs; 30-day retention; can modify
- Custom buckets: Create with configurable retention (1 day to 3650 days); can use CMEK

#### Log Sinks

A **sink** exports (copies) log entries that match a filter to a destination:

| Destination | Use Case |
|-------------|---------|
| **Cloud Storage** | Long-term archival (cost-effective) |
| **BigQuery** | SQL analysis of logs; security analytics |
| **Pub/Sub** | Real-time streaming to other systems; trigger Cloud Functions |
| **Cloud Logging bucket** | Route to a different project's log bucket (for centralization) |

- Sinks can be created at project, folder, or organization level
- **Aggregated sinks** (folder/org level): Export logs from all child projects with a single sink — useful for centralized SIEM integration
- Sink filter: Uses Cloud Logging filter syntax; can include/exclude specific log types, resources, or fields
- **Writer service account**: Each sink has a service account that writes to the destination; must be granted write access to the destination

#### Log Exclusion Filters

- Reduce log ingestion volume and cost by excluding noisy/unneeded logs
- Defined on the log router with exclusion rules
- Example: Exclude health check requests from load balancer access logs
- **Important**: Excluded logs are NOT stored anywhere — cannot be retrieved later

---

### Log-Based Metrics

- Create **custom metrics** from log entries using filter expressions
- Two types:
  - **Counter metrics**: Count log entries matching a filter (e.g., count HTTP 500 errors)
  - **Distribution metrics**: Record value distributions from log fields (e.g., response latency distribution from access logs)
- Log-based metrics appear in Cloud Monitoring and can be used in alerting policies and dashboards
- **Common use case**: Alert when error rate in logs exceeds a threshold

---

### VPC Flow Logs

- Records network flows (TCP/UDP) entering/leaving VM network interfaces
- Enabled per subnet
- Contains: source/dest IP, port, protocol, bytes transferred, packets
- Available in Cloud Logging after a few minutes
- Can export via log sink to BigQuery for network traffic analysis
- **Sampling rate**: By default, 50% sampling; can be adjusted (1%–100%)
- Use cases: Network monitoring, security forensics, compliance, billing analysis

---

### Firewall Rules Logging

- Log packets allowed or denied by firewall rules
- Enabled per firewall rule (`--enable-logging` flag)
- Can be expensive (high volume for busy VMs)
- Useful for: Security auditing, troubleshooting firewall rule effectiveness

---

### Log Explorer Filtering

Cloud Logging uses its own filter syntax (not SQL):

```
resource.type="gce_instance"
resource.labels.instance_id="1234567890"
severity>=ERROR
textPayload:"Connection refused"
protoPayload.methodName="v1.compute.instances.insert"
timestamp>="2024-01-01T00:00:00Z"
```

- Filters used in: Log Explorer queries, sink filters, exclusion filters, log-based metric filters
- `protoPayload`: Audit logs (structured protobuf)
- `jsonPayload`: Structured JSON logs
- `textPayload`: Unstructured text logs

## When to Use

- **Admin Activity Audit Logs**: Always — they're always on; use for post-incident investigation
- **Data Access Audit Logs**: Enable for sensitive resources (PCI data, PHI, confidential projects)
- **Log sink to BigQuery**: When you need SQL analysis of log data for security analytics or compliance reporting
- **Log sink to Cloud Storage**: Long-term archival at low cost
- **Aggregated sinks**: For organization-wide log centralization
- **VPC Flow Logs**: When you need network visibility for security or troubleshooting
- **Log-based metrics**: When alerting on error patterns in logs is needed

---

## When NOT to Use

- **Data Access Logs on all resources by default**: Can generate enormous volume and cost; enable selectively
- **VPC Flow Logs at 100% sampling on high-traffic subnets**: Can be very expensive; use sampling
- **Log exclusion for compliance-critical logs**: Excluded logs cannot be recovered

## Exam-Relevant Notes

### Common Traps

1. **Admin Activity logs cannot be disabled**: They're always on. A question asking "how to disable admin activity logs" — answer: you can't.

2. **Data Access logs are OFF by default**: If you're not seeing read/write operations in logs, check if Data Access logs are enabled.

3. **Aggregated sinks are at folder/org level**: Individual project sinks only export that project's logs. For org-wide log export, create a sink at the organization level.

4. **Log sink needs permission on destination**: When creating a sink, GCP creates a service account for the sink. You must grant that SA write access to the destination (e.g., `storage.objectCreator` on the GCS bucket, `bigquery.dataEditor` on the dataset).

5. **Excluded logs are gone**: Unlike sinks (which copy), exclusions prevent storage. Excluded logs cannot be recovered. Don't exclude logs you might need for compliance.

6. **Log retention extension requires a sink OR custom log bucket**: The default `_Default` bucket has 30-day retention. To keep logs longer, either export to GCS/BigQuery or create a custom log bucket with longer retention.

7. **VPC Flow Logs are per-subnet, not per-VPC**: Must be enabled on each subnet individually. Enabling on a VPC doesn't automatically enable on all subnets.

8. **Log-based metrics alert on patterns**: If you need to alert on a specific error message appearing in logs, the pattern is: create a log-based metric (counter) + create an alerting policy on that metric.

### Decision Tree: Log Storage Strategy

```
Need to keep logs for compliance (> 30 days)?
├── Yes → Create custom log bucket with extended retention OR
│          Create sink to Cloud Storage (cheaper for long-term)
│
Need to run SQL queries on logs?
├── Yes → Create sink to BigQuery
│
Need real-time processing of logs?
├── Yes → Create sink to Pub/Sub → Cloud Function
│
Default behavior sufficient (30 days, searchable in console)?
└── No action needed beyond default _Default bucket
```
