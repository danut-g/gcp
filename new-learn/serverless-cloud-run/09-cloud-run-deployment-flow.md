# 09 — Cloud Run Deployment Flow

| Step | What You Do | Where | Why | Example / Command | Expected Result | Verification |
|---|---|---|---|---|---|---|
| 1. Prepare your container | Build an app that listens on `$PORT`. | In your application code. | Cloud Run injects the expected port. | Conceptual behavior:<br><br>`listen host: 0.0.0.0`<br>`listen port: process.env.PORT \|\| 8080` | The app starts and listens on `0.0.0.0:$PORT`. | `docker run -e PORT=8080 -p 8080:8080 IMAGE`<br>`curl http://localhost:8080` |
| 2. Build and push the image | Build your container image and push it to Artifact Registry. | Local machine, CI/CD pipeline, or Cloud Build. | Cloud Run needs a container image. | Example image path:<br><br>`us-central1-docker.pkg.dev/PROJECT_ID/my-repo/my-app:v1` | Image exists in Artifact Registry. | Check the image in Artifact Registry or deploy it to Cloud Run. |
| 3. Deploy to Cloud Run | Deploy the image. | Cloud Shell, terminal, or CI/CD. | Creates the Cloud Run service and revision. | `gcloud run deploy my-service \`<br>`  --image=us-central1-docker.pkg.dev/PROJECT_ID/my-repo/my-app:v1 \`<br>`  --region=us-central1 \`<br>`  --allow-unauthenticated` | Cloud Run returns a service URL. | `curl https://SERVICE_URL` |
| 4. Configure IAM | For public service, use `--allow-unauthenticated`.<br><br>For private service, use `--no-allow-unauthenticated`, then grant the caller `roles/run.invoker`. | Cloud Run IAM configuration. | Controls who can invoke the service. | `gcloud run services add-iam-policy-binding my-service \`<br>`  --region=us-central1 \`<br>`  --member=serviceAccount:CALLER_SA@PROJECT_ID.iam.gserviceaccount.com \`<br>`  --role=roles/run.invoker` | Only authorized callers can invoke the service. | Invoke as an authorized caller and confirm unauthorized callers are rejected. |
| 5. Configure scaling | Set minimum instances, maximum instances, and concurrency. | Cloud Run service configuration. | Reduces cold starts and protects downstream systems. | `gcloud run services update my-service \`<br>`  --region=us-central1 \`<br>`  --min-instances=1 \`<br>`  --max-instances=20 \`<br>`  --concurrency=40` | At least one warm instance, maximum 20 instances, and 40 concurrent requests per instance. | Describe the service and check scaling settings. |
| 6. Configure secrets | Mount a Secret Manager secret and grant the runtime service account secret access. | Cloud Run service configuration and IAM. | Lets the app read sensitive values without hardcoding them. | `gcloud run services update my-service \`<br>`  --region=us-central1 \`<br>`  --set-secrets=DB_PASSWORD=db-password:latest`<br><br>Also grant the runtime service account:<br><br>`roles/secretmanager.secretAccessor` | The app can read `DB_PASSWORD`. | Check the app logs or endpoint behavior that depends on the secret. |
| 7. Configure VPC connectivity if needed | For private resources, use Direct VPC egress or a Serverless VPC Access connector. The PDF mentions both, and Google's current docs describe Direct VPC egress as the recommended option. | Cloud Run networking configuration. | Allows the service to reach private RFC1918/VPC resources. | Connector example:<br><br>`gcloud run deploy my-service \`<br>`  --image=... \`<br>`  --vpc-connector=my-connector \`<br>`  --vpc-egress=private-ranges-only` | Service can reach private RFC1918/VPC resources. | Test connectivity from the service to the private target. |
| 8. Manage traffic safely | Use canary rollout or rollback by shifting traffic between revisions. | Cloud Run revision and traffic management. | Allows controlled rollout or rollback without redeploying. | Canary:<br><br>`gcloud run services update-traffic my-service \`<br>`  --region=us-central1 \`<br>`  --to-revisions=old-revision=90,new-revision=10`<br><br>Rollback:<br><br>`gcloud run services update-traffic my-service \`<br>`  --region=us-central1 \`<br>`  --to-revisions=old-revision=100` | Controlled rollout or rollback without redeploying. | Check traffic split in Cloud Run or run repeated requests and inspect which revision serves them. |
